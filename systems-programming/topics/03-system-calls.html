1. מהי קריאת מערכת — ולמה אין דרך אחרת

בפרק הקודם ראינו שהתוכנה במחשב מתחלקת לשניים: קוד הקרנל, וכל "שאר" התוכנה — כל התוכניות והספריות. עכשיו מגיעה השאלה המעשית: כשתוכנית רגילה רוצה משהו מהמערכת — לפתוח קובץ, למשל — איך היא בכלל מדברת עם הקרנל? התשובה היא המנגנון שסביבו סובב כל הקורס:

קריאת מערכת (System call) היא המנגנון שבאמצעותו תהליך מבקש מהקרנל לבצע שירות עבורו. דוגמה מהשקף: פתיחת קובץ (open a file).

השקפים מציגים את יחסי הגומלין בתרשים "עוגת שכבות": הרבה אפליקציות (Many applications), קרנל אחד (One Kernel), חומרה אחת (One Hardware) — ושלושה חיצים שמספרים את כל הסיפור:

שימו לב מה כל חץ אומר:

  • אפליקציה ← חומרה (ישירות): האפליקציה מריצה על המעבד אך ורק הוראות לא-מיוחסות (non-privileged). דוגמה מהשקף: ADD.
  • קרנל ← חומרה: הקרנל מריץ גם הוראות מיוחסות וגם לא-מיוחסות. דוגמה להוראה מיוחסת: HALT, שעוצרת את פעולת ה-CPU.
  • אפליקציה ← קרנל: חץ ה-System calls — הדרך שבה תהליך מבקש שירות שהוא לא יכול לבצע בעצמו.

ולמה זו הדרך היחידה? כי המעבד עצמו אוכף את החלוקה: בשלב פענוח ההוראה (Instruction Decode) הוא בודק אם ההוראה מיוחסת. הוראה לא-מיוחסת מבוצעת בכל מצב; הוראה מיוחסת מבוצעת רק כשהמעבד במצב גרעין. אם תהליך במצב משתמש מנסה לבצע הוראה מיוחסת — המעבד מסרב לבצע אותה ויוצר פסיקה (Interrupt), שהטיפול בה מוביל להפסקה מיידית של התהליך. כלומר: אין "לפרוץ פנימה". תהליך שרוצה שירות שדורש הרשאות גבוהות חייב לבקש אותו מהקרנל — וזו בדיוק קריאת המערכת. בתרשים מבנה הקרנל שראינו בפרק הקודם, ממשק ה-System calls הוא שער הכניסה שדרכו עוברות כל הבקשות מהאפליקציות אל רכיבי הקרנל.

2. שש הקטגוריות של קריאות מערכת

אילו שירותים אפשר בכלל לבקש? השקפים מסווגים את קריאות המערכת לשש קטגוריות, עם דוגמאות מוכרות בכל אחת. חלק גדול מהפונקציות בטבלה הזו ילוו אותנו לאורך כל הקורס:

קטגוריה דוגמאות
Process Control fork(), exit(), wait()
File Manipulation open(), read(), write(), close()
Device Manipulation ioctl(), read(), write()
Information Maintenance getpid(), alarm(), sleep()
Communication pipe(), shmget(), mmap()
Protection chmod(), umask(), chown()

שימו לב ש-read() ו-write() מופיעות גם ב-File Manipulation וגם ב-Device Manipulation — אותן קריאות משמשות לעבודה מול קבצים ומול התקנים. הרביעייה המלאה open/read/write/close שייכת לקטגוריית ה-File Manipulation, והיא הגיבורה של היחידה הזו ושל יחידת מערכת הקבצים.

3. ה-API הסטנדרטי — read() כמקרה מבחן

לכל קריאת מערכת יש ממשק מתועד ומדויק. השקפים מדגימים זאת עם read() הזמינה במערכות UNIX ו-Linux: את ה-API שלה מקבלים מ-man page, על ידי הפקודה: 

man read

וכך נראה תיאור ה-API:

#include <unistd.h>

ssize_t    read(int fd, void *buf, size_t count)

השקף מפרק את שורת החתימה לשלושת חלקיה:

ssize_t
return value
read
function name
(int fd, void *buf, size_t count)
parameters

תוכנית שמשתמשת ב-read() חייבת לכלול את קובץ הכותרת unistd.h, כי שם מוגדרים (בין השאר) הטיפוסים ssize_t ו-size_t. ואלה הפרמטרים:

פרמטר משמעות
int fd ה-file descriptor שממנו קוראים
void *buf ה-buffer שאליו ייקראו הנתונים
size_t count מספר הבתים המקסימלי שייקראו אל תוך ה-buffer

וערכי החזרה:

  • הצלחה — מוחזר מספר הבתים שנקראו.
  • 0 — הגענו לסוף הקובץ (end of file, EOF).
  • -1 — אירעה שגיאה.

מלכודת מבחן קלאסית: ערך חזרה 0 מ-read() הוא EOF, לא שגיאה. שגיאה היא -1 בלבד. אל תתבלבלו בין השניים.

מקור: kernel-sdlc.pdf (עמ' 24)

4. המסלול המלא: מ-printf() ועד הקרנל ובחזרה

רגע — אם כל שירות מהקרנל עובר בקריאת מערכת, מה קורה כשאנחנו קוראים לפונקציה "רגילה" כמו printf()? השקפים עוקבים אחרי תוכנית C פשוטה: 

#include <stdio.h>
int main ( )
{
  ...
  printf ("Greetings");
  ...
  return 0;
}

printf() היא library call — פונקציה של ספריית glibc (ה-standard C library) — והיא זו שקוראת בעצמה לקריאת המערכת write(). בתרשים שבשקף, הספרייה יושבת בדיוק על הקו המפריד בין user mode (מעל) לבין kernel mode (מתחת): חץ יורד מ-printf("Greetings"); אל הספרייה, ממנה חץ עם התווית write ( ) אל write ( ) system call בתוך הקרנל — וחץ חוזר דרך הספרייה בחזרה אל הקוד, אל השורה שאחרי ה-printf.

את המעבר בפועל מבצעת רוטינת מעטפת — wrapper routine — בתוך glibc. תפקידה העיקרי של המעטפת:

  • להניח את כל ה-arguments שיש להעביר לקריאת המערכת ברגיסטרים המתאימים של המעבד (ואולי גם על ה-call stack).
  • לקבוע system call number ייחודי שהקרנל יקרא. כך הספרייה, שיושבת בין מערכת ההפעלה לאפליקציה, מגדילה את הפורטביליות (portability).

ואיך נכנסים בפועל למצב גרעין? זה בדיוק המקום שבו נסגר המעגל עם הפסיקות מסעיף 1. ראינו שם פסיקה שנוצרת בעל כורחו של תהליך — כשהוא מנסה לבצע הוראה מיוחסת והמעבד מסרב. אבל מנגנון הפסיקות, שמתכנני החומרה מממשים במעבד לצד ה-ISA ומצבי הריצה, משמש גם לכיוון ההפוך והמבוקש: ה-wrapper מפעיל את הוראת האסמבלי syscall — פסיקת תוכנה יזומה — והמעבד עובר מ-Ring 3 (מצב משתמש) ל-Ring 0 (מצב גרעין). כפי שמופיע ב-handouts של המרצה: "פקודת ה-syscall מעבירה את המעבד מ-Ring 3 ל-Ring 0", והבקשה מגיעה לפונקציית הליבה המתאימה בקרנל. בסיום השירות המעבד חוזר ל-Ring 3, וערך ההחזרה מגיע דרך הספרייה בחזרה לקוד שלנו.

🔒 יושלם בהמשך — הנושאים "סוגי פסיקות" ו"טיפול בפסיקות" (הסיווג המלא של מנגנון הפסיקות ותהליך הטיפול בהן) יתווספו כשהחומרים יעלו למודל.

5. הצצה לקרנל: מה קורה בפנים ב-open / read / write / close

מה קורה בצד השני של הפסיקה? לכל אחת מארבע הקריאות של ה-File Manipulation יש בקרנל אלגוריתם מסודר, שלב אחר שלב (ה-handouts של המרצה מתעדים אותו על Linux Kernel 6.14). כאן נסתפק בהצצה — הצלילה המלאה מחכה בפרקים FD, Inodes וארכיטקטורת I/O ו-File I/O מעשי.

open() — מהנתיב אל ה-FD

int open(const char *pathname, int flags, mode_t mode);

הקרנל מעתיק את מחרוזת הנתיב ממרחב המשתמש, מבצע Path Resolution — סריקה של עץ הספריות עד לקובץ המבוקש — ומאתר את ה-Inode שלו (או יוצר Inode חדש אם צוין הדגל O_CREAT והקובץ אינו קיים). לאחר מכן הוא יוצר אובייקט struct file ששומר את מצב הפתיחה, רושם מצביע אליו במקום הפנוי הראשון בטבלת תיאורי הקבצים של התהליך, ומחזיר את האינדקס הזה — ה-fd — למרחב המשתמש.

read() — מהדיסק (או מהמטמון) אל ה-buffer

ssize_t read(int fd, void *buf, size_t count);

אלגוריתם בן שמונה שלבים: הקרנל ממפה את ה-fd לאובייקט הקובץ, מוודא שהקובץ נפתח במצב שמאפשר קריאה, ופונה דרך שכבת ה-VFS למערכת הקבצים. אם הנתונים כבר נמצאים ב-Page Cache ב-RAM (Cache Hit) — מדלגים על הדיסק לגמרי; אחרת קוראים את הבלוקים מה-SSD. לבסוף הנתונים מועתקים בבטחה אל ה-buffer של התהליך (copy_to_user), מצביע המיקום בקובץ מתקדם, ומוחזר מספר הבתים שנקראו.

write() — כתיבה דרך המטמון

ssize_t write(int fd, const void *buf, size_t count);

אלגוריתם בן עשרה שלבים, שמנוהל לרוב כ-Buffered I/O: הנתונים מועתקים מה-buffer של התהליך אל ה-Page Cache ב-RAM (copy_from_user), הדף מסומן כ"מלוכלך" (Dirty), והכתיבה הפיזית ל-SSD מתבצעת רק בהמשך על ידי תהליכי רקע של הקרנל — תוך רישום שינויי המטא-דאטה ביומן (Journaling) להבטחת אמינות. לתהליך מוחזר מספר הבתים שנכתבו.

close() — לא רק "סגירת חלון"

int close(int fd);

אלגוריתם בן שבעה שלבים: הקרנל מסיר את ה-FD מטבלת התהליך (מרגע זה כל read/write עליו ייכשלו), ואז מפחית את מונה ההפניות (f_count) של אובייקט הקובץ המשותף. רק אם התהליך היה המחזיק האחרון (המונה הגיע לאפס) מתבצע ניקוי מלא ושחרור המשאבים בליבה; אחרת הקובץ נשאר פתוח עבור שאר המחזיקים. בהצלחה מוחזר 0.

מה לקחת מכאן: קריאת מערכת אינה "קסם" — מאחורי כל אחת מסתתר אלגוריתם קרנל מסודר ומתועד, עם בדיקות תקינות, מבני נתונים ומעברי Ring מדויקים. את המבנים עצמם (טבלת ה-FD, ‏struct file, ‏Inodes) נפרק לגורמים ביחידה 3.
