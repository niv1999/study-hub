1. מהי קריאת מערכת — ולמה אין דרך אחרת

בשיעורים הקודמים ראינו שהתוכנה במחשב מתחלקת לשניים: קוד הקרנל, וכל "שאר" התוכנה — כל התוכניות והספריות. עכשיו מגיעה השאלה המעשית: כשתוכנית רגילה רוצה משהו מהמערכת — לפתוח קובץ, למשל — איך היא בכלל מדברת עם הקרנל? התשובה היא המנגנון שסביבו סובב כל הקורס:

קריאת מערכת (System call) היא המנגנון שבאמצעותו תהליך מבקש מהקרנל לבצע שירות עבורו. דוגמה מהשקף: פתיחת קובץ (open a file).

שלוש מילים שכדאי להכיר לפני שממשיכים

אם המונחים הבאים חדשים לכם — הנה הגרסה הקצרה. כל השאר בפרק נשען עליהם:

  • הוראה (Instruction) — פקודה בודדת שהמעבד יודע לבצע, הלבנה הכי קטנה שממנה בנויה כל תוכנית. אוסף ההוראות שמעבד מסוים מכיר נקרא ה-ISA שלו.
  • הוראה מיוחסת מול לא-מיוחסת — מתכנני המעבד מחלקים את ההוראות לשתי קבוצות. ADD (חיבור שני מספרים) היא לא-מיוחסת — לא מסוכן לתת אותה לכל אחד. HALT (עצירת ה-CPU) היא מיוחסת — תוכנית אחת שתריץ אותה תשתק את כל המחשב.
  • מצב ריצה (privileged level) — "מתג" פנימי במעבד שקובע איזו רמת הרשאה פעילה כרגע. מוגדרים לפחות שני מצבים: מצב גרעין (kernel mode, הרשאה גבוהה) ומצב משתמש (user mode, הרשאה נמוכה). המצב הוא תכונה של המעבד ברגע נתון — לא של חשבון המשתמש שלכם במערכת.

השקפים מציגים את יחסי הגומלין בתרשים "עוגת שכבות": הרבה אפליקציות (Many applications), קרנל אחד (One Kernel), חומרה אחת (One Hardware) — ושלושה חיצים שמספרים את כל הסיפור:

שימו לב מה כל חץ אומר:

  • אפליקציה ← חומרה (ישירות): האפליקציה מריצה על המעבד אך ורק הוראות לא-מיוחסות (non-privileged). דוגמה מהשקף: ADD.
  • קרנל ← חומרה: הקרנל מריץ גם הוראות מיוחסות וגם לא-מיוחסות. דוגמה להוראה מיוחסת: HALT, שעוצרת את פעולת ה-CPU.
  • אפליקציה ← קרנל: חץ ה-System calls — הדרך שבה תהליך מבקש שירות שהוא לא יכול לבצע בעצמו.

למה זו הדרך היחידה?

כי המעבד עצמו אוכף את החלוקה. בכל הוראה שהוא מבצע יש שלב פענוח (Instruction Decode, בקיצור ID) שבו הוא מזהה איזו הוראה התבקש לבצע — ואז:

  • הוראה לא-מיוחסת — המעבד משלים אותה בכל מצב, גרעין או משתמש.
  • הוראה מיוחסת — המעבד משלים אותה רק במצב גרעין. אם הוא במצב משתמש הוא מסרב לבצע אותה ויוצר פסיקה (Interrupt) — קפיצה כפויה של המעבד אל שגרת טיפול בקרנל — והטיפול בה מוביל להפסקה מיידית של התהליך שכלל את ההוראה המיוחסת.

כלומר: אין "לפרוץ פנימה". תהליך שרוצה שירות שדורש הרשאות גבוהות חייב לבקש אותו מהקרנל — וזו בדיוק קריאת המערכת. בתרשים מבנה הקרנל מהפרק הקודם, ממשק ה-System calls הוא שער הכניסה שדרכו עוברות כל הבקשות מהאפליקציות אל רכיבי הקרנל.

מי בכלל קובע את הכללים האלה? לפי השקפים, מתכנני ארכיטקטורת החומרה הם שמתכננים שלושה דברים שילוו אותנו לאורך כל הפרק: (1) את מאפייני קבוצת ההוראות של המעבד (ה-ISA); (2) את מצבי הריצה (privileged levels); (3) את מנגנון הפסיקות הנתמך על ידי המעבד. שימו לב שהפסיקה היא מנגנון חומרתי — וזה בדיוק המנגנון שבסעיף 4 ישמש אותנו כדי להיכנס לקרנל מרצוננו.

2. שש הקטגוריות של קריאות מערכת

אילו שירותים אפשר בכלל לבקש? השקפים מסווגים את קריאות המערכת לשש קטגוריות, עם דוגמאות מוכרות בכל אחת. חלק גדול מהפונקציות בטבלה הזו ילוו אותנו לאורך כל הקורס:

קטגוריה דוגמאות מה מבקשים כאן
Process Control fork(), exit(), wait() יצירה, סיום והמתנה לתהליכים
File Manipulation open(), read(), write(), close() פתיחה, קריאה, כתיבה וסגירה של קבצים
Device Manipulation ioctl(), read(), write() עבודה מול התקנים (מסך, מקלדת, דיסק)
Information Maintenance getpid(), alarm(), sleep() מידע וזמנים על המערכת ועל התהליך
Communication pipe(), shmget(), mmap() העברת מידע בין תהליכים
Protection chmod(), umask(), chown() הרשאות ובעלות על קבצים

שימו לב ש-read() ו-write() מופיעות גם ב-File Manipulation וגם ב-Device Manipulation — אותן קריאות בדיוק משמשות לעבודה מול קבצים ומול התקנים. זו הצצה ראשונה לעיקרון "הכול קובץ" של UNIX. הרביעייה המלאה open/read/write/close שייכת לקטגוריית File Manipulation, והיא הגיבורה של היחידה הזו ושל יחידת מערכת הקבצים.

3. ה-API הסטנדרטי — read() כמקרה מבחן

API (Application Programming Interface) הוא "החוזה" של פונקציה: איך קוראים לה, מה מעבירים לה, ומה היא מחזירה. לכל קריאת מערכת יש חוזה כזה, מתועד ומדויק. השקפים מדגימים זאת עם read() הזמינה במערכות UNIX ו-Linux.

מה זה עושה: הפקודה הבאה פותחת בטרמינל את דף התיעוד הרשמי (man page) של read — משם לוקחים את ה-API: 

man read

מה זה עושה: וכך נראה תיאור ה-API שמתקבל — שורת ה-include ושורת החתימה:

#include <unistd.h>

ssize_t    read(int fd, void *buf, size_t count)

השקף מפרק את שורת החתימה לשלושת חלקיה:

ssize_t
return value
read
function name
(int fd, void *buf, size_t count)
parameters

תוכנית שמשתמשת ב-read() חייבת לכלול את קובץ הכותרת unistd.h, כי שם מוגדרים (בין השאר) הטיפוסים ssize_t ו-size_t. קובץ כותרת (header file, סיומת .h) הוא קובץ שמכיל הצהרות בלבד — שמות פונקציות, טיפוסים וקבועים; שורת #include מדביקה את תוכנו לתוכנית שלכם לפני הקומפילציה, כדי שהקומפיילר יכיר את השמות שאתם משתמשים בהם.

ואלה הפרמטרים:

פרמטר משמעות
int fd ה-file descriptor שממנו קוראים — המספר השלם שקיבלנו מ-open() ומזהה את הקובץ הפתוח
void *buf ה-buffer שאליו ייקראו הנתונים — כלומר אזור זיכרון שהתוכנית שלכם הכינה מראש (למשל מערך char buffer[4096]), "דלי" שהקרנל ימזוג לתוכו
size_t count מספר הבתים המקסימלי שייקראו אל תוך ה-buffer (בפועל ייתכן שפחות)

וערכי החזרה:

  • הצלחה — מוחזר מספר הבתים שנקראו בפועל.
  • 0 — הגענו לסוף הקובץ (end of file, EOF).
  • -1 — אירעה שגיאה.

מלכודת מבחן קלאסית: ערך חזרה 0 מ-read() הוא EOF, לא שגיאה — פשוט לא נשאר מה לקרוא. שגיאה היא -1 בלבד. אל תתבלבלו בין השניים.

4. המסלול המלא: מ-printf() ועד הקרנל ובחזרה

רגע — אם כל שירות מהקרנל עובר בקריאת מערכת, מה קורה כשאנחנו קוראים לפונקציה "רגילה" כמו printf()? השקפים עוקבים אחרי תוכנית C פשוטה.

מה זה עושה: תוכנית מינימלית שמדפיסה את המילה Greetings למסך:

#include <stdio.h>
int main ( )
{
  ...
  printf ("Greetings");
  ...
  return 0;
}

שלב א' — printf() היא לא קריאת מערכת

printf() היא library call — קריאה לפונקציה מתוך ספרייה. ספרייה היא אוסף פונקציות מוכנות וכתובות מראש שהתוכנית שלכם "מתחברת" אליו בזמן הבנייה או הטעינה, במקום לכתוב הכול מאפס. הספרייה הרלוונטית כאן היא glibc — ה-standard C library של לינוקס — ו-printf היא זו שקוראת בעצמה לקריאת המערכת write(), כי היא לבדה לא יכולה לגעת במסך.

נקודה למבחן: printf() שייכת לחבילת התוכנה glibc — החבילה שמועתקת למחשב בזמן ההתקנה של מערכת ההפעלה Linux. לא gcc (מהדר, כלי פיתוח), לא bash (מעטפת הפקודות), ובוודאי לא ה-Linux Kernel עצמו: printf רצה במרחב המשתמש, והקרנל רק מבצע עבורה את write().

בתרשים שבשקף, הספרייה יושבת בדיוק על הקו המפריד בין user mode (מעל) לבין kernel mode (מתחת): חץ יורד מ-printf("Greetings"); אל הספרייה, ממנה חץ עם התווית write ( ) אל write ( ) system call בתוך הקרנל — וחץ חוזר דרך הספרייה בחזרה אל הקוד, אל השורה שאחרי ה-printf.

שלב ב' — ה-wrapper של glibc

את המעבר בפועל מבצעת רוטינת מעטפת — wrapper routine — קטע קוד קטן בתוך glibc שיושב סביב כל קריאת מערכת. שני תפקידיה העיקריים לפי השקף:

  • להניח את כל ה-arguments שיש להעביר לקריאת המערכת ברגיסטרים המתאימים של המעבד (ואולי גם על ה-call stack). רגיסטר הוא תא זיכרון זעיר בתוך המעבד עצמו — יש רק כמה עשרות כאלה, והם המקום היחיד שהמעבד עובד מולו ישירות. זו "המדף" שעליו מניחים את הפרמטרים כדי שהקרנל ימצא אותם.
  • לקבוע system call number ייחודי שהקרנל יקרא — מספר סידורי שמזהה איזו קריאה התבקשה (ל-write מספר משלה, ל-read אחר). כך הספרייה, שיושבת בין מערכת ההפעלה לאפליקציה, מגדילה את הפורטביליות (portability): התוכנית שלכם קוראת ל-write() בשם, ולא צריכה להכיר את המספרים והרגיסטרים של ארכיטקטורת המעבד הספציפית.

שלב ג' — חוצים את הגבול

ואיך נכנסים בפועל למצב גרעין? כאן נסגר המעגל עם הפסיקות מסעיף 1. ראינו שם פסיקה שנוצרת בעל כורחו של תהליך — כשהוא מנסה לבצע הוראה מיוחסת והמעבד מסרב. אבל אותו מנגנון פסיקות עצמו, שמתכנני החומרה מממשים במעבד, משמש גם לכיוון ההפוך והמבוקש: ה-wrapper מפעיל את הוראת האסמבלי syscall — פסיקת תוכנה יזומה — והמעבד עובר מ-Ring 3 (מצב משתמש) ל-Ring 0 (מצב גרעין). כלשון ה-handouts של המרצה: "פקודת ה-syscall מעבירה את המעבד מ-Ring 3 ל-Ring 0". זו הסיבה שהסילבוס מגדיר את פסיקות התוכנה כמנגנון העיקרי למימוש קריאות מערכת.

המסלול המלא, בשש תחנות — כדאי לדעת לשחזר אותו בעל פה:

  1. הקוד שלכם קורא לפונקציית ספרייה (printf) או ישירות לעטיפת קריאת מערכת (write). המעבד ב-Ring 3.
  2. ה-wrapper ב-glibc מניח את הארגומנטים ברגיסטרים וקובע את מספר קריאת המערכת.
  3. הוראת syscall — פסיקת תוכנה. המעבד עובר ל-Ring 0 ונכנס לנקודת כניסה מסודרת של הקרנל.
  4. ניתוב לפי המספר: נקודת הכניסה של הקרנל קוראת את מספר קריאת המערכת ומפעילה לפיו את פונקציית הליבה המתאימה.
  5. פונקציית הליבה רצה (sys_openat, sys_read, sys_write, sys_close…) — עכשיו במצב גרעין מותר גם להוראות מיוחסות ולגישה לחומרה.
  6. חזרה: המעבד חוזר ל-Ring 3, וערך ההחזרה מטפס מהקרנל אל ה-wrapper וממנו אל הקוד שלכם — לשורה שאחרי הקריאה.

הרחבה — לא מהשקפים. הסילבוס מזכיר "סוגי פסיקות" ו"טיפול בפסיקות", אך לא הועלו שקפים בנושא. להשלמת התמונה, וכדי שסעיף זה יעמוד על רגליו — הנה המסגרת המקובלת, עקבית עם מה שכן מופיע בשקפים. לא חומר מחייב.

שלוש משפחות של פסיקות:

  • פסיקות חומרה / חיצוניות (hardware / external interrupts) — מקורן בהתקן חיצוני שמושך את תשומת לב המעבד: לחיצת מקש במקלדת, טיק של הטיימר, כרטיס רשת שקיבל מנה. הן א-סינכרוניות — מגיעות בלי קשר להוראה שהמעבד מריץ כרגע.
  • פסיקות תוכנה / מלכודות (software interrupts / traps) — יזומות בכוונה על ידי התוכנית עצמה. זו בדיוק הוראת syscall שהסעיף הזה תיאר, ולכן פסיקות תוכנה הן המנגנון העיקרי למימוש קריאות מערכת.
  • חריגות (exceptions / faults) — המעבד מייצר אותן כשאי אפשר להשלים את ההוראה הנוכחית: חלוקה באפס, גישה לכתובת שאינה בזיכרון (page fault), וגם ניסיון לבצע הוראה מיוחסת במצב משתמש — המקרה מסעיף 1.

זרימת הטיפול (זהה לכל השלוש):

  1. המעבד שומר את ההקשר של הקוד שרץ — לאן לחזור ומה היה מצב הדגלים.
  2. הוא מאתר את שגרת הטיפול לפי מספר הפסיקה בטבלה ייעודית — ה-IDT (Interrupt Descriptor Table).
  3. ה-ISR (Interrupt Service Routine) — שגרת הטיפול שבקרנל — רצה במצב גרעין.
  4. בסיום: שחזור ההקשר, חזרה ל-Ring 3 והמשך בדיוק מהנקודה שנקטעה — אלא אם הוחלט להפסיק את התהליך.

מקור: kernel-sdlc.pdf (עמ' 25), apps-kernel.pdf, open.pdf, read.pdf

5. הצצה לקרנל: מה קורה בפנים ב-open / read / write / close

מה קורה בצד השני של הפסיקה? לכל אחת מארבע הקריאות של File Manipulation יש בקרנל אלגוריתם מסודר, שלב אחר שלב (ה-handouts של המרצה מתעדים אותו על Linux Kernel 6.14). כאן נסתפק בהצצה — הצלילה המלאה מחכה בפרקים FD, Inodes וארכיטקטורת I/O ו-File I/O מעשי.

open() — מהנתיב אל ה-FD

מה זה עושה: מקבלת נתיב לקובץ ומחזירה מספר שלם שמייצג אותו מכאן והלאה:

int open(const char *pathname, int flags, mode_t mode);

הקרנל מעתיק את מחרוזת הנתיב ממרחב המשתמש, מבצע Path Resolution — סריקה של עץ הספריות עד לקובץ המבוקש — ומאתר את ה-Inode שלו (או יוצר Inode חדש אם צוין הדגל O_CREAT והקובץ אינו קיים). לאחר מכן הוא יוצר אובייקט struct file ששומר את מצב הפתיחה, רושם מצביע אליו במקום הפנוי הראשון בטבלת תיאורי הקבצים של התהליך, ומחזיר את האינדקס הזה — ה-fd — למרחב המשתמש (בדרך כלל 3, כי 0, 1 ו-2 כבר תפוסים).

read() — מהדיסק (או מהמטמון) אל ה-buffer

מה זה עושה: שואבת עד count בתים מהקובץ הפתוח אל תוך ה-buffer שלכם:

ssize_t read(int fd, void *buf, size_t count);

אלגוריתם בן שמונה שלבים: הקרנל ממפה את ה-fd לאובייקט הקובץ, מוודא שהקובץ נפתח במצב שמאפשר קריאה, ופונה דרך שכבת ה-VFS למערכת הקבצים. אם הנתונים כבר נמצאים ב-Page Cache ב-RAM (Cache Hit) — מדלגים על הדיסק לגמרי; אחרת קוראים את הבלוקים מה-SSD. לבסוף הנתונים מועתקים בבטחה אל ה-buffer של התהליך (copy_to_user), מצביע המיקום בקובץ מתקדם, ומוחזר מספר הבתים שנקראו.

write() — כתיבה דרך המטמון

מה זה עושה: מעבירה count בתים מה-buffer שלכם אל הקובץ הפתוח:

ssize_t write(int fd, const void *buf, size_t count);

אלגוריתם בן עשרה שלבים, שמנוהל לרוב כ-Buffered I/O: הנתונים מועתקים מה-buffer של התהליך אל ה-Page Cache ב-RAM (copy_from_user — הכיוון ההפוך מ-copy_to_user), הדף מסומן כ"מלוכלך" (Dirty), והכתיבה הפיזית ל-SSD מתבצעת רק בהמשך על ידי תהליכי רקע של הקרנל — תוך רישום שינויי המטא-דאטה ביומן (Journaling) להבטחת אמינות בקריסה. לתהליך מוחזר מספר הבתים שנכתבו.

close() — לא רק "סגירת חלון"

מה זה עושה: מודיעה לקרנל שסיימנו עם ה-fd הזה ומבקשת לשחרר את המשאבים:

int close(int fd);

אלגוריתם בן שבעה שלבים: הקרנל מסיר את ה-FD מטבלת התהליך (מרגע זה כל read/write עליו ייכשלו, והמספר פנוי להקצאה מחדש), ואז מפחית את מונה ההפניות (f_count) של אובייקט הקובץ המשותף. המונה נחוץ כי fork(), dup(), dup2() יכולים לגרום לכך ששני תהליכים (או שני FDs) יצביעו על אותו אובייקט קובץ. רק אם התהליך היה המחזיק האחרון (המונה הגיע לאפס) מתבצע ניקוי מלא ושחרור המשאבים בליבה; אחרת הקובץ נשאר פתוח עבור שאר המחזיקים. בהצלחה מוחזר 0.

טבלת ערכי ההחזרה — לשינון

קריאה בהצלחה בכישלון
open() ה-fd — מספר שלם אי-שלילי -1
read() מספר הבתים שנקראו · 0 = EOF -1
write() מספר הבתים שנכתבו בפועל -1
close() 0 -1

השגיאה שחוזרת בכל ארבעתן: EBADF — Bad file descriptor — כשה-fd אינו תקין או אינו פתוח. היא מופיעה גם כשמנסים read מקובץ שנפתח O_WRONLY (כתיבה בלבד), או write לקובץ שנפתח O_RDONLY (קריאה בלבד). בתוך קוד הקרנל השגיאה מיוצגת כערך שלילי (-EBADF); בקוד שלכם, במרחב המשתמש, היא מגיעה תמיד באותה צורה — -1 ועוד קוד ב-errno. זה בדיוק הנושא של הסעיף הבא.

6. מנגנון השגיאות — errno ו-perror()

ראינו שהקריאות מחזירות -1 כשמשהו השתבש — אבל מה בדיוק השתבש? כאשר תהליך במרחב המשתמש מבצע קריאת מערכת, הוא מבקש שירות ישירות מליבת מערכת ההפעלה — ושירותים כמו פתיחת קובץ, כתיבה לדיסק או יצירת תהליך עשויים להיכשל מסיבות מגוונות: קובץ לא קיים, חוסר הרשאות, חוסר זיכרון או פרמטרים שגויים. דף העזר של המרצה מוקדש בדיוק למנגנון שמספר לנו שנכשלנו — ולמה.

למה חייבים מנגנון דיווח?

קריאת מערכת היא גבול מעבר קריטי בין מרחב המשתמש למרחב הליבה. הליבה פועלת ברמת הרשאה גבוהה יותר (Kernel Mode) ויש לה אחריות לאכוף את כללי המערכת. כשקריאת מערכת נכשלת, יש הכרח מוחלט במנגנון שדרכו הליבה תוכל:

  1. לדווח על הכישלון — להודיע לתהליך הקורא כי הבקשה לא בוצעה בהצלחה.
  2. לספק את הסיבה הספציפית לכישלון — כדי שהתהליך יוכל לטפל בשגיאה בצורה נאותה (למשל לנסות שוב, לדווח למשתמש, או לסיים את פעולתו).

מוסכמת ההחזרה בלינוקס ובמערכות תואמות POSIX: הצלחה — ערך אי-שלילי (לרוב >= 0), המייצג את התוצאה החוקית של הקריאה: מספר בייטים שנכתבו, מזהה תהליך חדש, או file descriptor. כישלון — ערך שלילי מוסכם, לרוב -1, שהוא האות הראשוני והחשוב ביותר המעיד על כשל. הסיבה הספציפית לכישלון אינה מועברת דרך ערך ההחזרה עצמו — אלא דרך מנגנון נפרד: errno.

המשתנה errno

errno (קיצור של "Error Number") הוא המנגנון הסטנדרטי והמרכזי ביותר לדיווח על שגיאות הנובעות מקריאות מערכת ומקריאות לספריות (Library Calls) בסביבת POSIX:

  • תפקיד: כשקריאת מערכת נכשלת (ומחזירה -1), הליבה מעדכנת את הערך של errno למספר שלם חיובי המייצג את קוד השגיאה הספציפי שהתרחשה.
  • טווח: כל קוד שגיאה מייצג מצב כישלון מוגדר (לדוגמה, 2 = "אין קובץ או ספרייה כזו", 13 = "הרשאה נדחתה").

errno אינו משתנה גלובלי רגיל

מבחינה טכנית, errno אינו משתנה גלובלי רגיל — את כל הפסקה הזו המרצה הדגיש במרקר. הוא ממומש בצורה שמאפשרת לו להיות פר-תהליכי (Per-Process) או פר-תהליכון (Per-Thread): במערכות תואמות POSIX, ובפרט בלינוקס, errno מוגדר למעשה כמאקרו (Macro) המתרחב לביטוי שמחזיר את הערך המאוחסן במיקום זיכרון השייך לתהליך (או לתהליכון) הנוכחי.

הסיבה למימוש הזה היא בטיחות תהליכונים (Thread Safety): אילו errno היה משתנה גלובלי רגיל, שני תהליכונים שונים באותו תהליך המבצעים קריאות מערכת בו-זמנית היו דורסים זה את ערכו של זה — מצב מירוץ (Race Condition) שמוביל למידע שגיאה שגוי. הגישה הפר-תהליכונית מבטיחה שכל תהליכון יכול לקרוא את קוד השגיאה שלו באופן אמין.

מה זה עושה: השורה הבאה היא תנאי הכרחי לשימוש ב-errno — בלעדיה הקומפיילר אפילו לא יכיר את השם: 

#include <errno.h>

קובץ כותר זה מגדיר את המאקרו של errno ואת רשימת קודי השגיאה המוסכמים כמאקרואים (למשל EACCES עבור "Access Denied") — בלעדיו אי אפשר גם לכתוב בדיקות כמו if (errno == EACCES).

הערה חשובה — לקרוא מייד: לאחר קריאת מערכת כושלת, התוכנית חייבת לקרוא את הערך של errno מייד לאחר הכישלון, מכיוון שכל קריאת ספרייה או קריאת מערכת עוקבת (אפילו קריאה מוצלחת!) עלולה לדרוס את ערכו.

טבלת קודי השגיאה

קודי השגיאה הם מספרים שלמים חיוביים (הערך של errno). לכל מספר כזה מוגדר שם סמלי (Symbolic Name) המתחיל באות 'E', המשמש לקריאוּת קוד קלה יותר:

קוד מספרי (ב-errno) שם סמלי (מאקרו) תיאור קצר
1 EPERM Operation not permitted (אין הרשאה)
2 ENOENT No such file or directory (קובץ לא נמצא)
4 EINTR Interrupted system call (נקטעה על ידי אות)
11 EAGAIN / EWOULDBLOCK Resource temporarily unavailable (נסה שוב)
13 EACCES Permission denied (הרשאה נדחתה)
22 EINVAL Invalid argument (ארגומנט לא חוקי)

איפה הטבלה הזו בכלל מוגדרת?

גם את זה המרצה הדגיש במרקר — ויש כאן הבחנה עדינה בין השם לבין המספר:

  • ההגדרות הסמליות (ENOENT، EACCES וכו' מוגדרות בקובץ הכותר <errno.h> — זה מה שהתוכנית שלכם כוללת.
  • ההגדרות המספריות בפועל (ש-ENOENT הוא דווקא 2) מוגדרות ברמת הליבה: בקובץ כותר (header, קובץ .h) של ה-kernel — למשל asm-generic/errno-base.h — שמועתק לספריית הכותרות של המשתמש בעת בניית המערכת.

נקודה למבחן: לשאלה "היכן מוגדרים הערכים המספריים הממשיים של קודי השגיאה, ברמת המערכת?" — התשובה היא בקובץ header (קובץ .h) של ה-kernel. לא בקובץ ה-C של התוכנית, לא במצבי ה-CPU, ובוודאי לא "באופן אקראי בכל הרצה".

perror() — הודעת שגיאה בשפה טבעית

בעוד ש-errno מספק את הקוד המספרי והסמלי של השגיאה, לעיתים קרובות אנחנו רוצים להציג למשתמש הודעת שגיאה קריאה בשפה טבעית. זה תפקידה של perror().

מה זה עושה: זו חתימת הפונקציה — היא מקבלת מחרוזת אחת ואינה מחזירה דבר:

void perror(const char *s);

הפרמטר s הוא מחרוזת מותאמת אישית של המתכנת, שמעידה על הקטע בתוכנית שבו אירע הכישלון. הפונקציה מדפיסה אותה לפלט השגיאה הסטנדרטי (stderr), ואחריה מוסיפה נקודתיים, רווח, ואת תיאור השגיאה המילולי המתאים לערך הנוכחי של errno; לבסוף היא מוסיפה תו שורה חדשה (\n).

מה זה עושה: השימוש הקלאסי — ניסיון לפתוח קובץ, ואם הוא נכשל, דיווח מיידי:

if (open("non_existent_file.txt", O_RDONLY) == -1) {
    perror("Failed to open file");
    // ... טיפול בשגיאה ...
}

אם קריאת המערכת open נכשלה כי הקובץ לא נמצא (errno = 2 = ENOENT), הפלט יהיה: 

Failed to open file: No such file or directory

מלכודת ה-include: מכיוון ש-perror היא פונקציה סטנדרטית של ספריית הקלט/פלט, יש הכרח לכלול עבורה דווקא את <stdio.h> — ולא את <errno.h>. את <errno.h> כוללים עבור המשתנה errno ועבור השמות הסמליים; לרוב תזדקקו לשניהם.

7. עקרון היסוד: בודקים כל ערך החזרה

כלל אצבע בתכנות מערכות, וסעיף שלם בדף העזר של המרצה: יש לבדוק את ערך ההחזרה של כל קריאת מערכת וכל קריאת ספרייה שעלולה להיכשל, באופן עקבי. זו הדרך היחידה לוודא הצלחה או לזהות כישלון.

מה זה עושה: מבנה בדיקת שגיאות טיפוסי — כותבים, בודקים, מדווחים, יוצאים:

ssize_t bytes_written;
// ...
bytes_written = write(fd, buffer, count);
if (bytes_written == -1) {
    // 1. קריאת המערכת נכשלה
    // 2. ה-kernel עדכן את ערך errno
    perror("Error writing to file descriptor"); // הדפסת הודעת שגיאה קריאה
    exit(EXIT_FAILURE);
}
// 3. אם הגענו לכאן, ה-write הצליח (ייתכן שרק חלקית)

שימו לב להערה בשורה האחרונה: גם כשעברנו את הבדיקה וה-write "הצליח", ייתכן שנכתבו פחות בתים מ-count — כתיבה חלקית. הטיפול המלא ב-Partial I/O מחכה בפרק File I/O מעשי.

הדוגמה המלאה של המרצה

התרחיש: ניסיון פתיחת קובץ שלא קיים, או שאין למשתמש הרשאה לפתוח אותו. מה זה עושה: תוכנית שלמה שמדגימה את השימוש הבסיסי והנפוץ ביותר במנגנון — בדיקת ערך החזרה של -1 ודיווח באמצעות perror(): 

#include <stdio.h>      // עבור perror
#include <stdlib.h>
#include <unistd.h>     // עבור קריאת המערכת close
#include <fcntl.h>      // עבור קריאת המערכת open ודגלי גישה (O_RDONLY)

// הפונקציה המרכזית
int main() {
    int fd;
    const char *filename = "private_file.txt"; // קובץ שאינו קיים או נעול

    printf("Attempting to open file: %s\n", filename);

    // קריאת המערכת open(2)
    // מחזירה file descriptor (ערך >= 0) במקרה של הצלחה, או -1 במקרה של כישלון
    fd = open(filename, O_RDONLY);

    // בדיקת ערך ההחזרה של קריאת המערכת
    if (fd == -1) {
        // הכישלון אושר. הליבה עדכנה את errno.

        // שימוש ב-perror() לדיווח.
        // פונקציה זו משתמשת בערך הנוכחי של errno ומדפיסה:
        // "Failed to open file: [התיאור המילולי של קוד השגיאה]"
        perror("Failed to open file");

        // יציאה עם קוד כישלון
        return EXIT_FAILURE;
    }

    // קוד זה יתבצע רק במקרה של הצלחה
    printf("File opened successfully with file descriptor: %d\n", fd);
    close(fd);

    return EXIT_SUCCESS;
}

קריאה מודרכת, שלב אחר שלב:

  1. ארבעת ה-includes — stdio.h עבור perror (ו-printf), ‏fcntl.h עבור open ודגלי הגישה (O_RDONLY), ‏unistd.h עבור close, ‏ו-stdlib.h עבור EXIT_FAILURE / EXIT_SUCCESS (שני קבועים מוסכמים לקוד יציאה של התוכנית).
  2. open מחזירה file descriptor (ערך >= 0) בהצלחה או -1 בכישלון — ולכן הבדיקה היא if (fd == -1).
  3. בענף הכישלון: הליבה כבר עדכנה את errno, ולכן perror("Failed to open file") תדפיס ל-stderr את המחרוזת ואחריה את התיאור המילולי של קוד השגיאה — והתוכנית יוצאת עם EXIT_FAILURE.
  4. רק אם הפתיחה הצליחה מגיעים להדפסת ה-fd ולסגירה מסודרת עם close(fd).

מלכודות למבחן — סיכום הפרק:

  • -1 הוא רק האות לכשל; errno הוא הסיבה. קוד השגיאה לעולם לא מגיע דרך ערך ההחזרה עצמו.
  • errno תקף רק מייד אחרי הכישלון — כל קריאת ספרייה או קריאת מערכת עוקבת (אפילו מוצלחת) עלולה לדרוס אותו.
  • errno הוא פר-תהליכון, לא משתנה גלובלי רגיל — מאקרו של POSIX, בגלל Thread Safety.
  • השמות הסמליים מגיעים מ-<errno.h>; הערכים המספריים מוגדרים בקובץ header (.h) של ה-kernel.
  • perror דורשת <stdio.h>, לא <errno.h>, ומדפיסה ל-stderr.
  • printf() היא library call של חבילת glibc — לא קריאת מערכת ולא חלק מהקרנל.
