1. מהי קריאת מערכת — ולמה אין דרך אחרת

בפרק הקודם ראינו שהתוכנה במחשב מתחלקת לשניים: קוד הקרנל, וכל "שאר" התוכנה — כל התוכניות והספריות. עכשיו מגיעה השאלה המעשית: כשתוכנית רגילה רוצה משהו מהמערכת — לפתוח קובץ, למשל — איך היא בכלל מדברת עם הקרנל? התשובה היא המנגנון שסביבו סובב כל הקורס:

קריאת מערכת (System call) היא המנגנון שבאמצעותו תהליך מבקש מהקרנל לבצע שירות עבורו. דוגמה מהשקף: פתיחת קובץ (open a file).

השקפים מציגים את יחסי הגומלין בתרשים "עוגת שכבות": הרבה אפליקציות (Many applications), קרנל אחד (One Kernel), חומרה אחת (One Hardware) — ושלושה חיצים שמספרים את כל הסיפור:

שימו לב מה כל חץ אומר:

  • אפליקציה ← חומרה (ישירות): האפליקציה מריצה על המעבד אך ורק הוראות לא-מיוחסות (non-privileged). דוגמה מהשקף: ADD.
  • קרנל ← חומרה: הקרנל מריץ גם הוראות מיוחסות וגם לא-מיוחסות. דוגמה להוראה מיוחסת: HALT, שעוצרת את פעולת ה-CPU.
  • אפליקציה ← קרנל: חץ ה-System calls — הדרך שבה תהליך מבקש שירות שהוא לא יכול לבצע בעצמו.

ולמה זו הדרך היחידה? כי המעבד עצמו אוכף את החלוקה: בשלב פענוח ההוראה (Instruction Decode) הוא בודק אם ההוראה מיוחסת. הוראה לא-מיוחסת מבוצעת בכל מצב; הוראה מיוחסת מבוצעת רק כשהמעבד במצב גרעין. אם תהליך במצב משתמש מנסה לבצע הוראה מיוחסת — המעבד מסרב לבצע אותה ויוצר פסיקה (Interrupt), שהטיפול בה מוביל להפסקה מיידית של התהליך. כלומר: אין "לפרוץ פנימה". תהליך שרוצה שירות שדורש הרשאות גבוהות חייב לבקש אותו מהקרנל — וזו בדיוק קריאת המערכת. בתרשים מבנה הקרנל שראינו בפרק הקודם, ממשק ה-System calls הוא שער הכניסה שדרכו עוברות כל הבקשות מהאפליקציות אל רכיבי הקרנל.

2. שש הקטגוריות של קריאות מערכת

אילו שירותים אפשר בכלל לבקש? השקפים מסווגים את קריאות המערכת לשש קטגוריות, עם דוגמאות מוכרות בכל אחת. חלק גדול מהפונקציות בטבלה הזו ילוו אותנו לאורך כל הקורס:

קטגוריה דוגמאות
Process Control fork(), exit(), wait()
File Manipulation open(), read(), write(), close()
Device Manipulation ioctl(), read(), write()
Information Maintenance getpid(), alarm(), sleep()
Communication pipe(), shmget(), mmap()
Protection chmod(), umask(), chown()

שימו לב ש-read() ו-write() מופיעות גם ב-File Manipulation וגם ב-Device Manipulation — אותן קריאות משמשות לעבודה מול קבצים ומול התקנים. הרביעייה המלאה open/read/write/close שייכת לקטגוריית ה-File Manipulation, והיא הגיבורה של היחידה הזו ושל יחידת מערכת הקבצים.

מקור: kernel-sdlc.pdf (עמ' 23)

3. ה-API הסטנדרטי — read() כמקרה מבחן

לכל קריאת מערכת יש ממשק מתועד ומדויק. השקפים מדגימים זאת עם read() הזמינה במערכות UNIX ו-Linux: את ה-API שלה מקבלים מ-man page, על ידי הפקודה: 

man read

וכך נראה תיאור ה-API:

#include <unistd.h>

ssize_t    read(int fd, void *buf, size_t count)

השקף מפרק את שורת החתימה לשלושת חלקיה:

ssize_t
return value
read
function name
(int fd, void *buf, size_t count)
parameters

תוכנית שמשתמשת ב-read() חייבת לכלול את קובץ הכותרת unistd.h, כי שם מוגדרים (בין השאר) הטיפוסים ssize_t ו-size_t. ואלה הפרמטרים:

פרמטר משמעות
int fd ה-file descriptor שממנו קוראים
void *buf ה-buffer שאליו ייקראו הנתונים
size_t count מספר הבתים המקסימלי שייקראו אל תוך ה-buffer

וערכי החזרה:

  • הצלחה — מוחזר מספר הבתים שנקראו.
  • 0 — הגענו לסוף הקובץ (end of file, EOF).
  • -1 — אירעה שגיאה.

מלכודת מבחן קלאסית: ערך חזרה 0 מ-read() הוא EOF, לא שגיאה. שגיאה היא -1 בלבד. אל תתבלבלו בין השניים.

מקור: kernel-sdlc.pdf (עמ' 24)

4. המסלול המלא: מ-printf() ועד הקרנל ובחזרה

רגע — אם כל שירות מהקרנל עובר בקריאת מערכת, מה קורה כשאנחנו קוראים לפונקציה "רגילה" כמו printf()? השקפים עוקבים אחרי תוכנית C פשוטה: 

#include <stdio.h>
int main ( )
{
  ...
  printf ("Greetings");
  ...
  return 0;
}

printf() היא library call — פונקציה של ספריית glibc (ה-standard C library) — והיא זו שקוראת בעצמה לקריאת המערכת write(). בתרשים שבשקף, הספרייה יושבת בדיוק על הקו המפריד בין user mode (מעל) לבין kernel mode (מתחת): חץ יורד מ-printf("Greetings"); אל הספרייה, ממנה חץ עם התווית write ( ) אל write ( ) system call בתוך הקרנל — וחץ חוזר דרך הספרייה בחזרה אל הקוד, אל השורה שאחרי ה-printf.

את המעבר בפועל מבצעת רוטינת מעטפת — wrapper routine — בתוך glibc. תפקידה העיקרי של המעטפת:

  • להניח את כל ה-arguments שיש להעביר לקריאת המערכת ברגיסטרים המתאימים של המעבד (ואולי גם על ה-call stack).
  • לקבוע system call number ייחודי שהקרנל יקרא. כך הספרייה, שיושבת בין מערכת ההפעלה לאפליקציה, מגדילה את הפורטביליות (portability).

ואיך נכנסים בפועל למצב גרעין? זה בדיוק המקום שבו נסגר המעגל עם הפסיקות מסעיף 1. ראינו שם פסיקה שנוצרת בעל כורחו של תהליך — כשהוא מנסה לבצע הוראה מיוחסת והמעבד מסרב. אבל מנגנון הפסיקות, שמתכנני החומרה מממשים במעבד לצד ה-ISA ומצבי הריצה, משמש גם לכיוון ההפוך והמבוקש: ה-wrapper מפעיל את הוראת האסמבלי syscall — פסיקת תוכנה יזומה — והמעבד עובר מ-Ring 3 (מצב משתמש) ל-Ring 0 (מצב גרעין). כפי שמופיע ב-handouts של המרצה: "פקודת ה-syscall מעבירה את המעבד מ-Ring 3 ל-Ring 0", והבקשה מגיעה לפונקציית הליבה המתאימה בקרנל. בסיום השירות המעבד חוזר ל-Ring 3, וערך ההחזרה מגיע דרך הספרייה בחזרה לקוד שלנו.

🔒 יושלם בהמשך — הנושאים "סוגי פסיקות" ו"טיפול בפסיקות" (הסיווג המלא של מנגנון הפסיקות ותהליך הטיפול בהן) יתווספו כשהחומרים יעלו למודל.

מקור: kernel-sdlc.pdf (עמ' 25), apps-kernel.pdf, open.pdf, read.pdf

5. הצצה לקרנל: מה קורה בפנים ב-open / read / write / close

מה קורה בצד השני של הפסיקה? לכל אחת מארבע הקריאות של ה-File Manipulation יש בקרנל אלגוריתם מסודר, שלב אחר שלב (ה-handouts של המרצה מתעדים אותו על Linux Kernel 6.14). כאן נסתפק בהצצה — הצלילה המלאה מחכה בפרקים FD, Inodes וארכיטקטורת I/O ו-File I/O מעשי.

open() — מהנתיב אל ה-FD

int open(const char *pathname, int flags, mode_t mode);

הקרנל מעתיק את מחרוזת הנתיב ממרחב המשתמש, מבצע Path Resolution — סריקה של עץ הספריות עד לקובץ המבוקש — ומאתר את ה-Inode שלו (או יוצר Inode חדש אם צוין הדגל O_CREAT והקובץ אינו קיים). לאחר מכן הוא יוצר אובייקט struct file ששומר את מצב הפתיחה, רושם מצביע אליו במקום הפנוי הראשון בטבלת תיאורי הקבצים של התהליך, ומחזיר את האינדקס הזה — ה-fd — למרחב המשתמש.

read() — מהדיסק (או מהמטמון) אל ה-buffer

ssize_t read(int fd, void *buf, size_t count);

אלגוריתם בן שמונה שלבים: הקרנל ממפה את ה-fd לאובייקט הקובץ, מוודא שהקובץ נפתח במצב שמאפשר קריאה, ופונה דרך שכבת ה-VFS למערכת הקבצים. אם הנתונים כבר נמצאים ב-Page Cache ב-RAM (Cache Hit) — מדלגים על הדיסק לגמרי; אחרת קוראים את הבלוקים מה-SSD. לבסוף הנתונים מועתקים בבטחה אל ה-buffer של התהליך (copy_to_user), מצביע המיקום בקובץ מתקדם, ומוחזר מספר הבתים שנקראו.

write() — כתיבה דרך המטמון

ssize_t write(int fd, const void *buf, size_t count);

אלגוריתם בן עשרה שלבים, שמנוהל לרוב כ-Buffered I/O: הנתונים מועתקים מה-buffer של התהליך אל ה-Page Cache ב-RAM (copy_from_user), הדף מסומן כ"מלוכלך" (Dirty), והכתיבה הפיזית ל-SSD מתבצעת רק בהמשך על ידי תהליכי רקע של הקרנל — תוך רישום שינויי המטא-דאטה ביומן (Journaling) להבטחת אמינות. לתהליך מוחזר מספר הבתים שנכתבו.

close() — לא רק "סגירת חלון"

int close(int fd);

אלגוריתם בן שבעה שלבים: הקרנל מסיר את ה-FD מטבלת התהליך (מרגע זה כל read/write עליו ייכשלו), ואז מפחית את מונה ההפניות (f_count) של אובייקט הקובץ המשותף. רק אם התהליך היה המחזיק האחרון (המונה הגיע לאפס) מתבצע ניקוי מלא ושחרור המשאבים בליבה; אחרת הקובץ נשאר פתוח עבור שאר המחזיקים. בהצלחה מוחזר 0.

מה לקחת מכאן: קריאת מערכת אינה "קסם" — מאחורי כל אחת מסתתר אלגוריתם קרנל מסודר ומתועד, עם בדיקות תקינות, מבני נתונים ומעברי Ring מדויקים. את המבנים עצמם (טבלת ה-FD, ‏struct file, ‏Inodes) נפרק לגורמים ביחידה 3.

מקור: open.pdf, read.pdf, write.pdf, close.pdf

6. מנגנון השגיאות — errno ו-perror()

ראינו ש-read() מחזירה -1 כשמשהו השתבש — אבל מה בדיוק השתבש? כאשר תהליך במרחב המשתמש מבצע קריאת מערכת, הוא מבקש שירות ישירות מליבת מערכת ההפעלה — ושירותים כמו פתיחת קובץ, כתיבה לדיסק או יצירת תהליך עשויים להיכשל מסיבות מגוונות: קובץ לא קיים, חוסר הרשאות, חוסר זיכרון או פרמטרים שגויים. דף העזר של המרצה מוקדש בדיוק למנגנון שמספר לנו שנכשלנו — ולמה.

למה חייבים מנגנון דיווח?

קריאת מערכת היא גבול מעבר קריטי בין מרחב המשתמש למרחב הליבה. הליבה פועלת ברמת הרשאה גבוהה יותר (Kernel Mode) ויש לה אחריות לאכוף את כללי המערכת. כשקריאת מערכת נכשלת, יש הכרח מוחלט במנגנון שדרכו הליבה תוכל:

  1. לדווח על הכישלון — להודיע לתהליך הקורא כי הבקשה לא בוצעה בהצלחה.
  2. לספק את הסיבה הספציפית לכישלון — כדי שהתהליך יוכל לטפל בשגיאה בצורה נאותה (למשל לנסות שוב, לדווח למשתמש, או לסיים את פעולתו).

מוסכמת ההחזרה בלינוקס ובמערכות תואמות POSIX: הצלחה — ערך אי-שלילי (לרוב >= 0), המייצג את התוצאה החוקית של הקריאה: מספר בייטים שנכתבו, מזהה תהליך חדש, או file descriptor. כישלון — ערך שלילי מוסכם, לרוב -1, שהוא האות הראשוני והחשוב ביותר המעיד על כשל. הסיבה הספציפית לכישלון אינה מועברת דרך ערך ההחזרה עצמו — אלא דרך מנגנון נפרד: errno.

המשתנה errno

errno (קיצור של "Error Number") הוא המנגנון הסטנדרטי והמרכזי ביותר לדיווח על שגיאות הנובעות מקריאות מערכת ומקריאות לספריות (Library Calls) בסביבת POSIX:

  • תפקיד: כשקריאת מערכת נכשלת (ומחזירה -1), הליבה מעדכנת את הערך של errno למספר שלם חיובי המייצג את קוד השגיאה הספציפי שהתרחשה.
  • טווח: כל קוד שגיאה מייצג מצב כישלון מוגדר (לדוגמה, 2 = "אין קובץ או ספרייה כזו", 13 = "הרשאה נדחתה").

errno אינו משתנה גלובלי רגיל

מבחינה טכנית, errno אינו משתנה גלובלי רגיל — את כל הפסקה הזו המרצה הדגיש במרקר. הוא ממומש בצורה שמאפשרת לו להיות פר-תהליכי (Per-Process) או פר-תהליכון (Per-Thread): במערכות תואמות POSIX, ובפרט בלינוקס, errno מוגדר למעשה כמאקרו (Macro) המתרחב לביטוי שמחזיר את הערך המאוחסן במיקום זיכרון השייך לתהליך (או לתהליכון) הנוכחי.

הסיבה למימוש הזה היא בטיחות תהליכונים (Thread Safety): אילו errno היה משתנה גלובלי רגיל, שני תהליכונים שונים באותו תהליך המבצעים קריאות מערכת בו-זמנית היו דורסים זה את ערכו של זה — מצב מירוץ (Race Condition) שמוביל למידע שגיאה שגוי. הגישה הפר-תהליכונית מבטיחה שכל תהליכון יכול לקרוא את קוד השגיאה שלו באופן אמין.

כדי להשתמש ב-errno יש הכרח לכלול קובץ הגדרה ספציפי:

#include <errno.h>

קובץ כותר זה מגדיר את המאקרו של errno ואת רשימת קודי השגיאה המוסכמים כמאקרואים (למשל EACCES עבור "Access Denied") — בלעדיו אי אפשר גם לכתוב בדיקות כמו if (errno == EACCES).

הערה חשובה — לקרוא מייד: לאחר קריאת מערכת כושלת, התוכנית חייבת לקרוא את הערך של errno מייד לאחר הכישלון, מכיוון שכל קריאת ספרייה או קריאת מערכת עוקבת (אפילו קריאה מוצלחת!) עלולה לדרוס את ערכו.

טבלת קודי השגיאה

קודי השגיאה הם מספרים שלמים חיוביים (הערך של errno). לכל מספר כזה מוגדר שם סמלי (Symbolic Name) המתחיל באות 'E', המשמש לקריאוּת קוד קלה יותר:

קוד מספרי (ב-errno) שם סמלי (מאקרו) תיאור קצר
1 EPERM Operation not permitted (אין הרשאה)
2 ENOENT No such file or directory (קובץ לא נמצא)
4 EINTR Interrupted system call (נקטעה על ידי אות)
11 EAGAIN / EWOULDBLOCK Resource temporarily unavailable (נסה שוב)
13 EACCES Permission denied (הרשאה נדחתה)
22 EINVAL Invalid argument (ארגומנט לא חוקי)

והיכן הטבלה הזו מוגדרת? גם את זה המרצה הדגיש:

  • ההגדרות הסמליות (כגון ENOENT, EACCES וכו') מוגדרות בקובץ הכותר <errno.h>.
  • ההגדרות המספריות בפועל של הקודים מוגדרות ברמת הליבה, וקובץ הכותר של הליבה (asm-generic/errno-base.h וכו') מועתק לספריית הכותרות של המשתמש בעת בניית המערכת.

perror() — הודעת שגיאה בשפה טבעית

בעוד ש-errno מספק את הקוד המספרי והסמלי של השגיאה, לעיתים קרובות אנחנו רוצים להציג למשתמש הודעת שגיאה קריאה בשפה טבעית. זה תפקידה של perror(): 

void perror(const char *s);

הפונקציה מקבלת מחרוזת קלט s — מחרוזת מותאמת אישית של המתכנת, המעידה על הקטע בתוכנית שבו אירע הכישלון — ומדפיסה אותה לפלט השגיאה הסטנדרטי (stderr), ולאחריה היא מוסיפה נקודתיים, רווח, ואת התיאור השגיאה המילולי המתאים לערך הנוכחי של errno. לבסוף היא מוסיפה תו שורה חדשה (\n). דוגמה לשימוש קלאסי: 

if (open("non_existent_file.txt", O_RDONLY) == -1) {
    perror("Failed to open file");
    // ... טיפול בשגיאה ...
}

אם קריאת המערכת open נכשלה כי הקובץ לא נמצא (errno = 2 = ENOENT), הפלט יהיה: 

Failed to open file: No such file or directory

וכאן מלכודת include נוספת: מכיוון ש-perror היא פונקציה סטנדרטית של ספריית הקלט/פלט, יש הכרח לכלול דווקא את (ולא את errno.h!): 

#include <stdio.h>

עקרון היסוד: בודקים כל ערך החזרה

כלל אצבע בתכנות מערכות הוא: יש לבדוק את ערך ההחזרה של כל קריאת מערכת וכל קריאת ספרייה שעלולה להיכשל, באופן עקבי. זו הדרך היחידה לוודא הצלחה או לזהות כישלון. מבנה בדיקת שגיאות טיפוסי: 

ssize_t bytes_written;
// ...
bytes_written = write(fd, buffer, count);
if (bytes_written == -1) {
    // 1. קריאת המערכת נכשלה
    // 2. ה-kernel עדכן את ערך errno
    perror("Error writing to file descriptor"); // הדפסת הודעת שגיאה קריאה
    exit(EXIT_FAILURE);
}
// 3. אם הגענו לכאן, ה-write הצליח (ייתכן שרק חלקית)

שימו לב להערה בשורה האחרונה: גם כשעברנו את הבדיקה וה-write "הצליח", ייתכן שהכתיבה בוצעה רק חלקית.

דוגמה מלאה: זיהוי כישלון ודיווח כללי

הדוגמה המלאה מה-handout מדגימה את השימוש הבסיסי והנפוץ ביותר במנגנון: בדיקת ערך החזרה של -1 ושימוש בפונקציה perror() לדיווח מיידי וידידותי למשתמש. התרחיש: ניסיון פתיחת קובץ שלא קיים, או שאין למשתמש הרשאה לפתוח אותו. 

#include <stdio.h>      // עבור perror
#include <stdlib.h>
#include <unistd.h>     // עבור קריאת המערכת close
#include <fcntl.h>      // עבור קריאת המערכת open ודגלי גישה (O_RDONLY)

// הפונקציה המרכזית
int main() {
    int fd;
    const char *filename = "private_file.txt"; // קובץ שאינו קיים או נעול

    printf("Attempting to open file: %s\n", filename);

    // קריאת המערכת open(2)
    // מחזירה file descriptor (ערך >= 0) במקרה של הצלחה, או -1 במקרה של כישלון
    fd = open(filename, O_RDONLY);

    // בדיקת ערך ההחזרה של קריאת המערכת
    if (fd == -1) {
        // הכישלון אושר. הליבה עדכנה את errno.

        // שימוש ב-perror() לדיווח.
        // פונקציה זו משתמשת בערך הנוכחי של errno ומדפיסה:
        // "Failed to open file: [התיאור המילולי של קוד השגיאה]"
        perror("Failed to open file");

        // יציאה עם קוד כישלון
        return EXIT_FAILURE;
    }

    // קוד זה יתבצע רק במקרה של הצלחה
    printf("File opened successfully with file descriptor: %d\n", fd);
    close(fd);

    return EXIT_SUCCESS;
}

קריאה מודרכת, שלב אחר שלב:

  1. ארבעת ה-includes — stdio.h עבור perror (ו-printf), ‏fcntl.h עבור open ודגלי הגישה (O_RDONLY), ‏unistd.h עבור close, ‏ו-stdlib.h עבור EXIT_FAILURE / EXIT_SUCCESS.
  2. open מחזירה file descriptor (ערך >= 0) בהצלחה או -1 בכישלון — ולכן הבדיקה היא if (fd == -1).
  3. בענף הכישלון: הליבה כבר עדכנה את errno, ולכן perror("Failed to open file") תדפיס ל-stderr את המחרוזת ואחריה את התיאור המילולי של קוד השגיאה — והתוכנית יוצאת עם EXIT_FAILURE.
  4. רק אם הפתיחה הצליחה מגיעים להדפסת ה-fd ולסגירה מסודרת עם close(fd).

מלכודות למבחן:

  • errno תקף רק מייד אחרי הכישלון — כל קריאת ספרייה או קריאת מערכת עוקבת (אפילו מוצלחת) עלולה לדרוס אותו.
  • -1 הוא רק האות לכשל; errno הוא הסיבה. קוד השגיאה לעולם לא מגיע דרך ערך ההחזרה עצמו.
  • errno הוא פר-תהליכון, לא משתנה גלובלי רגיל — מאקרו של POSIX, בגלל Thread Safety.
