0. Process מול Program — ההבחנה

עד עכשיו הסתכלנו על המערכת מנקודת המבט של הקבצים: פתחנו, קראנו, כתבנו וסגרנו. מהשיעור הזה עולים קומה — אל מי שמבצע את כל הפעולות האלה: התהליך (Process).

ההבחנה שפותחת את היחידה פשוטה לנסח וקריטית להבין: תוכנית (Program) היא קובץ — אוסף פסיבי של הוראות ונתונים ששוכב על הדיסק ולא "קורה" בו כלום. תהליך הוא מה שנוצר כשהתוכנית הזו רצה: ישות חיה שהקרנל מנהל, עם מצב שמשתנה מרגע לרגע, משאבים שהוקצו לה, קבצים שהיא מחזיקה פתוחים וזהות משלה.

איך זה נראה בפועל בתוך הקרנל? התשובה של המרצה חד-משמעית: כל מה שהופך תוכנית פסיבית לתהליך חי מרוכז במבנה נתונים אחד — task_struct, שמייצג את "כל המטא-דאטה, ההקשר (Context), המשאבים והסטטוס" של תהליך (או Thread) בודד במערכת. התוכנית היא הקובץ; התהליך הוא הקובץ + ה-task_struct שהקרנל מחזיק עבורו. זה בדיוק מה שנפרק בשיעור הזה.

ועוד עיקרון אחד שכבר פגשנו בשיעור על חשבונות המשתמשים: אין "תהליך חסר זהות" בלינוקס — כל תהליך שרץ במרחב המשתמש חייב להיות משויך לזהות של חשבון משתמש תקף. נראה בהמשך העמוד איפה בדיוק הזהות הזו יושבת.

הרחבה — תוכנית אחת, כמה תהליכים

מכיוון שהתוכנית היא רק קובץ, אפשר להריץ אותה כמה פעמים בו-זמנית — וכל הרצה כזו היא תהליך נפרד: לכל אחד task_struct משלו, מזהה משלו, קבצים פתוחים משלו ומרחב זיכרון משלו. שני חלונות טרמינל שמריצים את אותו bash הם תוכנית אחת — ושני תהליכים שונים לגמרי.

🔒 יושלם בהמשך — לפי הסילבוס, שיעור 7 עוסק גם ביצירת תהליכים בפועל: fork() ו-exec(). השקפים האלה טרם הועלו למודל — הנושאים יתווספו לעמוד הזה כשהחומרים יעלו.

מקור: task_struct.pdf (עמ' 1)

1. task_struct — תעודת הזהות של התהליך בקרנל

מבנה הנתונים task_struct מוגדר בקובץ include/linux/sched.h בליבת לינוקס, והוא אחד ממבני הנתונים הגדולים, המרכזיים והחשובים ביותר בקרנל. בגרסאות מודרניות, כמו Linux Kernel 6.14, הוא מכיל מאות שדות ואלפי שורות קוד — ולכן המרצה מציג ממנו רק את השדות הארכיטקטוניים המרכזיים והקרדינליים ביותר: 

struct task_struct {
    unsigned int __state;              // מצב התהליך הנוכחי (Running, Sleeping וכו')
    pid_t pid;                         // מזהה התהליך (Process ID)
    pid_t tgid;                        // מזהה קבוצת הנימים (Thread Group ID)

    struct task_struct *real_parent;   // מצביע לאב האמיתי של התהליך
    struct task_struct *parent;        // מצביע לאב הנוכחי (למשל אחרי ptrace)
    struct list_head children;         // רשימת הבנים של התהליך
    struct list_head sibling;          // רשימת האחים (תהליכים באותו אב)

    struct mm_struct *mm;              // מצביע למרחב הזיכרון הווירטואלי (Virtual Memory)
    struct mm_struct *active_mm;       // משמש תהליכי קרנל לניהול זיכרון זמני

    struct fs_struct *fs;              // הקשר מערכת קבצים (תיקיית שורש, CWD)
    struct files_struct *files;        // טבלת תיאורי הקבצים הפתוחים (FD Table)

    struct sched_entity se;            // יישות תזמון עבור מתזמן הליבה (EEVDF/CFS)
    void *stack;                       // פוינטר למחסנית הליבה (Kernel Stack)

    struct signal_struct *signal;      // משותף לקבוצת נימים (Signals) ניהול אותות
    struct sighand_struct *sighand;    // מטפלי אותות
};

שימו לב לתבנית: כמעט כל שדה "כבד" הוא מצביע למבנה נתונים אחר (mm_struct, fs_struct, files_struct…) — ה-task_struct הוא הצומת שמחבר את כולם. את התמונה הזו נצייר בסעיף 3.

2. ניתוח שדה-שדה — מה מאוחסן, למה, ומתי

דפוס השאלה של המרצה — לכל שדה הוא שואל עד שלוש שאלות: (א) מה משמעות הערך הנשמר בו? (ב) מדוע שמירתו חשובה/הכרחית עבור הקרנל? (ג) מתי הערך מחושב ונשמר? במסמך המקורי שלוש השאלות נענות במלואן עבור fs ו-files — שווה לדעת לענות עליהן לכל שדה.

1. שדה המצב: __state

מה מאוחסן?

מסיכת ביטים (Bitmask) או מספר שלם המציין את מצבו הריאלי הנוכחי של התהליך במערכת ההפעלה:

ערךמשמעות (מהמסמך)
TASK_RUNNINGהתהליך רץ, או ממתין בתור המעבד.
TASK_INTERRUPTIBLE / TASK_UNINTERRUPTIBLEהתהליך ישן וממתין לאירוע או לדיסק.
TASK_STOPPED / EXIT_ZOMBIEמצבים נוספים שהמסמך מונה — מחזור החיים המלא של תהליך יילמד בשיעור 8 (Tasks Life Cycle).

זוכרים שבדוגמת ה-cp ההערה של המרצה אמרה ש-read() "מרדימה את התהליך" עד שהדיסק מספק את הנתונים? עכשיו יש לזה כתובת: השינה הזו היא בדיוק מצב ההמתנה לדיסק שנרשם ב-__state.

2–3. המזהים: pid ו-tgid

מה מאוחסן?

pid (Process ID) הוא מספר שלם ייחודי המזהה את התהליך או הנימה (Thread) הספציפיים הללו מול הקרנל — למשל PID 4521. tgid (Thread Group ID) הוא המזהה המשותף לכל הנימים (Threads) השייכים לאותה תוכנית אב (Process). ברוב המקרים, ה-tgid של הנימה הראשית שווה ל-PID שלה.

4. עץ המשפחה: real_parent · parent · children · sibling

מה מאוחסן?

מצביעים המקשרים את ה-task_struct הנוכחי אל שאר המשפחה:

  • real_parent — מצביע לאב האמיתי שיצר את התהליך.
  • parent — מצביע לאב הנוכחי — שיכול להיות שונה, למשל אחרי ptrace.
  • children — רשימת (list_head) הבנים שנולדו מהתהליך.
  • sibling — רשימת האחים: תהליכים שחולקים את אותו אב.

5. מרחב הזיכרון: mm ו-active_mm

מה מאוחסן?

mm הוא מצביע ל-struct mm_struct, המכיל את כל הגדרות מרחב הזיכרון הווירטואלי של התהליך: טבלאות הדפים, אזורי ה-Heap וה-Stack, והקטעים הבינאריים. active_mm משמש תהליכי קרנל לניהול זיכרון זמני.

6. הקשר מערכת הקבצים: fs

מה מאוחסן?

מצביע ל-struct fs_struct, השומר את "המידע הגיאוגרפי" של התהליך במערכת הקבצים: תיקיית העבודה הנוכחית (Present Working Directory — CWD) ותיקיית השורש (root) של התהליך.

למה הקרנל צריך את זה?

כאשר תהליך מריץ קריאת מערכת עם נתיב יחסי (Relative Path), הקרנל חייב לדעת היכן התהליך "נמצא" בעץ הספריות כדי להתחיל את אלגוריתם ה-Path Resolution מנקודת המוצא הנכונה — current->fs->pwd.

מתי מתעדכן?

מועתק מהאב בעת יצירת התהליך ב-fork(), ומתעדכן בכל פעם שהתהליך מריץ קריאת מערכת מסוג chdir().

7. טבלת תיאורי הקבצים: files

מה מאוחסן?

מצביע ל-struct files_struct, המנהל את מערך תיאורי הקבצים (FD Table) של התהליך — כלומר, מפת הביטים ומערך המצביעים לכל הקבצים הפתוחים (struct file *).

למה הקרנל צריך את זה?

שדה זה מקשר בין מספרי ה-FD שהתוכנית מכירה במרחב המשתמש (למשל fd = 3) לבין אובייקטי הקובץ הפתוחים בזיכרון הליבה. בלעדיו, הקרנל לא יוכל לבצע פעולות read, write או close — זו בדיוק תחילתה של שרשרת fd → fd_array → struct file שהכרנו במודול 5.

מתי מתעדכן?

מוקצה בעת יצירת התהליך (ומשוכפל או משותף בהתאם לדגלי ה-fork/clone), ומתעדכן בכל פעם שהתהליך פותח קובץ חדש (open) או סוגר קובץ (close).

8. יישות התזמון: se (Scheduling Entity)

מה מאוחסן?

מבנה מסוג struct sched_entity, המרכז את כל נתוני הזמן, העדיפות, והזמן הווירטואלי (Virtual Runtime) שהתהליך צרך במעבד — הנתונים שעליהם מסתמך מתזמן הליבה (EEVDF/CFS).

ומה עוד היה בשקף?

עוד שלושה שדות מופיעים בליסטינג עם הערה קצרה: stack — פוינטר למחסנית הליבה (Kernel Stack) של התהליך; signal — ניהול אותות, משותף לקבוצת הנימים; ו-sighand — מטפלי האותות (signal handlers). את עולם ה-Signals נלמד לעומק בשיעור 12.

4. ומי הבעלים? הזהות של התהליך — UID ו-struct cred

אמרנו בפתיחה שאין תהליך חסר זהות. איפה הזהות הזו נשמרת? מהשיעור על חשבונות המשתמשים אנחנו כבר יודעים את העיקרון: הקרנל של לינוקס אינו מודע כלל למחרוזות כמו alice. עבור מבני הנתונים של הליבה — כגון ה-task_struct — המשתמש מיוצג אך ורק באמצעות מספר שלם: UID (User Identifier). בקוד הליבה הזהות מיוצגת במבני הנתונים struct cred ו-kuid_t.

  • התרגום מהמחרוזת (alice) למספר (1001) מתבצע על ידי ספריות ה-C של מרחב המשתמש (כגון getpwnam), באמצעות קריאת קבצי התצורה של המערכת — טרם העברת הנתונים אל קריאות המערכת של הקרנל.
  • כבר בפתיחת חשבון מוגדרים ה-Credentials: מבני ה-UID, ה-GID ומטריצת ההרשאות שיוצמדו לכל תהליך עתידי שהמשתמש יפתח.
  • ה-UID של root הוא תמיד 0 — זהו הערך המספרי שבעטיו הקרנל מזהה תהליך כבעל הרשאות מלאות, שעוקף את רוב מגבלות האבטחה ומערכת הקבצים.

מקור: accounts.pdf (עמ' 1, 4)

5. מלכודות למבחן

parent אינו בהכרח real_parent. real_parent הוא האב האמיתי שיצר את התהליך; parent הוא האב הנוכחי — והוא יכול להשתנות, למשל אחרי ptrace. שאלה שמציגה אותם כמילים נרדפות — מלכודת.

tgid = pid — רק "ברוב המקרים". הניסוח המדויק של המסמך: ברוב המקרים ה-tgid של הנימה הראשית שווה ל-PID שלה. ה-pid ייחודי לכל נימה; ה-tgid משותף לכל הנימים של אותו תהליך.

לא לבלבל בין fs ל-files. fs הוא "המידע הגיאוגרפי" — תיקיית השורש וה-CWD, לצורך Path Resolution; files הוא טבלת תיאורי הקבצים הפתוחים. שמות דומים, תפקידים שונים לגמרי.

הקרנל לא מכיר את alice. בתוך ה-task_struct אין שם משתמש — יש UID מספרי בלבד. התרגום שם⇐מספר קורה במרחב המשתמש (getpwnam), לפני קריאות המערכת.
