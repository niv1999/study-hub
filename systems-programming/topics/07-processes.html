1. Process מול Program — ההבחנה שפותחת את היחידה

עד כה הסתכלנו על המערכת מנקודת המבט של הקבצים: פתחנו, קראנו, כתבנו וסגרנו. עכשיו עולים קומה — אל מי שמבצע את כל הפעולות האלה: התהליך (Process).

קחו את הדוגמה שתלווה את כל העמוד. בתיקיית העבודה שלכם יושב קובץ הרצה בשם example. כל עוד לא הרצתם אותו הוא סתם קובץ על הדיסק — רצף בייטים של קוד ונתונים שאיש אינו מבצע. ברגע שמקלידים ./example ולוחצים ENTER, הקרנל פותח את הקובץ, מוודא את כותרת ה-ELF שלו, טוען את הקטעים הבינאריים לזיכרון ומכוון את מצביע הפקודות לנקודת הכניסה — ומאותו רגע רץ במרחב המשתמש תהליך.

Program — תוכניתProcess — תהליך
מה זה קובץ הרצה (ELF) שיושב במערכת הקבצים — פסיבי. ההרצה החיה של אותו קובץ: קוד + נתונים + מצב שמשתנה מרגע לרגע.
איפה הוא נמצא על הדיסק, כמו כל קובץ אחר. בזיכרון, תחת ניהול הקרנל.
מי מנהל אותו אף אחד — עד שמריצים אותו לא "קורה" בו כלום. הקרנל, באמצעות רשומה אחת בזיכרון הליבה: task_struct.
איך מזהים אותו לפי שם ונתיב (/home/izhak/…/example). לפי מספר ייחודי — PID.

ומהו תהליך מבחינת הקרנל? התשובה של המרצה חד-משמעית: כל מה שהופך תוכנית פסיבית לתהליך חי מרוכז במבנה נתונים אחד — task_struct, המייצג את "כל המטא-דאטה, ההקשר (Context), המשאבים והסטטוס" של תהליך (או Thread) בודד במערכת. במשוואה אחת: תהליך = הקובץ שנטען לזיכרון + ה-task_struct שהקרנל מחזיק עבורו. פירוק המבנה הזה הוא כל השיעור.

הרחבה — תוכנית אחת, כמה תהליכים

מכיוון שהתוכנית היא רק קובץ, אפשר להריץ אותה כמה פעמים בו-זמנית — וכל הרצה כזו היא תהליך נפרד: לכל אחד task_struct משלו, PID משלו, קבצים פתוחים משלו ומרחב זיכרון משלו. שני חלונות טרמינל שמריצים את אותו bash הם תוכנית אחת — ושני תהליכים שונים לגמרי.

עיקרון נוסף שפגשנו בשיעור על חשבונות המשתמשים: אין "תהליך חסר זהות" בלינוקס — כל תהליך במרחב המשתמש חייב להיות משויך לחשבון משתמש תקף. איפה בדיוק יושבת הזהות הזו — בסעיף 5. ואיך תוכנית פסיבית הופכת לתהליך חי בפועל — בסעיף 6, בצמד fork() ו-execve().

מקור: task_struct.pdf (עמ' 1) · scenario.pdf (עמ' 2)

2. task_struct — תעודת הזהות של התהליך בקרנל

כדי שהקרנל יוכל לנהל תהליך הוא חייב לזכור עליו הכול: באיזה מצב הוא נמצא, מי יצר אותו, איזה זיכרון הוקצה לו, אילו קבצים הוא מחזיק פתוחים וכמה זמן מעבד הוא כבר צרך. כל זה נשמר במבנה אחד, task_struct, המוגדר בקובץ include/linux/sched.h בליבת לינוקס — אחד ממבני הנתונים הגדולים, המרכזיים והחשובים ביותר בקרנל. בגרסאות מודרניות, כמו Linux Kernel 6.14, הוא מכיל מאות שדות ואלפי שורות קוד, ולכן המרצה מציג ממנו רק את השדות הארכיטקטוניים המרכזיים והקרדינליים ביותר.

המשפט שצריך לצאת מהסעיף הזה: מבנה הנתונים שבו הקרנל מייצג יחידת ריצה — ישות שצריך להקצות לה ליבת מעבד — הוא struct task_struct. תהליך ו-Thread כאחד מיוצגים באותו מבנה בדיוק.

מילון זריז לפני שקוראים את הקוד (הרחבה — רקע כללי, לא מהמסמך)

struct
"רשומה" בשפת C: אוסף שדות בעלי שם שנשמרים יחד בזיכרון. הקוד למטה הוא התבנית; הקרנל מחזיק עותק אחד ממנה לכל תהליך שרץ במערכת.
*
מצביע (pointer) — שדה ששומר כתובת של מבנה אחר בזיכרון במקום את המבנה עצמו. struct mm_struct *mm אינו מכיל את הזיכרון של התהליך; הוא מכיל את הכתובת של המבנה שמתאר אותו.
list_head
רשימה מקושרת — התשתית הסטנדרטית של הקרנל לרשימות: כל איבר מחזיק מצביעים לאיבר הבא והקודם, וכך אפשר לעבור על "כל הבנים" בלי לדעת מראש כמה יש.
Bitmask
מסיכת ביטים — מספר שכל ביט בו הוא דגל דלוק/כבוי, כך ששדה קטן אחד מקודד אוסף שלם של מצבים או תכונות.
זיכרון וירטואלי
לכל תהליך יש "מפת כתובות" פרטית משלו; הכתובות שהתוכנית רואה מתורגמות (דרך טבלאות דפים) לכתובות פיזיות ב-RAM — ולכן שני תהליכים לא דורכים זה על הזיכרון של זה.
Scheduler (מתזמן)
הרכיב בקרנל שמחליט מי מבין התהליכים המוכנים לרוץ יקבל עכשיו ליבת מעבד, ולכמה זמן.

מה הקוד הבא עושה: זו ההגדרה של המבנה — רשימת השדות שהקרנל שומר לכל תהליך. השורות מסודרות בקבוצות (זהות, משפחה, זיכרון, קבצים, תזמון, אותות), וההערות בעברית הן של המרצה עצמו: 

struct task_struct {
    unsigned int __state;              // מצב התהליך הנוכחי (Running, Sleeping וכו')
    pid_t pid;                         // מזהה התהליך (Process ID)
    pid_t tgid;                        // מזהה קבוצת הנימים (Thread Group ID)

    struct task_struct *real_parent;   // מצביע לאב האמיתי של התהליך
    struct task_struct *parent;        // מצביע לאב הנוכחי (למשל אחרי ptrace)
    struct list_head children;         // רשימת הבנים של התהליך
    struct list_head sibling;          // רשימת האחים (תהליכים באותו אב)

    struct mm_struct *mm;              // מצביע למרחב הזיכרון הווירטואלי (Virtual Memory)
    struct mm_struct *active_mm;       // משמש תהליכי קרנל לניהול זיכרון זמני

    struct fs_struct *fs;              // הקשר מערכת קבצים (תיקיית שורש, CWD)
    struct files_struct *files;        // טבלת תיאורי הקבצים הפתוחים (FD Table)

    struct sched_entity se;            // יישות תזמון עבור מתזמן הליבה (EEVDF/CFS)
    void *stack;                       // פוינטר למחסנית הליבה (Kernel Stack)

    struct signal_struct *signal;      // משותף לקבוצת נימים (Signals) ניהול אותות
    struct sighand_struct *sighand;    // מטפלי אותות
};

שימו לב לתבנית: כמעט כל שדה "כבד" הוא מצביע למבנה נתונים אחר (mm_struct, fs_struct, files_struct…) — ה-task_struct עצמו הוא הצומת שמחבר את כולם. את התמונה הזו נצייר בסעיף 4.

🎓 מהשיעור בכיתה (מהמחברת)

שאלה שעולה מיד: אם יש task_struct אחד לכל תהליך — איפה הקרנל שומר את כולם? התשובה נכתבה על הלוח: ב-global task list — רשימה מקושרת דו-כיוונית (כל צומת מצביע גם קדימה וגם אחורה), שכל node שלה הוא task_struct אחד: 

global task list:

  [node] <=> [node] <=> [node] <=> ... <=> [node]
     |                       |
     v                       v
 task_struct            task_struct { fs, files, mm, ... }

שימו לב שזו רשימה אחרת מרשימות ה-children/sibling שבליסטינג: אלה מתארות את עץ המשפחה של תהליך מסוים, ואילו ה-global task list היא הרשימה של כל יחידות הריצה במערכת — וממנה גם ניזון המתזמן. המרצה סימן את הנקודה הזו לעצמו כ"לזכור". (בכיתה זה נאמר בעיקר כהכנה ל-Threads: גם כל thread הוא צומת ברשימה הזו.)

מקור: task_struct.pdf (עמ' 1)

3. ניתוח שדה-שדה — מה נשמר, למה, ומתי

דפוס השאלה של המרצה — לכל שדה הוא שואל שלוש שאלות: (א) מה משמעות הערך הנשמר בו? (ב) מדוע שמירתו חשובה/הכרחית עבור הקרנל? (ג) מתי הערך מחושב ונשמר? במסמך המקורי שלוש התשובות מופיעות במלואן רק עבור fs ו-files. בשאר השדות תשובה (א) היא של המרצה, ותשובות (ב) ו-(ג) מסומנות בתגית הרחבה — השלמה שלנו, נכונה ועקבית עם המסמך אך לא מצוטטת ממנו. כדאי לדעת לענות על שלושתן לכל שדה.

1 · __state — מצב התהליך ברגע זה

"באיזה מצב אני נמצא עכשיו: רץ, ישן, עצור?"

א · מה הערך אומר
Bitmask (מסיכת ביטים) או מספר שלם המציין את מצבו הריאלי הנוכחי של התהליך במערכת ההפעלה:
ערךמשמעות (מהמסמך)
TASK_RUNNINGהתהליך רץ, או ממתין בתור המעבד.
TASK_INTERRUPTIBLE / TASK_UNINTERRUPTIBLEהתהליך ישן וממתין לאירוע או לדיסק.
TASK_STOPPED / EXIT_ZOMBIEמצבים נוספים שהמסמך מונה — מחזור החיים המלא של תהליך נלמד בשיעור 8.
ב · למה הקרנל חייב אותו הרחבה
המתזמן חייב לדעת מי מוכן לרוץ: רק תהליך ב-TASK_RUNNING מועמד לקבל ליבת מעבד, ותהליך שממתין לדיסק לא יבזבז זמן מעבד לשווא.
ג · מתי מחושב ומתעדכן הרחבה
בכל שינוי מצב: כשהתהליך נחסם בהמתנה לנתונים, כשהאירוע מגיע והוא חוזר לתור המוכנים, כשהוא נעצר או מסתיים.

זוכרים את ההערה של המרצה בקוד ה-cp — ש-read() מרדימה את התהליך עד שהדיסק מספק את הנתונים? עכשיו יש לזה כתובת מדויקת: השינה הזו היא מצב ההמתנה שנרשם ב-__state.

2–3 · pid ו-tgid — המזהים

"מי אני מול הקרנל, ולאיזו קבוצת נימים אני שייך?"

א · מה הערך אומר
pid (Process ID) — מספר שלם ייחודי המזהה את התהליך או הנימה (Thread) הספציפיים הללו מול הקרנל, למשל PID 4521.
tgid (Thread Group ID) — המזהה המשותף לכל הנימים השייכים לאותה תוכנית אב (Process). ברוב המקרים ה-tgid של הנימה הראשית שווה ל-PID שלה.
ב · למה הקרנל חייב אותו הרחבה
זהו המפתח הייחודי שבו כל המערכת מדברת על התהליך: ב-user space המתכנת מזהה "תהליך" לפי מספר ה-PID ותו לא — הוא מה שמוחזר לאב מ-fork(), ומה שמופיע ב-ps.
ג · מתי מחושב ומתעדכן הרחבה
מוקצה על ידי הקרנל ברגע יצירת התהליך ב-fork(), ואינו משתנה לאורך חיי התהליך — גם execve() לא מחליפה אותו, כי היא מחליפה תוכן ולא יוצרת תהליך חדש (סעיף 6).
הרחבה — איך רואים PID בפועל

ב-Bash, הפקודה ps מציגה את התהליכים של הטרמינל, והמשתנה $$ מכיל את ה-PID של המעטפת עצמה:

$ ps
    PID TTY          TIME CMD
   4521 pts/0    00:00:00 bash
   4877 pts/0    00:00:00 ps

$ echo $$
4521

המספר 4521 הוא בדיוק הערך שיושב בשדה pid שב-task_struct של אותו Bash בזיכרון הליבה.

4 · real_parent · parent · children · sibling — עץ המשפחה

"מי יצר אותי, את מי אני יצרתי, ומי האחים שלי?"

א · מה הערך אומר
מצביעים המקשרים את ה-task_struct הנוכחי אל שאר המשפחה:
  • real_parent — מצביע לאב האמיתי שיצר את התהליך.
  • parent — מצביע לאב הנוכחי, שיכול להיות שונה, למשל אחרי ptrace (מנגנון הניפוי של לינוקס: תהליך אחד "מתחבר" לתהליך אחר כדי לעקוב אחריו — וכך נעשה זמנית האב שלו).
  • children — רשימה מקושרת (list_head) של הבנים שנולדו מהתהליך.
  • sibling — רשימת האחים: תהליכים שחולקים את אותו אב.
ב · למה הקרנל חייב אותו הרחבה
דרך הקשרים האלה הקרנל יודע למי לדווח כשתהליך מסתיים, ומה לעשות עם בנים שנשארו בלי אב — נושא שיעור 8 (Tasks Life Cycle).
ג · מתי מחושב ומתעדכן הרחבה
נבנה ברגע ה-fork(): מצביעי האב של הבן מכוונים אל היוצר, והבן מתווסף לרשימת ה-children של האב.

5 · mm ו-active_mm — מרחב הזיכרון

"איפה הקוד, הנתונים והמחסנית שלי יושבים בזיכרון?"

א · מה הערך אומר
mm הוא מצביע ל-struct mm_struct, המכיל את כל הגדרות מרחב הזיכרון הווירטואלי של התהליך: טבלאות הדפים, אזורי ה-Heap וה-Stack והקטעים הבינאריים. active_mm משמש תהליכי קרנל לניהול זיכרון זמני.
ב · למה הקרנל חייב אותו הרחבה
כל גישה של התהליך לכתובת בזיכרון מתורגמת דרך טבלאות הדפים שב-mm; בלעדיו הקרנל לא יכול להעמיד את התהליך לריצה ולא לבודד אותו משאר התהליכים.
ג · מתי מחושב ומתעדכן
מועתק מהאב ב-fork(), ונמחק ונבנה מחדש לגמרי ב-execve() — בדיוק הצעד שמתואר בתרחיש ה-Bash (סעיף 6).

6 · fs — הקשר מערכת הקבצים

"איפה אני עומד בעץ הספריות?" — שלוש התשובות כאן הן של המרצה, מילה במילה.

א · מה הערך אומר
מצביע ל-struct fs_struct, השומר את "המידע הגיאוגרפי" של התהליך במערכת הקבצים: תיקיית העבודה הנוכחית (Present Working Directory — CWD) ותיקיית השורש (root) של התהליך.
ב · למה הקרנל חייב אותו
כאשר תהליך מריץ קריאת מערכת עם נתיב יחסי (Relative Path), הקרנל חייב לדעת היכן התהליך "נמצא" בעץ הספריות כדי להתחיל את אלגוריתם ה-Path Resolution מנקודת המוצא הנכונה — current->fs->pwd.
ג · מתי מחושב ומתעדכן
מועתק מהאב בעת יצירת התהליך ב-fork(), ומתעדכן בכל פעם שהתהליך מריץ קריאת מערכת מסוג chdir().
🎓 מהשיעור בכיתה (מהמחברת)

המרצה חיבר את השדה הזה לשני דברים שמוכרים מהיום-יום, ושניהם שווים נקודות במבחן:

  • cd אינה תוכנית — היא פקודה פנימית (built-in) של ה-Bash, וכל מה שהיא עושה הוא לעדכן את ה-cwd ב-fs_struct של תהליך ה-Bash עצמו. זו גם הסיבה שאין /bin/cd: אילו היה מדובר בתוכנית חיצונית, היא הייתה רצה בתהליך בן ומשנה את ה-cwd שלו — ולא של המסוף שלכם. (ההסבר המלא על built-in מול חיצוני — מודול 4.)
  • נתיב שמתחיל ב-'/' מבטל את ה-cwd לגמרי. הדוגמה שנכתבה על הלוח: cwd = "/home/Itzhak", אבל אם קוראים ל-open("/etc/passwd", ...) — ה-Path Resolution מתחיל מהשורש ומתעלם מה-cwd. ה-cwd רלוונטי רק לנתיב יחסי.

7 · files — טבלת תיאורי הקבצים

"אילו קבצים אני מחזיק פתוחים?" — גם כאן שלוש התשובות הן של המרצה.

א · מה הערך אומר
מצביע ל-struct files_struct, המנהל את מערך תיאורי הקבצים (FD Table) של התהליך — כלומר מפת הביטים ומערך המצביעים לכל הקבצים הפתוחים (struct file *).
ב · למה הקרנל חייב אותו
השדה מקשר בין מספרי ה-FD שהתוכנית מכירה במרחב המשתמש (למשל fd = 3) לבין אובייקטי הקובץ הפתוחים בזיכרון הליבה. בלעדיו הקרנל לא יוכל לבצע read, write או close — זו בדיוק תחילת השרשרת fd → fd_array → struct file שהכרנו במודול 5.
ג · מתי מחושב ומתעדכן
מוקצה בעת יצירת התהליך (משוכפל או משותף בהתאם לדגלי ה-fork/clone), ומתעדכן בכל פעם שהתהליך פותח קובץ חדש (open) או סוגר קובץ (close).

8 · se — יישות התזמון (Scheduling Entity)

"כמה מעבד כבר קיבלתי, ומתי מגיע לי שוב?"

א · מה הערך אומר
מבנה מסוג struct sched_entity, המרכז את כל נתוני הזמן, העדיפות והזמן הווירטואלי (Virtual Runtime) שהתהליך צרך במעבד — הנתונים שעליהם מסתמך מתזמן הליבה (EEVDF/CFS).
ב · למה הקרנל חייב אותו הרחבה
בלי חשבונאות זמן לכל תהליך אין דרך הוגנת להחליט מי מקבל את הליבה הבאה — זה בדיוק הקלט של המתזמן.
ג · מתי מחושב ומתעדכן הרחבה
מאותחל ביצירת התהליך ומתעדכן על ידי המתזמן בכל פעם שהתהליך רץ ונעצר (החלפת הקשר).

9 · שלושת הנותרים בליסטינג

שדות שהמרצה מציג עם הערה קצרה בלבד — כדאי לזהות אותם בשאלה.

void *stack
פוינטר למחסנית הליבה (Kernel Stack) של התהליך — המחסנית שעליה הוא רץ כשהוא בתוך הקרנל.
struct signal_struct *signal
ניהול אותות (Signals) — משותף לקבוצת הנימים כולה.
struct sighand_struct *sighand
מטפלי האותות (signal handlers). עולם ה-Signals נלמד לעומק בשיעור 12.
🎓 מהשיעור בכיתה (מהמחברת)

את השדה void *stack המרצה הדגיש במרקר וכתב לצדו את המשוואה: Stack = kernel stack + user stack. לכל תהליך יש שתי מחסניות, לא אחת: מחסנית המשתמש — זו שנמצאת ב-memory image ושעליה רצות קריאות הפונקציות של התוכנית שלכם; ומחסנית הליבה — מחסנית נפרדת בזיכרון הקרנל, שאליה התהליך עובר ברגע שהוא נכנס לקריאת מערכת. השדה void *stack מצביע על השנייה. זו הסיבה שהמעבר Ring 3 → Ring 0 הוא בטוח: קוד המשתמש לעולם אינו כותב על המחסנית שהקרנל עובד עליה.

מקור: task_struct.pdf (עמ' 1–3)

4. התמונה המלאה — task_struct כצומת מרכזי

כשמסדרים את המצביעים על ציור אחד רואים למה המרצה קורא ל-task_struct "מרכזי": הוא נקודת הכניסה של הקרנל אל כל מה ששייך לתהליך. איך קוראים את התרשים: כל חץ הוא שדה־מצביע במבנה המרכזי, והשם שליד החץ הוא שם השדה עצמו.

🎓 מהשיעור בכיתה (מהמחברת) התרשים המרכזי של השיעור — מה-task_struct ועד ה-disk inode

את התרשים הזה המרצה צייר על הלוח כשיא השיעור, ואין לו מקבילה בשקפים. הוא לוקח את שני השדות fs ו-files שראינו זה עתה, וממשיך את השרשרת עד הסוף — עד הבייטים על ה-NVM. הוא מחבר בבת אחת את המודול הזה למודול 5:

שתי נקודות שהמרצה הדגיש בתרשים הזה:

  • שלושת המקומות הראשונים בטבלה תפוסים מראש — 0 = stdin, 1 = stdout, 2 = stderr. לכן ה-open() הראשון בתוכנית מחזיר תמיד 3.
  • ה-in-core inodes נשמרים ב-hash table בזיכרון (המרצה קרא לזה in-core inode list). זה מה שמאפשר ל-Path Resolution הבא למצוא את ה-inode בלי לגשת שוב ל-NVM האיטי — אותו רעיון שבשקפים נקרא inode_cache.

5. ומי הבעלים? הזהות של התהליך — UID

אמרנו בפתיחה שאין תהליך חסר זהות. איפה נשמרת הזהות הזו? העיקרון מגיע מהשיעור על חשבונות המשתמשים (מודול 02), והוא נוגע ישירות ל-task_struct:

  • הקרנל אינו מודע כלל למחרוזות כמו alice. עבור מבני הנתונים של הליבה — כגון ה-task_struct — המשתמש מיוצג אך ורק כמספר שלם: UID (User Identifier), במבנים struct cred ו-kuid_t.
  • התרגום alice → 1001 מתבצע במרחב המשתמש, על ידי ספריות ה-C (כגון getpwnam) שקוראות את קבצי התצורה — לפני שהנתונים מועברים לקריאות המערכת.
  • ה-UID של root הוא תמיד 0 — זהו הערך המספרי שבעטיו הקרנל מזהה תהליך כבעל הרשאות מלאות, שעוקף את רוב מגבלות האבטחה ומערכת הקבצים.

6. fork() ו-execve() — כך נולד תהליך

עד כאן פירקנו את ה-task_struct של תהליך קיים. עכשיו נראה איך תהליך נוצר: המשתמש מקליד ./example ולוחץ ENTER, וה-Bash — אחרי שקלט את השורה, פענח אותה וזיהה שמדובר בפקודה חיצונית שמחייבת תהליך חדש — עושה זאת בשני צעדים: fork() ואז execve().

🎓 מהשיעור בכיתה (מהמחברת)

בכיתה המרצה מתח את כל התרחיש על ציר זמן אחד, מהמחרוזת ועד לתהליך הרץ: 

> gcc example.c -o example
> ./example

bash:  parsing  ->  tokens  ->  command name = "./example"
                                      |
                                      | (no PATH search - the path is relative/explicit)
                                      v
                                  fork()      ->  new task = bash's child
                                      |
                                      v
                                  execve("path name")  ->  new memory image

הנקודה שהוא עצר עליה: מכיוון שהפקודה נכתבה כ-./example ולא כשם סתמי, ה-Bash אינו מחפש אותה ב-PATH — הנתיב כבר נתון לו. החיפוש ב-PATH רלוונטי רק לפקודות שנכתבות בשמן בלבד (למשל cp).

שלב א' — fork(): הקרנל משכפל את ה-task_struct

מה קורה בקרנל ברגע שה-Bash קורא ל-fork():

  • הקרנל מייצר עותק מלא (Clone) של מבנה הנתונים task_struct של תהליך ה-Bash הנוכחי.
  • נוצר תהליך חדש (Child Process) המהווה עותק מדויק של ה-Bash, והוא מקבל מזהה תהליך ייחודי משלו (PID).
  • טבלת ה-file descriptors (fd_array) ומצבי הזיכרון משוכפלים.
  • קריאת המערכת fork() מחזירה את הערך 0 לתהליך הבן, ואת מספר ה-PID של הבן אל תהליך האב.

וזה בדיוק מה שנשאל במבחן — מה הבן מקבל ומה לא:

✔ הבן כן מקבל✘ הבן לא מקבל
עותק של מרחב הזיכרון של האב (השדה mm). לא את אותו PID — הקרנל מקצה לו PID חדש וייחודי משלו.
עותק של טבלת ה-File descriptors (fd_array) — אותם קבצים פתוחים. הוא אינו מתחיל מתחילת main: הוא ממשיך מנקודת ה-fork — כלומר מהשורה שאחרי הקריאה.
ערך החזרה 0 מ-fork() — כך הוא יודע שהוא הבן. לא את ה-PID של האב כערך החזרה; ה-PID של הבן מוחזר דווקא לאב.

שימו לב איך הליסטינג מסעיף 2 נעשה פתאום קונקרטי: הבן מקבל pid חדש משלו (ומכיוון שה-tgid של הנימה הראשית שווה ל-pid שלה, גם הוא מתעדכן); מצביעי עץ המשפחה מתעדכנים — real_parent/parent של הבן מצביעים ל-Bash ורשימת ה-children של ה-Bash מקבלת איבר חדש; files → fd_array משוכפל, ולכן הבן רואה את אותם קבצים פתוחים; וגם mm משוכפל.

הרחבה — איך זה נראה בקוד C (השלמה, לא מופיע במסמך)

אותו קוד בדיוק רץ בשני התהליכים; ההבדל היחיד הוא הערך שחזר מ-fork(), ולפיו כל אחד יודע "מי אני":

pid_t pid = fork();

if (pid == 0) {
    /* אני הבן — קיבלתי 0 */
    execve("/home/izhak/system programming/example", argv, envp);
} else if (pid > 0) {
    /* אני האב (Bash) — קיבלתי את ה-PID של הבן */
}

שלב ב' — execve(): מוחקים את הישן, טוענים את החדש

תהליך הבן מזהה שהוא הבן — הערך שהוחזר לו מ-fork הוא 0 — ורק אז הוא קורא לקריאת המערכת: 

execve("/home/izhak/system programming/example", argv, envp)

(הנתיב המלא של קובץ ההפעלה שבנה המשתמש.) מה קורה בקרנל בעקבות ה-execve():

  • הקרנל פותח את קובץ ההפעלה example במערכת הקבצים, קורא את כותרת הקובץ (ELF Header) ומוודא שהיא תקינה.
  • הקרנל מוחק ומאפס לחלוטין את מרחב הזיכרון הישן שהועתק ב-fork (משחרר את הקוד, הנתונים והערימה הישנים).
  • הקרנל מקצה מרחב זיכרון חדש לגמרי, טוען אליו את הקטעים הבינאריים של example, בונה את מחסנית הריצה (Stack) עם הארגומנטים ומשתני הסביבה, ומאפס את מצביע הפקודות (Instruction Pointer — הרגיסטר במעבד שמחזיק את כתובת ההוראה הבאה שתבוצע) לנקודת ההתחלה (main או כניסת ה-ELF).

execve אינה יוצרת תהליך חדש — את זה עשה ה-fork. היא מחליפה את התוכן של התהליך הקיים: ה-task_struct וה-PID נשארים, ומרחב הזיכרון נמחק ונבנה מחדש. מכאן ואילך תהליך ה-Bash המקורי נשאר ברקע במצב המתנה (Sleep / Wait), ותהליך ה-example מתחיל לרוץ במרחב המשתמש.

🎓 מהשיעור בכיתה (מהמחברת)

שני מונחים שהמרצה כתב במפורש בהקשר הזה, ואינם מופיעים בשקפים — deep copy מול lazy copy:

  • fork() אינו מעתיק באמת את כל הזיכרון — זהו lazy copy, כלומר Copy-On-Write (COW): האב והבן מצביעים בהתחלה על אותם דפי זיכרון פיזיים, והעתקה אמיתית של דף מתבצעת רק ברגע שאחד מהם כותב אליו. זה מה שהופך את fork למהיר גם לתהליכים עם זיכרון עצום. מבחינת התוכנית התוצאה זהה לחלוטין ל"עותק מלא" שמתואר למעלה — ההבדל הוא במימוש ובביצועים.
  • execve(), לעומת זאת, בונה memory image חדש לגמרי — כאן אין קיצורי דרך: הישן נמחק והקטעים code/data נטענים מקובץ ההרצה. בכיתה נאמר שאת הטעינה עצמה עושה ה-loader כחלק מה-execve.

ונקודה שקל לפספס והמרצה אמר אותה במפורש: הקבצים הפתוחים שורדים את ה-exec. execve מוחקת את מרחב הזיכרון — אבל files → טבלת ה-fd נשארת כפי שהיא, כולל stdin, stdout ו-stderr. זו בדיוק הסיבה שהתוכנית החדשה יכולה להדפיס למסך בלי לפתוח שום דבר, וזה גם הבסיס להפניית קלט/פלט (redirection) ב-Shell.

שני השלבים האלה הם רק סופו של סיפור בן חמישה שלבים שמתחיל עוד במקלדת — קליטת התווים דרך ה-TTY Driver, ה-Tokenization של שורת הפקודה ובדיקת ה-Built-in. התרחיש המלא — ממקשי המקלדת ועד ההרצה — במודול 04.

לאן ממשיכים מכאן: Tasks Life Cycle — מצבי תהליך, יציאה, זומבים ו-wait ממשיך מהנקודה שבה עצרנו — מה עובר על ה-__state לאורך חיי התהליך ומי אוסף אותו כשהוא מסתיים; Threads — כיצד thread נראה בקרנל (task_struct נוסף עם אותו tgid) מסביר למה בכלל קיים השדה tgid; ושרת מקבילי — fork() בפעולה מראה את אותו fork() עצמו כשהוא מייצר תהליך לכל לקוח שמתחבר.

🎓 מהשיעור בכיתה (מהמחברת) שלושת התרחישים — מפת הדרכים לשאר הקורס

בסוף השיעור המרצה צייר שלושה תרחישים ממוספרים, זה מעל זה, כדי להראות לאן כל מה שלמדנו עד כה מוביל. שווה לשמור את התמונה הזו בראש — היא מסבירה למה בכלל צריך את השיעורים הבאים:

תרחישמה קורה בומה זה מכריח אותנו ללמוד
Ⅰ task אחד מעתיק מ-src ל-dest — בדיוק תוכנית ה-cp שראינו. כלום מעבר למה שכבר יש: קריאות מערכת, fd, inode. זה המצב שסיימנו בו.
Ⅱ כמה tasks / threads ניגשים לאותם src ו-dest — חלקם readers וחלקם writers. מכאן נולדים Threads (איך בכלל מריצים כמה יחידות באותו תהליך) ומיד אחריהם סנכרון — Race Condition ומנעולים (שיעור 11).
Ⅲ client מול Cloud server שמשרת הרבה לקוחות בו-זמנית — multiple tasks, שוב readers ו-writers. זה כבר עולם ה-Sockets (שיעור 13) והשרת המקבילי (שיעור 14) — אותו fork/thread, אבל לכל לקוח שמתחבר.

הרעיון שמאחד את השלושה: ברגע שיותר מיחידת ריצה אחת נוגעת באותו קובץ, "מי כותב מתי" מפסיק להיות מובן מאליו — וזו השאלה שממנה נגזר כל המשך הקורס.

מקור: scenario.pdf (עמ' 1–2); התרחישים Ⅰ/Ⅱ/Ⅲ ומונחי ה-deep/lazy copy — מהמחברת, שיעורי 9.8.2026 ו-13.8.2026

7. שאלות בסגנון הבחינה

שלוש שאלות בניסוח שבו הן מופיעות בבחינה לדוגמה. נסו לענות לפני שפותחים את התשובה.

שאלה 1

באיזה מבנה נתונים משתמש הקרנל כדי לייצג יחידת ריצה — כזו שצריך להקצות לה ליבת מעבד?

  1. struct process_struct
  2. struct task_struct
  3. struct thread_info
  4. struct memory_block

התשובה: 2 — struct task_struct. זהו המבנה שמייצג את כל המטא-דאטה, ההקשר, המשאבים והסטטוס של יחידת ריצה בודדת — תהליך או Thread — והוא מוגדר ב-include/linux/sched.h.

למה השאר לא: process_struct ו-memory_block הם שמות מומצאים שנשמעים סבירים אך אינם קיימים בקרנל; thread_info אינו הייצוג של יחידת הריצה — הייצוג היחיד שהמסמך מכיר, גם לתהליך וגם ל-Thread, הוא task_struct.

שאלה 2

איזה מזהה מייצג "תהליך" עבור המתכנת ב-user space (לא עבור הקרנל!)?

  1. FD id
  2. GID
  3. PID
  4. UID

התשובה: 3 — PID. שימו לב לזוג: בתוך הקרנל התהליך הוא ה-task_struct (שאלה 1); כלפי המתכנת במרחב המשתמש התהליך הוא מספר — ה-PID. זה הערך שמוחזר לאב מ-fork() ושמופיע ב-ps.

למה השאר לא: FD מזהה קובץ פתוח בתוך תהליך, לא את התהליך; UID ו-GID מזהים משתמש וקבוצת משתמשים — הבעלים של התהליך (סעיף 5), לא התהליך עצמו.

שאלה 3

כאשר נקראת fork() — מה נכון לגבי תהליך הבן?

  1. הוא מקבל את אותו PID של האב.
  2. הוא מקבל עותק של מרחב הזיכרון של האב ושל טבלת ה-File descriptors שלו.
  3. הוא מתחיל את הריצה מתחילת main.
  4. הוא מקבל מ-fork() את ה-PID של האב.

התשובה: 2. ב-fork() משוכפלים גם מצבי הזיכרון וגם טבלת ה-file descriptors (fd_array) של האב.

  • 1 שגוי — הבן מקבל PID חדש וייחודי משלו; שני תהליכים לעולם לא חולקים PID.
  • 3 שגוי — הבן אינו מתחיל את התוכנית מהתחלה. הוא עותק של האב ברגע ה-fork, וממשיך מהשורה שאחרי הקריאה. רק execve() תגרום להתחלה מנקודת הכניסה — ואז כבר של תוכנית אחרת.
  • 4 שגוי — ההפך: הבן מקבל 0, והאב הוא שמקבל את ה-PID של הבן.

מקור: task_struct.pdf · scenario.pdf (עמ' 1–2) · ניסוח לפי הבחינה לדוגמה של המרצה

8. מלכודות למבחן

fork יוצר, execve מחליף. אחרי fork() יש שני תהליכים; execve() לא מוסיף שלישי — הוא מוחק את מרחב הזיכרון של הבן וטוען לתוכו תוכנית אחרת. ה-task_struct וה-PID של הבן נשארים אותם.

parent אינו בהכרח real_parent. real_parent הוא האב האמיתי שיצר את התהליך; parent הוא האב הנוכחי, והוא יכול להשתנות — למשל אחרי ptrace. שאלה שמציגה אותם כמילים נרדפות היא מלכודת.

tgid = pid — רק "ברוב המקרים". הניסוח המדויק של המסמך: ברוב המקרים ה-tgid של הנימה הראשית שווה ל-PID שלה. ה-pid ייחודי לכל נימה; ה-tgid משותף לכל הנימים של אותו תהליך.

לא לבלבל בין fs ל-files. fs הוא "המידע הגיאוגרפי" — תיקיית השורש וה-CWD, לצורך Path Resolution; files הוא טבלת תיאורי הקבצים הפתוחים. שמות דומים, תפקידים שונים לגמרי.

הקרנל לא מכיר את alice. בתוך ה-task_struct אין שם משתמש — יש UID מספרי בלבד. התרגום שם ⇐ מספר קורה במרחב המשתמש (getpwnam), לפני קריאות המערכת.

🎓 מהשיעור בכיתה (מהמחברת)

הנקודות שהמרצה הדגיש בקול או סימן על הלוח כ"לזכור" — הוסיפו אותן לרשימה שלמעלה:

  • ה-global task list היא רשימה מקושרת דו-כיוונית שכל צומת בה הוא task_struct — לא לבלבל עם children/sibling שהם עץ המשפחה.
  • Stack = kernel stack + user stack — לכל תהליך שתי מחסניות, והשדה void *stack מצביע על מחסנית הליבה.
  • fork = lazy copy (COW); execve = memory image חדש לגמרי. אם בשאלה כתוב ש-fork "מעתיק את כל הזיכרון פיזית" — זו לא הדרך שבה זה ממומש.
  • הקבצים הפתוחים שורדים את ה-exec, כולל stdin/stdout/stderr. הזיכרון נמחק, טבלת ה-fd לא.
  • cd היא built-in של ה-Bash שמעדכנת את ה-cwd ב-fs_struct; נתיב שמתחיל ב-'/' מתעלם מה-cwd לחלוטין.
  • בטבלת ה-fd המקומות 0, 1, 2 תפוסים מראש — ולכן ה-open הראשון מחזיר 3.
