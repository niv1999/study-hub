⏱ זמן משוער: 50 דק'

מקור: threads (1).pdf מקור: threads.pdf מקור: code.pdf מקור: מחברת 20.8

0. אינטואיציה — תוכנית אחת, כמה "קווי ביצוע"

תוכנית אחת מריצה כמה קווי ביצוע בו-זמנית, בתוך תהליך אחד ועל אותו זיכרון. כל קו ביצוע כזה נקרא Thread (חוט, או "תהליכון").

מילון זריז — ארבעה מושגים שנצטרך כבר בשקף הראשון:

  • PC (Program Counter) — אוגר במעבד שמחזיק את כתובת ההוראה הבאה: "איפה השליטה נמצאת עכשיו".
  • אוגרים (registers) — תאי זיכרון זעירים ומהירים בתוך המעבד. כל חישוב עובר דרכם; הם מחזיקים את "מצב העבודה" הרגעי.
  • Stack Frame (מסגרת מחסנית) — "מגירה" שנפתחת במחסנית בכל קריאה לפונקציה ובה המשתנים המקומיים וכתובת החזרה, ונסגרת בסיומה. המחסנית היא ערימת המגירות האלה.
  • בו-זמנית (concurrently) — שני קטעי קוד מתקדמים באותו פרק זמן, בלי שהאחד חייב להסתיים לפני שהשני מתחיל. עם כמה ליבות (cores) הם ירוצו ממש יחד; עם ליבה אחת מערכת ההפעלה מחליפה ביניהם מהר-מהר. בשני המקרים המתכנת לא יודע מי מתקדם מתי.

הסיפור של המרצה: main, f1, f2, f3

המצגת The thread concept — אותה תוכנית פעמיים, רגילה ועם חוטים:

שקף 3 (חד-חוטי): כש-main קוראת ל-f1() השליטה (ה-PC) עוברת אליה וחוזרת בסיומה; ואז f2, ואז f3:

At each time: the control is either in the main, or f1, or f2, or f3 — Not concurrently !!
בכל רגע נתון השליטה נמצאת או ב-main, או ב-f1, או ב-f2, או ב-f3 — לא במקביל!!

שקף 4 (רב-חוטי): main לא קוראת ל-f1 אלא יוצרת חוט חדש ומשייכת אותו לקוד של f1, וממשיכה מיד. אחרי create_thread הראשון חוט ה-main וחוט ה-f1 יכולים לרוץ בו-זמנית !!; אחרי השני יש 3 חוטים — main, f1, f2 — ושלושתם יכולים לרוץ בו-זמנית. f3() איננה חוט: קריאת פונקציה רגילה, ולכן רצה בתוך חוט ה-main. יצירת חוט היא החלטה מפורשת של המתכנת, פונקציה-פונקציה.

המילה "יכולים" — המרצה הדגיש אותה: 'can' – depends on the availability of a processor (a core) and the scheduling (= allocation of cores) of the OS. יצירת חוטים לא מבטיחה ריצה מקבילה — היא תלויה בזמינות ליבה (core) ובהחלטות המתזמן. אנחנו רק מאפשרים מקביליות; מי שמחליט הוא הקרנל.

🎓 מהשיעור בכיתה (מהמחברת)

המרצה פתח את השיעור מהנקודה הזאת: "ריצה בו זמנית" נכתב על הלוח עם קו תחתון ולידו (concurrency) — זו המטרה של כל הנושא. מיד אחר כך סימן ⊛ ("חשוב") ליד ההבחנה בין תוכנית single threaded לבין תוכנית multi threaded — שתי הקטגוריות שסביבן בנוי כל השיעור.

1. Process מול Thread — מה משותף ומה פרטי

ארבע האמירות של המרצה, מילה במילה — זה הלב של השיעור:

  • כל תהליך יושב במרחב הכתובות שלו, מופרד ומוגן מתהליכים אחרים.
  • חוטים בתוך תהליך חולקים את מרחב הכתובות של התהליך — חולקים את ה-Code, ה-Data וה-Files.
  • קל לתקשר ולשתף פעולה — אבל אין הגנה מחוטים אחרים באותו תהליך.
  • לכל חוט יש סט אוגרים ומחסנית משלו, וכל הנתונים הדרושים כדי להשהות ולהקפיא אותו בזמן שחוט אחר מקבל את תשומת הלב של המעבד (all the necessary data to be able to suspend and freeze it).

למה אוגרים ומחסנית פרטיים לכל חוט? כי הקרנל עלול לעצור חוט בכל רגע ולהריץ אחר, וכדי להחזיר אותו בדיוק לנקודת העצירה צריך את ה-PC, האוגרים והמחסנית שלו — ה"הקשר" (Context) של החוט.

בתהליך הרב-חוטי code | data | files פרושים על כל הרוחב כי הם משותפים; registers ו-stack מופיעים שלוש פעמים, אחת לכל חוט (הסימן המתולתל = החוט עצמו).

אותו תרשים, בהגדלה: מה יושב איפה במרחב הכתובות

  • פר-חוט: Thread 1/2 stack — ובה ה-Stack Frame של routine1()/routine2() ומשתניהן (var1, var2, var3); ולצידה קופסת Stack Pointer / Prgrm. Counter / Registers. ה-PC מצביע לקוד שהחוט מריץ וה-SP למחסנית שלו — שני חוטים, אותו קוד, מצבים שונים. שתי המחסניות באותו מרחב כתובות: פרטיות לוגית, לא הגנה.
  • לכל התהליך: User Address Space אחד; text (הקוד), data (arrayA, arrayB) ו-heap (malloc) משותפים — מצביע ש-malloc החזיר לחוט אחד תקף גם באחר, וה-data הוא המקום שבו נולדות ההתנגשויות.
  • גם משותפים: Process ID / User ID / Group ID — לכל החוטים אותו PID ואותו UID; ו-Files / Locks / Sockets — File Descriptor שחוט אחד פתח, כל חוט אחר קורא וכותב דרכו.

"קל לתקשר — אבל אין הגנה". מרחב הכתובות של כל תהליך מופרד ומוגן, וכדי להעביר נתון בין תהליכים צריך מנגנון IPC (מודול 10). שני חוטים באותו תהליך פשוט רואים את אותו משתנה — בלי העתקה ובלי תיווך. זה הכוח (תקשורת בחינם) וזו הסכנה (Race Condition, מודול 11).

ארבעת השילובים האפשריים

מלבן אפור = תהליך, סימן מתולתל = חוט. תהליך אחד / חוט אחד; תהליך אחד / חוטים מרובים (הנושא כאן); תהליכים מרובים / חוט אחד (bash שיוצר תהליך-בן לכל פקודה — מודול 07); ותהליכים מרובים / חוטים מרובים. שני צירים בלתי-תלויים, לא "או-או".

שאלה מהבחינה לדוגמה — והתשובה של המרצה

שאלה מס' 2 בחלק א' של הבחינה לדוגמה (10 נק'):

מהו ההבדל הבסיסי ביותר בין Process לבין Thread מבחינת מרחב הכתובות?

תשובת המרצה (מילה במילה מדף הפתרון):
"תהליך (Process) מחזיק במרחב כתובות וירטואלי פרטי ומבודד. לעומתו Thread חולק את מרחב הכתובות של התהליך עם Threads אחרים באותו תהליך."

מה בודקים כאן: מילות המפתח פרטי ומבודד (לתהליך) מול חולק (לחוט). שתי שורות מספיקות; אם נשאר מקום, הוסיפו את המשלים — אבל לכל חוט מחסנית ואוגרים משלו.

2. המודל בקרנל — PCB, TCB, ו-task_struct אחד לכל חוט

מה מערכת ההפעלה מחזיקה כדי לנהל חוט?

מבנהבמודל החד-חוטיבמודל הרב-חוטי
Process Control Block (PCB) אחד אחד לכל התהליך — לא נכפל
User Address Space אחד אחד לכל התהליך — זה בדיוק ה"שיתוף"
Thread Control Block (TCB) לא קיים בנפרד אחד לכל חוט
User Stack אחד אחד לכל חוט
Kernel Stack אחד אחד לכל חוט — נקודה שקל לפספס!

למה גם Kernel Stack פר-חוט? כי כל חוט מבצע קריאות מערכת בעצמו ורץ אז ב-Kernel Mode — בלי מחסנית משלו שם, שני חוטים שנמצאים יחד בקרנל היו דורסים זה את המחסנית של זה.

ולינוקס? "תהליכים קלי משקל"

לינוקס רואה חוטים כ"תהליכים קלי משקל" (Lightweight Processes) — חולקים את אותו מרחב זיכרון אך פועלים כיישויות ביצוע נפרדות. אין מבנה נתונים נפרד לחוט: הקרנל מנהל task_struct אחד לכל "יחידת ביצוע" (מודול 07), ומה שמאחד אותם לתהליך הוא שדה אחד:

  • pid — מזהה ייחודי של יחידת הביצוע מול הקרנל; לכל חוט pid משלו, וזה ה-TID (Thread ID).
  • tgid (Thread Group ID) — המזהה המשותף לכל חוטי התוכנית, שווה ל-PID של החוט הראשי. ולכן ה-PID שאנחנו מכירים הוא למעשה ה-tgid (המספר שרואים ב-ps): אותו תהליך ⇐ אותו tgid, TID שונה.

שאלה 9 בבחינה לדוגמה: "באיזה מבנה נתונים משתמש ה-Kernel לייצג יחידת ביצוע [= כזו שצריך להקצות עבורה ליבה (core)]?" — התשובה: struct task_struct. שימו לב לניסוח "יחידת ביצוע": המרצה בחר אותו בכוונה, כי הוא נכון גם לתהליך וגם לחוט.

pthread_t — המזהה שקיים רק אצלנו

פרט ש"קריטי למתכנתי מערכות": בקוד מזהים חוט במשתנה מטיפוס pthread_t.

  • בלינוקס בדרך כלל unsigned long.
  • אינו מספר אקראי: ברוב המימושים (glibc) הערך הוא כתובת בזיכרון של ה-Thread Control Block, בתוך מרחב הכתובות של המשתמש.
  • Opaque Type (טיפוס אטום): ניגשים אליו רק דרך פונקציות הספרייה. מחזיק מידע על ה-Stack של החוט, מצב הריצה שלו וערכי החזרה.
  • הקרנל לא משתמש בו בכלל — הוא מנהל חוטים לפי TID. ה-pthread_t קיים רק ב-User Space, כדי שספריית ה-pthreads תנהל חוטים בלי להעיק על הקרנל.

אל תשוו pthread_t ל-TID. pthread_t = כתובת של מבנה בספרייה (user space); TID = מזהה שהקרנל הקצה. בתוכנית הראשונה בהמשך המרצה מדפיס את pthread_self() תחת התווית "My TID" — הפשטה דידקטית; טכנית זה pthread_t, וה-TID האמיתי מושג עם gettid().

🎓 מהשיעור בכיתה (מהמחברת)

⊛ מודל שלוש השכבות שהמרצה כתב על הלוח (וחזר אליו פעמיים) — "איפה כל פונקציה יושבת":

האפליקציההקוד שלנו — main, foo…
▼ קוראת לפונקציית ספרייה
glibc (NPTL)ספריית ה-threads — pthread_create, pthread_join, pthread_exit. רצה ב-user mode
▼ ובסופה קריאת מערכת
kernelclone() ⇐ יצירת task_struct חדש

⊛ שכבת האמצע: glibc היא ספרייה משותפת — ה-memory image שלה קיים פעם אחת בלבד ב-MM לכל התהליכים; עותק לכל תהליך היה דורש זיכרון רב. NPTL — המרצה פענח "native posix thread interface", בהקשר של קרנל 6.14. (המקובל: Native POSIX Thread Library; במחברת נכתב "interface".)

⊛ שרשרת המימוש (נכתבה ב-20.8 וב-27.8 — חזרה שהיא סימן לשאלת מבחן):

pthread_create()our code calls it
→
NPTL (glibc)user mode
→
struct pthreadthe TCB
→
clone()system call
→
task_structin the kernel

⊛ והמשפט שסוגר אותה (23.8): "NPTL מכירה את המבנה של הקרנל — אבל הקרנל לא מכיר את NPTL." היא הגשר בין המבנה שבו אנחנו מתארים חוט לזה שבו הקרנל מנהל אותו: ה-struct pthread (ה-TCB) מוקצה על ה-heap של NPTL ולכן בלתי-נראה לקרנל, והקרנל מכיר רק את ה-task_struct שנוצר ב-clone() (ומגרסה 6.14 — clone3()). בתוכנית הדוגמה ספר שלושה חוטים — main + t₁ + t₂ — ולכל אחד struct pthread ומחסנית משלו.

⊛ והתרשים שצייר בשלושה צבעים: שלושה task_struct נפרדים (main שחור, thread 1 כחול, thread 2 ירוק), כל אחד עם שדה mm שמצביע לאותו mem img (code, data, bss, heap), ולכל אחד קופסת Stack נפרדת.

🎓 מהשיעור בכיתה (מהמחברת)

לינוקס מול Windows — הפשטה מול מימוש (שיעור 26.7): ב-Windows שני מבנים נפרדים — E-Process לתהליך ו-E-Thread לחוט. בלינוקס אין הפרדה כזו: גם תהליך וגם חוט הם task, ושניהם מיוצגים ב-task_struct. שאלת השוואה קלאסית. המקבילה של pthread_create ב-Windows היא CreateProcess/create_process — מול POSIX אצלנו.

⊛ "תהליך יקר, חוט זול" — באותו שיעור העמיד זה מול זה simple_bash.c שקורא ל-fork(), מול concurrent_server.c שקורא ל-accept() ואז ל-pthread_create(), והדגיש ש-process יקר לעומת חוט. ב-20.8 נימק למה: ב-fork צריך לבנות mem img חדש, וב-pthread_create לא — אותו memory image, ורק ה-Stack נפרד. מכאן המסקנה שבה סגר את השיעור: ה-Context Switch בין חוטים מהיר הרבה יותר מאשר בין תהליכים — מרחב הכתובות לא מתחלף. ⊛ ב-23.8 ירד לרזולוציית החומרה: במעבר בין חוטים ה-mem img נשאר, ומה שמתחלף הוא ה-Stack — משחזרים את כתובת ה-Stack של החוט לאוגר SP (Stack Pointer) ומעדכנים את ה-MMU במיקום ובגודל של ה-mem img. תפקיד ה-MMU: לתרגם כתובות וירטואליות לפיזיות.

🎓 מהשיעור בכיתה (מהמחברת)

⊛ שיעור 23.8 — אינטגרציה: המרצה מתח על הלוח מסלול אחד רצוף, מהקלדת פקודה ב-bash ועד שחוט שני רץ. שאלת סדר-פעולות קלאסית:

  1. bash קולט את המחרוזת, מבצע parsing, מזהה שזו איננה פקודה פנימית — וקורא ל-fork().
  2. fork() היא פונקציית מעטפת ב-glibc ב-user mode, שמעבירה את מספר קריאת המערכת (system call number) לאוגר של ה-CPU (מודול 04).
  3. פקודת syscall ⇐ פסיקה: החומרה מעבירה user → kernel וטוענת ל-PC את כתובת ה-ISR.
  4. ה-ISR בודק את האוגר שבו נשמר ה-sys_call_value ומנתב ל-do_fork().
  5. do_fork() קוראת ל-kernel_clone(), וזו יוצרת task_struct חדש לבן.
  6. חזרה ל-user mode, וה-PC חוזר לכתובת ב-user space מיד אחרי ה-fork(): באב ערך ההחזרה שונה מ-0 ⇐ wait(), ובבן הוא 0 ⇐ execve() (מודול 07).
  7. execve() ⇐ ה-loader מוחק את ה-mem img הקיים ובונה חדש לפי ההנחיות שבקובץ ה-ELF.
  8. main() רצה ומגיעה ל-pthread_create().
  9. NPTL מקצה struct pthread על ה-heap שלה, ומחסנית לחוט החדש.
  10. ובסופה clone() ⇐ kernel_clone() ⇐ task_struct שני, של החוט.

שני קצות המסלול זהים מנקודת מבט הקרנל: גם fork() וגם pthread_create() מסתיימים ב-kernel_clone() שיוצרת task_struct. ההבדל הוא סביב: ב-fork נבנה mem img חדש, וב-pthread_create — לא.

3. Pthreads — ה-API שאיתו עובדים

Pthreads (POSIX Threads) — התקן שמגדיר איך תוכנית C יוצרת ומנהלת חוטים; בלינוקס ממומש ב-glibc (NPTL), עם #include <pthread.h>. ארבע הפונקציות שנצטרך:

פונקציהמה היא עושה
pthread_createיוצרת חוט חדש ומשייכת אותו לפונקציה. החוט מתחיל לרוץ מיד.
pthread_selfמחזירה את המזהה (pthread_t) של החוט הקורא — "מי אני".
pthread_joinחוסמת את החוט הקורא עד שחוט אחר מסיים. "חכה לו".
pthread_exitמסיימת את החוט הנוכחי בלבד — שאר החוטים ממשיכים.

pthread_create() — ארבעת הארגומנטים

החתימה המלאה (man page):

int pthread_create(pthread_t *thread,
                   const pthread_attr_t *attr,
                   void *(*start_routine)(void *),
                   void *arg);

ובקוד של המרצה:

pthread_t my_thread;

if (pthread_create(&my_thread, NULL, foo, NULL)) {
    return 1;
}
#בקודמה זה
1 &my_thread פרמטר פלט. מצביע למשתנה שבו הספרייה תכתוב את מזהה החוט החדש; לכן מעבירים כתובת (&) ולא ערך.
2 NULL (attr) מאפייני החוט — למשל גודל המחסנית. NULL = ברירת מחדל, שהיא לרוב 8MB מחסנית.
3 foo (start_routine) מצביע לפונקציה — ה-"main" של החוט החדש, שם הוא מתחיל את חייו. החתימה חייבת להיות void *f(void *).
4 NULL (arg) הנתון שיועבר לפונקציה. הטיפוס void* ⇐ מצביע לכל דבר. NULL = לא מעבירים כלום.

הרשימה כפי שהמרצה כתב אותה בדף העזר — מילה במילה:

  1. &my_thread: מצביע למשתנה שבו הספרייה תכתוב את המזהה של החוט החדש שנוצר.
  2. attr (NULL): מאפשר להגדיר מאפיינים מיוחדים (כמו גודל מחסנית).
  3. NULL אומר ל-Linux להשתמש בברירת המחדל (לרוב 8MB).
  4. start_routine (foo): מצביע לפונקציה. זהו ה-"Main" של החוט החדש. שם הוא מתחיל את חייו.
  5. arg (NULL): כאן ניתן להעביר נתונים לתוך החוט. מאחר והטיפוס הוא void*, ניתן להעביר מצביע לכל דבר.

[כך במקור] — המרצה מדבר על ארבעה ארגומנטים אך מונה חמישה פריטים. פריט 3 אינו ארגומנט נפרד אלא המשך ההסבר על attr (פריט 2). הארגומנטים בפועל ארבעה, כמו בטבלה שלמעלה.

⊛ מוסכמת ערך ההחזרה — ההבדל מקריאות מערכת

בניגוד לקריאות מערכת רגילות ב-C, שמחזירות -1 ומעדכנות את errno — פונקציות pthread מחזירות את קוד השגיאה עצמו (מספר חיובי) אם הן נכשלות, ו-0 אם הן מצליחות.

לכן הבדיקה בקוד היא if (pthread_create(...)) — "שונה מאפס ⇐ שגיאה" (בסעיף 5 מפורשות != 0). וגם: אין טעם ב-perror אחרי פונקציית pthread שנכשלה — errno לא עודכן (המרצה כן משתמש בו שם, כדפוס אחיד).

🎓 מהשיעור בכיתה (מהמחברת)

המרצה סימן את הנקודה הזאת ב-⊛ וכתב אותה בשתי שורות מודגשות ליד הצילום של הקוד: "+ בהצלחה: מחזירה 0", "– בכישלון: מחזירה err code" — ומולן: "קריאות מערכת מחזירות -1 ומעדכנות את errno". זו שאלת מבחן קלאסית; אל תבלבלו.

⊛ pthread_create היא לא קריאת מערכת

המרצה הדגיש במרקר ירוק: pthread_create היא פונקציית מעטפת (Wrapper) לקריאת המערכת המורכבת clone() — רצה ב-user mode בתוך glibc, מכינה את ה-TCB (struct pthread) ואת מחסנית החוט, ורק בסופה מבצעת clone(). למה צריך task_struct לחוט? "כי צריך לנהל אותו!" — הוא יחידת ביצוע שהמתזמן מריץ, ולכן עובר בין ready ל-running כמו תהליך (מודול 08). הוא מקבל pid משלו (ה-TID) אבל אותו tgid — ולכן ה-PID שווה.

🎓 מהשיעור בכיתה (מהמחברת)

המסלול המלא מקובץ מקור עד ה-main thread, כפי שהמרצה שרטט בכיתה:
thread_example.c ⇐ קובץ הרצה בפורמט ELF ⇐ bash > ./thread_example ⇐ ה-bash task קוראת ל-fork() (נוצר ה-task_struct של ה-main thread) ⇐ execve() (נבנה ה-memory image: code, data, bss, heap, stack) ⇐ ready-queue ⇐ ה-scheduler בוחר ⇐ Context Switch ⇐ ורק אז main() רצה ומגיעה ל-pthread_create. ⊛ ה-pid וה-tgid של ה-main thread זהים.

שלוש הפונקציות האחרות

pthread_t pthread_self(void);
int  pthread_join(pthread_t thread, void **retval);
void pthread_exit(void *retval);
  • pthread_self() — מחזירה את ה-pthread_t של החוט הקורא. בלי ארגומנטים ובלי כישלון.
  • pthread_join(tid, NULL) — חוסמת את החוט הקורא עד שהחוט שמזהו הועבר מסיים; הארגומנט השני אוסף את ערך ההחזרה שלו (NULL = "לא מעניין אותי"). ההקבלה של waitpid().
  • pthread_exit(NULL) — מסיימת את החוט הנוכחי בלבד, בניגוד ל-exit() שמסיימת את כל התהליך. גם return רגיל מפונקציית החוט מסיים אותו — "Returning from this function terminates the thread".
🎓 מהשיעור בכיתה (מהמחברת)

⊛ "איך מסיימים thread? לא ב-exit" — כך נרשם על הדף, בסימון "חשוב": exit() מסיים את כל התהליך על כל חוטיו, לא את החוט שקרא לו. מי שמסיים חוט אחד הוא pthread_exit.

pthread_exit הוא גם מה שמאפשר ל-NPTL לשחרר את מבני החוט — ה-struct pthread, המחסנית וה-task struct שבקרנל. ולצידו רשם המרצה, עם ⊛: pthread_join הוא ה-wait/waitpid של עולם החוטים — "מחכה ל-child שה-pid שלו מסוים".

הרחבה — לא מהשקפים

איך מקמפלים. תוכנית שמשתמשת ב-pthreads נבנית עם הדגל -pthread: gcc thread_example.c -o thread_example -pthread. בלעדיו הקישור (linking) ייכשל עם undefined reference to `pthread_create'. -pthread (ולא -lpthread) הוא הצורה המומלצת, כי הוא מגדיר גם את ההגדרות הנכונות בזמן הקומפילציה.

התוכנית הראשונה — PID זהה, TID שונה

התוכנית שפותחת את דף העזר Linux Threads: שני חוטים באותו תהליך מדפיסים אותו PID אבל TID שונה. 

#include <pthread.h> // POSIX threads library
#include <stdio.h>
#include <unistd.h>  // For sleep() and getpid() functions

/* Global variable to store the thread ID.
   Shared across all threads in this process. */
pthread_t my_thread;



/* Helper function to display the IDs of the calling thread */
void print_my_ids(void)
{
    pid_t pid;      // Process ID (Common to all threads in the process)
    pthread_t tid;  // Thread ID (Unique identifier within the pthread library)

    pid = getpid();       // System call to get the Process ID from the Kernel
    tid = pthread_self(); // Library function to get the current thread's ID

    printf("My PID = %u, My TID = %u\n", (unsigned int)pid, (unsigned int)tid);
}



/* Entry point function for the newly created thread */
void* foo(void* arg)
{
    /* Print the ID stored in the global variable upon creation */
    printf("Thread:%u\n", (unsigned int)my_thread);

    /* Call helper to show this is a separate thread in the same process */
    print_my_ids();

    return NULL; // Returning from this function terminates the thread
}

foo היא ה"פונקציה הראשית" של החוט, ולכן חתימתה void* foo(void* arg). וה-main: 

int main(int argc, const char* argv[])
{
    /* pthread_create: Spawns a new thread executing the 'foo' function.
       Returns 0 on success, or an error code otherwise. */
    if (pthread_create(&my_thread, NULL, foo, NULL)) {
        return 1;
    }

    /* Execution inside the Main Thread */
    printf("Main Thread:");
    print_my_ids();

    /* * Pause for 2 seconds. This is crucial to prevent the Main Thread
     * from finishing main(). If main() exits, the Kernel terminates
     * the entire process and all its threads.
     */
    sleep(2);

    return 0;
}

מה יודפס — ואיך לקרוא את הפלט

שלוש שורות; המספרים משתנים בכל הרצה:

$ ./thread_example
Main Thread:My PID = 4711, My TID = 1180476672
Thread:1172083968
My PID = 4711, My TID = 1172083968
  • ה-PID זהה (4711) — אותו תהליך, אותם משאבי מערכת. getpid() היא קריאת מערכת שמחזירה את המזהה מהקרנל.
  • ה-TID שונה — לכל חוט מזהה משלו.
  • Thread:1172083968 ו-My TID = 1172083968 הם אותו מספר: מה שהספרייה כתבה לגלובלי my_thread, ומה ש-pthread_self() החזירה בתוך החוט.

הסדר בין השורות אינו מובטח! ייתכן שהחוט החדש יספיק להדפיס לפני ה-main. גם printf("Main Thread:") נכתב בלי \n ולכן "נדבק" לשורת ה-PID שאחריו — ומכאן ערבוב אפשרי. סדר הריצה של חוטים אינו בשליטת המתכנת.

⊛ ולמה sleep(2) הכרחית

ב-Linux, אם ה-Main Thread מסיים את פונקציית ה-main, הוא "גורר איתו" את כל התהליך לסגירה — כל החוטים מתים איתו. ה-sleep מבטיח שהחוט החדש יספיק לרוץ ולהדפיס לפני שהתהליך כולו מת.

יציאה מ-main שקולה ל-exit() (מודול 08). הפתרון הנכון אינו sleep אלא pthread_join(my_thread, NULL) — המתנה בפועל במקום ניחוש, כמו בסעיף 5.

🎓 מהשיעור בכיתה (מהמחברת)

ליד שורת ה-sleep(2) בצילום של הקוד רשום בכתב יד: "2 שניות זה הרבה!" — כלומר המרצה עצמו הבהיר שזה טריק דידקטי, לא תכנון נכון. הוא גם ציין שבתוכנית הזאת יש שני חוטים: main ו-t1.

4. מפת הזיכרון — איפה יושב כל משתנה, ומי רואה אותו

מרחב הכתובות של תוכנית C מחולק למקטעים (segments), ולכל סוג משתנה מקטע קבוע. המקטע קובע אם המשתנה משותף או פרטי:

מקטעמה נמצא בומשותף לכל החוטים?
text (code) הוראות המכונה של התוכנית — כל הפונקציות ✔ משותף
.data משתנים גלובליים מאותחלים — למשל int g_initialized_status = 1; ✔ משותף
.bss משתנים גלובליים לא מאותחלים — למשל pthread_mutex_t g_sync_mutex;. מאותחל אוטומטית לאפס / false ✔ משותף
Heap הקצאות דינמיות — כל malloc ✔ משותף (הזיכרון עצמו נגיש לכולם)
Stack המשתנים המקומיים של כל פונקציה — ה-Stack Frame ✘ מחסנית נפרדת לכל חוט

ההערות בקוד ה-Reader/Writer (סעיף 5) ממפות כל משתנה למקטע שלו (/* .data segment */, /* .bss */, /* Stack Frame */, /* Heap */) — מפת ה"משותף מול נפרד":

משתניםמקטע (לפי הערות הקוד)משותף בין החוטים?
g_initialized_status, g_file_path, g_total_bytes_processed .data — גלובלים מאותחלים כן — עותק אחד לכל התהליך
g_sync_mutex, g_data_cond, g_shared_transfer_char .bss — גלובלים לא מאותחלים כן — זה כל הרעיון: התא המשותף גר כאן
g_has_data, g_stream_finished .bss — ההערה מציינת: מאותחל ל-false כברירת מחדל כן — דגלי הסנכרון ששני הצדדים קוראים
local_fd, local_bytes_read, read_buf (המצביע) Stack Frame של ה-Reader לא — לכל חוט מחסנית משלו
local_processed_count, local_bytes_written, write_buf (המצביע) Stack Frame של ה-Writer לא — נגישים רק לקוד של ה-Writer
main_fd, reader_tid, writer_tid, payload, payload_len Stack Frame של main לא — החוט הראשי הוא קו ביצוע בפני עצמו
ההקצאות של malloc(sizeof(char)) (הזיכרון שאליו מצביעים read_buf/write_buf) Heap ה-Heap שייך למרחב המשותף — אבל כל באפר הוקצה על-ידי חוט אחד ורק הוא נוגע בו

קונבנציית השמות של המרצה מאפשרת לקרוא את המפה ישר מהשמות: גלובלי מתחיל ב-g_, מקומי ב-local_.

🎓 מהשיעור בכיתה (מהמחברת)

למה לכל חוט מחסנית משלו: "כדי שלא תהיה התנגשות". הדוגמה שנתן — משתנה המונה i של לולאת for: במחסנית משותפת, שני חוטים שמריצים את אותה פונקציה היו דורסים זה לזה את ה-i. מחסנית פר-חוט פותרת זאת מראש — לכל חוט Stack Frame משלו לאותה פונקציה. ומה שנשאר משותף — data, bss ו-heap — הוא המקום שבו כן צריך מנגנון סנכרון.

⊛ ובשיעור 23.8: החוט החדש והחוט הראשי חולקים Code, data, bss ו-heap — אבל לכל אחד Stack משלו, ואותה מחסנית NPTL מקצה מתוך ה-heap. ברירת המחדל — 8MB, וגודל אחר נקבע דרך הארגומנט השני של pthread_create (ה-attr); ה-NULL שם אומר ל-NPTL "השתמשי בברירת המחדל". בשמות שנתן לשני האחרונים: param 3 = entry pt — כתובת תחילת הפונקציה (foo), ו-param 4 = הארגומנט שמועבר לה (אצלנו NULL, כי foo אינה מקבלת ארגומנטים).

5. הדוגמה המלאה — Reader/Writer בתוכנית אחת

התוכנית המלאה שהמרצה חילק (code.pdf): main יוצר קובץ shared_file עם open/write/close וכותב לתוכו 52 אותיות (a–z ואז A–Z), ואז יוצר שני חוטים: Reader שקורא בייט אחר בייט, ו-Writer שמדפיס כל בייט למסך. הבייטים עוברים דרך תא זיכרון גלובלי אחד — משתנה char יחיד, g_shared_transfer_char.

בתוכנית יש שלושה חוטים, לא שניים: main, Reader ו-Writer — ה-main רק ממתין ב-pthread_join, אבל הוא קו ביצוע מלא עם מחסנית משלו.

הקוד המלא — מילה במילה

כמו תמיד אצל המרצה, כל קריאת מערכת וכל קריאת pthread נבדקת מיד עם חזרתה. 

#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <pthread.h>
#include <string.h>
#include <stdbool.h>

/* Global Initialized Variables (.data segment) */
int g_initialized_status = 1;
const char *g_file_path = "shared_file";
size_t g_total_bytes_processed = 0;

/* Global Uninitialized Variables (.bss segment) */
pthread_mutex_t g_sync_mutex;
pthread_cond_t g_data_cond;
char g_shared_transfer_char;

/* Synchronization Control Flags (.bss segment - initialized to false by default) */
bool g_has_data = false;
bool g_stream_finished = false;

/* Reader Thread Routine */
void *reader_thread_func(void *arg) {
    /* Reader Thread Local Variables (Stack Frame) */
    int local_fd = -1;
    ssize_t local_bytes_read = 0;
    char *read_buf = NULL;

    /* Allocate 1-byte dynamic buffer on the Heap */
    read_buf = (char *)malloc(sizeof(char));
    if (read_buf == NULL) {
        perror("Reader: Failed to allocate read_buf");
        pthread_exit(NULL);
    }

    /* Open shared_file for reading using Linux System Call open() */
    local_fd = open(g_file_path, O_RDONLY);
    if (local_fd == -1) {
        perror("Reader: Failed to open file");
        free(read_buf);
        pthread_exit(NULL);
    }

    /* Processing Loop: Read byte-by-byte via system call read() */
    while ((local_bytes_read = read(local_fd, read_buf, 1)) > 0) {
        pthread_mutex_lock(&g_sync_mutex);

        /* Wait until the Writer thread consumes the previous byte */
        while (g_has_data) {
            pthread_cond_wait(&g_data_cond, &g_sync_mutex);
        }

        /* Transfer byte to shared global transfer storage */
        g_shared_transfer_char = *read_buf;
        g_has_data = true;

        /* Signal the Writer thread that a new byte is available */
        pthread_cond_signal(&g_data_cond);
        pthread_mutex_unlock(&g_sync_mutex);
    }

    if (local_bytes_read == -1) {
        perror("Reader: Error occurred during read()");
    }

    /* Signal stream completion to Writer thread */
    pthread_mutex_lock(&g_sync_mutex);
    while (g_has_data) {
        pthread_cond_wait(&g_data_cond, &g_sync_mutex);
    }
    g_stream_finished = true;
    pthread_cond_signal(&g_data_cond);
    pthread_mutex_unlock(&g_sync_mutex);

    /* Cleanup resources */
    close(local_fd);
    free(read_buf);
    pthread_exit(NULL);
}

/* Writer Thread Routine */
void *writer_thread_func(void *arg) {
    /* Writer Thread Local Variables (Stack Frame) */
    int local_processed_count = 0;
    ssize_t local_bytes_written = 0;
    char *write_buf = NULL;

    /* Allocate 1-byte dynamic buffer on the Heap */
    write_buf = (char *)malloc(sizeof(char));
    if (write_buf == NULL) {
        perror("Writer: Failed to allocate write_buf");
        pthread_exit(NULL);
    }

    while (1) {
        pthread_mutex_lock(&g_sync_mutex);

        /* Wait until Reader supplies new data or signals EOF */
        while (!g_has_data && !g_stream_finished) {
            pthread_cond_wait(&g_data_cond, &g_sync_mutex);
        }

        /* Check for termination condition */
        if (!g_has_data && g_stream_finished) {
            pthread_mutex_unlock(&g_sync_mutex);
            break;
        }

        /* Retrieve byte into dynamic write buffer */
        *write_buf = g_shared_transfer_char;
        g_has_data = false;
        local_processed_count++;

        /* Echo byte to standard output via system call write() */
        local_bytes_written = write(STDOUT_FILENO, write_buf, 1);
        if (local_bytes_written == -1) {
            perror("Writer: Error writing to stdout");
        }

        /* Signal Reader thread that buffer is cleared */
        pthread_cond_signal(&g_data_cond);
        pthread_mutex_unlock(&g_sync_mutex);
    }

    /* Update global metric */
    pthread_mutex_lock(&g_sync_mutex);
    g_total_bytes_processed = (size_t)local_processed_count;
    pthread_mutex_unlock(&g_sync_mutex);

    write(STDOUT_FILENO, "\n", 1);

    /* Cleanup resources */
    free(write_buf);
    pthread_exit(NULL);
}

/* Main Thread Execution Entry Point */
int main(void) {
    /* Main Thread Local Variables (Stack Frame) */
    int main_fd = -1;
    pthread_t reader_tid;
    pthread_t writer_tid;

    const char *payload = "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";
    size_t payload_len = strlen(payload);

    /* Initialize Synchronization Primitives dynamically */
    if (pthread_mutex_init(&g_sync_mutex, NULL) != 0) {
        perror("Main: Mutex initialization failed");
        return EXIT_FAILURE;
    }
    if (pthread_cond_init(&g_data_cond, NULL) != 0) {
        perror("Main: Condition variable initialization failed");
        pthread_mutex_destroy(&g_sync_mutex);
        return EXIT_FAILURE;
    }

    /* Step 1: Create shared_file */
    printf("Start creating shared_file\n");

    main_fd = open(g_file_path, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (main_fd == -1) {
        perror("Main: Failed to create file");
        pthread_mutex_destroy(&g_sync_mutex);
        pthread_cond_destroy(&g_data_cond);
        return EXIT_FAILURE;
    }

    if (write(main_fd, payload, payload_len) == -1) {
        perror("Main: Failed to write payload");
        close(main_fd);
        pthread_mutex_destroy(&g_sync_mutex);
        pthread_cond_destroy(&g_data_cond);
        return EXIT_FAILURE;
    }

    if (close(main_fd) == -1) {
        perror("Main: Failed to close file");
        pthread_mutex_destroy(&g_sync_mutex);
        pthread_cond_destroy(&g_data_cond);
        return EXIT_FAILURE;
    }

    printf("Finished creating shared_file\n");

    /* Step 2: Spawn Reader Thread */
    printf("Start creating the reader thread\n");
    if (pthread_create(&reader_tid, NULL, reader_thread_func, NULL) != 0) {
        perror("Main: Failed to create reader thread");
        return EXIT_FAILURE;
    }
    printf("created the reader thread\n");

    /* Step 3: Spawn Writer Thread */
    printf("Start creating the writer thread\n");
    if (pthread_create(&writer_tid, NULL, writer_thread_func, NULL) != 0) {
        perror("Main: Failed to create writer thread");
        return EXIT_FAILURE;
    }
    printf("created the writer thread\n");

    /* Step 4: Join Secondary Threads */
    pthread_join(reader_tid, NULL);
    pthread_join(writer_tid, NULL);

    /* Clean up global synchronization primitives */
    pthread_mutex_destroy(&g_sync_mutex);
    pthread_cond_destroy(&g_data_cond);

    return EXIT_SUCCESS;
}

קריאה מודרכת — פונקציה אחר פונקציה

main — הבמאי: מכין, יוצר, ממתין, מנקה

  • אתחול הסנכרון — pthread_mutex_init ואז pthread_cond_init, לפני שקיים חוט. הניקוי בכשלים מדורג — rollback בסדר הפוך להקצאה.
  • יצירת shared_file — open(g_file_path, O_WRONLY | O_CREAT | O_TRUNC, 0644), אותם דגלים והרשאות שב-cp; כתיבת payload (52 אותיות, אורך לפי strlen) וסגירה — לפני שהחוטים נולדים.
  • יצירת שני החוטים — pthread_create פעמיים: Reader ואז Writer.
  • המתנה וניקוי — pthread_join פעמיים (main נחסם עד ששניהם מסיימים), ורק אז pthread_mutex_destroy + pthread_cond_destroy. הסדר קדוש: init לפני create, join לפני destroy — אסור להשמיד פרימיטיבה שעוד בשימוש. אין כאן sleep, כי יש join.

reader_thread_func — הצד המזין

מקצה באפר של בייט אחד על ה-Heap, פותח את הקובץ עם open(g_file_path, O_RDONLY) ומקבל File Descriptor משלו, ואז לולאת הליבה — בייט אחד בכל סיבוב: 

while ((local_bytes_read = read(local_fd, read_buf, 1)) > 0) {
    pthread_mutex_lock(&g_sync_mutex);

    /* Wait until the Writer thread consumes the previous byte */
    while (g_has_data) {
        pthread_cond_wait(&g_data_cond, &g_sync_mutex);
    }

    /* Transfer byte to shared global transfer storage */
    g_shared_transfer_char = *read_buf;
    g_has_data = true;

    /* Signal the Writer thread that a new byte is available */
    pthread_cond_signal(&g_data_cond);
    pthread_mutex_unlock(&g_sync_mutex);
}

read: >0 = מספר הבתים שנקראו, 0 = סוף קובץ, -1 = שגיאה (⇐ perror). ההמתנה כל עוד g_has_data דולק = "ה-Writer עוד לא צרך את הבייט הקודם". בסיום הלולאה פרוטוקול הסיום: נועלים, ממתינים שהבייט האחרון ייצרך, רק אז g_stream_finished = true, מסמנים, משחררים ומנקים (close, free, pthread_exit(NULL)).

writer_thread_func — הצד הצורך

גם הוא מקצה באפר של בייט אחד על ה-Heap. שתי הבדיקות החשובות בתוכנית יושבות בראש ה-while (1) שלו: 

pthread_mutex_lock(&g_sync_mutex);

/* Wait until Reader supplies new data or signals EOF */
while (!g_has_data && !g_stream_finished) {
    pthread_cond_wait(&g_data_cond, &g_sync_mutex);
}

/* Check for termination condition */
if (!g_has_data && g_stream_finished) {
    pthread_mutex_unlock(&g_sync_mutex);
    break;
}

אין בייט אבל הזרם הסתיים ⇐ unlock ו-break (תנאי הסיום); אחרת יש בייט לצרוך: write(STDOUT_FILENO, write_buf, 1) (עם בדיקת -1), קידום מונה מקומי, סימון ל-Reader ושחרור. אחרי הלולאה הוא מעדכן פעם אחת בלבד, תחת mutex, את המדד הגלובלי g_total_bytes_processed מהמונה המקומי — מזעור הזמן שבו מחזיקים את המנעול.

הפרוטוקול כפינג-פונג — מי מחכה למה

התא המשותף מכיל בייט אחד, ולכן שני הצדדים עובדים בתורות. הכול תחת המנעול:

מיממתין כל עוד…וכשמתפנה — עושהואז מסמן
Reader (על כל בייט) g_has_data דולק — התא עוד מלא מניח בייט חדש בתא, מדליק g_has_data pthread_cond_signal ⇐ "יש בייט!"
Writer (על כל סיבוב) !g_has_data && !g_stream_finished — אין בייט ואין EOF צורך את הבייט, מכבה g_has_data, כותב למסך pthread_cond_signal ⇐ "התא פנוי!"
Reader (אחרי EOF) g_has_data דולק — הבייט האחרון עוד לא נצרך מדליק g_stream_finished pthread_cond_signal ⇐ "נגמר הזרם!"
Writer (בסיום) — רואה !g_has_data && g_stream_finished ⇐ break — (רק משחרר את המנעול)

אותו condition variable אחד (g_data_cond) משמש את שלושת המסרים — "יש בייט", "התא פנוי" ו"הזרם הסתיים". מי שמבחין ביניהם אינו ה-cond אלא הדגלים שכל צד בודק בלולאת ה-while שלו.

מה כל קריאת סנכרון עושה — בשורה אחת

התיאוריה המלאה — מה זה Race Condition, איך Mutex ממומש, מה קורה בקרנל — במודול 11.

קריאהמה היא עושה בתוכנית הזאת
pthread_mutex_init / …_destroy אתחול דינמי של המנעול ב-main, והשמדתו אחרי ה-join. פרימיטיבה חיה רק בין ה-init ל-destroy שלה.
pthread_mutex_lock / unlock תוחמים "אזור מוגן": בין lock ל-unlock רק חוט אחד יכול להימצא. בקוד כל נגיעה במצב המשותף עטופה בזוג הזה. חוט שקורא lock כשהמנעול תפוס — ממתין.
pthread_cond_wait(&cond, &mutex) "לך לישון עד שיקראו לך": משחררת את המנעול ומרדימה את החוט בפעולה אחת; כשמישהו מסמן, החוט מתעורר כשהמנעול שוב בידיו וחוזר לבדוק את תנאי ה-while. בלי השחרור הזה הצד השני לעולם לא היה מצליח לנעול — והכול היה נתקע.
pthread_cond_signal(&cond) מעיר חוט שממתין על אותו condition variable. בקוד הוא נקרא תמיד באותה נקודה: אחרי שינוי הדגלים, לפני ה-unlock.

6. הצצה קדימה — מה קורה כששני חוטים נוגעים באותו משתנה

דף העזר Linux Threads (עמ' 4–9): שני חוטים שכל אחד מבצע counter++ מיליון פעמים על אותו גלובלי מקבלים תוצאה נמוכה מ-2,000,000 ושונה בכל הרצה, כי counter++ אינה אטומית — ברמת המעבד Read → Modify → Write, והקרנל רשאי להפסיק בין ההוראות: שני חוטים שקראו 100, העלו ל-101 וכתבו 101 — איבדו קידום אחד. זה Race Condition, ונלמד כראוי במודול 11 — סנכרון Threads (הגדרה מדויקת, דוגמת חשבון הבנק, והפתרון עם Mutex).

7. מלכודות למבחן

⊛ מוסכמת ערכי ההחזרה. פונקציות pthread מחזירות 0 בהצלחה וקוד שגיאה חיובי בכישלון; קריאות מערכת (open, read, fork…) מחזירות -1 ומעדכנות errno. if (pthread_create(...) == -1) בשאלה = שגיאה — סוג "קטע הקוד השגוי" שהמרצה אוהב בחלק א'.

⊛ pthread_create אינה קריאת מערכת. פונקציית ספרייה ב-glibc (NPTL) שרצה ב-user mode; קריאת המערכת שהיא עוטפת היא clone(), וזו יוצרת בקרנל task_struct חדש לחוט. השרשרת שהמרצה חזר עליה פעמיים: pthread_create → NPTL (glibc) → struct pthread (TCB) → clone() → task_struct.

pthread_t ≠ TID. pthread_t קיים רק ב-User Space; ברוב המימושים כתובת של ה-TCB בזיכרון המשתמש, והוא Opaque Type (אסור לגעת בשדותיו). הקרנל מזהה חוט לפי TID ולא משתמש ב-pthread_t בכלל.

אם main מסתיים — כולם מתים. היציאה מ-main מפילה את כל התהליך וחוטיו, גם באמצע עבודה. זו הסיבה ל-sleep(2) בתוכנית הראשונה, והפתרון הנכון הוא pthread_join. (המרצה בשוליים: "2 שניות זה הרבה!")

גם ה-Kernel Stack הוא פר-חוט. בשקף המודלים לכל חוט שלושה: Thread Control Block + User Stack + Kernel Stack; אחד לתהליך נשארים ה-PCB וה-User Address Space. קל לענות "רק ה-User Stack" ולטעות.

"יכולים לרוץ במקביל" ≠ "ירוצו במקביל". המרצה הדגיש את 'can': המקביליות תלויה בזמינות ליבה (core) ובתזמון מערכת ההפעלה — שלושה חוטים על ליבה אחת ירוצו לסירוגין. ובקוד של השקף, f3() איננה חוט: קריאת פונקציה רגילה בתוך חוט ה-main.

אותו PID, TID שונה — ו-task_struct לכל חוט. לא "תהליך = task_struct אחד": בלינוקס לכל חוט task_struct משלו עם pid (= TID) משלו, ומה שמאחד אותם הוא tgid משותף — המספר שאנחנו קוראים לו PID.

⊛ למה חוט "זול" ותהליך "יקר". בלשון השיעור: ב-pthread_create אין צורך לבנות memory image חדש — אותו אחד, ורק ה-Stack נפרד; ב-fork כן. מאותה סיבה ה-Context Switch בין חוטים מהיר בהרבה — מרחב הכתובות לא מתחלף. ולהשוואה: ב-Windows שני מבנים נפרדים (E-Process / E-Thread), ובלינוקס task_struct אחד לשניהם.

⊛ אף פעם לא מסיימים חוט ב-exit(). exit() מפיל את כל התהליך על כל חוטיו; מסיים חוט אחד בלבד הוא pthread_exit, והוא גם מאפשר ל-NPTL לשחרר את מבני החוט (struct pthread, המחסנית, ה-task_struct). ובאותה נשימה: pthread_join הוא ההקבלה המדויקת של wait/waitpid — המתנה לחוט מסוים, כמו המתנה ל-child עם pid מסוים.

מחסנית לכל חוט — 8MB כברירת מחדל, ומתוך ה-heap. החוטים חולקים code, data, bss ו-heap, אבל לכל אחד Stack משלו ש-NPTL מקצה מתוך ה-heap, בגודל 8MB כברירת מחדל. גודל אחר נקבע דרך הארגומנט השני (attr) של pthread_create, לא דרך אף אחד מהאחרים.
