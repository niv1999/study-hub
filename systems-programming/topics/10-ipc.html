תקשורת בין תהליכים (IPC) — pipe, FIFO ו-dup2

⏱ זמן משוער: 30 דק'

מקור: הסילבוס בלבד (טרם הועלו שקפים)

📝

השלמה מהסילבוס — טרם הועלו שקפים לשיעור זה.

העמוד נכתב לפי רשימת הנושאים בסילבוס ומקורות חיצוניים (man pages, Stevens & Rago, Robert Love). כשיעלו החומרים של המרצה — העמוד ייכתב מחדש לפיהם. למבחן: הנושאים כאן מופיעים בסילבוס, אך המרצה טרם לימד אותם — תנו להם עדיפות נמוכה יותר.

לפי מחברת הכיתה של כל 13 המפגשים, הנושא לא נלמד בפועל בשיעורים — סביר שמשקלו במבחן נמוך; העמוד כאן כדי שהסילבוס יהיה מכוסה.

0. למה בכלל צריך IPC? כי תהליכים מבודדים זה מזה

בסילבוס שיעור 10 פותח במילה אחת בסוגריים: isolation. זו לא מילת קישור — זו כל הסיבה לקיומו של הנושא. בואו נזכיר מה למדנו במודול 07: כשfork() יוצר תהליך בן, הקרנל מבצע שכפול של ה-task_struct ושל מרחב הזיכרון. המילה החשובה היא "שכפול": הבן מקבל עותק, לא שותפות.

התוכנית הקטנה הזו מדגימה את הבידוד. שני התהליכים משנים את אותו משתנה — לכאורה:

int x = 5;

if (fork() == 0) {          /* child  */
    x = 100;
    printf("child:  x = %d\n", x);
    exit(0);
}
wait(NULL);                 /* parent waits for the child */
printf("parent: x = %d\n", x);

הפלט:

child:  x = 100
parent: x = 5

הבן שינה את x שלו ל-100, והאב עדיין רואה 5. אלה שתי כתובות שונות בזיכרון שבמקרה נקראות באותו שם בקוד המקור. אין "משתנה משותף" בין תהליכים — וזה בכוונה: אם כל תהליך היה יכול לכתוב לזיכרון של שכנו, מספיק באג אחד בדפדפן כדי להשחית את מסד הנתונים. הבידוד הוא תכונת אבטחה ויציבות, לא מגבלה טכנית שאפשר לעקוף.

המסקנה: אם התהליכים מבודדים, כל תקשורת ביניהם חייבת לעבור דרך הקרנל — הישות היחידה שרואה את שניהם. מנגנון כזה נקרא IPC — Inter-Process Communication: הקרנל מספק "צינור" משותף, ושני התהליכים ניגשים אליו בעזרת קריאות מערכת.

זה גם ההבדל מול Threads: שני חוטים באותו תהליך חולקים את .data, ולכן אצלם הבעיה היא הפוכה — יותר מדי שיתוף (Race Condition). תהליכים נמצאים בקצה השני של הסקאלה.

משפחת מנגנוני ה-IPC בלינוקס — מפה בשורה אחת כל אחד

pipe() — צינור אנונימי
זרם בתים חד-כיווני בין תהליכים קרובי משפחה (אב ובן שירשו את אותם FDs). הנושא המרכזי בשיעור.
Named Pipe (FIFO)
אותו צינור בדיוק, אבל עם שם בתוך מערכת הקבצים — ולכן גם שני תהליכים זרים לגמרי יכולים להיפגש בו.
Sockets
ערוץ דו-כיווני, גם בין מכונות שונות ברשת — הנושא של מודול 13.
Signals
"נקישה" אסינכרונית של סיבית אחת (בלי תוכן) — הנושא של מודול 12.
Shared Memory / Message Queues / Semaphores (אזכור בלבד)
משפחת ה-System V / POSIX IPC: אזור זיכרון שממופה לשני תהליכים, תור הודעות, ומונה סנכרון. לא נדרשים בסילבוס.
🎓 מהשיעור בכיתה (מהמחברת)

pipe מופיע במחברת פעם אחת בלבד — בשיעור 2.8, בעמוד של מפת משפחות מערכות ההפעלה (BSD / Unix / Linux / Windows NT / macOS). המרצה כתב באדום, זו לצד זו, את המילים "מיקרו-קרנל" ו-pipe — כלומר הצינור הוזכר שם כדוגמה לערוץ שדרכו רכיבים מדברים זה עם זה (רעיון מרכזי במיקרו-קרנל, שבו שירותי המערכת הם תהליכים נפרדים שמתקשרים בהודעות). מעבר לאזכור הזה — בכל 13 מפגשי הכיתה (19.7–3.9) לא נלמדו pipe, FIFO או dup2.

כל שלושת המנגנונים בעמוד הזה מתנהגים כמו קובץ: מקבלים File Descriptor, ומדברים איתו ב-read() ו-write(). זה בדיוק העיקרון שהמרצה חוזר עליו לאורך כל הקורס — "הכול קובץ". לכן כל מה שלמדתם במודול 06 על ערכי החזרה ועל Partial I/O תקף גם כאן.

1. pipe() — הצינור האנונימי

pipe() היא קריאת המערכת שמבקשת מהקרנל ליצור אובייקט קרנל חדש: מאגר (buffer) קטן בזיכרון הקרנל שמתנהג כמו תור — מה שנכנס ראשון יוצא ראשון. מיד עם היצירה הקרנל מחזיר לתהליך שני File Descriptors: אחד לקצה הקריאה ואחד לקצה הכתיבה.

החתימה

#include <unistd.h>

int pipe(int pipefd[2]);
רכיבמשמעות
pipefdמערך של שני int שאתם מקצים (בדרך כלל על המחסנית). אתם מספקים אותו — הקרנל רק ממלא אותו.
pipefd[0]קצה הקריאה (read end). ממנו קוראים ב-read(). אסור לכתוב אליו.
pipefd[1]קצה הכתיבה (write end). אליו כותבים ב-write(). אסור לקרוא ממנו.
ערך החזרה0 בהצלחה, -1 בשגיאה ואז errno נקבע (למשל EMFILE — נגמרו ה-FDs לתהליך). זו בדיוק מוסכמת השגיאות ממודול 03.

עזר זיכרון: 0 כמו stdin — קוראים; 1 כמו stdout — כותבים.

שלוש תכונות שמגדירות מה צינור יכול ומה לא:

  • חד-כיווני — הנתונים זורמים רק מקצה הכתיבה לקצה הקריאה. לשיחה דו-כיוונית צריך שני צינורות.
  • זרם בתים (byte stream) — הצינור לא שומר גבולות הודעה. אם כתבתם "abc" ואז "def", ייתכן ש-read() אחד יחזיר "abcdef". בדיוק כמו קובץ — ובדיוק כמו סוקט SOCK_STREAM.
  • חסום בגודלו (bounded) — המאגר סופי (בלינוקס: 64KB כברירת מחדל). כשהוא מתמלא, write() נחסם עד שהקורא יפנה מקום; כשהוא ריק, read() נחסם עד שמישהו יכתוב. הצינור מסנכרן את שני התהליכים בלי שכתבתם שורת סנכרון אחת.

המילה אנונימי היא הנקודה הקריטית: לצינור אין שם בשום מקום במערכת הקבצים. אי אפשר "לפתוח" אותו מתהליך אחר — הדרך היחידה להגיע אליו היא לרשת את ה-FD. ולכן הדפוס הקלאסי הוא תמיד: pipe() ואז fork(), בסדר הזה.

הדפוס הקלאסי: pipe → fork → close → write/read → close

  1. pipe(pipefd) — נוצר האובייקט; לתהליך יש כעת שני FDs חדשים (למשל 3 ו-4).
  2. fork() — כזכור ממודול 07: הקרנל משכפל את טבלת ה-FDs (fd_array). כעת ארבעה FDs מצביעים על שני קצות אותו צינור: 3 ו-4 אצל האב, ו-3 ו-4 אצל הבן.
  3. כל צד סוגר את הקצה שאינו זקוק לו — הכותב סוגר את קצה הקריאה, הקורא סוגר את קצה הכתיבה.
  4. write() / read() — זרימת הנתונים.
  5. close() — הכותב סוגר את קצה הכתיבה שלו; זו ההודעה "סיימתי".

למה חובה לסגור את הקצוות המיותרים? כי כאן חוזר בדיוק המנגנון של Reference Counting ממודול 06 וממודול 14: לכל קצה של הצינור יש struct file משלו עם מונה f_count, ו-fork() מגדיל אותו. הכלל של הקרנל: read() מחזיר 0 (EOF) רק כאשר ה-f_count של קצה הכתיבה יורד לאפס — כלומר רק כשכל התהליכים סגרו את קצה הכתיבה. אם האב שכח close(pipefd[1]), הבן ייתקע ב-read() לנצח, וימתין לנתונים מקצה כתיבה שאיש כבר לא מתכוון לכתוב אליו. זו התקיעה הקלאסית ביותר בנושא.

כך זה נראה בזיכרון הקרנל אחרי שכל צד סגר את הקצה המיותר (המצב הרצוי):

דוגמה מלאה: האב כותב "hello", הבן קורא ומדפיס

התוכנית פותחת צינור, מתפצלת, ואז האב שולח מחרוזת אחת לבן. שימו לב לארבע ה-close() — כל אחת מהן חיונית:

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    int     pipefd[2];
    pid_t   pid;
    char    buf[64];
    ssize_t n;

    if (pipe(pipefd) == -1) {          /* [0] = read end, [1] = write end */
        perror("pipe");
        exit(EXIT_FAILURE);
    }

    if ((pid = fork()) == -1) {        /* the fd table is duplicated here   */
        perror("fork");
        exit(EXIT_FAILURE);
    }

    if (pid == 0) {                    /* ---------- child: the reader ---------- */
        close(pipefd[1]);              /* MUST: otherwise read() never sees EOF   */

        n = read(pipefd[0], buf, sizeof(buf) - 1);
        if (n > 0) {
            buf[n] = '\0';
            printf("child got: %s\n", buf);
        }
        n = read(pipefd[0], buf, sizeof(buf) - 1);
        printf("child second read returned: %zd\n", n);   /* 0 == EOF */

        close(pipefd[0]);
        exit(EXIT_SUCCESS);
    }

    /* ---------- parent: the writer ---------- */
    close(pipefd[0]);                  /* the parent is not going to read */

    const char *msg = "hello";
    if (write(pipefd[1], msg, strlen(msg)) == -1)
        perror("write");

    close(pipefd[1]);                  /* THIS is what turns the child's read() into 0 */

    wait(NULL);                        /* reap the child (module 08) */
    return 0;
}

הפלט הצפוי:

child got: hello
child second read returned: 0

ה-read() השני הוא הלב של הדוגמה: הוא לא נכשל ולא מחזיר -1 — הוא מחזיר 0, בדיוק כמו read() בסוף קובץ. זהו הסימן היחיד שהצינור נסגר. אילו האב היה שוכח את close(pipefd[1]), השורה השנייה לעולם לא הייתה מודפסת: הבן היה נחסם שם עד קץ הימים.

הרחבה — לא מהשקפים

הכיוון ההפוך: מה קורה אם כותבים לצינור שאף אחד כבר לא קורא ממנו? הקרנל שולח לכותב את הסיגנל SIGPIPE, שברירת המחדל שלו היא להרוג את התהליך — ולכן yes | head -1 מסתיים לבד. אם התוכנית מתעלמת מ-SIGPIPE (ראו מודול 12), write() יחזיר במקום זאת -1 עם errno == EPIPE. עוד פרט מ-man 7 pipe: כתיבה של עד PIPE_BUF בתים (4096 בלינוקס) מובטחת כאטומית — היא לא תשתזר עם כתיבה של תהליך אחר.

2. Named Pipe (FIFO) — צינור שיש לו שם

לצינור האנונימי יש חיסרון אחד גדול: הוא דורש קרבת משפחה. שני תהליכים שהופעלו בשני חלונות טרמינל שונים לא יכולים לחלוק אותו, כי אין להם אב משותף שהריץ pipe() לפניהם. FIFO — Named Pipe פותר בדיוק את זה: אותו מנגנון בדיוק, אבל הפעם יש לצינור שם בתוך מערכת הקבצים, ולכן כל תהליך שיודע את הנתיב יכול לפתוח אותו ב-open() רגיל.

החתימה

#include <sys/types.h>
#include <sys/stat.h>

int mkfifo(const char *pathname, mode_t mode);

pathname — הנתיב שבו ייווצר ה-FIFO; mode — הרשאות בבסיס אוקטלי (למשל 0666, בדיוק כמו ב-open() ממודול 06, וכפוף ל-umask). מחזירה 0 בהצלחה, -1 בשגיאה — ו-EEXIST אם הקובץ כבר קיים (מצב שבדרך כלל אפשר פשוט להתעלם ממנו).

שלוש נקודות שחייבים להבין כאן:

  • מה שנוצר הוא רק שם. ב-ls -l תראו את התו p בעמודת סוג הקובץ (prw-r--r--) — סוג קובץ נוסף לצד - (רגיל), d (תיקייה), b/c (התקנים) ו-s (סוקט) שראינו במודול 05. יש לו inode, אבל אין לו Data Blocks: הנתונים לעולם לא נכתבים לדיסק, אלא יושבים במאגר בזיכרון הקרנל — בדיוק כמו בצינור אנונימי. הגודל ב-ls יהיה תמיד 0.
  • הפתיחה חוסמת עד שיש צד שני. open(path, O_RDONLY) נחסם עד שתהליך אחר יפתח את אותו FIFO ב-O_WRONLY, ולהפך. זהו מנגנון פגישה (rendezvous): שני הצדדים חייבים להיות נוכחים כדי שהערוץ ייפתח. (עם הדגל O_NONBLOCK: פתיחה לקריאה מצליחה מיד, ופתיחה לכתיבה נכשלת ב-ENXIO כשאין קורא.)
  • ה-FIFO שורד את התהליכים. השם נשאר בדיסק גם אחרי ששני הצדדים סיימו, עד שמישהו יריץ rm (כלומר unlink()). הנתונים, לעומת זאת, נעלמים — הם היו רק בזיכרון.

הדגמה של דקה בשני חלונות טרמינל. חלון א' — יוצרים את ה-FIFO ומנסים לקרוא ממנו:

$ mkfifo /tmp/f            # the shell command; calls mkfifo(2)
$ ls -l /tmp/f
prw-r--r-- 1 niv niv 0 Sep  6 10:12 /tmp/f
    ^ 'p' = pipe

$ cat /tmp/f               # blocks! open(O_RDONLY) waits for a writer

חלון ב' — כותבים לאותו נתיב, ומיד חלון א' מתעורר ומדפיס:

$ echo hi > /tmp/f         # open(O_WRONLY) -> both sides are now present
$                          # ... and window A prints:  hi
$ rm /tmp/f                # unlink() - the name is gone

שימו לב מה בדיוק קרה: cat ו-echo הם שני תהליכים שאין ביניהם שום קשר משפחתי — ובכל זאת הם החליפו נתונים. זה ההבדל היחיד והמהותי מול pipe().

ואותו דבר בקוד C — שלד שני התהליכים (רק השורות המהותיות):

/* ---------- the reader process ---------- */
mkfifo("/tmp/f", 0666);                  /* EEXIST is fine - it may already be there */

int fd = open("/tmp/f", O_RDONLY);       /* BLOCKS until a writer arrives */
char buf[128];
ssize_t n = read(fd, buf, sizeof buf);   /* 0 == every writer closed the FIFO */
close(fd);

/* ---------- the writer process (a totally unrelated program) ---------- */
int fd = open("/tmp/f", O_WRONLY);       /* BLOCKS until a reader arrives */
write(fd, "hi\n", 3);
close(fd);                               /* the reader's read() now returns 0 */

מרגע שה-open() חזר, אין שום הבדל בין FIFO לצינור אנונימי: אותו read()/write(), אותה חסימה כשהמאגר ריק או מלא, אותו EOF כשכל הכותבים סגרו, ואותו SIGPIPE כשאין קוראים. ההבדל הוא רק בדרך ההיכרות — ירושה דרך fork() מול נתיב במערכת הקבצים.

3. dup() ו-dup2() — הפניית קלט ופלט

עד כאן ידענו לבנות צינור. עכשיו השאלה המעניינת: איך גורמים לתוכנית קיימת, שכתובה עם printf ו-scanf ולא יודעת דבר על צינורות, לכתוב אל הצינור במקום למסך? התשובה היא I/O Redirection, והכלי שלה הוא dup2().

נזכיר את המוסכמה ממודול 05: לכל תהליך יש שלושה FDs שנפתחים עבורו מראש — 0 = stdin, 1 = stdout, 2 = stderr — ובדרך כלל שלושתם מחוברים לטרמינל. הפונקציה printf של glibc, בסופו של דבר, קוראת ל-write(1, ...). היא לא שואלת לאן FD מספר 1 מצביע. ולכן: אם נשנה את התא מספר 1 בטבלת ה-FDs כך שיצביע לקובץ או לצינור — כל ה-printfים בתוכנית יזרמו לשם, בלי לשנות בה שורת קוד אחת.

שתי החתימות

#include <unistd.h>

int dup(int oldfd);              /* copy oldfd to the LOWEST free fd number */
int dup2(int oldfd, int newfd);  /* copy oldfd to EXACTLY newfd            */
dup(oldfd)dup2(oldfd, newfd)
איזה FD מתקבלהמספר הפנוי הנמוך ביותר — הקרנל בוחרבדיוק newfd — אתם בוחרים
אם ה-FD היעד תפוסלא רלוונטי (נבחר פנוי)נסגר קודם, אוטומטית ואטומית
ערך החזרהה-FD החדש, או -1newfd, או -1 (למשל EBADF אם oldfd אינו תקין)
למה משתמשים בושמירת עותק גיבוי של FD לפני הפניהההפניה עצמה — זה הכלי המעשי

פרט קטן ששווה לזכור: אם oldfd == newfd, dup2 אינו עושה דבר ואינו סוגר כלום — הוא פשוט מחזיר את newfd.

מה בדיוק קורה במבני הנתונים של הקרנל

זו הנקודה שהמרצה אוהב לבחון: dup2 לא מעביר אף בית ולא יוצר אובייקט קובץ חדש. הוא נוגע רק בטבלת ה-fd_array של התהליך. התא newfd מקבל מצביע לאותו struct file שאליו מצביע oldfd, ומונה ההפניות f_count של אותו אובייקט גדל ב-1 — בדיוק המנגנון שראינו באלגוריתם ה-close() של המרצה (מודול 06, שלבים 3–4).

ההשלכות המיידיות, ושלושתן שאלות מבחן פוטנציאליות:

  • ה-offset משותף. אותו struct file = אותו f_pos. כתיבה דרך FD אחד מקדמת את המיקום גם עבור השני; הם לא ידרסו זה את זה.
  • הדגלים משותפים (O_APPEND וחבריו) — הם שדה ב-struct file, לא ב-FD.
  • close() על אחד מהם אינו סוגר את הקובץ — הוא רק מוריד את f_count מ-2 ל-1. האובייקט מושמד רק כשהמונה מגיע לאפס.

דוגמה 1: הפניית stdout לקובץ (cmd > file ביד)

ארבע שורות שהופכות כל printf בהמשך התוכנית לכתיבה אל out.txt:

#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>

int main(void)
{
    int fd = open("out.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd == -1) { perror("open"); exit(EXIT_FAILURE); }

    if (dup2(fd, STDOUT_FILENO) == -1) {   /* STDOUT_FILENO == 1 */
        perror("dup2");
        exit(EXIT_FAILURE);
    }
    close(fd);              /* the spare fd is not needed: f_count 2 -> 1 */

    printf("this line lands in out.txt\n");   /* glibc calls write(1, ...) */
    fflush(stdout);         /* flush before exit, to be explicit */
    return 0;
}

הסדר קריטי ומעיד על הבנה: קודם open, אחר כך dup2, אחר כך close של ה-FD המקורי. ה-dup2 סגר עבורנו את FD מספר 1 הישן (זה שהצביע לטרמינל) ובאותה נשימה שם שם את הקובץ.

דוגמה 2: לבנות ls | wc -l ביד

שילוב הכול: צינור אחד, שני בנים, שתי הפניות, ושתי סגירות אצל האב. זה, בקירוב טוב, מה שה-Bash עושה בכל פעם שאתם מקלידים |:

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    int   pipefd[2];
    char *ls_argv[] = { "ls", NULL };
    char *wc_argv[] = { "wc", "-l", NULL };

    if (pipe(pipefd) == -1) { perror("pipe"); exit(EXIT_FAILURE); }

    if (fork() == 0) {                      /* ---- child 1: "ls" ---- */
        dup2(pipefd[1], STDOUT_FILENO);     /* its stdout -> write end   */
        close(pipefd[0]);                   /* close BOTH originals      */
        close(pipefd[1]);
        execvp(ls_argv[0], ls_argv);        /* fd_array survives execve! */
        perror("execvp ls");
        exit(EXIT_FAILURE);
    }

    if (fork() == 0) {                      /* ---- child 2: "wc -l" ---- */
        dup2(pipefd[0], STDIN_FILENO);      /* its stdin  <- read end     */
        close(pipefd[0]);
        close(pipefd[1]);
        execvp(wc_argv[0], wc_argv);
        perror("execvp wc");
        exit(EXIT_FAILURE);
    }

    close(pipefd[0]);       /* THE PARENT MUST CLOSE BOTH ENDS.          */
    close(pipefd[1]);       /* otherwise wc never sees EOF and hangs.    */

    wait(NULL);             /* reap both children (module 08)            */
    wait(NULL);
    return 0;
}

הרצה:

$ gcc mypipe.c -o mypipe && ./mypipe
7

למה ההפניה שורדת את execve()? כי טבלת ה-FDs היא שדה ב-task_struct — היא חיה בקרנל, לא במרחב המשתמש. execve מוחק ומאפס את מרחב הזיכרון (קוד, נתונים, מחסנית) וטוען ELF חדש, בדיוק כפי שראינו בתרחיש ה-Bash של מודול 04 — אבל fd_array נשאר כמות שהוא. ולכן ls מתחיל לרוץ כשה-FD מספר 1 שלו כבר מחובר לצינור, בלי שיידע על כך דבר. זה בדיוק מה שהופך את שלישיית fork → dup2 → execve למנגנון ההפניה של כל shell ביוניקס.

איך Bash מממש את זה בפועל

נחזור לתרחיש חמשת השלבים של המרצה (מודול 04): Line Discipline → Tokenization → Built-in Check → fork() → execve(). ההפניה נכנסת בדיוק בין שלב 4 לשלב 5, בתוך תהליך הבן:

הפקודה שהקלדתםמה ה-Bash מבצע (בבן, אחרי fork ולפני execve)
cmd > file fd = open("file", O_WRONLY|O_CREAT|O_TRUNC, 0644) → dup2(fd, 1) → close(fd) → execve(cmd…). (עבור >> — אותו דבר עם O_APPEND במקום O_TRUNC.)
cmd < file fd = open("file", O_RDONLY) → dup2(fd, 0) → close(fd) → execve
cmd1 | cmd2 pipe() → שני fork: בבן א׳ dup2(pipefd[1], 1), בבן ב׳ dup2(pipefd[0], 0); כל אחד סוגר את שני המקוריים ואז execve. האב סוגר את שני הקצוות וממתין.
cmd 2>&1 dup2(1, 2) — גם stderr מצביע כעת לאותו struct file כמו stdout

וזו התשובה לשאלה "למה ה-shell לא צריך לדעת דבר על התוכניות שהוא מריץ": הוא לא משנה אותן. הוא רק מסדר להן את טבלת ה-FDs לפני שהן מתחילות לרוץ.

4. pipe מול FIFO מול socket

שלושתם ערוצי תקשורת שמנוהלים בקרנל, ולשלושתם ניגשים דרך FD. ההבדלים:

pipe (אנונימי)FIFO (Named Pipe)socket
מי יכול להשתמש רק תהליכים קרובי משפחה — שירשו את ה-FD דרך fork() כל שני תהליכים על אותה מכונה שיודעים את הנתיב גם תהליכים על מכונות שונות ברשת
שם / כתובת אין שום שם נתיב במערכת הקבצים (סוג קובץ p) כתובת IP + פורט (מודול 13)
כיוון חד-כיווני חד-כיווני (לכל פתיחה) דו-כיווני (full-duplex)
איך נוצר / מאיפה ה-FD pipe(pipefd) — שני FDs בבת אחת mkfifo() פעם אחת, ואז open() בכל צד socket() + bind/listen/accept או connect
תוחלת חיים קיים כל עוד FD אחד פתוח; נעלם לגמרי כשכולם נסגרו השם נשאר עד rm; הנתונים — כמו בצינור קיים כל עוד החיבור וה-FDs פתוחים (ואז TIME_WAIT)
הממשק read() / write() / close() — זהה לשלושתם. "הכול קובץ".

5. מלכודות למבחן

  1. שכחת close() על הקצה המיותר ⇐ תקיעה, לא שגיאה. אם מישהו עדיין מחזיק את קצה הכתיבה פתוח, ה-read() נחסם לנצח במקום להחזיר 0: התוכנית לא קורסת ולא מדפיסה שגיאה — היא פשוט נתלית. מלכודת מובהקת לשאלות "האם קטע הקוד תקין?".
  2. pipe() חייב לבוא לפני fork(). אם כל תהליך קורא ל-pipe() בעצמו, נוצרו שני צינורות נפרדים לגמרי ושום נתון לא יעבור. הירושה של ה-FD היא כל המנגנון.
  3. בלבול בין pipefd[0] ל-pipefd[1]. כתיבה ל-pipefd[0] תיכשל ב-EBADF. זכרו: 0 = קריאה (כמו stdin), 1 = כתיבה (כמו stdout).
  4. הצינור חד-כיווני. שימוש באותו צינור לשני הכיוונים גורם לתהליך לקרוא את מה שהוא עצמו כתב. לשיחה דו-כיוונית: שני צינורות (או סוקט).
  5. dup2 אינו מעתיק בתים ואינו יוצר struct file חדש. הוא רק מוסיף מצביע בטבלת ה-FDs ומגדיל את f_count. מכאן: ה-offset משותף, ו-close() על אחד העותקים אינו סוגר את הקובץ.
  6. סדר הפעולות סביב execve. ה-dup2 חייב להתבצע אחרי fork ולפני execve, ורק בתוך הבן. אחרי execve אין כבר קוד משלכם שירוץ — אבל ה-FDs עצמם שורדים אותו, וזה כל הטריק.
  7. כתיבה לצינור בלי קוראים = SIGPIPE. ברירת המחדל היא מוות של התהליך הכותב, לא ערך החזרה שגוי. אם מתעלמים מהסיגנל — מקבלים -1 ו-EPIPE.
