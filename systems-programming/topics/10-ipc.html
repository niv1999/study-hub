תקשורת בין תהליכים (IPC) — pipe, FIFO ו-dup2

⏱ זמן משוער: 20 דק'

מקור: הסילבוס בלבד (טרם הועלו שקפים)

📝

השלמה מהסילבוס — טרם הועלו שקפים לשיעור זה.

העמוד נכתב לפי רשימת הנושאים בסילבוס ומקורות חיצוניים (man pages, Stevens & Rago, Robert Love).

לפי מחברת הכיתה של כל 13 המפגשים הנושא לא נלמד בפועל — סביר שמשקלו במבחן נמוך. העמוד כאן כדי שהסילבוס יהיה מכוסה: תנו לו עדיפות נמוכה יותר.

0. למה בכלל צריך IPC? כי תהליכים מבודדים זה מזה

הסילבוס פותח את שיעור 10 במילה isolation: fork() משכפל את ה-task_struct ואת מרחב הזיכרון — הבן מקבל עותק, לא שותפות: 

int x = 5;

if (fork() == 0) {          /* child  */
    x = 100;
    printf("child:  x = %d\n", x);
    exit(0);
}
wait(NULL);                 /* parent waits for the child */
printf("parent: x = %d\n", x);

הפלט:

child:  x = 100
parent: x = 5

שתי כתובות שונות בזיכרון שנקראות באותו שם בקוד. אין משתנה משותף בין תהליכים — הבידוד הוא תכונת אבטחה, לא מגבלה שכדאי לעקוף.

המסקנה: כל תקשורת בין תהליכים מבודדים חייבת לעבור דרך הקרנל, הישות היחידה שרואה את שניהם. זהו IPC — Inter-Process Communication.

מנגנוני ה-IPC בלינוקס

זרם בתים חד-כיווני בין תהליכים קרובי משפחה. הנושא המרכזי בשיעור.
Named Pipe (FIFO)
אותו צינור, עם שם במערכת הקבצים — ולכן גם תהליכים זרים יכולים להיפגש בו.
Sockets
ערוץ דו-כיווני, גם בין מכונות ברשת — מודול 13.
Signals
"נקישה" אסינכרונית בלי תוכן — מודול 12.
Shared Memory / Message Queues / Semaphores (אזכור בלבד)
System V / POSIX IPC: זיכרון ממופה לשני תהליכים, תור הודעות, מונה סנכרון. לא נדרשים בסילבוס.
🎓 מהשיעור בכיתה (מהמחברת)

pipe מופיע במחברת פעם אחת בלבד — בשיעור 2.8, בעמוד של מפת משפחות מערכות ההפעלה (BSD / Unix / Linux / Windows NT / macOS). המרצה כתב באדום, זו לצד זו, את המילים "מיקרו-קרנל" ו-pipe — כלומר הצינור הוזכר שם כדוגמה לערוץ שדרכו רכיבים מדברים זה עם זה (רעיון מרכזי במיקרו-קרנל, שבו שירותי המערכת הם תהליכים נפרדים שמתקשרים בהודעות). מעבר לאזכור הזה — בכל 13 מפגשי הכיתה (19.7–3.9) לא נלמדו pipe, FIFO או dup2.

1. pipe() — הצינור האנונימי

pipe() יוצרת אובייקט קרנל: מאגר (buffer) בזיכרון הקרנל שמתנהג כתור FIFO. הקרנל מחזיר שני File Descriptors — אחד לכל קצה.

החתימה

#include <unistd.h>

int pipe(int pipefd[2]);
רכיבמשמעות
pipefdמערך של שני int שאתם מקצים (בדרך כלל על המחסנית); הקרנל רק ממלא אותו.
pipefd[0]קצה הקריאה (read end) — read() בלבד.
pipefd[1]קצה הכתיבה (write end) — write() בלבד.
ערך החזרה0 בהצלחה, -1 בשגיאה ואז errno נקבע (למשל EMFILE — נגמרו ה-FDs לתהליך).

עזר זיכרון: 0 כמו stdin, 1 כמו stdout.

שלוש תכונות מגדירות:

  • חד-כיווני — רק מקצה הכתיבה לקצה הקריאה; לדו-כיווני צריך שני צינורות.
  • זרם בתים (byte stream) — אין גבולות הודעה: "abc" ואז "def" עשויים לחזור ב-read() אחד כ-"abcdef", כמו בקובץ וכמו בסוקט SOCK_STREAM.
  • חסום בגודלו (bounded) — המאגר סופי (64KB בלינוקס). מלא ⇐ write() נחסם; ריק ⇐ read() נחסם. הצינור מסנכרן את שני התהליכים מעצמו.

אנונימי = אין לו שם במערכת הקבצים; הדרך היחידה אליו היא לרשת את ה-FD, ולכן הסדר תמיד pipe() ואז fork().

הדפוס הקלאסי: pipe → fork → close → write/read → close. ה-fork() משכפל את fd_array, ולכן ארבעה FDs מצביעים על שני קצות אותו צינור; כל צד סוגר את הקצה שאינו משמש אותו, ובסוף הכותב סוגר גם את קצה הכתיבה — ההודעה "סיימתי".

למה חובה לסגור את הקצוות המיותרים? Reference Counting: לכל קצה struct file משלו עם מונה f_count ש-fork() מגדיל. הכלל: read() מחזיר 0 (EOF) רק כשה-f_count של קצה הכתיבה מתאפס — רק כשכל התהליכים סגרו אותו.

דוגמה מלאה: האב כותב "hello", הבן קורא ומדפיס

ארבע ה-close() — כל אחת חיונית:

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    int     pipefd[2];
    pid_t   pid;
    char    buf[64];
    ssize_t n;

    if (pipe(pipefd) == -1) {          /* [0] = read end, [1] = write end */
        perror("pipe");
        exit(EXIT_FAILURE);
    }

    if ((pid = fork()) == -1) {        /* the fd table is duplicated here   */
        perror("fork");
        exit(EXIT_FAILURE);
    }

    if (pid == 0) {                    /* ---------- child: the reader ---------- */
        close(pipefd[1]);              /* MUST: otherwise read() never sees EOF   */

        n = read(pipefd[0], buf, sizeof(buf) - 1);
        if (n > 0) {
            buf[n] = '\0';
            printf("child got: %s\n", buf);
        }
        n = read(pipefd[0], buf, sizeof(buf) - 1);
        printf("child second read returned: %zd\n", n);   /* 0 == EOF */

        close(pipefd[0]);
        exit(EXIT_SUCCESS);
    }

    /* ---------- parent: the writer ---------- */
    close(pipefd[0]);                  /* the parent is not going to read */

    const char *msg = "hello";
    if (write(pipefd[1], msg, strlen(msg)) == -1)
        perror("write");

    close(pipefd[1]);                  /* THIS is what turns the child's read() into 0 */

    wait(NULL);                        /* reap the child (module 08) */
    return 0;
}

הפלט הצפוי:

child got: hello
child second read returned: 0

ה-read() השני מחזיר 0 ולא -1 — הסימן היחיד שהצינור נסגר. בלי close(pipefd[1]) אצל האב, הבן היה נחסם שם לנצח.

הרחבה — לא מהשקפים

כתיבה לצינור שאיש לא קורא ממנו: הקרנל שולח לכותב SIGPIPE, שברירת המחדל שלו להרוג את התהליך (ולכן yes | head -1 מסתיים לבד). אם מתעלמים ממנו (מודול 12) — write() מחזיר -1 עם errno == EPIPE. עוד מ-man 7 pipe: כתיבה של עד PIPE_BUF בתים (4096) אטומית.

2. Named Pipe (FIFO) — צינור שיש לו שם

FIFO — Named Pipe הוא אותו מנגנון בדיוק, אבל עם שם בתוך מערכת הקבצים: כל תהליך שיודע את הנתיב פותח אותו ב-open() רגיל, גם בלי קרבת משפחה.

החתימה

#include <sys/types.h>
#include <sys/stat.h>

int mkfifo(const char *pathname, mode_t mode);

pathname — נתיב ה-FIFO; mode — הרשאות אוקטליות (0666, כפוף ל-umask). מחזירה 0 / -1, עם EEXIST אם הקובץ כבר קיים (אפשר להתעלם).

שלוש נקודות:

  • מה שנוצר הוא רק שם. סוג הקובץ ב-ls -l הוא p (prw-r--r--), לצד -, d, b/c ו-s (מודול 05). יש לו inode אבל אין לו Data Blocks — הנתונים בזיכרון הקרנל, והגודל תמיד 0.
  • הפתיחה חוסמת עד שיש צד שני — open(O_RDONLY) נחסם עד שמישהו יפתח ב-O_WRONLY, ולהפך (rendezvous). עם O_NONBLOCK: קריאה מצליחה מיד, כתיבה נכשלת ב-ENXIO.
  • ה-FIFO שורד את התהליכים. השם נשאר בדיסק עד rm (unlink()); הנתונים נעלמים — הם היו רק בזיכרון.

חלון א':

$ mkfifo /tmp/f            # the shell command; calls mkfifo(2)
$ ls -l /tmp/f
prw-r--r-- 1 niv niv 0 Sep  6 10:12 /tmp/f
    ^ 'p' = pipe

$ cat /tmp/f               # blocks! open(O_RDONLY) waits for a writer

חלון ב' — וחלון א' מתעורר ומדפיס:

$ echo hi > /tmp/f         # open(O_WRONLY) -> both sides are now present
$                          # ... and window A prints:  hi
$ rm /tmp/f                # unlink() - the name is gone

cat ו-echo הם תהליכים ללא קשר משפחתי — וזה ההבדל מול pipe(). בקוד C: 

/* ---------- the reader process ---------- */
mkfifo("/tmp/f", 0666);                  /* EEXIST is fine - it may already be there */

int fd = open("/tmp/f", O_RDONLY);       /* BLOCKS until a writer arrives */
char buf[128];
ssize_t n = read(fd, buf, sizeof buf);   /* 0 == every writer closed the FIFO */
close(fd);

/* ---------- the writer process (a totally unrelated program) ---------- */
int fd = open("/tmp/f", O_WRONLY);       /* BLOCKS until a reader arrives */
write(fd, "hi\n", 3);
close(fd);                               /* the reader's read() now returns 0 */

מרגע שה-open() חזר אין הבדל בין FIFO לצינור אנונימי. ההבדל הוא רק בדרך ההיכרות — ירושה דרך fork() מול נתיב במערכת הקבצים.

3. dup() ו-dup2() — הפניית קלט ופלט

I/O Redirection מפנה את הפלט של תוכנית קיימת אל הצינור, והכלי שלה dup2(). לכל תהליך שלושה FDs פתוחים מראש (מודול 05): 0 = stdin, 1 = stdout, 2 = stderr. printf קוראת בסוף ל-write(1, ...) ואינה שואלת לאן FD 1 מצביע — לכן שינוי התא מספר 1 מפנה את כל הפלט בלי לשנות שורת קוד.

שתי החתימות

#include <unistd.h>

int dup(int oldfd);              /* copy oldfd to the LOWEST free fd number */
int dup2(int oldfd, int newfd);  /* copy oldfd to EXACTLY newfd            */
dup(oldfd)dup2(oldfd, newfd)
איזה FD מתקבלהמספר הפנוי הנמוך ביותר — הקרנל בוחרבדיוק newfd — אתם בוחרים
אם ה-FD היעד תפוסלא רלוונטינסגר קודם, אוטומטית ואטומית
ערך החזרהה-FD החדש, או -1newfd, או -1 (EBADF אם oldfd אינו תקין)
למה משתמשים בועותק גיבוי של FD לפני הפניהההפניה עצמה

אם oldfd == newfd, dup2 אינו עושה דבר ואינו סוגר כלום — רק מחזיר את newfd.

מה בדיוק קורה במבני הנתונים של הקרנל

dup2 לא מעביר אף בית ולא יוצר אובייקט קובץ חדש. הוא נוגע רק ב-fd_array: התא newfd מקבל מצביע לאותו struct file של oldfd, ו-f_count גדל ב-1. שלוש ההשלכות:

  • ה-offset משותף — אותו struct file = אותו f_pos.
  • הדגלים משותפים (O_APPEND וחבריו) — שדה ב-struct file, לא ב-FD.
  • close() על אחד מהם אינו סוגר את הקובץ — רק מוריד את f_count מ-2 ל-1; האובייקט מושמד כשהמונה מתאפס.

דוגמה 1: הפניית stdout לקובץ (cmd > file ביד)

כל printf בהמשך התוכנית ייכתב אל out.txt:

#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>

int main(void)
{
    int fd = open("out.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd == -1) { perror("open"); exit(EXIT_FAILURE); }

    if (dup2(fd, STDOUT_FILENO) == -1) {   /* STDOUT_FILENO == 1 */
        perror("dup2");
        exit(EXIT_FAILURE);
    }
    close(fd);              /* the spare fd is not needed: f_count 2 -> 1 */

    printf("this line lands in out.txt\n");   /* glibc calls write(1, ...) */
    fflush(stdout);         /* flush before exit, to be explicit */
    return 0;
}

הסדר קריטי: open → dup2 → close של ה-FD המקורי.

דוגמה 2: לבנות ls | wc -l ביד

צינור אחד, שני בנים, שתי הפניות ושתי סגירות אצל האב — מה שה-Bash עושה בכל |:

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    int   pipefd[2];
    char *ls_argv[] = { "ls", NULL };
    char *wc_argv[] = { "wc", "-l", NULL };

    if (pipe(pipefd) == -1) { perror("pipe"); exit(EXIT_FAILURE); }

    if (fork() == 0) {                      /* ---- child 1: "ls" ---- */
        dup2(pipefd[1], STDOUT_FILENO);     /* its stdout -> write end   */
        close(pipefd[0]);                   /* close BOTH originals      */
        close(pipefd[1]);
        execvp(ls_argv[0], ls_argv);        /* fd_array survives execve! */
        perror("execvp ls");
        exit(EXIT_FAILURE);
    }

    if (fork() == 0) {                      /* ---- child 2: "wc -l" ---- */
        dup2(pipefd[0], STDIN_FILENO);      /* its stdin  <- read end     */
        close(pipefd[0]);
        close(pipefd[1]);
        execvp(wc_argv[0], wc_argv);
        perror("execvp wc");
        exit(EXIT_FAILURE);
    }

    close(pipefd[0]);       /* THE PARENT MUST CLOSE BOTH ENDS.          */
    close(pipefd[1]);       /* otherwise wc never sees EOF and hangs.    */

    wait(NULL);             /* reap both children (module 08)            */
    wait(NULL);
    return 0;
}

הרצה:

$ gcc mypipe.c -o mypipe && ./mypipe
7

למה ההפניה שורדת את execve()? טבלת ה-FDs היא שדה ב-task_struct, בקרנל. execve מוחק את מרחב הזיכרון וטוען ELF חדש — אבל fd_array נשאר, ולכן ls מתחיל לרוץ כשה-FD 1 שלו כבר מחובר לצינור. זו שלישיית fork → dup2 → execve, מנגנון ההפניה של כל shell.

איך Bash מממש את זה בפועל

בתרחיש חמשת השלבים של המרצה (מודול 04) ההפניה נכנסת בין fork() ל-execve(), בתוך הבן:

הפקודה שהקלדתםמה ה-Bash מבצע (בבן, אחרי fork ולפני execve)
cmd > file fd = open("file", O_WRONLY|O_CREAT|O_TRUNC, 0644) → dup2(fd, 1) → close(fd) → execve(cmd…). (עבור >> — אותו דבר עם O_APPEND במקום O_TRUNC.)
cmd < file fd = open("file", O_RDONLY) → dup2(fd, 0) → close(fd) → execve
cmd1 | cmd2 pipe() → שני fork: בבן א׳ dup2(pipefd[1], 1), בבן ב׳ dup2(pipefd[0], 0); כל אחד סוגר את שני המקוריים ואז execve. האב סוגר את שני הקצוות וממתין.
cmd 2>&1 dup2(1, 2) — גם stderr מצביע כעת לאותו struct file כמו stdout

4. pipe מול FIFO מול socket

שלושתם ערוצי תקשורת שמנוהלים בקרנל, ולשלושתם ניגשים דרך FD. ההבדלים:

pipe (אנונימי)FIFO (Named Pipe)socket
מי יכול להשתמש רק תהליכים קרובי משפחה — שירשו את ה-FD דרך fork() כל שני תהליכים על אותה מכונה שיודעים את הנתיב גם תהליכים על מכונות שונות ברשת
שם / כתובת אין שום שם נתיב במערכת הקבצים (סוג קובץ p) כתובת IP + פורט (מודול 13)
כיוון חד-כיווני חד-כיווני (לכל פתיחה) דו-כיווני (full-duplex)
איך נוצר / מאיפה ה-FD pipe(pipefd) — שני FDs בבת אחת mkfifo() פעם אחת, ואז open() בכל צד socket() + bind/listen/accept או connect
תוחלת חיים קיים כל עוד FD אחד פתוח; נעלם לגמרי כשכולם נסגרו השם נשאר עד rm; הנתונים — כמו בצינור קיים כל עוד החיבור וה-FDs פתוחים (ואז TIME_WAIT)
הממשק read() / write() / close() — זהה לשלושתם. "הכול קובץ".

5. מלכודות למבחן

  1. שכחת close() על הקצה המיותר ⇐ תקיעה, לא שגיאה. כל עוד מישהו מחזיק את קצה הכתיבה פתוח, ה-read() נחסם לנצח במקום להחזיר 0.
  2. pipe() חייב לבוא לפני fork(). אם כל תהליך קורא ל-pipe() בעצמו נוצרו שני צינורות נפרדים ושום נתון לא יעבור.
  3. בלבול בין pipefd[0] ל-pipefd[1]. כתיבה ל-pipefd[0] תיכשל ב-EBADF: 0 = קריאה, 1 = כתיבה.
  4. הצינור חד-כיווני. שימוש באותו צינור לשני הכיוונים גורם לתהליך לקרוא את מה שכתב בעצמו; לדו-כיווני — שני צינורות או סוקט.
  5. dup2 אינו מעתיק בתים ואינו יוצר struct file חדש. רק מצביע נוסף בטבלת ה-FDs ו-f_count גדל. מכאן: offset משותף, ו-close() על עותק אחד אינו סוגר את הקובץ.
  6. סדר הפעולות סביב execve. ה-dup2 חייב אחרי fork ולפני execve, ורק בתוך הבן — ה-FDs שורדים את execve, הקוד שלכם לא.
  7. כתיבה לצינור בלי קוראים = SIGPIPE. ברירת המחדל היא מוות של הכותב, לא ערך החזרה שגוי; אם מתעלמים מהסיגנל — -1 ו-EPIPE.
