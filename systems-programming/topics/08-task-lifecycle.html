1. האינטואיציה — לתהליך יש ביוגרפיה

מודול 7 הראה מה תהליך הוא — רשומת task_struct בקרנל. כאן מחזור החיים שלה (בלשון המרצה: life cycle של task): נולדת (סעיף 2), ממתינה לתורה, רצה, נרדמת (סעיף 3), מסיימת (סעיף 4) — ומישהו צריך לאסוף אותה (סעיף 5).

מהו "task"? יחידת הביצוע של הקרנל — מה שמקצים עבורו ליבת מעבד (core) ומה שמיוצג ברשומת task_struct אחת. גם תהליך וגם thread הם task — ולכן המצבים, התור והיציאה שנלמד כאן תקפים לשניהם. ההבדל ביניהם: מודול 9.

והנקודה שמפתיעה: התהליך לא נעלם ברגע שסיים.

תור המעבד (ready queue / run queue)
ה-task-ים המוכנים לרוץ שמחכים לליבה; הקרנל בוחר מתוכם את הבא בתור.
פרוסת זמן (time slice)
הזמן המוגבל שהקרנל מקצה לתהליך על הליבה; בסופו הוא מוחזר לתור — נקודת המפגש עם Context Switch.
חסימה (blocking)
התהליך ביקש שירות שלא מוכן (דיסק, רשת, מנעול) והקרנל מרדים אותו (מודול 6).
טבלת התהליכים (process table)
אוסף כל ה-task_struct-ים במערכת; בכיתה צוירה כרשימה מקושרת דו-כיוונית (global task list). מוגבלת בגודל — ולכן זומבים מסוכנים.

מקור: task_struct.pdf · מחברת 16.8 (דיאגרמת המצבים, ready queue) · מחברת 13.8 (global task list)

2. יצירה — fork() ו-clone()

הכלל הראשון: תהליך חדש נוצר תמיד על ידי תהליך קיים — אין "לידה ספונטנית", מישהו חייב לקרוא לקריאת מערכת שיוצרת אותו. הקרנל בונה task_struct חדש ומצמיד לו PID משלו.

🎓 מהשיעור בכיתה (מהמחברת)

על הלוח נרשמה, בקו תחתון, משפחת הקריאות שיוצרות תהליך: fork(), clone(), clone3(), vfork() וכו' (בהנדאאוטים מופיעה רק fork()). הרעיון המשותף: הקצאת משאבים לתהליך החדש — חומרה (מעבד, זיכרון) ומשאבים שהקרנל מנהל — לצורך תמונת ריצה והתקדמות הריצה.

מה הבן מקבל ומה הוא לא מקבל

שאלת המבחן הקלאסית של הנושא (סעיף 7 בעמוד זה). fork() יוצרת, בלשון המרצה, שכפול מדויק (exact duplicate) של התהליך:

✔ הבן כן מקבל✘ הבן לא מקבל
עותק של מרחב הזיכרון של האב — אותו קוד, נתונים ומחסנית ברגע הפיצול. לא את אותו PID — מזהה חדש וייחודי משלו (שני תהליכים לעולם לא חולקים PID).
עותק של טבלת ה-File descriptors — אותם קבצים ו-סוקטים פתוחים, באותם מספרים. אינו מתחיל מתחילת main — ממשיך מהשורה שאחרי ה-fork, כי הוא עותק של האב ברגע הפיצול.
ערך החזרה 0 מ-fork() — כל מה שמאפשר לו לדעת שהוא הבן. לא את ה-PID של האב כערך החזרה; האב הוא שמקבל את ה-PID של הבן.

שלושת הענפים — "מי מריץ מה"

בעל-פה: fork() מחזירה 0 לבן ואת ה-PID של הבן לאב. לכן אחרי ה-fork שני תהליכים מריצים את אותו if וכל אחד נופל לענף אחר (Concurrent.pdf): 

pid_t pid = fork();

if (pid < 0) {
    /* עדיין תהליך אחד — fork נכשלה */
    perror("fork failed");
    close(client_fd);
}
else if (pid == 0) {
    /* --- Child Process Code --- */
    close(server_fd);          /* הבן לא צריך את הסוקט המאזין */
    /* ... הטיפול בלקוח ... */
    close(client_fd);
    exit(0);                   /* Terminate child process - very important! */
}
else {
    /* --- Parent Process Code --- */
    close(client_fd);          /* האב מוותר על ה-FD של הלקוח */
    while (waitpid(-1, NULL, WNOHANG) > 0);   /* איסוף זומבים */
}
pidמי אנימה אני עושה
< 0עדיין רק האב — הבן לא נוצרמטפל בשגיאה; אין תהליך שני.
== 0אני הבןעושה את עבודתי, ואז exit(0).
> 0אני האב, והערך הוא ה-PID של הבןממשיך בשלי — ואחראי לאסוף את הבן.

למה ה-exit(0) בסוף קוד הבן הוא "very important!" (כך בהערת המרצה בקוד): בלעדיו הבן ממשיך לזרום בקוד, נופל חזרה ללולאת ה-while(1) של השרת ומבצע accept בעצמו — שני שרתים שנלחמים על אותם לקוחות (מודול 14). סיום תהליך הוא פעולה מפורשת, לא משהו שקורה "כשנגמר הקוד".

ומה עם הזיכרון? הצעד השני — execve()

fork() לבדה נותנת עוד עותק של אותה תוכנית; להרצת תוכנית אחרת צריך את execve(): מחיקת מרחב הזיכרון הישן, אימות כותרת ה-ELF, הקצאת מרחב חדש, טעינת הקטעים ובניית מחסנית עם argv והסביבה (פירוט — מודול 7, מודול 4). מקומו במחזור החיים: אינו יוצר task חדש ואינו משנה PID — רק מחליף את תוכן הראש.

🎓 מהשיעור בכיתה (מהמחברת)

בכיתה זה צויר ברמת השדות — ההסבר החד ל"למה צריך גם fork וגם exec":

  • אחרי fork() — ה-*mm של ה-child task_struct מצביע אל אותה תמונת זיכרון של ה-Bash: שתי הרשומות לאותה כתובת.
  • רק אחרי execve() — ה-*mm של הבן מצביע ל-mem img חדש, של התוכנית שביקשנו להריץ, על כל הקטעים: code, data, bss, stack, heap.

ויצירת חוט — אותו סיפור, דגלים אחרים

pthread_create() קוראת מתחת לפני השטח ל-clone() ויוצרת task_struct נוסף באותו ready queue. ההבדל מ-fork הוא רק מה משותף: tgid ו-mm משותפים, ולכל חוט pid ומחסנית משלו (מודול 9).

מקור: scenario.pdf · Concurrent.pdf · task_struct.pdf · מחברת 16.8

3. מצבים ומעברי מצבים — מה יושב בשדה __state

השדה __state — "מסיכת ביטים (Bitmask) או מספר שלם המציין את מצבו הריאלי הנוכחי של התהליך במערכת ההפעלה" — נלמד במלואו ב-מודול 7. כאן מעניין מה שהעמוד הזה מוסיף: הדיאגרמה — איך task נע בין הערכים.

הדיאגרמה כפי שצוירה על הלוח

🎓 מהשיעור בכיתה (מהמחברת)

המרצה כתב על הלוח את הכותרת "מחזור החיים (life cycle) של task" ומיד אחריה "דיאגרמת מצבים — State diagram", וצייר: 

(new) ──► (ready) ⇄ (running) ──► (exit)
                       │
                    (wait)
                       ▲
                       └──── back to ready

כלומר: new → ready; ready ⇄ running בשני הכיוונים; running → exit; ומ-running ענף נוסף — wait — שממנו חוזרים ל-ready.

השמות שעל הלוח (new / ready / running / wait / exit) הם הכלליים של תורת מערכות ההפעלה; אלה שבהנדאאוט הם המימוש הלינוקסי שלהם — שתי השכבות יחד:

טבלת הערכים של __state

לדעת בעל-פה:

הערךהמשמעותהגורם האופייניאיך יוצאים ממנו
TASK_RUNNING "רץ או ממתין בתור מעבד" (לשון ההנדאאוט). נוצר ב-fork/clone, התעורר מהמתנה, או הוחזר לתור בסוף פרוסת הזמן. המתזמן מוציא אותו לריצה או מחזיר לתור; ביקש שירות חוסם — לשינה; סיים — ל-EXIT_ZOMBIE.
TASK_INTERRUPTIBLE ישן וממתין לאירוע, וניתן להעיר אותו באמצע — למשל באות. sleep(); המתנה לקלט; חוט שנחסם על mutex תפוס דרך futex. האירוע קרה (נתונים הגיעו / המנעול שוחרר / הזמן חלף) — חזרה ל-Ready.
TASK_UNINTERRUPTIBLE ישן וממתין לדיסק — שינה "עמוקה" שאי אפשר להפריע לה. read/write שירדה עד ההתקן (מודול 6). ה-I/O הסתיים; ההתקן מודיע לקרנל, והתהליך חוזר ל-Ready.
TASK_STOPPED הופסק — קפוא בנקודה שבה היה, לא רץ ולא ממתין לאירוע. הרחבה Ctrl-Z ב-מעטפת, או האותות SIGSTOP/SIGTSTP. הרחבה אות המשך (SIGCONT, בפועל fg) מחזיר אותו ל-Ready. הרחבה
EXIT_ZOMBIE סיים לרוץ — והרשומה עדיין קיימת. אין קוד לבצע, אבל ה-task_struct נשאר בטבלת התהליכים. exit(), חזרה מ-main, או סיום לא-יזום. רק כשהאב קורא ל-wait()/waitpid() — סעיף 5.

המסומן הרחבה אינו מהשקפים: המרצה מנה את TASK_STOPPED ברשימת הערכים אך לא פירט מי גורם לו.

Ready ו-Running הם אותו ערך — ההבדל אינו במצב אלא במיקום: ב-ready queue = מוכן, על ליבה = רץ; בשניהם התהליך לא ממתין לכלום.

🎓 מהשיעור בכיתה (מהמחברת)

בשיעור מאוחר יותר המרצה רשם על הלוח טבלה קטנטנה של מצבי task, וסימן מה קיים ומה לא:

  • ✗ awake
  • ✓ running
  • ✓ ready

כלומר: אין מצב ששמו "awake" — יש running ויש ready, ובדיוק את שניהם הקרנל מסמן באותו TASK_RUNNING.

מי מזיז את ה-task בין המצבים — המתזמן

את המעבר ready → running מבצע המתזמן (scheduler) — רכיב בקרנל שבוחר מה-ready queue את מי שירוץ. הנתונים שלו יושבים ב-task_struct, בשדה se: 

struct sched_entity se;   // יישות תזמון עבור מתזמן הליבה (EEVDF/CFS)

לפי ההנדאאוט se הוא "מבנה מסוג struct sched_entity, המרכז את כל נתוני הזמן, העדיפות, והזמן הווירטואלי (Virtual Runtime) שהתהליך צרך במעבד"; המתזמן נקרא EEVDF/CFS ונותן למי שקיבל עד כה הכי פחות מעבד.

🎓 מהשיעור בכיתה (מהמחברת)

ארבע נקודות שנרשמו על הלוח ואינן מופיעות בשום הנדאאוט:

  • "הקצאת מעבד (processor / core allocation) — נעשית ע"י הקרנל לבד!" — "לבד" הודגשה בקו תחתון: לתוכנית אין דרך לדרוש ליבה, היא רק נכנסת לתור.
  • הקרנל בוחר מתוך ה-ready queue לפי schedule policy, והמרצה נתן קירוב מעשי: ~FIFO ("מי שהגיע ראשון").
  • "הקרנל מקצה ליבה לפרק זמן מוגבל" — ואז אחת משתיים: נגמר הזמן → running → ready, או שנכנס ל-wait, או שסיים → running → exit.
  • ⊛ תהליך ה-idle (סומן ככוכב "חשוב"): ה-ready-q לעולם לא ריק — תמיד יש בו לפחות את ה-idle, שלא עושה כלום; קודו נרשם על הלוח כ-while(1) ∞ / Nop() ∞.

פרוסת זמן ו-Context Switch

התהליך שיורד מהליבה בסוף פרוסת הזמן היה באמצע פקודה, עם ערכים באוגרים. לכן כל מעבר כרוך ב-Context Switch: הקרנל שומר את ההקשר ב-task_struct וטוען את ההקשר של הבא.

🎓 מהשיעור בכיתה (מהמחברת)

ההסבר של המרצה, כמעט מילה במילה: "הקרנל שומר את ערכי האוגרים של המעבד הנוכחיים — ה-GPRs, ה-stack ptrs — אחרת התהליך, כשיחזור לרוץ, לא ידע איפה הוא עצר." ומי שמאחסן את זה הוא ה-task_struct עצמו. (במחברת נרשם בטעות "Content switch".) המרצה גם צייר ציר זמן צבעוני מרגע ה-power up: פסים אדומים = הקרנל, כחולים וירוקים = תהליכי user שונים — המעבד מתחלף ביניהם לאורך כל חיי המערכת.

למה בכלל צריך את מצבי השינה? כי חסימה עדיפה על המתנה סרק

תהליך שביקש בייט מהדיסק (איטי בסדרי גודל) ונשאר TASK_RUNNING "בודק אם הגיעו הנתונים" — שורף פרוסות זמן לריק. לכן הקרנל מוריד אותו מהתור לגמרי ומחזירו רק כשהאירוע קרה. ההנדאאוט על ה-Mutex מתאר את המנגנון בשלושה שלבים:

1 · ניסיון הנעילה

הספרייה מנסה לתפוס את המנעול ב-user space בפעולה אטומית (Compare-and-Swap). מנעול פנוי — נגמר הסיפור, בלי קרנל ובלי החלפת מצב.

2 · ההמתנה (Wait State)

בלשון המרצה: "החוט לא מבצע 'לולאה אינסופית' (זה היה מבזבז זמן CPU)". במקומה קריאת המערכת futex, שמעבירה את החוט למצב Sleep/Blocked, וה-Kernel מוציא אותו מתור התזמון (Scheduler) עד שהמנעול משתחרר.

3 · השחרור

pthread_mutex_unlock "מעיר" חוט ממתין, והקרנל מחזיר אותו ל-Ready — לא ל-running: כל דרך חזרה אל המעבד עוברת בתור (מודול 11).

4. מסלול היציאה — מה קורה כשתהליך מסיים

מי מוחק את התהליך, ומתי? רוב המשאבים משתחררים מיד, וחלק אחד עקשן נשאר עד שמישהו יאסוף אותו.

שתי דרכים לצאת: יזומה ולא יזומה

🎓 מהשיעור בכיתה (מהמחברת)

המרצה חילק את היציאה מ-running לשתיים, בתוך סוגר מסולסל אחד:

  • "בצורה יזומה: קריאה ל-exit" — התהליך עצמו החליט שסיים.
  • "בצורה לא יזומה: כתוצאה מ-exception" — תקלה שהמעבד זרק (חלוקה באפס, כתובת לא חוקית), והקרנל הרג את התהליך בעקבותיה.

ומשמאל לסוגר אפשרות שלישית: "תהליך אחר יכול להרוג את התהליך ע"י kill / signal" (מודול 12).

הדרךמי יזםדוגמה
יציאה יזומה התהליך עצמו exit(0) בסוף קוד הבן; חזרה מ-main.
יציאה לא יזומה הקרנל, בעקבות exception גישה לזיכרון לא חוקי, חלוקה באפס — התוכנית "קרסה".
הריגה מבחוץ תהליך אחר kill / signal — למשל Ctrl-C במסוף.

שתי הצורות של היציאה היזומה

שתיהן שקולות: התהליך מסיים ומוסר לקרנל קוד יציאה. 

exit(0);      /* מכל מקום בתוכנית, בכל עומק של קריאות */

return 0;     /* רק מתוך main — שקול ל-exit(0) */

מה קורה כשה-main מסתיים — ולמה זה נוגע גם לחוטים

מהערת המרצה בקוד ב-threads.pdf:

/* Pause for 2 seconds. This is crucial to prevent the Main Thread
   from finishing main(). If main() exits, the Kernel terminates
   the entire process and all its threads. */
sleep(2);

אם ה-Main Thread מסיים את main, הקרנל מסיים את כל התהליך ואת כל החוטים שבו — גם באמצע עבודה; בניסוח המרצה, ה-main "גורר איתו את כל התהליך לסגירה". לכן ה-sleep(2) שם (מודול 9).

הרחבה — לא מהשקפים

return מ-main אינו קופץ לקרנל: הוא חוזר לקוד ההפעלה של glibc, וזו קוראת ל-exit() עם הערך שהוחזר. ההבדל המעשי: exit() אפשר לקרוא מכל מקום, return מסיים רק מתוך main.

מה משתחרר מיד, ומה נשאר

ברגע ש-exit מתבצעת הקרנל מפרק את רוב מה שהחזיק:

המשאבמה קורה לו ביציאה
תמונת הזיכרון (mm — code/data/bss/stack/heap) משוחררת מיד. הדפים חוזרים למערכת — אין יותר קוד לבצע.
טבלת ה-File Descriptors נסגרת מיד, ולכל קובץ/סוקט פתוח יורד ה-reference count. בלשון המרצה: בלי סגירה "ה-socket לעולם לא ייסגר באמת, כי ה-reference count לעולם לא יגיע לאפס" (מודול 5, מודול 6, מודול 14).
ה-task_struct עצמו נשאר! עובר ל-EXIT_ZOMBIE ומחזיק פריט מידע אחד שעוד מעניין מישהו: קוד היציאה. ישוחרר רק כשהאב יאסוף אותו.

למה להשאיר את הרשומה? כי סיום הבן הוא מידע שהאב אולי עוד צריך — הצליח או נכשל, ובאיזה קוד. נשארת גוויה עם פתק: זה ה-זומבי.

קוד היציאה (exit status)

המוסכמה ביוניקס: 0 = הצלחה, כל ערך אחר = כישלון. בקוד המרצה — exit(0) בסוף קוד הבן, ו-exit(EXIT_FAILURE) אחרי כל perror בהקמת השרת.

הרחבה — לא מהשקפים

הערך שנכתב ל-int status אינו קוד היציאה אלא מספר ארוז: גם איך הבן הסתיים (יזום? נהרג באות?) וגם באיזה קוד. מפענחים במאקרו — WIFEXITED(status) ואז WEXITSTATUS(status). בקוד המרצה לא נדרש, כי הוא מעביר NULL.

מקור: Concurrent.pdf (exit(0), reference count) · threads.pdf (סיום main הורג את כל התהליך) · task_struct.pdf (EXIT_ZOMBIE, mm, files) · מחברת 16.8 (יזום מול לא יזום, kill/signal)

5. זומבים — ומי אוסף אותם

לנושא כותרת נפרדת בהנדאאוט ("4. Handling Zombie Processes") והוא שאלה מלאה בבחינה לדוגמה. ההגדרה, מילה במילה:

בלשון המרצה: "בלינוקס, כאשר תהליך בן מסתיים הוא נשאר בטבלת התהליכים כ-'Zombie' עד שהאב קורא ל-wait(). אם השרת רץ זמן רב בלי waitpid, טבלת התהליכים תתמלא."

שלוש הבחנות שנובעות ממנו — כולן שאלות מבחן:

  • הזומבי אינו רץ: אין לו קוד ואין לו זיכרון, ולא צורך מעבד — רשומה, לא תהליך פעיל.
  • אבל כן תופס מקום: ה-task_struct שלו בטבלת התהליכים וה-PID שלו — שניהם משאב מוגבל.
  • רק האב יכול לאסוף אותו, ורק בקריאה מפורשת. אין ניקוי אוטומטי.

למה זה מסוכן דווקא בשרת. שרת מקבילי עושה fork לכל לקוח; 50 לקוחות בשנייה בלי איסוף = 50 זומבים בשנייה. הטבלה מתמלאת ואז לא ניתן ליצור תהליכים חדשים במערכת — לא בשרת ולא בשום תוכנית אחרת (שאלה 11).

wait() מול waitpid()

שתיהן אומרות "אב, אסוף בן שסיים"; waitpid נותנת שליטה: איזה בן, האם רוצים סטטוס, והאם מוכנים להיחסם. 

#include <sys/wait.h>   /* ההנדאאוט מציין: Required for zombie process handling (waitpid) */

pid_t wait(int *status);
pid_t waitpid(pid_t pid, int *status, int options);
הארגומנטמה הוא אומרהערכים שמופיעים אצל המרצה
pid על איזה בן להמתין. -1 = כל בן שהוא (זה מה שהמרצה מעביר); מספר חיובי = בן מסוים לפי ה-PID שלו.
status מצביע ל-int שאליו ייכתב קוד היציאה הארוז. NULL = "לא מעניין אותנו סטטוס היציאה", רק שחרור הרשומה.
options דגלים שמשנים את ההתנהגות. WNOHANG = לא חוסם (Non-blocking); בלעדיו אב שאין לו בן שסיים נתקע בקריאה.

ערך ההחזרה מניע את הלולאה שבהמשך: waitpid מחזירה PID של בן שנאסף (> 0), 0 כשיש בנים אך אף אחד לא סיים, או -1 כשאין בנים.

השורה של המרצה, מילה במילה

כל מערכת ניקוי הזומבים — שורה אחת בענף האב, אחרי close(client_fd): 

/* Zombie Process Cleanup:
 * Using waitpid with WNOHANG allows the parent to clean up finished children
 * without blocking (Non-blocking).
 */
while (waitpid(-1, NULL, WNOHANG) > 0);
waitpid(-1, NULL, WNOHANG)
כל בן שהוא; בלי סטטוס; בלי להיחסם — השרת חייב לחזור מיד ל-accept, אחרת הוא הופך בפועל לשרת טורי.
> 0
תנאי הלולאה: "כל עוד באמת נאסף מישהו". כל סיבוב אוסף זומבי אחד; כשלא נשארו — הקריאה מחזירה 0 (או -1) והלולאה נעצרת.
;
גוף לולאה ריק — כל העבודה בתנאי. ניב מקובל ב-C, וגם מלכודת קריאה: קל לפספס את הנקודה-פסיק ולחשוב שהשורה הבאה היא גוף הלולאה.

למה לולאה ולא קריאה בודדת? ייתכן ששלושה בנים סיימו במקביל; קריאה בודדת אוספת אחד ומשאירה שניים. הלולאה מרוקנת את התור וחוזרת מיד, בלי לחסום.

הרחבה — לא מהשקפים

איך זומבי נראה בפועל? ב-ps הוא מופיע עם המצב Z והכיתוב <defunct>: 

$ ps -e -o pid,ppid,stat,comm
  PID  PPID STAT COMMAND
 3120     1 Ss   server
 3121  3120 Z    server <defunct>      <-- זומבי: סיים, אבל האב (3120) עוד לא אסף
 3122  3120 Z    server <defunct>

ה-PPID של שני הזומבים הוא 3120 — האב שלא קרא ל-waitpid; ברגע שיקרא, שתי השורות ייעלמו.

ומה אם האב לא רוצה לבדוק כל הזמן? כשבן מסתיים הקרנל שולח לאב SIGCHLD, והאב יכול להתקין מטפל שקורא ל-waitpid ברגע הנכון (מודול 12). המרצה בחר בפשוט — לולאת WNOHANG בכל סיבוב.

מקור: Concurrent.pdf (סעיף 4 — Handling Zombie Processes) · example-ans.pdf (שאלה 11) · task_struct.pdf (EXIT_ZOMBIE) · מחברת 16.8 (⊛ wait for child)

6. יתומים — הצד השני של המטבע

הרחבה — לא מהשקפים

הסילבוס מזכיר בשיעור 8 "orphans ו-zombies", אך בהנדאאוטים מפורט רק הזומבי; הסעיף מבוסס על ידע כללי (man wait, Stevens & Rago).

יתום = תהליך שעדיין רץ אבל האב שלו מת לפניו. בלי אב הרשומה שלו הייתה נתקעת לנצח כזומבי, ולכן הקרנל מבצע אימוץ (re-parenting): השדה parent ברשומת הבן מוסב אל init / systemd, PID 1, התהליך הראשון שנוצר באתחול, שקורא ל-wait() בלי הרף — וכל יתום שיסיים ייאסף מיד.

הקישור לחומר הנלמד: ההנדאאוט מציין ש-parent הוא "האב הנוכחי" ויכול להשתנות (ולכן נבדל מ-real_parent) — אימוץ יתומים הוא מקרה כזה.

Zombie (זומבי)Orphan (יתום)
מי מת הבן מת; האב חי. האב מת; הבן חי.
המצב ב-__state EXIT_ZOMBIE TASK_RUNNING / sleeping — רץ רגיל
צורך משאבים? לא מעבד, אבל תופס שורה בטבלה ו-PID. כן — תהליך חי לכל דבר.
מי פותר האב, ב-wait()/waitpid(). הקרנל, אוטומטית — אימוץ ל-init/systemd (PID 1).
מסוכן? כן — בהצטברות ממלא את הטבלה עד שאי אפשר ליצור תהליכים חדשים. בדרך כלל לא — יש אב מאמץ שיאסוף אותו.

משפט המפתח: זומבי = מת שלא נאסף; יתום = חי בלי אב. אם בשאלה כתוב "טבלת התהליכים מתמלאת" — זומבים, לא יתומים.

מקור: הסילבוס (שיעור 8: orphans ו-zombies) + הרחבה כללית · task_struct.pdf (real_parent מול parent)

7. שאלות בסגנון הבחינה

1-2 כלשונן בבחינה לדוגמה, עם התשובות שהמרצה סימן; 3-4 תרגול נוסף בסגנון "האם הקוד תקין? הסבירו את השגיאה" (חלק א' בבחינה).

שאלה 1

במסגרת מטלת תכנות בקורס "תכנות מערכות", התבקשו הסטודנטים לפתח concurrent Echo server. מה יקרה אם האב לא יבצע waitpid() בכלל?

  1. השרת יקרוס מיד.
  2. טבלת התהליכים תתמלא ב"זומבים" עד שלא ניתן יהיה ליצור תהליכים חדשים במערכת.
  3. הבנים ימשיכו לרוץ לנצח.
  4. ה-Kernel יסגור את השרת אוטומטית.

התשובה: 2. כל בן שסיים נשאר בטבלה כזומבי עד wait(); בשרת ארוך-טווח הם מצטברים, הטבלה מתמלאת, ואי אפשר ליצור תהליכים חדשים.

למה השאר לא: השרת לא קורס — הוא ממשיך לרוץ, וזו הסכנה (התקלה מגיעה מאוחר ובשקט). הבנים לא ממשיכים לרוץ — הם סיימו לגמרי. ולקרנל אין מנגנון שסוגר שרת "בגלל זומבים"; הוא רק מסרב ליצור תהליכים כשהטבלה מלאה.

שאלה 2

כאשר מבוצעת קריאת fork() אזי תהליך הבן:

  1. מקבל PID זהה לאב.
  2. מתחיל את הביצוע מתחילת פונקציית ה-main.
  3. מקבל עותק של מרחב הזיכרון ושל טבלת ה-File descriptors של האב.
  4. אף אחת מהתשובות הנ"ל אינה נכונה.

התשובה: 3. ההגדרה אצל המרצה — "an exact duplicate": אותה תמונת זיכרון ואותה טבלת FD ("לכל תהליך, אב ובן, יהיה עותק משלו של ה-File Descriptors").

למה השאר לא: 1 הפוכה — PID הוא מספר ייחודי. 2 היא המלכודת המרכזית: הבן אינו מתחיל מ-main אלא ממשיך מהשורה שאחרי ה-fork — הוא עותק של האב ברגע הפיצול, כולל ה-PC. ומכיוון ש-3 נכונה, "אף אחת מהנ"ל" (4) שגויה — מסיח שהמרצה שותל כמעט בכל שאלה סגורה.

שאלה 3 תרגול נוסף (לא מהשקפים)

סטודנט כתב כך את ניקוי הזומבים בענף האב. האם הקוד תקין פונקציונלית? אם לא — הסבירו את השגיאה. 

else {
    /* --- Parent Process Code --- */
    close(client_fd);
    while (waitpid(-1, NULL, 0) > 0);   /* ניקוי זומבים */
}

לא תקין. השגיאה: הארגומנט השלישי הוא 0 במקום WNOHANG.

הקוד יאסוף זומבים — אבל בצורה חוסמת: בלי WNOHANG, כשאין בן שסיים, האב נעצר בתוך waitpid, אינו חוזר ל-accept, ולקוחות חדשים אינם מתקבלים.

התוצאה: השרת מאבד את יתרונו וחוזר להתנהג כשרת טורי — הבעיה שבגללה עברנו ל-fork מלכתחילה ("אם לקוח אחד שלח הודעה גדולה לאט, כל שאר הלקוחות נחסמו").

התיקון: while (waitpid(-1, NULL, WNOHANG) > 0); — קוצר את כל מי שסיים וחוזר מיד.

שאלה 4 תרגול נוסף (לא מהשקפים)

סטודנט רצה שכל בן ידפיס מיהו האב שיצר אותו, וכתב: 

pid_t pid = fork();

if (pid == 0) {
    printf("I am the child, my parent is %d\n", pid);
    exit(0);
}

האם הפלט יהיה נכון? הסבירו.

לא. הפלט תמיד יהיה "my parent is 0".

בלבול בין שני ערכי ההחזרה: לבן מוחזר 0, ולאב ה-PID של הבן. הענף pid == 0 הוא קוד הבן, ולכן pid מכיל 0 בהגדרה.

מסקנה: ערך ההחזרה של fork הוא סימן זיהוי לענף: 0 = "אני הבן", חיובי = "אני האב וזה הבן שלי", שלילי = הקריאה נכשלה.

התיקון: getppid() למזהה האב — או להדפיס את מזהה הבן בענף האב, שם pid מחזיק אותו.

מקור: example-ans.pdf (שאלות 11-12, כולל התשובות המסומנות) · Concurrent.pdf (בסיס לשאלות 3-4)

8. מלכודות למבחן

הנקודות שהכי קל ליפול בהן. הפריטים המסומנים ב-⊛ הודגשו במיוחד בשיעור.

  • Ready ו-Running אינם שני ערכים שונים — שניהם TASK_RUNNING. "באיזה מצב נמצא תהליך שממתין בתור המעבד?" — TASK_RUNNING, לא TASK_READY שלא קיים.
  • הבן אינו מתחיל מ-main אלא ממשיך מהשורה שאחרי ה-fork — המסיח של המרצה בשאלה 12.
  • fork מחזירה 0 לבן ואת ה-PID של הבן לאב, ולא להפך; כל "מי אני?" בקוד נגזר מערך ההחזרה בלבד.
  • execve אינה יוצרת task חדש ואינה משנה PID — רק מחליפה את תמונת הזיכרון. היוצרת היא fork/clone.
  • שכחת exit(0) בסוף קוד הבן = שני שרתים (המרצה כתב שם "very important!"): הבן ממשיך ללולאת while(1) ומבצע accept בעצמו.
  • זומבי אינו "תהליך שממשיך לרוץ" — הוא סיים לגמרי, ונשארה הרשומה בטבלה. המסיח "הבנים ימשיכו לרוץ לנצח" בשאלה 11 קיים בשביל הבלבול הזה.
  • waitpid בלי WNOHANG חוסמת — בתוך לולאת accept זו שגיאה פונקציונלית: הקבילות נעלמת.
  • סיום main הורג את כל התהליך: "If main() exits, the Kernel terminates the entire process and all its threads". חוזר כשאלה גם במודול 9.
  • ⊛ הקצאת המעבד נעשית ע"י הקרנל לבד (כך הודגש בשיעור) — תוכנית לא יכולה לבקש ליבה, רק להיכנס ל-ready queue.
  • ⊛ ה-ready-q לעולם אינו ריק — תמיד יש בו את תהליך ה-idle, שקודו נרשם בשיעור כ-while(1) ∞ / Nop() ∞.
  • ⊛ Context Switch = שמירת ה-GPRs וה-stack pointers ב-task_struct — "אחרת התהליך, כשיחזור לרוץ, לא ידע איפה עצר".
  • unlock מחזיר את החוט ל-Ready, לא ל-Running — אין קיצור דרך אל המעבד.
  • זומבי מול יתום: זומבי = מת שלא נאסף (הבן מת, האב חי); יתום = חי בלי אב (האב מת, והקרנל מאמץ את הבן ל-PID 1).
  • TASK_UNINTERRUPTIBLE שמור לדיסק — המתנה למנעול או sleep() היא TASK_INTERRUPTIBLE.
