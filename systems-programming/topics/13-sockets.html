1. האינטואיציה — סוקט הוא "קצה שיחה" שהקרנל מנהל בשבילכם

עד עכשיו כל ה-I/O שלמדנו היה מקומי: פתחנו קובץ על ההתקן, קראנו ממנו וכתבנו אליו. עכשיו אנחנו רוצים משהו אחר לגמרי — שתי תוכניות שרצות על שני מחשבים שונים ומדברות זו עם זו. התוכנית שלכם לא יודעת לשלוח חבילות ברשת, לא מכירה כרטיס רשת ולא יודעת מה זה TCP. כל זה נמצא בקרנל. מה שהתוכנית כן צריכה זה ידית אחיזה אחת שדרכה תוכל לשלוח ולקבל — והידית הזו נקראת socket (סוקט).

ההגדרה של הסילבוס, מילה במילה: סוקט הוא אובייקט Kernel. כלומר: מבנה נתונים שהקרנל יוצר ומנהל בזיכרון הליבה, המייצג קצה אחד של שיחת רשת. התוכנית שלכם לעולם לא נוגעת באובייקט הזה ישירות — היא מקבלת עליו מספר, בדיוק כמו שקיבלה מספר על קובץ פתוח.

1.1 רקע קצר: איך בכלל עוברים בייטים ברשת

כדי שהמונחים בהמשך יהיו מוכרים, כדאי לרענן את מחסנית הרשת בשורה אחת. כשדפדפן שולח בקשה, הבקשה נבנית בשכבות: התוכן האפליקטיבי (למשל בקשת http עם method כמו get/post) נארז בתוך TCP packets, אלה נארזים בתוך IP packets, וכרטיס הרשת (NIC) בונה מהם frame ושולח אותו על הכבל — שכבות 2, 3 ו-4. כל זה מתרחש מתחת לסוקט. הסוקט הוא בדיוק הנקודה שבה התוכנית נכנסת למגדל הזה: היא נותנת בייטים, והקרנל עושה את כל השאר.

🎓 מהשיעור בכיתה (מהמחברת)

את הרענון הזה המרצה צייר על הלוח כשרשרת אחת: http request → TCP packets → IP packets → NIC → frame, ולצדה כתב "2, 3, 4" — מספרי השכבות שכל אחת מהן מוסיפה את העטיפה שלה (חזרה מקורס הרשתות).

1.2 שלושה מושגים שחייבים להכיר לפני הקוד

אלה מונחים שיחזרו בכל שורה של הקוד בהמשך. אם הם חדשים לכם — קראו אותם עכשיו, לא אחר כך.

כתובת IP (IP address)
מספר שמזהה מחשב (ליתר דיוק: ממשק רשת) ברשת. ב-IPv4 זהו מספר של 32 סיביות שנהוג לכתוב כארבעה מספרים, למשל 127.0.0.1. הכתובת המיוחדת הזו נקראת localhost ופירושה "המחשב הזה עצמו" — ולכן אפשר להריץ את השרת ואת הלקוח על אותו מחשב בלי רשת אמיתית בכלל.
Port (פורט)
כתובת IP מזהה מחשב — אבל על מחשב אחד רצים בו-זמנית עשרות שירותים. ה-Port הוא מספר (16 סיביות, 0–65535) שמזהה איזו תוכנית על אותו מחשב מקבלת את הנתונים. הצמד IP + Port הוא "הכתובת המלאה" של קצה שיחה. בדוגמה של המרצה הפורט הוא 8080. Port ו-Type הם, לפי הסילבוס, המאפיינים של הסוקט.
Client ו-Server (לקוח ושרת)
שני תפקידים בשיחה, לא שני סוגי מחשבים. השרת הוא הצד שמחכה: הוא תופס פורט קבוע ומצהיר "אני כאן, פנו אליי". הלקוח הוא הצד שיוזם: הוא יודע את ה-IP ואת הפורט של השרת ופונה אליו. אי-הסימטריה הזו היא בדיוק ההבדל בין רצף הקריאות של השרת לרצף של הלקוח.
🎓 מהשיעור בכיתה (מהמחברת)

המרצה פתח את השיעור ברקע ההיסטורי: הבסיס לסוקטים הוא Unix — ה-socket API נולד שם — ומיד הבהיר: "אנחנו מתמקדים בלינוקס 6.14".

הוא גם מיפה את סוגי היישומים ברשת: 3 מודלים עיקריים — client-server (זה שנלמד, ולידו הוא כתב את הדוגמה echo client server), P2P, ו-hybrid.

1.3 "הכול קובץ" — ולכן גם הסוקט הוא FD

זו הנקודה שמחברת את השיעור הזה לכל מה שלמדנו ביחידה 3. כשקראנו open() קיבלנו File Descriptor — מספר שלם קטן שהוא אינדקס בטבלת הקבצים הפתוחים של התהליך (fd_array), ובתא עצמו יושב מצביע לאובייקט struct file בזיכרון הליבה. socket() עושה בדיוק את אותו הדבר: היא יוצרת אובייקט קרנל, רושמת מצביע אליו בתא הפנוי הראשון בטבלה של התהליך, ומחזירה את מספר התא.

לכן — ורק בגלל זה — כל מה שיודעים לעשות על קובץ עובד גם על סוקט: read() קוראת ממנו, write() כותבת אליו, close() סוגרת אותו, והוא נספר באותו f_count. בקוד של המרצה בהמשך תראו את זה בעיניים: השרת קורא מהסוקט עם read() — אותה קריאת מערכת בדיוק שקראה מקובץ ב-cp.

🎓 מהשיעור בכיתה (מהמחברת)

בכיתה המרצה הגיע לסוקט מתוך מערכת הקבצים. הוא כתב על הלוח את הכותרת "סוגי הקבצים בלינוקס 6.14" ומנה: קובץ רגיל (regular), ספרייה (directory), character device, block device … ובהמשך הרשימה — socket. כלומר הסוקט אינו "חריג" שנדחף למערכת הקבצים; הוא סוג קובץ בפני עצמו, ולכן ה-VFS יודע לטפל בו כמו בכל קובץ אחר.

לצד זה הוא הדגיש את מבנה הטבלאות: לכל task יש טבלת קבצים פתוחים משלו — יש N תהליכים ⇒ יש N טבלאות fd table — והערך ש-socket() מחזירה הוא ה-index של הכניסה באותה טבלה. את הסוקט עצמו הוא תיאר בהשוואה מוכרת משפת C: "כמו FILE *" — ידית אחת שדרכה עובד כל השאר.

2. socket() — יצירת האובייקט ומאפייניו

הקריאה הראשונה בכל תוכנית רשת, בשני הצדדים כאחד, היא socket(). היא אומרת לקרנל: "צור לי אובייקט סוקט מסוג מסוים, ותן לי עליו FD". שימו לב מה אין בקריאה הזו: אין בה כתובת IP ואין בה פורט. הסוקט נולד "ריק" — קצה שיחה שעדיין לא קשור לשום מקום. קשירת הכתובת תגיע בשלב נפרד (bind()).

מה זה עושה: יוצר סוקט IPv4 מסוג TCP ושומר את ה-FD שהוחזר במשתנה server_fd; אם הקריאה נכשלה (החזירה ערך שלילי) — מדפיסים שגיאה ויוצאים. 

    // 1. Create the Socket (File Descriptor)
    // AF_INET = IPv4, SOCK_STREAM = TCP
    if ((server_fd = socket(AF_INET, SOCK_STREAM, 0)) < 0) {
        perror("socket failed");
        exit(EXIT_FAILURE);
    }
#הארגומנטמה הוא קובעהערך בקוד של המרצה
1 domain — משפחת הכתובות באיזה סוג רשת מדובר, ולכן איך נראית הכתובת. AF_INET = IPv4.
2 type — סוג התקשורת איזה "אופי" יהיה לזרימת הנתונים: זרם אמין ורציף, או הודעות בודדות. SOCK_STREAM = TCP.
3 protocol — מספר הפרוטוקול איזה פרוטוקול קונקרטי לממש בתוך אותו סוג. 0 — כלומר ברירת המחדל של הסוג שנבחר.
🎓 מהשיעור בכיתה (מהמחברת)

המרצה כתב את החתימה על הלוח ומיספר את שלושת הארגומנטים 1/2/3 מעליהם: Socket ( AF_IN , סוג התקשורת , מספר הפרוטוקול ) ;. הוא הדגיש במרקר את AF_IN… וכתב לצדו IPv4, ולידו הוסיף: אם רוצים לעבוד עם IPv6 — …IN6.

מתחת ל"סוג התקשורת" (מודגש במרקר צהוב) הוא פירט את הרשימה, כשהשורה הראשונה מודגשת:

  • SOCK_STREAM — TCP ← זה מה שנשתמש בו לאורך כל היחידה
  • SOCK_DGRAM — UDP
  • SOCK_RAW

ולארגומנט השלישי, "מספר הפרוטוקול", הוא כתב 0 — כברירת מחדל.

ערך ההחזרה — אותה מוסכמה שאתם כבר מכירים. בהצלחה socket() מחזירה FD — מספר שלם אי-שלילי, האינדקס של הכניסה בטבלת הקבצים הפתוחים של התהליך. בכישלון היא מחזירה -1, בדיוק כמו open(), ולכן הבדיקה בקוד היא < 0 ואחריה perror(). זו אותה מוסכמת בדיקת ערך ההחזרה שראינו בשיעור על טיפול בשגיאות.

🎓 מהשיעור בכיתה (מהמחברת)

המרצה שרטט על הלוח את המסלול המלא של הקריאה, מהתוכנית ועד הקרנל — אותו מסלול שראינו ביחידת קריאות המערכת, הפעם עם socket():

  • glibc — ה-standard C wrapper: הפונקציה Socket() שבתוכו מכניסה את sys call number של socket ופונה לקרנל.
  • בקרנל — sys call dispatcher, שבודק את סוג הקריאה ומפעיל את הפונקציה המתאימה.
  • socket() שבקרנל יוצרת ומשייכת inode ב-VFS (כמו בקובץ), ומגדירה את הפעולות של הקובץ לפי הסוג — כאן SOCK_STREAM, כלומר TCP.

ואת השורה האחרונה הוא סימן כסיכום: "fd = 3 — הקובץ שנפתח הוא Socket מספר 3" (0/1/2 תפוסים ב-stdin/stdout/stderr); ואם התקבל -1 — בודקים errno.

הרחבה — SOCK_STREAM מול SOCK_DGRAM, בשתי שורות (לא מהשקפים)

SOCK_STREAM (TCP) נותן זרם בייטים אמין ומסודר: מה שנשלח מגיע, בסדר הנכון, ואם חבילה אבדה — הקרנל שולח אותה שוב. SOCK_DGRAM (UDP) שולח הודעות בודדות ללא ערובה — מהיר יותר, אבל הודעה יכולה ללכת לאיבוד או להגיע בסדר אחר. כל הקוד ביחידה הזו הוא TCP, ולכן מותר לנו להתייחס לחיבור כאל צינור שאפשר לקרוא ולכתוב בו בלי לדאוג לאובדן.

3. סוקט מול קישור (connection) — ההבחנה שהמרצה מדגיש במפורש

זו הנקודה הכי מבלבלת בשיעור, והמרצה טרח לציין אותה פעמיים: פעם ברשימת ה-Notes שבסוף המסמך ("The difference between socket and accept"), ופעם בהערה שכתב בגוף הקוד עצמו. הסילבוס מנסח אותה כ"הבחנה בין סוקט לבין קישור".

התמונה הנכונה היא כזו: לשרת יש שני סוגי FD, ולא אחד.

הסוקט המאזין — server_fd ה-FD של השיחה — client_fd
מי יוצר אותו socket() — פעם אחת, בתחילת התוכנית. accept() — מחדש, בכל פעם שלקוח מתחבר.
מה תפקידו לתפוס את הפורט ולהמתין לבקשות חיבור. לא מעבירים דרכו נתונים. להעביר את הבייטים של השיחה עם לקוח אחד ספציפי.
כמה יש אחד לכל חיי התוכנית. אחד לכל לקוח — "A new FD is created specifically for this conversation".
מתי נסגר בסוף התוכנית: close(server_fd). בסוף כל שיחה: close(client_fd) — ואז חוזרים ל-accept().
🎓 מהשיעור בכיתה (מהמחברת)

בשיעור האחרון (3.9) המרצה נתן לשני הסוקטים שמות בעברית, ואת הראשון הוא הקרין כהערה מודפסת משלו — ציטוט מהמרצה, מילה במילה:

"הסוקט הזה שה-server task מקבל בעקבות הקריאה ל-socket() ישמש את ה-server task 'המקורי' כסוקט האזנה.
היינו, סוקט שידרכו הוא יקבל בקשות connect().
או 'עליו' הוא יבצע accept()"

ובכתב ידו הוא נתן את השם השני — "סוקט השירות": זה ש-accept מחזירה, אחד לכל לקוח. במילים שלו על הלוח: סוקט אחד מאזין + סוקט אחר לכל לקוח. כלומר סוקט האזנה = server_fd, סוקט השירות = client_fd.

המשפט שצריך לצאת מהסעיף: socket() יוצרת סוקט; accept() יוצרת קישור — ואיתו FD חדש ונפרד לגמרי. השרת קורא וכותב רק דרך ה-FD שהוחזר מ-accept(). קריאה מ-server_fd היא שגיאה קלאסית — ומועמדת מצוינת לשאלת "האם הקטע תקין?" במבחן.

4. רצף הקריאות — טבלת השלבים של המרצה

המרצה מספר בקוד את שלבי השרת מ-1 עד 6. הסדר עצמו הוא חומר למבחן: כל שלב מניח שהשלב שלפניו כבר קרה, ולכן היפוך של שניים מהם שובר את התוכנית (בדיוק כמו בשאלה 4 במבחן לדוגמה, בסעיף 10 למטה). קראו את הטבלה, ואז את הקוד — ותראו שהיא בדיוק אותו דבר במילים.

# הקריאה מה היא מבקשת מהקרנל ערך ההחזרה טיפול בכישלון בקוד
1 socket(AF_INET, SOCK_STREAM, 0) צור אובייקט סוקט IPv4/TCP ותן לי עליו FD. FD (אי-שלילי); -1 בשגיאה. perror("socket failed") ‏+ exit(EXIT_FAILURE)
2 setsockopt(…, SO_REUSEADDR | SO_REUSEPORT, …) קבע דגלים על הסוקט — כאן: אפשר קשירה מחדש מיידית לאותה כתובת/פורט. 0 בהצלחה; ערך שונה מאפס = שגיאה. perror("setsockopt") ‏+ exit(EXIT_FAILURE)
— מילוי struct sockaddr_in address אין כאן קריאת מערכת — זו הכנה של הכתובת בזיכרון המשתמש בלבד. — —
3 bind(server_fd, &address, …) קשור את הסוקט לכתובת ולפורט — "מהיום הפורט 8080 שלי". 0 בהצלחה; -1 בשגיאה. perror("bind failed") ‏+ exit(EXIT_FAILURE)
4 listen(server_fd, 3) העבר את הסוקט למצב פסיבי והחזק תור של עד 3 חיבורים ממתינים. 0 בהצלחה; -1 בשגיאה. perror("listen") ‏+ exit(EXIT_FAILURE)
5 accept(server_fd, …) חסום אותי עד שיגיע לקוח, ואז צור FD חדש לשיחה איתו. FD חדש של השיחה; -1 בשגיאה. perror("accept") ‏+ continue — לא יוצאים!
6 read(client_fd, buffer, BUFFER_SIZE) ואז send(client_fd, buffer, bytes_read, 0) קרא מהשיחה עד שהיא נגמרת, ושלח כל מה שהתקבל בחזרה — זהו ה-Echo. מספר הבתים שנקראו; 0 = הלקוח התנתק; שלילי = שגיאה. 0 ⇒ printf("Client disconnected\n"); שלילי ⇒ perror("read error")
7 close(client_fd), ובסוף close(server_fd) שחרר את ה-FD של השיחה שהסתיימה, ובסוף גם את הסוקט המאזין. 0 בהצלחה. בקוד אין בדיקה — ה-FD נסגר וחוזרים ל-accept().

שימו לב לאי-סימטריה בטיפול בשגיאות, כי היא מכוונת: כישלון של socket, setsockopt, bind או listen הוא קטלני — בלעדיהם אין שרת בכלל, ולכן exit(EXIT_FAILURE). לעומת זאת כישלון של accept נוגע ללקוח אחד בלבד, ולכן הקוד עושה continue וממשיך לקבל לקוחות אחרים.

מה זה Echo? השירות הפשוט ביותר שאפשר לכתוב: כל מה שהלקוח שולח — השרת מחזיר בדיוק כפי שהתקבל, בלי לשנות אף בייט. בזכות הפשטות הזו כל תשומת הלב מופנית למנגנון: רצף הקריאות, ה-FD-ים והחסימות.

5.1 כותרות, קבועים ומשתנים

5.2 שלבים 1–2 והכנת הכתובת

מה זה עושה: יוצר את הסוקט, מדליק עליו את דגלי השימוש-החוזר, וממלא את מבנה הכתובת שאליה נרצה להיקשר — משפחת הכתובות, "כל הממשקים", והפורט בסדר הבתים של הרשת. 

    // 1. Create the Socket (File Descriptor)
    // AF_INET = IPv4, SOCK_STREAM = TCP
    if ((server_fd = socket(AF_INET, SOCK_STREAM, 0)) < 0) {
        perror("socket failed");
        exit(EXIT_FAILURE);
    }


    // 2. Set Socket Options - Efficiency and Reusability
    // SO_REUSEADDR allows the server to restart immediately without waiting
    // for the kernel's TIME_WAIT state to expire.
    if (setsockopt(server_fd, SOL_SOCKET, SO_REUSEADDR | SO_REUSEPORT, &opt, sizeof(opt))) {
        perror("setsockopt");
        exit(EXIT_FAILURE);
    }

    address.sin_family = AF_INET;
    address.sin_addr.s_addr = INADDR_ANY; // Listen on all network interfaces (including localhost)

  • INADDR_ANY — להאזין על כל ממשקי הרשת (כולל localhost). כלומר: לא אכפת לנו דרך איזה כרטיס רשת יגיע הלקוח.
  • htons(PORT) — המרה ל-Network Byte Order, שהוא Big Endian. הרחבה על מה זה בכלל — בסעיף 8.
הרחבה — מה בדיוק יש בתוך struct sockaddr_in (לא מהשקפים)

המרצה משתמש במבנה בלי לפרק אותו. הנה שלושת השדות שהקוד נוגע בהם, כדי שהשורות למעלה יהיו קריאות:

השדהמה הוא מכילהערך בקוד

    if (bind(server_fd, (struct sockaddr *)&address, sizeof(address)) < 0) {

    }


    // 4. Listen - Putting the socket in passive mode to wait for connections
    // Backlog is set to 3 (the number of pending connections allowed in the queue)

backlog = 3 — מה זה אומר בדיוק? לפי ההערה בקוד: "the number of pending connections allowed in the queue" — מספר החיבורים הממתינים המותרים בתור. זה לא מספר הלקוחות שהשרת יטפל בהם בסך הכול, ולא מספר החיבורים במקביל: זה גודל התור שבו לקוחות שכבר התחברו יושבים וממתינים לכך שהשרת יקרא accept(). 5.4 שלבים 5–6: הלולאה הראשית

מה זה עושה: לולאה אינסופית שבכל סיבוב מקבלת לקוח אחד, מנהלת איתו את כל שיחת ה-Echo עד הסוף, סוגרת את ה-FD שלו — ורק אז חוזרת לקבל את הלקוח הבא. 

    while(1) {
        // 5. Accept - Block until a new client arrives.
        // A new FD is created specifically for this conversation.
        if ((client_fd = accept(server_fd, (struct sockaddr *)&address, (socklen_t*)&addrlen)) < 0) {
            perror("accept");
            continue; // Continue trying to accept other clients
        }

        printf("New client connected\n");

        // 6. Echo Loop - Read and Write
        // Efficiency: Using a single buffer and avoiding unnecessary copies.
        ssize_t bytes_read;
        while ((bytes_read = read(client_fd, buffer, BUFFER_SIZE)) > 0) {
            // Send the data back exactly as it was received
            send(client_fd, buffer, bytes_read, 0);
        }

        if (bytes_read == 0) {
            printf("Client disconnected\n");
        } else if (bytes_read < 0) {
            perror("read error");
        }

        close(client_fd); // Close the current client's FD
    }

    close(server_fd);
    return 0;
}
  • ההערה שהמרצה כתב בקוד היא הנקודה החשובה של השיעור: "A new FD is created specifically for this conversation" — ולכן מכאן והלאה כל ה-I/O הוא על client_fd, לא על server_fd.
  • תנאי הסיום של לולאת ה-Echo: הלולאה רצה כל עוד read מחזירה ערך חיובי (= נקראו בתים). מחזירה 0 ⇒ הלקוח התנתק; מחזירה ערך שלילי ⇒ שגיאה. זו התבנית הסטנדרטית לזיהוי EOF על סוקט.
  • send(client_fd, buffer, bytes_read, 0) — שולחים בדיוק bytes_read בתים, ולא את כל המאגר בן 4096 הבתים. הארגומנט האחרון הוא דגלים, וכאן 0 = בלי דגלים מיוחדים.
  • ssize_t הוא הטיפוס המוחזר מ-read: מספר שלם עם סימן, כדי שיוכל להחזיק גם את -1 של שגיאה. ו-close(server_fd) שבסוף הוא בפועל שורה שלא נגיע אליה — while(1) אינסופית — והיא שם כניקיון קוד תקין.

6. client.c — הצד השני של השיחה

המרצה מתאר את הלקוח בשורה אחת: "הלקוח שולח הודעה ומדפיס את התשובה שהתקבלה מהשרת". שימו לב למה אין בו: אין bind, אין listen ואין accept. לקוח לא תופס פורט קבוע ולא מחכה לאיש — הוא רק צריך לדעת לאן לפנות.

מה זה עושה: יוצר סוקט, ממלא את כתובת השרת (פורט + IP), וממיר את מחרוזת ה-IP לייצוג בינארי — ואז מתחבר. 

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <arpa/inet.h>
#include <sys/socket.h>

#define PORT 8080
#define BUFFER_SIZE 4096

int main() {
    int sock = 0;
    struct sockaddr_in serv_addr;
    char *hello = "Hello from client! This message should be echoed.";
    char buffer[BUFFER_SIZE] = {0};


    // 1. Create the Socket
    if ((sock = socket(AF_INET, SOCK_STREAM, 0)) < 0) {
        printf("\n Socket creation error \n");
        return -1;
    }

    serv_addr.sin_family = AF_INET;
    serv_addr.sin_port = htons(PORT);


    // 2. Convert IP address from text to binary structure
    if (inet_pton(AF_INET, "127.0.0.1", &serv_addr.sin_addr) <= 0) {
        printf("\nInvalid address/ Address not supported \n");
        return -1;
    }


    // 3. Connect to the server
    if (connect(sock, (struct sockaddr *)&serv_addr, sizeof(serv_addr)) < 0) {
        printf("\nConnection Failed \n");
        return -1;
    }
  • inet_pton (presentation to network) ממירה כתובת IP מטקסט למבנה בינארי. הכתובת כאן היא "127.0.0.1" — כלומר השרת רץ על אותו מחשב.
  • שימו לב לבדיקת הכישלון: <= 0, ולא == -1. זו חריגה מהמוסכמה הרגילה, והיא נקודה קלאסית לשאלת "האם הקטע תקין?".
  • connect היא הקריאה שיוצרת בפועל את החיבור מול השרת — ומולה, בצד השרת, משתחררת accept מהחסימה.
  • הלקוח לא כולל את <errno.h> (בשונה מהשרת) — כי הוא מדפיס הודעות עם printf במקום עם perror.
🎓 מהשיעור בכיתה (מהמחברת)

את שתי השורות האלה המרצה פירק בכיתה. על "127.0.0.1" הוא כתב: "הכתובת המיוחדת, ה-loopback, מייצגת את ה-local Host" — ולכן ה-client task וה-server task נמצאים על אותו המחשב (הפורט בדוגמה: 8080).

ואת connect() הוא תיאר מצד הקרנל — זהו למעשה תיאור לחיצת היד של TCP:

  • הקריאה ל-connect מתחילה את החיבור: ה-TCP שבקרנל שולח הודעת Syn.
  • בצד השרת הבקשה נכנסת לתור ה-Pending וממתינה שם עד שהשרת יקרא ל-accept.
  • בינתיים הקרנל מעביר את ה-client task למצב המתנה.
  • כשמגיע Syn Ack Segment, הקרנל מוציא את המשימה מההמתנה ומעביר אותה ל-Ready — ובמילים שלו: "= פעולת Context Switch".

זו הסיבה ש-connect "מצליחה" גם כשהשרת עסוק: את לחיצת היד משלים הקרנל, לא התוכנית — היא רק מכניסה את החיבור לתור.

מה זה עושה: שולח את המחרוזת, מדפיס אישור, קורא את מה שהשרת החזיר, מדפיס אותו — וסוגר. הסגירה הזו היא מה שיגרום ל-read בשרת להחזיר 0. 

    // 4. Send Data
    send(sock, hello, strlen(hello), 0);
    printf("Message sent to server\n");

    // 5. Receive Echo from server
    int valread = read(sock, buffer, BUFFER_SIZE);
    if (valread > 0) {
        printf("Echo received: %s\n", buffer);
    }


    // 6. Close the connection
    close(sock);
    return 0;
}

7. "Why is this code efficient?" — שלוש הנקודות של המרצה

המרצה מקדיש לכך סעיף נפרד עם כותרת משלו. שלוש הנקודות האלה הן בדיוק סוג החומר שהופך לשאלה פתוחה במבחן ("הסבירו מדוע…"), ולכן כדאי לדעת אותן במילים שלו.

7.1 Buffer Size Alignment — למה דווקא 4096

מה שהמרצה כותב: "הגדרנו את BUFFER_SIZE כ-4096 בתים. זהו גודל ה-Page הסטנדרטי ברוב ארכיטקטורות לינוקס. ביצוע פעולות read ו-write בכפולות של גודל העמוד ממקסם את יעילות ה-I/O מול הקרנל."

למה זה נכון, בשפה פשוטה: הקרנל מנהל זיכרון ביחידות קבועות בשם Page — 4096 בתים כל אחת. כשהמאגר שלנו הוא בדיוק בגודל עמוד, כל העברת נתונים "יושבת" על גבולות העמודים במקום לחצות אותם, ואין עבודה מיותרת של פיצול והדבקה. אותו 4096 בדיוק הופיע גם בתוכנית simple_cp — זו לא מקריות, זו תבנית שהמרצה חוזר עליה.

🎓 מהשיעור בכיתה (מהמחברת)

בשיעור האחרון (3.9) המרצה הקרין על כך הערה מודפסת משלו — ציטוט מהמרצה, מילה במילה:

"הערה:
השימוש בפונקציה setsockopt הוא בהחלט דוגמא ל-production grade code !!
וגם השימוש ב-buffer יחיד.
וגם גודל ה-buffer: 4096 בתים. שזה הגודל של page שהקרנל 'עושה' בו שימוש לצורך מימוש/ניהול ה-virtual memory. ז"א, הקרנל 'מחליף' מידע בין ה-MM וה-NVM ביחידות של דפים."

זה ההסבר המלא ל-BUFFER_SIZE 4096: 4096 הוא גודל ה-page שבו הקרנל משתמש לניהול ה-virtual memory, והוא מזיז מידע בין הזיכרון הראשי (MM) לאחסון (NVM) ביחידות של דפים — ולכן מאגר בגודל דף מתיישר בדיוק עם מה שהקרנל עושה ממילא.

7.2 Zero-Copy Logic (רעיוני)

מה שהמרצה כותב: "בקוד ה-Echo איננו מעבדים את המחרוזת. הנתונים נכנסים למאגר ונשלחים החוצה מיד. בגרסאות לינוקס מתקדמות אפשר היה להשתמש ב-splice() כדי לבצע העברה ישירה בתוך הקרנל בלי העתקה ל-User Space; אבל לדוגמה ראשונה, שימוש במאגר קבוע הוא האיזון הנכון."

מה הרעיון: בדרך הרגילה הבייטים עושים מסע כפול — קרנל ← buffer במרחב המשתמש ← בחזרה לקרנל. אם התוכנית לא עושה כלום עם הבייטים (וב-Echo היא באמת לא), אפשר עקרונית לוותר על שתי ההעתקות ולתת לקרנל להזרים אותם ישירות מקצה לקצה — זה מה ש-splice() עושה. המרצה מציין את זה כדי להראות שהוא מודע לאופציה, ובוחר במאגר הפשוט מטעמי לימוד.

7.3 SO_REUSEADDR

מה שהמרצה כותב: "תכונה קריטית במערכות לינוקס. בלי הדגל הזה, אם השרת קורס או נסגר, הפורט יישאר 'תקוע' במצב TIME_WAIT למשך כמה דקות, וימנע הפעלה מחדש מיידית."

למה אכפת לכם: זה בדיוק התסריט של פיתוח — מריצים שרת, עוצרים אותו (Ctrl+C), מתקנים שורה, מריצים שוב — ומקבלים bind failed: Address already in use. הדגל הזה הוא מה שמונע את התסכול הזה.

🎓 מהשיעור בכיתה (מהמחברת)

בכיתה המרצה ניסח את זה דרך ערך ההחזרה של bind: בלי הדגל הקרנל יכול להחזיר -1 ל-bind, כי ייתכן שהפורט עדיין "תפוס" מהחיבור הקודם — אחרי חילופי הסגירה של TCP (FIN ואז FIN Ack) הכתובת נשארת ב-TIME_WAIT. את הפתרון הוא כתב על הלוח בשני שמות, בדיוק כפי שהם מופיעים בקוד: Set sock opt ⟵ Reuse_addr ; reuse_port. וההערה על התרשים הקטן שצייר: המקום שבו זה נכנס הוא בין socket() ל-bind().

הרחבה — מה זה TIME_WAIT בעצם (לא מהשקפים)

כששני צדדים סוגרים חיבור TCP, הצד שסגר ראשון נשאר במצב TIME_WAIT למשך זמן קצוב. הסיבה: ייתכן שחבילה ישנה עדיין משוטטת ברשת, והקרנל רוצה לוודא שהיא לא תגיע ותתפרש בטעות כשייכת לחיבור חדש שנוצר על אותו צמד IP+Port. כל עוד הכתובת במצב הזה, קשירה חוזרת אליה נדחית — ומכאן ה"פורט התקוע". SO_REUSEADDR אומר לקרנל: אני יודע מה אני עושה, תן לי להיקשר בכל זאת. (הנימוק הזה הוא רקע כללי; המרצה מציין את המצב עצמו ואת התוצאה שלו.)

בסוף המסמך המרצה מוסיף סעיף בשם Notes ובו שלוש שורות בלבד. שורות קצרות כאלה, שנכתבות במפורש כ"שימו לב", הן מועמדות טבעיות לשאלות. הנה כל אחת מהן, ומה עומד מאחוריה.

8.1 "The difference between socket and accept"

זו אותה הבחנה שפירקנו בסעיף 3, והמרצה חוזר עליה כאן — וזו הדגשה, לא כפילות מקרית. בקצרה: socket() יוצרת את הסוקט המאזין; accept() יוצרת FD חדש ונפרד לשיחה. לשרת יש בו-זמנית server_fd ו-client_fd, והם אינם מתחלפים.

8.2 "Byte Order" — הפונקציה htons

htons = Host TO Network Short — "מהמארח לרשת, עבור מספר בגודל short (16 סיביות)". היא ממירה את מספר הפורט מסדר הבתים של המחשב שלכם לסדר הבתים של הרשת, שהוא Big-Endian. המרצה מציין במפורש את נושא Big-Endian מול Little-Endian ברשתות.

למה זה נחוץ בכלל: מספר בן 16 סיביות מורכב משני בתים, ומחשבים שונים שומרים אותם בזיכרון בסדר הפוך זה מזה. אם כל אחד ישלח לפי ה"מנהג" שלו, פורט 8080 יתפרש בצד השני כמספר אחר לגמרי. לכן הרשת מגדירה סדר אחד מוסכם, וכל תוכנית ממירה אליו לפני השליחה.

🎓 מהשיעור בכיתה (מהמחברת)

בכיתה המרצה פתח את ראשי התיבות מתחת לשורת הקוד עצמה: ליד htons הוא כתב "host to network", ולצד השורה serv_addr.sin_port = htons(PORT); — "הכנסת הפורט", המספר 8080, ומתחתיו "(16 ביטים)": זו הסיבה שההמרה היא דווקא htons (short = 16 סיביות) — הפורט הוא 16 ביט. את הצורך עצמו הוא הסביר דרך Big/Little endian: למכונות שונות יש סדר אחסון שונה, ולכן מבצעים המרה לאותו סדר מוסכם לפני שהמספר יוצא לרשת.

הרחבה — Big-Endian מול Little-Endian בדוגמה אחת (לא מהשקפים)

המספר 8080 הוא בהקסדצימלי 0x1F90 — כלומר שני בתים: 1F ו-90.

סדר הבתיםאיך המספר יושב בזיכרוןמי משתמש בו
Big-Endian 1F 90 — הבית ה"גדול" קודם הרשת (Network Byte Order)
Little-Endian 90 1F — הבית ה"קטן" קודם מעבדי x86/x86-64 — כלומר רוב המחשבים שתריצו עליהם

מכאן: על מחשב x86 טיפוסי, htons באמת מחליפה את שני הבתים. שכחתם אותה? הפורט שייקשר יהיה 0x901F = 36895, והלקוח שפונה ל-8080 פשוט לא ימצא אף אחד.

8.3 "Blocking vs. Non-blocking"

המרצה כותב: "בדוגמה זו read ו-accept הן קריאות חוסמות (blocking)".

מה זו קריאה חוסמת: קריאת מערכת שלא חוזרת עד שיש לה מה להחזיר. התהליך שקרא לה עובר למצב שינה (Blocked), המתזמן מוציא אותו מהמעבד ונותן את הליבה למישהו אחר, וכשהאירוע קורה — הקרנל מעיר אותו ומעביר אותו חזרה ל-Ready. זה לא "בזבוז" של מעבד; זו המתנה יעילה.

ולמה זה קריטי דווקא כאן: אלה שתי החסימות שקובעות את כל אופיו של השרת. accept חוסמת כשאין לקוח, read חוסמת כשהלקוח הנוכחי לא שלח כלום — ובזמן שהשרת חסום על read של לקוח אחד, הוא לא ב-accept, ולכן אף לקוח אחר לא מתקבל. זו בדיוק הסיבה שהשרת נקרא איטרטיבי, וזו הבעיה שהמודול הבא בא לפתור.

🎓 מהשיעור בכיתה (מהמחברת)

בכיתה המרצה נתן ל"חוסמת" נוסחה מדויקת: "כאשר השרת מבצע קריאה ל-accept — אז יתכנו 2 אפשרויות":

  1. קיים Pending Connect בתור — במקרה כזה הקריאה אינה חוסמת: היא חוזרת מיד עם FD חדש.
  2. אין pending Connect — במקרה כזה הקרנל מעביר את ה-Server task למצב המתנה, וזו הקריאה החוסמת.

כלומר accept אינה "תמיד חוסמת" — היא חוסמת רק כשהתור ריק. זו בדיוק ההשלמה של תור ה-Pending מהצד של connect (סעיף 6).

9. מריצים את זה — מה בדיוק יופיע על המסך

הדרך הבטוחה ביותר לדעת מה תוכנית תדפיס היא לקרוא את שורות ה-printf שלה. בשני הקבצים יש בסך הכול חמש הדפסות במסלול התקין, ולכן הפלט צפוי לחלוטין. פותחים שני חלונות טרמינל — אחד לשרת, אחד ללקוח.

חלון 1 — השרת
Server listening on port 8080...
New client connected
Client disconnected

שלוש השורות מגיעות משלוש נקודות מדויקות בקוד: printf("Server listening on port %d...\n", PORT) אחרי ש-listen הצליחה (ו-%d מוחלף ב-PORT, כלומר 8080); printf("New client connected\n") מיד אחרי accept שהצליחה; ו-printf("Client disconnected\n") כאשר bytes_read == 0. אחריהן השרת סוגר את client_fd, חוזר לראש הלולאה, ונשאר תלוי על accept — הסמן פשוט עומד, בלי שורה חדשה.

חלון 2 — הלקוח
Message sent to server
Echo received: Hello from client! This message should be echoed.

השורה הראשונה היא printf("Message sent to server\n") שאחרי send. השורה השנייה היא printf("Echo received: %s\n", buffer), ו-%s מוחלף בתוכן המאגר — כלומר בדיוק אותה מחרוזת שהוגדרה בתחילת הלקוח (char *hello = "Hello from client! This message should be echoed."), כי השרת החזיר אותה בלי לשנות בייט. אחר כך הלקוח סוגר ומסתיים.

שאר ההדפסות בקוד שייכות למסלולי כישלון בלבד, ולכן לא יופיעו בהרצה תקינה: בלקוח " Socket creation error ", "Invalid address/ Address not supported " ו-"Connection Failed "; בשרת perror עם הטקסטים "socket failed", "setsockopt", "bind failed", "listen", "accept" ו-"read error". (פקודות ההידור וההרצה עצמן — gcc, ./server — אינן מופיעות במסמך של המרצה; מה שמופיע כאן הוא הפלט המודפס בלבד.)

9.1 ומה קורה כשמגיע לקוח שני באמצע?

זו השאלה שמסבירה את כל השם "איטרטיבי". נניח שהשרת נמצא באמצע הטיפול בלקוח א' — כלומר הוא חסום על read(client_fd, …) — ובדיוק אז לקוח ב' מריץ connect.

  1. ה-connect של לקוח ב' מצליח: את לחיצת היד של TCP משלים הקרנל, לא התוכנית שלנו.
  2. החיבור נכנס לתור ההמתנה של הסוקט המאזין — אותו backlog בגודל 3.
  3. בשרת לא מודפס כלום: השורה printf("New client connected\n") נמצאת אחרי accept, והשרת עדיין לא הגיע אליה.
  4. לקוח ב' מצדו כבר שלח והדפיס Message sent to server — ועכשיו הוא תקוע ב-read שלו, כי אין מי שיענה לו.
  5. רק כשלקוח א' סוגר, read בשרת מחזירה 0, השרת מדפיס Client disconnected, סוגר את ה-FD שלו, חוזר ל-accept — ורק אז שולף את לקוח ב' מהתור ומדפיס עבורו New client connected.

המסקנה: לקוח אחד "מחזיק" את השרת כולו. אם לקוח א' פתח חיבור ופשוט שתק חמש דקות — כל שאר הלקוחות ממתינים חמש דקות. ואם יגיעו יותר מ-backlog חיבורים ממתינים, החיבורים הנוספים יידחו. הפתרון — תהליך נפרד לכל לקוח באמצעות fork() אחרי accept() — הוא כל התוכן של מודול 14: שרת מקבילי.

10. שאלה בסגנון הבחינה — "האם הקטע תקין פונקציונלית?"

זהו הפורמט הקבוע של חלק א' במבחן: מציגים קטע קוד שכתבו סטודנטים, ואתם צריכים לקבוע אם הוא תקין — ואם לא, להסביר במדויק מהי השגיאה ומדוע היא מתרחשת. נתחיל בשאלה האמיתית מהמבחן לדוגמה של המרצה, ואחריה שלושה תרגילים באותו סגנון.

שאלה מס' 4 — מהבחינה לדוגמה של המרצה

במסגרת מטלת תכנות בקורס "תכנות מערכות", התבקשו הסטודנטים לפתח concurrent Echo server.

לפניך קטע קוד שכתבו סטודנטים כחלק מהפתרון. עליך לקבוע האם הוא תקין פונקציונלית, ואם לא – עליך להסביר במדויק מהי השגיאה ומדוע היא מתרחשת. 

int main() {
    int server_fd, client_fd;
    struct sockaddr_in address;
    int opt = 1;
    int addrlen = sizeof(address);
    char buffer[BUFFER_SIZE];


    address.sin_family = AF_INET;
    address.sin_addr.s_addr = INADDR_ANY;
    address.sin_port = htons(PORT);

    if (bind(server_fd, (struct sockaddr *)&address, sizeof(address)) < 0) {
        perror("bind failed");
        exit(EXIT_FAILURE);
    }



    if ((server_fd = socket(AF_INET, SOCK_STREAM, 0)) < 0) {
        perror("socket failed");
        exit(EXIT_FAILURE);
    }

תשובת המרצה:

"הקטע אינו תקין מבחינה פונקציונלית. הקריאה ל-bind() מתבצעת לפני הקריאה ל-socket(). מה שאומר שערכו של המשתנה server_fd הוא 'זבל'."

מה עומד מאחורי זה:

int server_fd; הוא משתנה מקומי שהוכרז ולא אותחל. בשפת C משתנה מקומי לא מאותחל מכיל מה שהיה באותו מקום במחסנית — מספר אקראי לחלוטין. כשמעבירים אותו ל-bind, הקרנל מנסה לפרש אותו כאינדקס בטבלת הקבצים הפתוחים של התהליך, ושם אין אובייקט סוקט — יש שם או כלום, או משהו אחר לגמרי.

הסדר ההגיוני הוא בדיוק הפוך, וזה כל העניין: socket() יוצרת את האובייקט ומחזירה את ה-FD; bind() מקבלת FD קיים וקושרת אותו לכתובת. אי אפשר לקשור למשהו שעדיין לא נוצר.

ניסוח לתשובה במבחן: "אינו תקין. bind() נקראת לפני socket(), ולכן server_fd אינו מאותחל ומכיל 'זבל'; הוא אינו מתאר סוקט קיים, ולכן הקשירה תיכשל." — שתי שורות, ובדיוק בשפה של המרצה.

10.1 תרגול נוסף — שלושה קטעים באותו סגנון לא מהשקפים

שלושת הקטעים הבאים נגזרו מהקוד של המרצה על ידי שינוי שורה אחת בכל פעם. הם אינם מהמבחן לדוגמה — הם תרגול. נסו לענות לפני שאתם פותחים.

תרגיל א' — האם הקטע תקין פונקציונלית?

    address.sin_family = AF_INET;
    address.sin_addr.s_addr = INADDR_ANY;
    address.sin_port = PORT;              /* PORT == 8080 */

    if (bind(server_fd, (struct sockaddr *)&address, sizeof(address)) < 0) {
        perror("bind failed");
        exit(EXIT_FAILURE);
    }

אינו תקין. חסרה ההמרה htons.

השדה sin_port חייב להכיל את הפורט ב-Network Byte Order (Big-Endian), והקוד כותב לתוכו את המספר בסדר הבתים של המארח. על מעבד x86 טיפוסי, שהוא Little-Endian, הפורט שייקשר בפועל אינו 8080.

ומה שהופך את זה למסוכן במיוחד: bind עצמה תצליח — מבחינת הקרנל התבקש פורט חוקי לגמרי, סתם לא זה שהתכוונתם אליו. לא תודפס שום שגיאה, השרת ידפיס בשמחה Server listening on port 8080... (כי printf מדפיס את PORT, לא את מה שנקשר), ופשוט אף לקוח לא ימצא אותו. התיקון: address.sin_port = htons(PORT);

תרגיל ב' — האם הקטע תקין פונקציונלית?

        if ((client_fd = accept(server_fd, (struct sockaddr *)&address, (socklen_t*)&addrlen)) < 0) {
            perror("accept");
            continue;
        }

        printf("New client connected\n");

        ssize_t bytes_read;
        while ((bytes_read = read(server_fd, buffer, BUFFER_SIZE)) > 0) {
            send(client_fd, buffer, bytes_read, 0);
        }

אינו תקין. הקריאה נעשית מה-FD הלא נכון.

read מקבלת כאן את server_fd — הסוקט המאזין — במקום את client_fd שהוחזר זה עתה מ-accept. זו בדיוק ההבחנה שהמרצה מציין ב-Notes: "the difference between socket and accept".

הסוקט המאזין אינו מחובר לאף לקוח; הוא רק מחזיק תור של בקשות חיבור. הוא איננו זרם נתונים, ולכן הבייטים של הלקוח לעולם לא יגיעו דרכו. בפועל read תחזיר ערך שלילי, לולאת ה-Echo לא תרוץ אפילו פעם אחת, והשרת יגיע ישר לענף perror("read error") — אחרי שכבר הדפיס New client connected. הלקוח מצדו יישאר תלוי ב-read שלו עד שהשרת יסגור. התיקון: read(client_fd, buffer, BUFFER_SIZE).

תרגיל ג' — האם הקטע תקין פונקציונלית?

    while(1) {
        if ((client_fd = accept(server_fd, (struct sockaddr *)&address, (socklen_t*)&addrlen)) < 0) {
            perror("accept");
            continue;
        }

        ssize_t bytes_read;
        while ((bytes_read = read(client_fd, buffer, BUFFER_SIZE)) > 0) {
            send(client_fd, buffer, bytes_read, 0);
        }

        if (bytes_read == 0) {
            printf("Client disconnected\n");
        }
    }   /* חוזרים ל-accept ... */

אינו תקין. חסרה השורה close(client_fd); בסוף הסיבוב.

זו שגיאה ערמומית, כי בהתחלה נראה שהכול עובד: הלקוח הראשון מקבל את ה-Echo שלו, השרת מדפיס Client disconnected וחוזר ל-accept. אבל כל סיבוב של הלולאה מדליף FD אחד.

שני נזקים, ושניהם שווים נקודות: (1) טבלת ה-FD של התהליך היא משאב סופי — אחרי מספיק לקוחות היא מתמלאת ו-accept תתחיל להיכשל, כלומר השרת יפסיק לתפקד; (2) כפי שראינו בשיעור על close, המונה f_count של אובייקט ה-struct file לעולם לא יגיע לאפס, ולכן הקרנל לא באמת מפרק את החיבור ולא משחרר את משאביו. התיקון: close(client_fd); בסוף כל סיבוב — בדיוק כפי שכתוב בקוד המקורי, עם ההערה // Close the current client's FD.

11. מלכודות למבחן

  • הסדר קדוש. socket → bind → listen → accept. לא ניתן לקשור (bind) סוקט שלא נוצר, ולא ניתן לקבל (accept) על סוקט שלא הועבר למצב פסיבי (listen). כל היפוך של שניים ⇐ הקטע אינו תקין.
  • accept מחזירה FD חדש. לא את server_fd, לא את מספר הפורט של הלקוח — אלא FD נפרד לשיחה הזו. כל ה-read/send עוברים דרכו בלבד.
  • read() == 0 פירושו שהלקוח סגר (EOF), ולא "לא היו נתונים". 0 ⇒ יציאה מהלולאה; ערך שלילי ⇒ שגיאה ⇒ perror.
  • send מול write. על סוקט שניהם עובדים — הוא FD ככל FD — אבל ל-send יש ארגומנט רביעי של דגלים (בקוד: 0). המרצה משתמש ב-read לקריאה וב-send לכתיבה — שלבו את זה בזיכרון כמו שהוא כתב.
  • שולחים bytes_read בתים, לא BUFFER_SIZE. send(client_fd, buffer, bytes_read, 0) — אחרת תשלחו זבל שנשאר במאגר מהסיבוב הקודם.
  • סוגרים שני FD-ים. close(client_fd) בסוף כל שיחה, ו-close(server_fd) בסוף התוכנית. שכחת הראשון = דליפת FD-ים בכל לקוח.
  • backlog = אורך תור ההמתנה, לא מספר הלקוחות שהשרת יטפל בהם ולא מספר החיבורים במקביל. בקוד האיטרטיבי הוא 3 (בקוד המקבילי — 10).
  • SO_REUSEADDR נועד ל-TIME_WAIT, כדי לאפשר לשרת לעלות מחדש מיד. הוא לא קשור למספר הלקוחות, לא מאיץ את הרשת ולא מייתר את bind.
  • אחרי כישלון accept עושים continue, לא exit. אחרי כישלון של socket/setsockopt/bind/listen — דווקא exit(EXIT_FAILURE).
  • הבדיקה של inet_pton היא <= 0 ולא == -1 — חריגה מהמוסכמה הרגילה, וקל ליפול עליה.
