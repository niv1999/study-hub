על המבחן הזה

זהו מבחן התרגול האחרון מתוך ארבעה, והוא נכתב כסימולציה מלאה: מעורב על כל חומר הקורס, בפורמט המדויק של המרצה יצחק נודלר — 4 שאלות פתוחות (10 נק׳ כל אחת) ואחריהן 10 שאלות סגורות [= ׳אמריקאיות׳] (6 נק׳ כל אחת), במספור רציף 1–14. רמת הקושי כאן היא של המבחן האמיתי ומעלה: קטעי הקוד ארוכים יותר, המסיחים קרובים יותר לאמת, ובכל שאלה סגורה נבדק נושא אחר. אם עברתם את המבחן הזה בכבוד — אתם מוכנים.

  • יחידה 1 — ההגדרה האופרטיבית של הקרנל ומצבי הריצה.
  • יחידה 2 — מסלול קריאת המערכת, ה-wrapper של glibc ולולאת ההעתקה של cp.
  • יחידה 3 — Inodes ומספרים שמורים, f_pos ו-O_APPEND.

  • יחידה 5 — pthread_t מול TID, מנעול משותף, CAS ו-futex.
  • יחידה 6 — סדר קריאות השרת, listen/accept וניהול FDs אחרי fork.

שאלה 1 10 נק׳

מהן שתי האבסטרקציות המרכזיות שמספק הקרנל למתכנת, ומאילו מבני נתונים בנויה כל אחת מהן?

תשובת מודל:

הקרנל מספק שתי אבסטרקציות: Task — יחידת ביצוע, המיוצגת בקרנל על ידי struct task_struct; ו-File — יחידת אחסון, המיוצגת על ידי Inode (המטא-דאטה) יחד עם Data Blocks (התוכן עצמו על ה-NVM).
בזכות שתי ההפשטות האלה המתכנת עובד מול ׳מכונה מורחבת׳ ולא מול חומרה.

מה בודקים: (1) ששתי האבסטרקציות נאמרות בשמן — Task ו-File (ולא ׳תהליכים וקבצים׳ סתם); (2) ש-Task = task_struct (מוגדר ב- include/linux/sched.h), והוא מייצג גם תהליך וגם Thread — בלינוקס אין מבנה נפרד לחוט; (3) ש-File = Inode + Data Blocks, ושה-Inode מחזיק מטא-דאטה בלבד (סוג והרשאות, בעלים, גודל, חותמות זמן, מיפוי בלוקים) והבלוקים מחזיקים את התוכן. בונוס: אזכור המונח extended machine / אבסטרקציה, או ההערה שגם סוקט וגם התקן מקבלים Inode ולכן ׳הכול קובץ׳.

שאלה 2 10 נק׳

בלינוקס נהוג לומר ש״הכול קובץ״. הסבירו מה המשמעות המדויקת של האמירה הזו עבור socket: מה מחזירה הקריאה socket(AF_INET, SOCK_STREAM, 0), ומה נוצר עבורה בקרנל?

תשובת מודל:

הסוקט הוא סוג קובץ בלינוקס, בדיוק כמו קובץ רגיל, תיקייה או התקן. לכן הקרנל יוצר עבורו Inode בשכבת ה-VFS, וה-VFS מגדיר לו את סט הפעולות המתאים לסוגו.
הקריאה socket() מחזירה File Descriptor — אינדקס בטבלת הקבצים הפתוחים של ה-task — או -1 בכישלון, ואז errno.
בזכות זה אפשר לקרוא ולכתוב לסוקט באותן קריאות מערכת עצמן: read, write/send ו-close.

מה בודקים: (1) שנאמר במפורש שסוקט הוא סוג קובץ ברשימת סוגי הקבצים (רגיל / תיקייה / character device / block device / socket); (2) שנאמר שנוצר לו Inode ב-VFS — זה ההסבר המדויק ל׳הכול קובץ׳, ולא רק אמירה כללית; (3) שערך ההחזרה מזוהה כ-FD (אינדקס בטבלת הקבצים הפתוחים), עם מוסכמת ה--1 לכישלון. בונוס: שאותן קריאות מערכת גנריות עובדות עליו, ושהארגומנטים הם משפחת כתובות (AF_INET = IPv4), סוג תקשורת (SOCK_STREAM = TCP) ומספר פרוטוקול (0 = ברירת מחדל).

שאלה 3 10 נק׳

במסגרת מטלת תכנות בקורס ״תכנות מערכות״, התבקשו הסטודנטים לפתח תוכנית בשם my_copy.c להעתקת קבצים בלינוקס, תוך שימוש אך ורק ב-System Calls (open, read, write, close).

לפניך לולאת ההעתקה שכתבו סטודנטים. שני ה-FD נפתחו קודם לכן בהצלחה, ו-BUFFER_SIZE מוגדר כ-4096.
עליך לקבוע האם הקטע תקין פונקציונלית, ואם לא — עליך להסביר במדויק מהי השגיאה ומדוע היא מתרחשת. 

    ssize_t bytes_read;

    while ((bytes_read = read(src_fd, buffer, BUFFER_SIZE)) > 0) {

        if (write(dest_fd, buffer, BUFFER_SIZE) != BUFFER_SIZE) {
            perror("Error writing data");
            close(src_fd);
            close(dest_fd);
            exit(EXIT_FAILURE);
        }
    }

תשובת מודל:

הקטע אינו תקין מבחינה פונקציונלית.
הכתיבה מבצעת תמיד write של BUFFER_SIZE בייטים במקום של bytes_read — מספר הבייטים שנקראו בפועל.
read() רשאית להחזיר פחות ממה שביקשנו (Partial I/O), ובוודאי בקריאה האחרונה של הקובץ. לכן בהעתקה האחרונה נכתבים גם ׳שאריות׳ מהקריאה הקודמת שנשארו בבאפר: קובץ היעד יוצא גדול מהמקור וזנבו מזוהם.
הבאג מתחבא: הוא לא יתגלה כלל אם גודל הקובץ הוא כפולה מדויקת של 4096.

מה בודקים: (1) שנקבע במפורש שהקטע אינו תקין; (2) שהשגיאה מזוהה במדויק — הארגומנט השלישי של write חייב להיות bytes_read, לא BUFFER_SIZE; (3) שההסבר מדוע נכון — read מחזירה את מספר הבייטים שנקראו בפועל (Partial I/O), ובקריאה האחרונה זהו לרוב פחות מ-4096, ולכן נכתבים בייטים ישנים מהבאפר. בונוס: אזכור התוצאה המדידה — קובץ היעד גדול מהמקור וזנבו שגוי; ושהבאג ׳נעלם׳ כשגודל הקובץ הוא כפולה של BUFFER_SIZE. אין ניקוד על ׳זה עובד׳ — זו מלכודת.

שאלה 4 10 נק׳

במסגרת מטלת תכנות בקורס ״תכנות מערכות״, התבקשו הסטודנטים לתקן את דוגמת חשבון הבנק מרובת החוטים כך שלא ייווצר race condition על שדה ה-balance.

לפניך הפתרון שהגישו הסטודנטים. main יוצרת ארבעה חוטים (שניים מפקידים ושניים מושכים) ומבצעת עליהם pthread_join.
עליך לקבוע האם הקטע תקין פונקציונלית, ואם לא — עליך להסביר במדויק מהי השגיאה ומדוע היא מתרחשת. 

typedef struct { double balance; } BankAccount;

BankAccount my_account = { 1000.0 };          /* shared by all threads */

void* deposit_service(void* arg)
{
    pthread_mutex_t lock;
    pthread_mutex_init(&lock, NULL);

    for (int i = 0; i < 100000; i++) {

        pthread_mutex_lock(&lock);

        double temp = my_account.balance;
        temp += 10.0;
        my_account.balance = temp;

        pthread_mutex_unlock(&lock);
    }

    pthread_mutex_destroy(&lock);
    return NULL;
}

תשובת מודל:

הקטע אינו תקין מבחינה פונקציונלית.
המשתנה lock הוא משתנה מקומי, ולכן הוא יושב על ה-Stack של החוט — ולכל חוט Stack משלו.
התוצאה: כל אחד מארבעת החוטים נועל מנעול אחר לגמרי, אף חוט אינו חוסם אף אחד, ואין כאן Mutual Exclusion בכלל.
לכן ה-race condition על balance נשאר בדיוק כפי שהיה: Context Switch בין קריאת ה-temp לבין העדכון גורם לדריסה, והתוצאה שונה בכל הרצה.
התיקון: המנעול חייב להיות משותף — משתנה גלובלי (או שדה בתוך BankAccount) שמאותחל פעם אחת, למשל עם PTHREAD_MUTEX_INITIALIZER.

מה בודקים: (1) שנקבע במפורש שהקטע אינו תקין; (2) שהשגיאה מזוהה במדויק — המנעול הוא משתנה מקומי על ה-Stack של כל חוט, ולכן ישנם ארבעה מנעולים נפרדים ולא אחד משותף; (3) שההסבר מדוע נכון — חוטים חולקים code / data / bss / heap, אבל ל-Stack של כל חוט אין שיתוף; מנעול חייב לחיות בזיכרון המשותף כדי לחסום. בונוס: אמירה שהקוד ׳עובר קומפילציה ורץ׳ ופשוט מחזיר יתרות שונות בכל הרצה (Non-determinism), והצעת התיקון (מנעול גלובלי / שדה במבנה המשותף). שימו לב: זו לא שאלת deadlock — כאן דווקא אף אחד לא נחסם, וזו הבעיה.

המבחן הזה נוגע בכל יחידות הקורס. אם טעיתם בשאלה — כאן נמצא העמוד שאליו כדאי לחזור, לפני שאתם ניגשים לסבב הבא.

מה לומדים מהמבחן הזה

  1. הבאג כמעט תמיד נמצא ב״כמה״ ולא ב״מה״. בשאלה 3 הקריאות והכתיבות נכונות — רק הארגומנט השלישי שגוי. read מחזירה את מספר הבייטים שנקראו בפועל, ולכן write חייבת לקבל bytes_read. זו בדיוק המשמעות של Partial I/O.
  2. מנעול שאינו משותף אינו מנעול. בשאלה 4 כל השורות נכונות — lock, unlock, destroy — אבל המנעול הוא משתנה מקומי, ולכל חוט Stack משלו. לפני שאתם בודקים איך נועלים, בדקו איפה יושב המשתנה: data / bss / heap משותפים, Stack לא.
  3. דעו מי עושה מה — הספרייה או הקרנל. זו החלוקה שחוזרת בשאלות 6, 11 ו-12: ה-wrapper של glibc ו-pthread_t חיים במרחב המשתמש; ה-syscall dispatcher, TID, task_struct ותור הממתינים של ה-futex חיים בקרנל. מסיח שמחליף בין השניים נראה נכון לגמרי.
  4. מיקום הקריאה בקובץ שייך לפתיחה, לא לקובץ. f_pos שמור ב-struct file — אובייקט לכל open() — ולא ב-Inode המשותף. לכן שתי פתיחות מתקדמות בנפרד, ולכן O_APPEND הכרחי כשכמה כותבים לאותו קובץ.
  5. fork מעתיק, execve מחליף — והקבצים שורדים את שניהם. שאלות 9 ו-14 נופלות על זה: execve מוחקת את ה-memory image אבל לא את טבלת ה-FDs; ו-fork מעתיק את הטבלה תוך העלאת ה-Reference Count, ולכן שני התהליכים חייבים לסגור.
  6. לא לפסול את ״אף אחת מהתשובות הנ״ל״. בשאלה 5 היא מסיח ובשאלה 7 היא התשובה הנכונה — בדיוק כמו במבחן לדוגמה של המרצה. בדקו כל אפשרות לגופה.

מה עוד לחזור עליו לפני המבחן

סיימתם את ארבעת מבחני התרגול. זו רשימת החזרה האחרונה — הדברים שהמרצה הדגיש שוב ושוב ושחוזרים כמעט בכל גרסה של הבחינה:

  1. סדר קריאות המערכת של השרת בעל פה. socket → setsockopt → bind → listen → accept → read/send → close; בצד הלקוח socket → inet_pton → connect → send → read → close. ולזכור: accept חוסמת, backlog = 3 באיטרטיבי ו-10 בקונקורנטי, ובלי SO_REUSEADDR ה-bind נכשל בגלל TIME_WAIT.
  2. שתי מוסכמות ערכי ההחזרה — ולא לבלבל ביניהן. קריאת מערכת שנכשלת מחזירה -1 ומעדכנת errno (perror מדפיסה ל-stderr); פונקציות pthread_* מחזירות 0 בהצלחה וקוד שגיאה חיובי בכישלון. ולזכור: read מחזירה 0 ב-EOF, לא -1.
  3. המספרים. סקטור = 512 בייט; בלוק = 8 × 512 = 4096; Disk Inode = 256 בייט; inode 2 = תיקיית השורש (ו-0, 1 אינם בשימוש); fd 3 = ה-FD הפנוי הראשון; 13 מצביעים ב-Inode (10 direct + single/double/triple indirect); uid של root = 0.
  4. המסלול המלא של הרצת תוכנית. .c → ELF → bash מפרקת לטוקנים ובודקת אם הפקודה פנימית → fork() (נוצר task_struct; 0 לבן, PID לאב) → execve() (מוחק את ה-memory image ובונה חדש; הקבצים הפתוחים שורדים) → ready queue → scheduler → Context Switch → main().
  5. שדות ה-task_struct ומה כל אחד מחזיק: __state, pid מול tgid (שווים ⇐ main thread), mm (מרחב הזיכרון הווירטואלי), fs (CWD ו-root), files (טבלת ה-FD), se (יישות התזמון) — ובלינוקס אין מבנה נפרד ל-thread.
  6. שלוש הסכנות של תכנות מקבילי ושישה מנגנוני הסנכרון. race condition / deadlock (קיפאון) / starvation (הרעבה); והמנגנונים: mutex, semaphore, conditional variable, rw lock, spin lock, barrier. ולזכור ש-counter++ הוא שלוש הוראות מכונה (Read / Modify / Write).
  7. מה משותף ומה פרטי בחוטים. משותפים: code, data, bss, heap, pid/tgid, קבצים פתוחים, מנעולים וסוקטים. פרטיים לכל חוט: Stack, PC, אוגרים ו-task_struct משלו. ולזכור: אם main() מסתיימת — הקרנל הורג את כל התהליך ואת כל חוטיו.
  8. ענו קצר ומדויק — וחלקו את הזמן. 14 שאלות ב-150 דקות: בערך 15 דקות לכל שאלה פתוחה ו-8 דקות לכל סגורה. תשובות המרצה עצמו הן 2–3 שורות עם המונחים הנכונים; פסקה שמסתובבת סביב העניין לא מקבלת יותר נקודות, ורק גוזלת זמן משאלות אחרות.
