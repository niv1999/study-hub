0. האינטואיציה — מחזור החיים של קובץ

בפרק הקודם ראינו את הארכיטקטורה: ה-File Descriptor הוא אינדקס בטבלת התהליך, שמוביל ל-struct file, שמוביל ל-Inode. עכשיו נראה את התנועה: מה בדיוק קורה כשקוראים לכל אחת מארבע קריאות המערכת שמרכיבות את חיי הקובץ — open(), read(), write(), close() — צעד אחר צעד, כפי שזה ממומש ב-Linux Kernel 6.14.

המרצה מלווה כל קריאה בשני חלקים: הממשק (חתימה, פרמטרים, ערכי חזרה) — מה שאתם כותבים ב-C — והאלגוריתם בקרנל — מה שקורה מאחורי הקלעים מרגע פקודת ה-syscall ועד החזרה למרחב המשתמש. שני החלקים הם חומר למבחן.

1. open() — לפתוח (או ליצור) קובץ

החתימה המלאה

int open(const char *pathname, int flags, mode_t mode);

שלושת הארגומנטים

ארגומנטבדוגמהתפקיד
pathname "/home/Itzhak/lecture01" מחרוזת המצביעה על הנתיב שבו ממוקם הקובץ (או שבו ייווצר). מכיוון שהיא מתחילה ב-'/', הקרנל מזהה מיד נתיב אבסולוטי (Absolute Path): ב-Path Resolution הוא מתעלם מתיקיית העבודה הנוכחית (CWD) ומתחיל את הסריקה ישירות מתיקיית השורש הגלובלית (root dentry).
flags O_RDWR | O_CREAT משתנה ביטים (Bitmask) המכיל מספר הגדרות יחד באמצעות פעולת Bitwise OR (|): O_RDWR = פתיחה למצב שמאפשר גם קריאה וגם כתיבה; O_CREAT = אם הקובץ אינו קיים פיזית — יש ליצור אותו אוטומטית (לייצר Inode חדש ולהוסיף רשומה לתיקיית היעד). אם הקובץ כבר קיים — הדגל מתעלם באדיבות והקובץ נפתח רגיל.
mode 0644 מוגדר אך ורק כאשר משתמשים ב-O_CREAT, ומציין את הרשאות האבטחה הראשוניות של הקובץ החדש אם הוא נוצר כעת. הערך כפוף תמיד לסינון מסכת ההרשאות של התהליך — ה-umask.

ערכי חזרה

  • הצלחה: מספר שלם אי-שלילי — ה-fd. הקרנל בוחר את המקום הפנוי הראשון בטבלת תיאורי הקבצים של התהליך (למשל 3, כי 0,1,2 תפוסים).
  • כישלון: -1 — ואז בודקים fd == -1 ומדפיסים את השגיאה עם perror().

הקוד מהחוברת

#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>

int main() {
    int fd;

    fd = open("/home/Itzhak/lecture01", O_RDWR | O_CREAT, 0644);

    if (fd == -1) {
        perror("Error opening/creating file");
        return 1;
    }

    close(fd);
    return 0;
}

מה קורה בקרנל (Linux Kernel 6.14) מרגע ביצוע הפקודה?

  1. מעבר מ-User ל-Kernel Mode: קריאת ה-open מפעילה פקודת אסמבלי (syscall), והמעבד עובר מ-Ring 3 ל-Ring 0. בגרעין מודרני כמו 6.14 הקריאה מתועלת לפונקציית הליבה הראשית sys_openat (הפרמטר הראשון המרומז הוא AT_FDCWD, אך מתעלמים ממנו כי הנתיב אבסולוטי).
  2. העתקת הנתיב ממרחב המשתמש: הקרנל מעתיק בבטחה את מחרוזת הנתיב מזיכרון המשתמש אל זיכרון הקרנל באמצעות פונקציית העתקה ייעודית — strncpy_from_user.
  3. Path Resolution — איתור או יצירת Inode: הקרנל סורק את עץ הספריות החל מהשורש (/), עובר דרך home ואז Itzhak, ומגיע לשם הסופי lecture01. אם הקובץ קיים — הוא מאתר את ה-Inode שלו בטבלת ה-Inodes. אם הקובץ אינו קיים (וצוין O_CREAT) — הקרנל מקצה Inode חדש, רושם אותו ב-Inode Bitmap, יוצר Directory Entry חדש תחת התיקייה Itzhak, ומחיל את ההרשאות שהועברו ב-mode (בכפוף ל-umask) על שדה ה-i_mode של ה-Inode החדש.
  4. יצירת אובייקט קובץ פתוח (struct file): הקרנל מקצה מבנה נתונים דינמי בשם struct file, השומר את מצב הפתיחה הנוכחי של התהליך — כגון ה-File Offset שמתחיל כרגע ב-0, והדגלים שנבחרו כמו O_RDWR.
  5. הקצאת File Descriptor: הקרנל סורק את טבלת תיאורי הקבצים של התהליך השמורה ב-current->files (מבנה struct files_struct), מוצא את המקום הפנוי הראשון (למשל אינדקס 3), ורושם בתא מצביע אל ה-struct file שיצר.
  6. חזרה למרחב המשתמש: הקרנל מחזיר את המספר 3 אל פונקציית ה-open במרחב המשתמש. מספר זה (fd) הוא המפתח שבו ישתמש התהליך בכל פעם שירצה לקרוא או לכתוב לקובץ.

מלכודות למבחן: (1) הארגומנט mode רלוונטי רק בשילוב O_CREAT; (2) אם הקובץ כבר קיים — O_CREAT פשוט מתעלם והקובץ נפתח רגיל; (3) נתיב שמתחיל ב-'/' גורם לקרנל להתעלם לגמרי מה-CWD; (4) mode תמיד עובר סינון של ה-umask — ההרשאות בפועל אינן בהכרח מה שכתבתם.

מקור: open.pdf (עמ' 1–3)

2. read() — שמונה שלבים מה-fd ועד הבאפר

read() היא הפעולה הבסיסית שבאמצעותה תוכנית במרחב המשתמש שואבת נתונים מקובץ פתוח. ב-Linux Kernel 6.14 היא מתבצעת דרך שכבת ה-VFS, עושה שימוש נרחב במטמון הזיכרון (Page Cache) של הקרנל, ומנהלת את התקשורת עם התקני ה-SSD במידת הצורך.

חתימה ופרמטרים

ssize_t read(int fd, void *buf, size_t count);
פרמטרטיפוסתפקיד
fdint תיאור הקובץ שקיבלנו מ-open — האינדקס בטבלת תיאורי הקבצים של התהליך.
bufvoid * באפר במרחב המשתמש שאליו הקרנל יעתיק את הנתונים.
countsize_t מספר הבייטים המקסימלי לקריאה.

ערכי חזרה ושגיאות

  • מספר חיובי — מספר הבייטים שנקראו בפועל.
  • 0 — הגענו לסוף הקובץ (EOF).
  • EBADF — fd לא תקין / לא פתוח, או קובץ שנפתח אך ורק לכתיבה (O_WRONLY) — אין אישור קריאה ב-f_mode.
  • EFAULT — כתובת הבאפר של המשתמש פגומה או לא חוקית; copy_to_user תופסת את החריגה מבלי לגרום לקריסת מערכת ההפעלה.

האלגוריתם בקרנל — שלב אחר שלב

  1. כניסה לקרנל ואיתור אובייקט הקובץ (fdget / sys_read): פקודת ה-syscall מעבירה את המעבד מ-Ring 3 ל-Ring 0 והבקשה מגיעה ל-sys_read. הקרנל פונה לטבלת תיאורי הקבצים של התהליך (current->files) ושולף את המצביע ל-struct file * התואם. fd לא תקין → עצירה מיידית עם EBADF.
  2. בדיקת תקינות והרשאות קריאה (f_mode): הקרנל מוודא שהקובץ נפתח במקור עם דגל קריאה חוקי (O_RDONLY או O_RDWR). קובץ שנפתח רק לכתיבה — הפעולה נחסמת מיד עם EBADF.
  3. הפעלת ממשק ה-VFS (vfs_read / read_iter): פונקציית התווך הגנרית vfs_read ניגשת למערך הפעולות של מערכת הקבצים (file->f_op->read_iter); עבור ext4 הקריאה מנותבת למתודה הייעודית ext4_file_read_iter.
  4. בדיקת מטמון הזיכרון (Page Cache Lookup — Hit vs. Miss): הקרנל מחשב איזה עמוד זיכרון (Page, בגודל 4KB) מכיל את הבייטים המבוקשים לפי המיקום הנוכחי בקובץ (f_pos) ובודק האם העמוד כבר קיים ב-RAM. Cache Hit — הנתונים כבר בזיכרון: מדלגים לחלוטין על הדיסק, מהירות אדירה. Cache Miss — חייבים לפנות ל-SSD.
  5. קריאת הבלוקים מהדיסק (רק ב-Cache Miss): דרייבר מערכת הקבצים מתרגם את הדרישה הלוגית לבלוקים פיזיים (בעזרת עץ ה-Extents של ה-Inode); הקרנל מייצר אובייקט bio ושולח בקשת I/O דרך שכבת הבלוקים (blk-mq) ובקר ה-NVMe; הבלוקים נקראים מה-SSD אל תוך ה-Page Cache — ורק אחרי שהנתונים ב-RAM ממשיכים הלאה.
  6. העתקה למרחב המשתמש (copy_to_user): תהליך המשתמש אינו יכול לגשת לזיכרון הליבה מסיבות אבטחה, ולכן הקרנל מפעיל את פונקציית ההעברה המוגנת copy_to_user, שמעתיקה את הבייטים מבאפר הקרנל אל הבאפר (buf) של התהליך.
  7. עדכון מיקום הקובץ (f_pos): מצביע ה-File Offset, השמור ב-struct file, גדל בדיוק במספר הבייטים שנקראו בפועל — כך שהקריאה הבאה תמשיך לינארית מאותה נקודה.
  8. סיום וחזרה: שחרור הנעילות מדפי הזיכרון, עדכון חותמת זמן קריאה (atime ב-Inode אם נדרש), חזרה ל-Ring 3 והחזרת מספר הבייטים שנקראו.

f_pos הוא פר-פתיחה, לא פר-קובץ: מכיוון ש-f_pos שמור באובייקט ה-struct file של פתיחת הקובץ הספציפית, שני תהליכים שונים שפתחו את אותו קובץ מחזיקים מצביעי f_pos נפרדים ועצמאיים לחלוטין.

מלכודת למבחן: read() שמחזירה 0 היא לא שגיאה — זה סוף הקובץ (EOF). וזכרו מהחוברת של cp: הקרנל מרדים את התהליך עד שהדיסק/מערכת הקבצים מספקים את הנתונים.

מקור: read.pdf (עמ' 1–3)

3. write() — עשרה שלבים והסוד של ה-Buffered I/O

write() מעבירה נתונים מהתהליך אל קובץ פתוח — אבל הנקודה החשובה ביותר היא שב-Linux Kernel 6.14 הכתיבה מנוהלת לרוב במנגנון Buffered I/O (קלט/פלט ממוקד מטמון): הנתונים נכתבים תחילה אל ה-Page Cache ב-RAM ורק בהמשך מסונכרנים אל התקן ה-SSD הפיזי — אלא אם הוגדרו דגלי סנכרון מיידי.

חתימה ופרמטרים

ssize_t write(int fd, const void *buf, size_t count);
פרמטרטיפוסתפקיד
fdint תיאור הקובץ שאליו כותבים.
bufconst void * באפר המקור בתהליך. שימו לב: const — בניגוד ל-read, שבה void * (הקרנל רק קורא מהבאפר שלנו, לא משנה אותו).
countsize_t מספר הבייטים לכתיבה.

ערכי חזרה ושגיאות

  • מספר חיובי — מספר הבייטים שנכתבו בפועל (תואם ל-count).
  • EBADF — fd לא תקין, או קובץ שנפתח אך ורק לקריאה (O_RDONLY) — הכתיבה נחסמת בבדיקת f_mode.

האלגוריתם בקרנל — שלב אחר שלב

  1. כניסה לקרנל ואיתור אובייקט הקובץ (fdget / sys_write): מעבר מ-Ring 3 ל-Ring 0; הבקשה מגיעה ל-sys_write (או ksys_write). הקרנל שולף מ-current->files את המצביע ל-struct file *; fd לא תקין → EBADF.
  2. בדיקת הרשאות כתיבה (f_mode): נדרש דגל כתיבה חוקי מהפתיחה (O_WRONLY או O_RDWR).
  3. מצבי כתיבה מיוחדים ונעילות (Locks & O_APPEND): אם הקובץ נפתח עם O_APPEND — לפני כל כתיבה הקרנל מעדכן אוטומטית את f_pos להצביע בדיוק על סופו הנוכחי של הקובץ (ערך ה-i_size של ה-Inode), כדי שהנתונים החדשים יתווספו תמיד לסוף בלי לדרוס מידע קיים — קריטי בסביבה מרובת-תהליכים. במקביל מופעלים מנעולים ברמת ה-In-Core Inode (כגון i_rwsem) כדי למנוע מצבי תחרות (Race Conditions) שבהם שני תהליכים כותבים לאותו קובץ בדיוק באותה מיקרו-שנייה.
  4. הפעלת ה-VFS (vfs_write / ext4_file_write_iter): הבקשה מנותבת דרך שכבת ההפשטה למתודת ה-write_iter של מערכת הקבצים — ב-ext4 זו ext4_file_write_iter, שמנהלת את הכתיבה לעץ ה-Extents.
  5. הקצאת דפי זיכרון + Read-Modify-Write: זהו הלב הפועם של כתיבה ממוקדת מטמון. הקרנל מחשב איזה עמוד 4KB תואם למיקום הכתיבה (f_pos) ובודק אם הוא במטמון. אם העמוד אינו בזיכרון (Cache Miss) והכתיבה מעדכנת חלק בלבד מהבלוק (Partial Block Write — למשל 100 בייט באמצע בלוק של 4KB), הקרנל נאלץ לבצע Read-Modify-Write: לקרוא תחילה את הבלוק הפיזי מה-SSD אל ה-RAM, כדי ששאר חלקי הבלוק לא יושחתו. אם מדובר בכתיבה מלאה של עמוד שלם (4KB) — פשוט מקצים עמוד ריק ב-RAM בלי לקרוא מהדיסק.
  6. העתקת הנתונים לקרנל (copy_from_user) וסימון Dirty: הפונקציה המוגנת copy_from_user מעתיקה מבאפר התהליך אל דפי ה-Page Cache (הכיוון ההפוך מ-copy_to_user של read). מיד לאחר מכן הדף מסומן בדגל Dirty Page (SetPageDirty) — סימון שהנתונים ב-RAM שונים כעת ממה שעל הדיסק ודורשים סינכרון עתידי.
  7. עדכון המטא-דאטה (f_pos & i_size): קידום f_pos בדיוק במספר הבייטים שנכתבו; אם הקובץ גדל מעבר לגודלו הקודם — עדכון שדה i_size ב-In-Core Inode; וסימון ה-Inode עצמו כמלוכלך (I_DIRTY_DATASYNC).
  8. הקצאת בלוקים פיזיים (Extents & Block Allocation): אם הקובץ גדל מעבר לבלוקים שהוקצו לו, ext4 משתמשת לרוב ב-Delayed Allocation (הקצאה דחויה) — דחיית ההקצאה הפיזית על ה-SSD כדי לייעל אותה ולמנוע פיצול (Fragmentation), בעוד הנתונים שמורים בבטחה ב-Page Cache. כשההקצאה מתבצעת לבסוף, עץ ה-Extents ב-Inode מתעדכן ומצביע על מתחמי הבלוקים החדשים.
  9. רישום ביומן (Journaling / Writeback): להבטחת אמינות מערכת הקבצים בקריסה, ext4 רושמת את שינויי המטא-דאטה ליומן הטרנזקציות המנוהל על ידי תת-המערכת jbd2. הנתונים עצמם שוהים בינתיים ב-Page Cache, וייכתבו פיזית ל-SSD על ידי תהליכי רקע של הקרנל (חוטי ה-Writeback / flusher threads) — או מיידית, אם הקובץ נפתח עם דגלי סנכרון מחמירים (O_SYNC או O_DSYNC).
  10. סיום וחזרה: שחרור הנעילות מעל ה-Inode, חזרה ל-Ring 3 והחזרת מספר הבייטים שנכתבו בפועל.

אז מתי הדיסק באמת מתעדכן?

שני מנגנוני הגנה בשלב 3 — אל תערבבו: O_APPEND פותר את בעיית ה"לאן כותבים" (תמיד לסוף הקובץ, לפי i_size), ואילו הנעילה i_rwsem פותרת את בעיית ה"מי כותב עכשיו" — מניעת Race Condition בין שני תהליכים שכותבים בו-זמנית. שניהם פועלים יחד בסביבה מרובת-תהליכים.

מקור: write.pdf (עמ' 1–4)

4. close() — הרבה יותר מ"סגירת חלון"

close() מודיעה לקרנל שהתהליך סיים לעבוד עם קובץ פתוח, ומבקשת לנתק את הקשר בינו לבין ה-FD ולשחרר את המשאבים. אבל הפעולה אינה מסתכמת ב"סגירת חלון" — היא מנהלת מנגנוני ניפוי הפניות (Reference Counting), שחרור זיכרון וסינכרון מורכבים.

חתימה וערכי חזרה

int close(int fd);
  • 0 — הצלחה מלאה של פעולת הסגירה.
  • EBADF — ה-fd שגוי או אינו פתוח.

האלגוריתם בקרנל — שלב אחר שלב

  1. כניסה לקרנל ואימות ה-FD (sys_close / __close_fd): מעבר מ-Ring 3 ל-Ring 0; הקרנל בודק שה-fd בגבולות החוקיים של טבלת התהליך ושמצביע על אובייקט קובץ פעיל. fd שגוי → EBADF.
  2. הסרת ה-FD מטבלת התהליך: הקרנל מוחק מיד את הרישום מתוך current->files->fd_array[fd] ומאפס את הסיביות המתאימות במפת הביטים של ה-FDs. מרגע זה ה-FD חדל להתקיים עבור התהליך: read/write נוספים על אותו מספר ייכשלו מיד עם EBADF, והמספר מתפנה להקצאה מחדש לקובץ או סוקט עתידיים.
  3. הפחתת מונה ההפניות (fput): הקרנל מפעיל את fput() על ה-struct file * שאליו הצביע ה-FD, והמונה הפנימי f_count קטן ב-1 (באופן אטומי — atomic_long_sub_and_test).
  4. בדיקת מצב המונה — האם זהו המחזיק האחרון? ראו את התרשים למטה.
  5. מתודת השחרור של מערכת הקבצים (file_operations->release): מופעלת פונקציית הניקוי המותאמת של מערכת הקבצים או הדרייבר (file->f_op->release, למשל ext4_release_file): מחיקת מבני נתונים זמניים של הפתיחה, שחרור נעילות רשומות (Record Locks) שהתהליך החזיק, וניקוי קשרים מול התקני חומרה או סוקטים.
  6. ניקוי מתווה ה-VFS (dput & iput): dput מפחית את מונה ההפניות של ה-dentry — שעשוי להשתחרר או להישאר במטמון ה-Dcache לשימוש עתידי מהיר; iput מפחית את מונה ההפניות של ה-In-Core Inode — ואם הגיע לאפס (ואין קישורים קשיחים פעילים), מתבצע סינכרון סופי של המטא-דאטה (אם הוגדר) והזיכרון משתחרר מטבלת ה-Hash של הליבה. לבסוף, זיכרון ה-struct file מוחזר למטמון ה-SLAB הקרנלי שממנו הוקצה (filp_cachep).
  7. סיום וחזרה: חזרה ל-Ring 3 והחזרת הערך 0 (הצלחה).

החלטת ההפניות — f_count

למה בכלל צריך מונה? כי תהליכים בלינוקס יכולים לשכפל תיאורי קבצים — באמצעות fork(), dup() או dup2() — כך ששני תהליכים שונים (או שני FDs שונים באותו תהליך) מצביעים בדיוק על אותו אובייקט struct file בזיכרון.

f_count > 0 אחרי ההפחתה

ישנם עדיין מחזיקים נוספים (למשל תהליך אב ותהליך בן שירש את הפתיחה). הקרנל מסתפק בהפחתת המונה ויוצא — הקובץ נשאר פתוח עבור יתר המחזיקים.

f_count == 0

התהליך היה "הבעלים האחרון" ואיש אינו משתמש עוד באובייקט. הקרנל ממשיך מיד לניקוי המלא: release → dput/iput → החזרת ה-struct file ל-SLAB.

מלכודת למבחן — close אינה flush: עברו שוב על שבעת השלבים — אין בהם שלב של כתיבת ה-Dirty Pages לדיסק. כפי שראינו באלגוריתם של write, את הסנכרון הפיזי ל-SSD מבצעים תהליכי ה-Writeback ברקע (רק ב-iput, ורק כשמונה ה-Inode מגיע לאפס, מתבצע סינכרון סופי של המטא-דאטה אם הוגדר). כלומר: close() שהחזירה 0 אינה אישור שהנתונים כבר על הדיסק.

מקור: close.pdf (עמ' 1–3)

5. Partial I/O — הלולאה הנכונה

‎read() מחזירה את מספר הבייטים שנקראו בפועל — לא בהכרח את count שביקשתם. לכן קוד נכון אף פעם לא קורא "פעם אחת ודי": הוא רץ בלולאה עד שמוחזר 0 (EOF), ובכל סיבוב כותב בדיוק את מה שנקרא (bytes_read) ומוודא שהכתיבה הצליחה במלואה. כך בדיוק עושה גרסת קריאות המערכת של תוכנית ה-cp מהחוברת (simple_cp_syscall.c): 

    /*
     * read() is a system call. It requests the Kernel to copy data from the
     * file into our buffer. The Kernel puts the process to sleep until the
     * disk/filesystem delivers the data.
     */
    while ((bytes_read = read(src_fd, buffer, BUFFER_SIZE)) > 0) {
        /*
         * write() is a system call. It asks the Kernel to take data from our
         * buffer and place it into the destination file.
         */
        bytes_written = write(dest_fd, buffer, bytes_read);
        if (bytes_written != bytes_read) {
            perror("Error writing data");
            close(src_fd);
            close(dest_fd);
            exit(EXIT_FAILURE);
        }
    }

    /*
     * close() is a system call. It informs the Kernel that we are done.
     * The Kernel can now free the resources associated with these file descriptors.
     */
    close(src_fd);
    close(dest_fd);

    return EXIT_SUCCESS;

מה הופך את הלולאה הזו ל"נכונה"?

  • העתקה במקטעים: ‎BUFFER_SIZE = 4096 — קוראים וכותבים במקטעים (chunks) של 4KB, לא בייט-בייט.
  • תנאי העצירה הוא ‎> 0: הלולאה נעצרת כשמוחזר 0 — כלומר EOF — ולא לפי ניחוש של גודל הקובץ.
  • כותבים bytes_read, לא BUFFER_SIZE: בסיבוב האחרון ייתכן שנקראו פחות מ-4096 בייטים — כותבים בדיוק את מה שנקרא.
  • בודקים ‎bytes_written != bytes_read: זהו הטיפול בשגיאת כתיבה — ואם נכשלנו, סוגרים את שני ה-FDs לפני היציאה (דליפת descriptors היא באג קלאסי).
  • הטיפוס הנכון: הערך המוחזר מ-read/write הוא ssize_t (עם סימן) — לא size_t.

6. סיכום השוואתי — ארבע הקריאות זו מול זו

קריאהמחזירה בהצלחהשגיאות שראינופונקציית הליבההמנגנון המרכזי בקרנל
open() fd — המקום הפנוי הראשון בטבלה -1 (בודקים עם perror) sys_openat Path Resolution → Inode → יצירת struct file → הקצאת FD
read() מספר הבייטים שנקראו; 0 = EOF EBADF, EFAULT sys_read Page Cache (Hit/Miss) → copy_to_user → קידום f_pos
write() מספר הבייטים שנכתבו EBADF sys_write Buffered I/O: copy_from_user → Dirty Pages → Journaling → Writeback
close() 0 EBADF sys_close הסרה מ-fd_array → fput (f_count) → שחרור משאבים

שימו לב לסימטריה: כל ארבע הקריאות מתחילות באותם שני צעדים — מעבר Ring 3 → Ring 0, ותרגום ה-fd ל-struct file (חוץ מ-open, שהיא זו שיוצרת אותם) — וכולן מחזירות EBADF על fd לא תקין.

🔒 יושלם בהמשך — לפי הסילבוס, שיעור 6 כולל גם את lseek() (שינוי מיקום בקובץ) ואת stat() (גישה למטא-דאטה). הנושאים יתווספו לעמוד זה כשהחומרים יעלו למודל.
