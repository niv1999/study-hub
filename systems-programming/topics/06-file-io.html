0. האינטואיציה — מחזור החיים של קובץ

הארכיטקטורה ממודול 5: File Descriptor (אינדקס בטבלת התהליך) → struct file → Inode. כאן — התנועה: ארבע קריאות המערכת של חיי הקובץ, צעד אחר צעד ב-Linux Kernel 6.14.

המרצה מלמד כל קריאה בשני חלקים, ושניהם חומר למבחן: הממשק (חתימה, פרמטרים, ערכי חזרה) והאלגוריתם בקרנל — מה-syscall ועד החזרה למרחב המשתמש.

חמישה מושגים שחוזרים לאורך כל העמוד

מונחמה זה, במשפט אחד
באפר (buffer) מערך בייטים שהתוכנית מקצה: הקרנל שופך אליו נתונים (קריאה) או לוקח מהם (כתיבה). בקוד המרצה — char buffer[4096];.
מיקום בקובץ (File Offset / f_pos) כמה בייטים פנימה אנחנו כרגע בקובץ. נפתח ב-0, מתקדם אוטומטית אחרי כל read/write, ושמור בתוך ה-struct file של הפתיחה.
חסימה (blocking) קריאה "חוסמת" לא חוזרת מיד. בהערות המרצה ב-cp: read() מרדים את התהליך — מוציא אותו מהריצה עד שהדיסק/מערכת הקבצים מספקים נתונים, ואז מעיר וחוזר.
Page Cache אזור ב-RAM שבו הקרנל מחזיק עותק של דפי הקובץ (Page = 4KB), כדי לא לגעת בדיסק בכל פעולה. מנוהל ברמת ה-Inode.
size_t מול ssize_t size_t = שלם ללא סימן, לגדלים וכמויות (הפרמטר count). ssize_t = עם סימן, הטיפוס המוחזר מ-read/write — כי חייב להחזיק גם -1.

מוסכמת השגיאות — לכל ארבע הקריאות: קריאה שנכשלה מחזירה -1 ומעדכנת את errno בקוד הסמלי (למשל EBADF — Bad file descriptor); perror() מדפיסה את התיאור המילולי. בקרנל אותה שגיאה היא ערך שלילי — -EBADF — וכך היא מופיעה באלגוריתמים למטה. בדיקת ערך ההחזרה נלמדה במודול 3.

🎓 מהשיעור בכיתה (מהמחברת)

המרצה כתב על הלוח שלוש קריאות מערכת שונות לגמרי זו לצד זו — open,‏ connect ו-socket — ולכל אחת את אותה שורה: מחזירה -1, ולידה "syscall fails". שתי האחרונות מעולם ה-Sockets שיילמד בהמשך, וזו הנקודה: המוסכמה זהה בכל קריאות המערכת, גם באלה שעוד לא ראיתם.

1. open() — לפתוח (או ליצור) קובץ

מאתרת (או יוצרת) את ה-Inode, בודקת הרשאות, ומחזירה File Descriptor — מספר שלם קטן שדרכו יתבצעו כל הפעולות הבאות.

החתימה המלאה

int open(const char *pathname, int flags, mode_t mode);

בלי O_CREAT לא מעבירים ארגומנט שלישי — כמו בפתיחת המקור ב-cp: src_fd = open(argv[1], O_RDONLY);.

שלושת הארגומנטים

ארגומנטבדוגמהתפקיד
pathname "/home/Itzhak/lecture01" הנתיב שבו הקובץ ממוקם (או ייווצר). התחלה ב-'/' = נתיב אבסולוטי (Absolute Path): ב-Path Resolution הקרנל מתעלם מה-CWD וסורק מתיקיית השורש (root dentry).
flags O_RDWR | O_CREAT משתנה ביטים (Bitmask) המצרף הגדרות עם Bitwise OR (|) — טבלת הדגלים למטה.
mode 0644 אך ורק עם O_CREAT — ההרשאות הראשוניות של הקובץ החדש, תמיד בכפוף למסכת ההרשאות של התהליך, ה-umask.

הדגלים שראינו בקורס

דגלמה הוא אומר לקרנל
O_RDONLYקריאה בלבד (כך נפתח קובץ המקור ב-cp).
O_WRONLYכתיבה בלבד; read() על פתיחה כזו ייחסם.
O_RDWRקריאה וכתיבה.
O_CREAT אינו קיים — צור (Inode חדש + Directory Entry בתיקיית היעד). קיים — הדגל מתעלם.
O_TRUNCקובץ קיים — אפס את תוכנו (חתוך לאורך 0). כך נפתח קובץ היעד ב-cp: O_WRONLY | O_CREAT | O_TRUNC.
O_APPENDכל כתיבה מתווספת לסוף הקובץ. המנגנון — שלב 3 של אלגוריתם ה-write.
O_SYNC / O_DSYNCסנכרון מחמיר: הכתיבה יורדת לדיסק מיד, בלי להמתין לתהליכי הרקע (שלב 9 של write).

פירוק 0644 (אוקטלי)

6
Owner — הבעלים
rw-
4
Group — הקבוצה
r--
4
Others — כל השאר
r--

אוקטלי (בסיס 8) — מכאן הקידומת 0. כל ספרה היא סכום: 4 = קריאה, 2 = כתיבה, 1 = הרצה; לכן 6 = 4+2 ו-4 = קריאה בלבד. בפועל ההרשאות נכתבות לשדה i_mode של ה-Inode, אחרי סינון ה-umask.

ערכי חזרה ושגיאות

  • הצלחה: ה-fd — שלם אי-שלילי (למשל 3, כי 0,1,2 תפוסים).
  • כישלון: -1 — בודקים fd == -1 ומדפיסים עם perror().

הקוד מהחוברת — הדוגמה היחידה עם שלושת הארגומנטים

פותח את /home/Itzhak/lecture01 לקריאה+כתיבה, יוצר אותו עם 0644 אם אינו קיים, ובכישלון מדפיס ויוצא. 

#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>

int main() {
    int fd;

    fd = open("/home/Itzhak/lecture01", O_RDWR | O_CREAT, 0644);

    if (fd == -1) {
        perror("Error opening/creating file");
        return 1;
    }

    close(fd);
    return 0;
}

מה קורה בקרנל (Linux Kernel 6.14) מרגע ביצוע הפקודה?

  1. מעבר מ-User ל-Kernel Mode: פקודת אסמבלי syscall, Ring 3 ל-Ring 0. ב-6.14 הקריאה מתועלת ל-sys_openat (הפרמטר המרומז AT_FDCWD נזנח כי הנתיב אבסולוטי).
  2. העתקת הנתיב ממרחב המשתמש: לזיכרון הקרנל, ב-strncpy_from_user.
  3. Path Resolution — איתור או יצירת Inode: סריקת עץ הספריות / → home → Itzhak → lecture01. קיים — איתור ה-Inode בטבלת ה-Inodes. לא קיים + O_CREAT — הקצאת Inode חדש, רישום ב-Inode Bitmap, יצירת Directory Entry תחת Itzhak, וכתיבת ה-mode (בכפוף ל-umask) לשדה i_mode.
  4. יצירת אובייקט קובץ פתוח: הקצאת struct file — מצב הפתיחה: File Offset שמתחיל ב-0 והדגלים שנבחרו (O_RDWR).
  5. הקצאת File Descriptor: סריקת הטבלה ב-current->files (struct files_struct), המקום הפנוי הראשון (למשל 3), ורישום מצביע ל-struct file.
  6. חזרה למרחב המשתמש: הקרנל מחזיר 3 — ה-fd שדרכו התהליך יקרא ויכתוב.

מלכודות למבחן: (1) mode רק עם O_CREAT; (2) קובץ קיים ⇐ O_CREAT מתעלם ונפתח רגיל; (3) נתיב שמתחיל ב-'/' ⇐ הקרנל מתעלם מה-CWD; (4) mode עובר סינון umask — ההרשאות בפועל אינן בהכרח מה שכתבתם; (5) ה-fd הוא המקום הפנוי הראשון בטבלה, לא מספר רץ גלובלי.

מקור: open.pdf (עמ' 1–3); דגלי היעד — simple_cp.pdf (עמ' 2)

2. read() — שמונה שלבים מה-fd ועד הבאפר

שואבת נתונים מקובץ פתוח אל מרחב המשתמש: דרך שכבת ה-VFS, בהישענות על ה-Page Cache, ופנייה ל-SSD רק בעת הצורך.

חתימה ופרמטרים

ssize_t read(int fd, void *buf, size_t count);
פרמטרטיפוסתפקיד
fdint ה-fd מ-open — האינדקס בטבלת תיאורי הקבצים של התהליך.
bufvoid * הבאפר במרחב המשתמש שאליו הקרנל יעתיק. לא const — הקרנל משנה אותו.
countsize_t מספר הבייטים המקסימלי לקריאה — בקשה, לא הבטחה.

ערכי חזרה ושגיאות

  • מספר חיובי — הבייטים שנקראו בפועל.
  • 0 — סוף הקובץ (EOF). לא שגיאה.
  • -1 + errno = EBADF (בקרנל: -EBADF) — fd לא תקין/לא פתוח, או קובץ שנפתח רק לכתיבה (O_WRONLY) — אין אישור קריאה ב-f_mode.
  • -1 + errno = EFAULT — כתובת באפר המשתמש פגומה; copy_to_user תופסת את החריגה בלי להפיל את המערכת.
🎓 מהשיעור בכיתה (מהמחברת)

המרצה סימן מעל הארגומנט השלישי את השם שהוא נותן לו — granularity level (רמת הגרעיניות): כמה נתונים מבקשים בכל קריאה בודדת. 

                          granularity level
                                  |
                                  v
char my_buf[BUFFER_SIZE];
n = read(source_fd, my_buf, 1);   /* one byte per call */
  • source_fd — ה-fd מ-open; my_buf — הבאפר במרחב המשתמש.
  • המרצה הדגיש וחזר: read מחזירה 0 ב-EOF — ולא -1; -1 שמור אך ורק לשגיאה.
  • הערך המוחזר הוא הבייטים שנקראו בפועל, לא בהכרח מה שביקשנו — Partial I/O, סעיף 5.
  • ה-granularity קובע גם כמה יקרה הקריאה — "Syscall יקר!", סעיף 5.

שימוש מינימלי — עד 4096 בייטים, ובדיקת שלושת המצבים

char    buffer[4096];
ssize_t bytes_read;

bytes_read = read(src_fd, buffer, 4096);

if (bytes_read == -1) {          /* כישלון */
    perror("Error reading from file descriptor");
    exit(EXIT_FAILURE);
}
if (bytes_read == 0) {           /* EOF — אין עוד מה לקרוא */
    /* ... */
}
/* אחרת: bytes_read בייטים תקינים ממתינים ב-buffer */

האלגוריתם בקרנל — שמונה שלבים

  1. כניסה לקרנל ואיתור אובייקט הקובץ (fdget / sys_read): Ring 3 → Ring 0 אל sys_read; שליפת struct file * מטבלת תיאורי הקבצים (current->files). fd לא תקין → -EBADF.
  2. הרשאות קריאה (File Status & f_mode): f_mode = השדה ב-struct file ששומר את מצב הגישה שנקבע בפתיחה. נדרש O_RDONLY או O_RDWR; קובץ שנפתח רק לכתיבה → -EBADF.
  3. ממשק ה-VFS (new_sync_read / vfs_read): vfs_read ניגשת למערך פעולות מערכת הקבצים (file->f_op->read / read_iter) ומפעילה את מתודת הקריאה — לרוב read_iter; ב-ext4 ext4_file_read_iter.
  4. בדיקת מטמון הזיכרון (Page Cache Lookup — Hit vs. Miss): איזה עמוד 4KB מכיל את הבייטים לפי f_pos, והאם הוא ב-RAM. Hit — מדלגים על הדיסק; Miss — פונים ל-SSD.
  5. קריאת הבלוקים מהדיסק (SSD Read & Block I/O — רק ב-Miss): הדרייבר מתרגם לבלוקים פיזיים דרך עץ ה-Extents של ה-Inode; נוצר bio ונשלחת בקשת I/O דרך שכבת הבלוקים (blk-mq) ובקר ה-NVMe. הבלוקים נקראים מה-SSD אל תוך ה-Page Cache, ורק אז ממשיכים.
  6. העתקה למרחב המשתמש (copy_to_user): תהליך משתמש אינו רשאי לגשת לזיכרון הליבה, ולכן ההעברה מבאפר הקרנל אל buf נעשית בפונקציה המוגנת.
  7. עדכון מיקום הקובץ (f_pos): ה-File Offset ב-struct file גדל בבייטים שנקראו בפועל — הקריאה הבאה ממשיכה משם.
  8. סיום והחזרה למרחב המשתמש: שחרור נעילות דפי הזיכרון, עדכון atime ב-Inode אם נדרש, Ring 0 → Ring 3, והחזרת הבייטים שנקראו בפועל (0 ב-EOF).

f_pos הוא פר-פתיחה, לא פר-קובץ: הוא שמור ב-struct file של הפתיחה הספציפית — שני תהליכים שפתחו אותו קובץ מחזיקים f_pos נפרדים.

מלכודות למבחן: (1) read() שמחזירה 0 היא לא שגיאה — זה EOF; (2) count הוא תקרה, לא הבטחה — עובדים לפי הערך שהוחזר; (3) הקריאה חוסמת — הקרנל מרדים את התהליך עד שהנתונים מגיעים (הערות קוד ה-cp).

מקור: read.pdf (עמ' 1–3)

3. write() — עשרה שלבים והסוד של ה-Buffered I/O

מעבירה נתונים מהתהליך אל קובץ פתוח. הנקודה המרכזית: הכתיבה מנוהלת לרוב במנגנון Buffered I/O (קלט/פלט ממוקד מטמון) — הנתונים נכתבים תחילה אל ה-Page Cache ב-RAM ורק בהמשך מסונכרנים אל ה-SSD, אלא אם הוגדרו דגלי סנכרון מיידי.

חתימה ופרמטרים

ssize_t write(int fd, const void *buf, size_t count);
פרמטרטיפוסתפקיד
fdint הקובץ שאליו כותבים.
bufconst void * באפר המקור בתהליך. const — בניגוד ל-read: הקרנל רק קורא ממנו.
countsize_t מספר הבייטים לכתיבה.

ערכי חזרה ושגיאות

  • מספר חיובי — מספר הבייטים שנכתבו בפועל (תואם ל-count).
  • -1 עם errno = EBADF (בקרנל: -EBADF) — fd לא תקין, או קובץ שנפתח רק לקריאה (O_RDONLY) — נחסם בבדיקת f_mode.

שימוש מינימלי — כותבים bytes_read, לא את גודל הבאפר

ssize_t bytes_written;

bytes_written = write(dest_fd, buffer, bytes_read);

if (bytes_written == -1) {
    /* 1. קריאת המערכת נכשלה   2. הקרנל עדכן את errno */
    perror("Error writing to file descriptor");
    exit(EXIT_FAILURE);
}
/* 3. אם הגענו לכאן ה-write הצליח — ייתכן שרק חלקית */

האלגוריתם בקרנל — עשרה שלבים

  1. כניסה לקרנל ואיתור אובייקט הקובץ (fdget / sys_write): Ring 3 → Ring 0 אל sys_write (או ksys_write); שליפת struct file * מ-current->files. fd לא תקין → -EBADF.
  2. הרשאות כתיבה (f_mode): נדרש דגל כתיבה מהפתיחה (O_WRONLY או O_RDWR); O_RDONLY בלבד → -EBADF.
  3. מצבי כתיבה מיוחדים ונעילות (Locks & O_APPEND): O_APPEND → f_pos מוצב על סוף הקובץ (i_size של ה-Inode) לפני כל כתיבה, כדי להוסיף בלי לדרוס — קריטי מרובת-תהליכים. במקביל מנעולי In-Core Inode (i_rwsem) נגד Race Conditions בין כותבים בו-זמנית.
  4. VFS ומערכת הקבצים (vfs_write / ext4_file_write_iter): ניתוב ל-write_iter של מערכת הקבצים — ב-ext4 ext4_file_write_iter, שמנהלת את הכתיבה לעץ ה-Extents.
  5. הבאה/הקצאה של דפי זיכרון (Page Cache Allocation & Read-Modify-Write): איזה עמוד 4KB תואם ל-f_pos, והאם הוא במטמון. Cache Miss + כתיבת חלק בלבד מהבלוק (Partial Block Write — 100 בייט באמצע בלוק 4KB) → Read-Modify-Write: קריאת הבלוק מה-SSD ל-RAM תחילה, שלא יושחתו שאר חלקיו. עמוד שלם (4KB) → הקצאת עמוד ריק ב-RAM בלי קריאה מהדיסק.
  6. העתקה ממרחב המשתמש וסימון Dirty (copy_from_user): מבאפר התהליך אל דפי ה-Page Cache (הכיוון ההפוך מ-copy_to_user של read), והדף מסומן Dirty Page (SetPageDirty) — ה-RAM שונה מהדיסק ודורש סינכרון.
  7. עדכון מטא-דאטה, מיקום ו-Inode (i_size & f_pos): f_pos מתקדם בבייטים שנכתבו; אם הקובץ גדל — i_size ב-In-Core Inode מתעדכן; וה-Inode מסומן כמלוכלך (I_DIRTY_DATASYNC).
  8. הקצאת בלוקים פיזיים (Extents & Block Allocation): אם נדרש מקום חדש, ext4 משתמשת לרוב ב-Delayed Allocation (הקצאה דחויה) — דחיית ההקצאה הפיזית לייעול ולמניעת פיצול (Fragmentation), בעוד הנתונים ב-Page Cache. בהקצאה בפועל ה-Extents מעדכן את עץ המיפוי ב-Inode ומצביע על הבלוקים החדשים.
  9. סינכרון ורישום ביומן (Journaling / Writeback): לאמינות בקריסה, ext4 רושמת את שינויי המטא-דאטה ליומן הטרנזקציות של jbd2. הנתונים שוהים ב-Page Cache וייכתבו ל-SSD בידי תהליכי רקע (Writeback / flusher threads) — או מיידית עם O_SYNC/O_DSYNC.
  10. סיום והחזרה למרחב המשתמש: שחרור נעילות ה-Inode, Ring 0 → Ring 3, והחזרת מספר הבייטים שנכתבו בפועל.

אז מתי הדיסק באמת מתעדכן?

היתרון: כתיבה חוזרת לאותו אזור מעדכנת דף שכבר ב-RAM, וקריאה של מה שנכתב זה עתה תיפגע ב-Cache Hit; מחיר הדיסק משולם פעם אחת, ברקע ובאצווה.

🎓 מהשיעור בכיתה (מהמחברת)

בכיתה המרצה צייר את אותו מנגנון בדיוק, אבל בשמות שלו: בקרנל יש data block buffer — ענן של בלוקים שנקראו מה-NVM אל ה-MM. בלוק ששונה בזיכרון ועוד לא ירד לדיסק מסומן בדגל dirty. זהו אותו רעיון שבשקפים נקרא Page Cache ו-Dirty Page; שווה להכיר את שני השמות, כי בשאלה בכיתה הוא עשוי להשתמש בניסוח שלו.

וההדגמה היומיומית שהוא נתן, בקופסה על הלוח: Ctrl + S → flush אל ה-NVM. כלומר: כל עוד לא "שמרתם", העריכה יושבת בבאפר של הקרנל ב-RAM בלבד — וזו הסיבה האמיתית שהמסמך נעלם בהפסקת חשמל.

שני מנגנוני הגנה בשלב 3 — אל תערבבו: O_APPEND פותר את "לאן כותבים" (תמיד לסוף, לפי i_size); הנעילה i_rwsem פותרת את "מי כותב עכשיו" — מניעת Race Condition בין שני תהליכים בו-זמנית. שניהם פועלים יחד.

מקור: write.pdf (עמ' 1–4); תבנית בדיקת השגיאה — error.pdf (עמ' 5)

4. close() — הרבה יותר מ"סגירת חלון"

מודיעה לקרנל שהתהליך סיים עם הקובץ, מנתקת אותו מה-FD ומשחררת משאבים — דרך ניפוי הפניות (Reference Counting).

חתימה, ערכי חזרה ושגיאות

int close(int fd);
  • 0 — הצלחה.
  • -1 עם errno = EBADF (בקרנל: -EBADF) — ה-fd שגוי, מחוץ לגבולות הטבלה, או אינו פתוח.

שימוש מינימלי

שני ה-FDs של ה-cp בסיום. גם במסלול השגיאה סוגרים את מה שכבר נפתח — דליפת descriptors היא באג קלאסי. 

/* close() is a system call. It informs the Kernel that we are done.
 * The Kernel can now free the resources associated with these file descriptors. */
close(src_fd);
close(dest_fd);

האלגוריתם בקרנל — שבעה שלבים

  1. כניסה לקרנל ואימות ה-FD (sys_close / __close_fd): Ring 3 → Ring 0; ה-fd (למשל 3) בגבולות טבלת התהליך ומצביע על אובייקט קובץ פעיל. fd שגוי או לא פתוח → -EBADF.
  2. הסרת ה-FD מטבלת התהליך (inverse fd_install): מחיקת הרישום מ-current->files->fd_array[fd] ואיפוס הסיביות במפת הביטים. מכאן ה-FD חדל להתקיים עבור התהליך: read/write על אותו מספר ייכשלו ב--EBADF, והמספר מתפנה להקצאה מחדש.
  3. הפחתת מונה ההפניות (fput): fput() על ה-struct file * מקטין את f_count ב-1 אטומית (atomic_long_sub_and_test).
  4. האם זהו המחזיק האחרון? f_count > 0 — יש מחזיקים נוספים; הקרנל יוצא כאן והקובץ נשאר פתוח עבורם. f_count == 0 — הבעלים האחרון, וממשיכים לניקוי המלא בשלבים 5–6.
  5. מתודת השחרור של מערכת הקבצים (file_operations->release): file->f_op->release (למשל ext4_release_file) — מחיקת מבנים זמניים של הפתיחה, שחרור נעילות רשומות (Record Locks), וניקוי קשרים מול התקני חומרה וסוקטים.
  6. ניקוי ה-VFS — dentry ו-inode (dput & iput): dput מפחית את מונה ה-dentry — שישתחרר או יישאר במטמון ה-Dcache; iput מפחית את מונה ה-In-Core Inode, ובאפס (ואין קישורים קשיחים פעילים) מתבצע סינכרון סופי של המטא-דאטה (אם הוגדר) והזיכרון משתחרר מטבלת ה-Hash. לבסוף ה-struct file חוזר למטמון ה-SLAB שממנו הוקצה (filp_cachep) — מנגנון המחזור של הקרנל למבנים קטנים ותדירים.
  7. סיום והחזרה למרחב המשתמש: חזרה ל-Ring 3 והחזרת 0 (הצלחה).

מונה ההפניות — f_count

למה צריך מונה: fork(), dup() ו-dup2() משכפלים תיאורי קבצים, כך ששני תהליכים (או שני FDs באותו תהליך) מצביעים על אותו struct file; בלי מונה, ה-close הראשון היה הורס אותו תחת כל היתר. הסרת ה-FD מהטבלה (שלב 2) קורית תמיד — במונה (שלב 4) תלוי רק גורל ה-struct file המשותף.

מלכודת למבחן — close אינה flush: בשבעת השלבים אין כתיבת Dirty Pages לדיסק; את הסנכרון הפיזי ל-SSD מבצעים תהליכי ה-Writeback ברקע (ב-iput מסונכרנת רק המטא-דאטה, ורק כשהמונה מתאפס). close() שהחזירה 0 אינה אישור שהנתונים על הדיסק.

מקור: close.pdf (עמ' 1–3)

5. Partial I/O — הלולאה הנכונה

‎read() מחזירה את הבייטים שנקראו בפועל, לא בהכרח את count: הקובץ עלול להיגמר באמצע (שלב 8 מחזיר את מה שהצטבר), ובקצה יש כמעט תמיד שארית קטנה מ-4KB. לכן קוד נכון רץ בלולאה עד 0 (EOF) — לולאת ההעתקה של ה-cp (simple_cp_syscall.c): 

    /*
     * read() is a system call. It requests the Kernel to copy data from the
     * file into our buffer. The Kernel puts the process to sleep until the
     * disk/filesystem delivers the data.
     */
    while ((bytes_read = read(src_fd, buffer, BUFFER_SIZE)) > 0) {
        /*
         * write() is a system call. It asks the Kernel to take data from our
         * buffer and place it into the destination file.
         */
        bytes_written = write(dest_fd, buffer, bytes_read);
        if (bytes_written != bytes_read) {
            perror("Error writing data");
            close(src_fd);
            close(dest_fd);
            exit(EXIT_FAILURE);
        }
    }

    /*
     * close() is a system call. It informs the Kernel that we are done.
     * The Kernel can now free the resources associated with these file descriptors.
     */
    close(src_fd);
    close(dest_fd);

    return EXIT_SUCCESS;

מה הופך את הלולאה הזו ל"נכונה"?

  • מקטעים של ‎BUFFER_SIZE = 4096 — לא בייט-בייט; בדיוק גודל ה-Page של ה-Page Cache.
  • תנאי עצירה ‎> 0: עוצרים על 0 = EOF, לא על ניחוש גודל הקובץ; גם -1 מסיים, כי אינו גדול מ-0.
  • כותבים bytes_read, לא BUFFER_SIZE: בסיבוב האחרון נקראו לרוב פחות מ-4096; אחרת היינו מעתיקים "זבל" ישן מהבאפר אל היעד.
  • בודקים ‎bytes_written != bytes_read — וסוגרים את שני ה-FDs לפני היציאה.
  • הטיפוס: ssize_t (עם סימן), לא size_t — שבו -1 היה הופך למספר עצום חיובי והבדיקה נשברת.

🎓 מהשיעור בכיתה (מהמחברת) "Syscall יקר!" — למה גודל ה-granularity קובע את המהירות

המרצה כתב על הלוח: "Syscall יקר [בזמן]!". כל קריאת מערכת גוררת מעבר Ring 3 → Ring 0 וחזרה, בדיקות תקינות, מציאת ה-struct file ונעילות — תקורה שמשולמת בכל קריאה, בלי קשר למספר הבייטים. ההדגמה שלו, על קובץ בגודל 4096 בייט:

granularity (הארגומנט השלישי)כמה קריאות read יידרשוהמשמעות
1 בייט4096 קריאות מערכתאיטי קיצונית — מחיר המעבר לקרנל משולם 4096 פעם עבור 4KB.
2 בייט2048 קריאות מערכתחצי מהתקורה, עדיין רחוק מהאופטימום.
4096 בייטקריאה אחתמעבר אחד, ובדיוק גודל ה-Page של ה-Page Cache — לכן BUFFER_SIZE ב-cp הוא 4096.

הדגש למבחן (המרצה סימן כנקודה לזכור): ה-granularity אינו משפיע על נכונות — גם בייט-בייט ההעתקה נכונה — אלא על מספר קריאות המערכת, ולכן על הזמן. read(fd, buf, 1) בלולאה = פגם ביצועים, לא באג.

🎓 מהשיעור בכיתה (מהמחברת) תרגיל ה-cp כפי שפורק על הלוח — טבלת ה-fd, שני in-core inodes ו-O_CREAT

שתי הפתיחות מקבלות את המקומות הפנויים הראשונים — 3 ו-4, כי 0, 1, 2 תפוסים על ידי stdin, stdout, stderr: 

example task_struct
   |
 [files] --> open fd table          in-core inodes
              0  stdin
              1  stdout
              2  stderr
              3  ---------------->  in-core inode  (source file)
              4  ---------------->  in-core inode  (dest file)   dirty? W/Append?
                                          |
                                          v
                                    disk inode  { owner, mode, ... , data --> data blocks }
  • שני in-core inodes נפרדים — למקור וליעד, שניהם ב-MM, כל אחד מצביע אל ה-disk inode שלו על ה-NVM (owner, mode, ומצביעי data אל ה-Data Blocks). המבנה המלא — מודול 5.
  • פתיחת קובץ היעד: על הלוח dest_fd = open(pathname_dest, flags, mode), והמרצה סימן את O_CREAT כנקודה לזכור — היעד לרוב אינו קיים.
  • Write מול Append: כשהקובץ כן קיים — לדרוס (O_TRUNC, כמו ב-cp) או להוסיף בסופו (O_APPEND). המרצה הצמיד לזה lseek() (סעיף 7): O_APPEND כותב תמיד לסוף, ולמיקום אחר — lseek.
  • ה-write ליעד מעדכן את ה-data block דרך הבאפר בקרנל, והבלוק מסומן dirty עד ה-flush (סעיף 3).
הרחבה — למה בכלל "חלקי"?

בשקפי ה-write הערך המוחזר מתואר כתואם ל-count (וכך בקובץ רגיל), אבל בשקף בדיקת השגיאות (error.pdf, מודול 3) המרצה כותב: "אם הגענו לכאן ה-write הצליח — ייתכן שרק חלקית". == -1 מזהה כישלון אך אינו מבטיח שכל הבייטים נכתבו — ולכן ה-cp מוסיף bytes_written != bytes_read.

מקור: simple_cp.pdf (עמ' 2–3); כתיבה חלקית — error.pdf (עמ' 5)

🎓 מהשיעור בכיתה (מהמחברת) fread/fwrite הן glibc — ו-FILE אינו file descriptor

ההבחנה שהמרצה סגר איתה את השיעור: open, read, write, close הן קריאות מערכת; הפונקציות מקורס C — fopen, fread, fwrite, fprintf, fscanf, fclose — הן פונקציות ספרייה של glibc: רצות במרחב המשתמש, מנהלות באפר משלהן, ובסוף קוראות בעצמן ל-read/write.

7. הרחבה — לא מהשקפים: lseek(), stat() וקריאת תיקייה

הרחבה — לא מהשקפים

הסילבוס מזכיר בשיעור 6 שינוי מיקום וגישה למטא-דאטה, אך אין להם שקפים. הסעיף מתבסס על דפי ה-man — לא חומר בחינה.

lseek() — להזיז את מצביע המיקום

מזיזה את f_pos ידנית, בלי לגעת בדיסק — רק משנה שדה ב-struct file. 

off_t lseek(int fd, off_t offset, int whence);
whenceהמשמעות
SEEK_SETמיקום חדש = offset מתחילת הקובץ.
SEEK_CURמיקום חדש = הנוכחי + offset (שלילי = אחורה).
SEEK_ENDמיקום חדש = סוף הקובץ + offset.

ערך החזרה: המיקום החדש בבייטים מתחילת הקובץ; בכישלון (off_t) -1. מכאן הטריק: קפיצה לסוף = גודל הקובץ. 

off_t size = lseek(fd, 0, SEEK_END);   /* קפיצה לסוף → הערך המוחזר הוא גודל הקובץ */
lseek(fd, 0, SEEK_SET);                /* חזרה להתחלה */

stat() / fstat() — לקרוא את המטא-דאטה

שואבות את שדות ה-Inode אל מבנה במרחב המשתמש; stat() לפי נתיב, fstat() לפי fd פתוח. 

int stat(const char *pathname, struct stat *statbuf);
int fstat(int fd, struct stat *statbuf);
שדה ב-struct statמה הוא מחזיק
st_modeסוג הקובץ + ביטי הרשאות = שדה ה-i_mode של ה-Inode (לשם נכתב ה-0644 מ-open).
st_sizeגודל בבייטים = i_size שה-write מעדכן כשהקובץ גדל.
st_inoמספר ה-Inode — המזהה שאליו מצביעה ה-Directory Entry.
st_nlinkמספר הקישורים הקשיחים (hard links) — המונה שבשלב iput של close.
st_uidה-UID של בעל הקובץ.
 
struct stat sb;

if (fstat(fd, &sb) == -1) {
    perror("fstat");
    exit(EXIT_FAILURE);
}
printf("size = %lld bytes, inode = %lu\n",
       (long long) sb.st_size, (unsigned long) sb.st_ino);

קריאת תיקייה — opendir / readdir / closedir

תיקייה = קובץ שתוכנו רשומות; שלוש הפונקציות (<dirent.h>) עוברות עליהן אחת-אחת. כל רשומה חוזרת כ-struct dirent עם d_name + d_ino — צמד השדות של Directory Entry ממודול 5; readdir מחזירה NULL בסוף. 

DIR *d = opendir("/home/Itzhak");
struct dirent *e;

while ((e = readdir(d)) != NULL)
    printf("%s -> inode %lu\n", e->d_name, (unsigned long) e->d_ino);

closedir(d);

8. בדיקה עצמית
