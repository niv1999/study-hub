0. האינטואיציה — מחזור החיים של קובץ

בפרק הקודם ראינו את הארכיטקטורה: ה-File Descriptor הוא אינדקס בטבלת התהליך, שמוביל ל-struct file, שמוביל ל-Inode. עכשיו נראה את התנועה: מה בדיוק קורה כשקוראים לכל אחת מארבע קריאות המערכת שמרכיבות את חיי הקובץ — open(), read(), write(), close() — צעד אחר צעד, כפי שזה ממומש ב-Linux Kernel 6.14.

המרצה מלווה כל קריאה בשני חלקים: הממשק (חתימה, פרמטרים, ערכי חזרה) — מה שאתם כותבים ב-C — והאלגוריתם בקרנל — מה שקורה מאחורי הקלעים מרגע פקודת ה-syscall ועד החזרה למרחב המשתמש. שני החלקים הם חומר למבחן.

חמישה מושגים שחוזרים לאורך כל העמוד

אם אף פעם לא כתבתם C או עבדתם בלינוקס — אלה חמש המילים שכדאי להכיר לפני שממשיכים:

מונחמה זה, במשפט אחד
באפר (buffer) מערך בייטים שאתם מקצים בתוכנית שלכם, והוא משמש כ"דלי" שאליו הקרנל שופך נתונים (בקריאה) או שממנו הוא לוקח אותם (בכתיבה). בקוד של המרצה זה פשוט char buffer[4096];.
מיקום בקובץ (File Offset / f_pos) מספר יחיד שאומר "כמה בייטים פנימה אנחנו נמצאים כרגע בקובץ". הוא נפתח ב-0 ומתקדם אוטומטית אחרי כל read/write. הקרנל שומר אותו בתוך אובייקט ה-struct file של הפתיחה.
חסימה (blocking) קריאת מערכת "חוסמת" = היא לא חוזרת מיד. כמו שכתוב בהערות של המרצה בקוד ה-cp: read() מרדים את התהליך — הקרנל מוציא אותו מהריצה עד שהדיסק/מערכת הקבצים מספקים את הנתונים, ורק אז מעיר אותו וחוזר.
Page Cache אזור זיכרון ב-RAM שבו הקרנל מחזיק עותק של דפי הקובץ (Page = 4KB), כדי לא לגעת בדיסק הפיזי בכל פעולה. מנוהל ברמת ה-Inode של הקובץ.
size_t מול ssize_t size_t = טיפוס שלם ללא סימן, שמשמש לגדלים וכמויות (הפרמטר count). ssize_t = אותו דבר עם סימן — וזה הטיפוס שמוחזר מ-read/write, בדיוק כי הוא צריך להיות מסוגל להחזיק גם את הערך -1 שמסמן כישלון.

מוסכמת השגיאות — תקפה לכל ארבע הקריאות: קריאת מערכת שנכשלה מחזירה למרחב המשתמש את הערך -1, ומעדכנת את errno בקוד השגיאה הסמלי (למשל EBADF — Bad file descriptor); perror() מדפיסה את התיאור המילולי. בתוך הקרנל אותה שגיאה מיוצגת כערך שלילי — -EBADF — וכך היא מופיעה בשקפי האלגוריתמים למטה. בדיקת ערך ההחזרה של כל קריאת מערכת נלמדה לעומק במודול 3.

🎓 מהשיעור בכיתה (מהמחברת)

כדי להראות שזו באמת מוסכמה ולא מקרה, המרצה כתב על הלוח שלוש קריאות מערכת שונות לגמרי זו לצד זו — open,‏ connect ו-socket — ולכל אחת רשם את אותה שורה: מחזירה -1, ולידה "syscall fails". שתי האחרונות שייכות לעולם ה-Sockets שיילמד בהמשך הקורס, וזו בדיוק הנקודה: המוסכמה זהה בכל קריאות המערכת, גם באלה שעוד לא ראיתם.

1. open() — לפתוח (או ליצור) קובץ

open() היא הקריאה שמתחילה הכול: היא אומרת לקרנל "אני רוצה גישה לקובץ הזה", והקרנל — אחרי שהוא מאתר (או יוצר) את ה-Inode ובודק הרשאות — מחזיר File Descriptor, מספר שלם קטן שדרכו יתבצעו כל הפעולות הבאות.

החתימה המלאה

int open(const char *pathname, int flags, mode_t mode);

זו החתימה עם שלושת הארגומנטים. כשלא יוצרים קובץ חדש (כלומר בלי O_CREAT) פשוט לא מעבירים את השלישי — בדיוק כמו בפתיחת קובץ המקור בתוכנית ה-cp: src_fd = open(argv[1], O_RDONLY);.

שלושת הארגומנטים

ארגומנטבדוגמהתפקיד
pathname "/home/Itzhak/lecture01" מחרוזת המצביעה על הנתיב שבו ממוקם הקובץ (או שבו ייווצר). מכיוון שהיא מתחילה ב-'/', הקרנל מזהה מיד נתיב אבסולוטי (Absolute Path): ב-Path Resolution הוא מתעלם מתיקיית העבודה הנוכחית (CWD) ומתחיל את הסריקה ישירות מתיקיית השורש הגלובלית (root dentry).
flags O_RDWR | O_CREAT משתנה ביטים (Bitmask) המכיל מספר הגדרות יחד באמצעות פעולת Bitwise OR (|) — ראו את טבלת הדגלים מיד למטה.
mode 0644 מוגדר אך ורק כאשר משתמשים ב-O_CREAT, ומציין את הרשאות האבטחה הראשוניות של הקובץ החדש אם הוא נוצר כעת. הערך כפוף תמיד לסינון מסכת ההרשאות של התהליך — ה-umask.

הדגלים שראינו בקורס

דגלמה הוא אומר לקרנל
O_RDONLYפתח לקריאה בלבד. (כך נפתח קובץ המקור ב-cp.)
O_WRONLYפתח לכתיבה בלבד. ניסיון read() על פתיחה כזו ייחסם.
O_RDWRפתח במצב שמאפשר גם קריאה וגם כתיבה.
O_CREAT אם הקובץ אינו קיים פיזית — צור אותו אוטומטית (הקצאת Inode חדש + הוספת Directory Entry בתיקיית היעד). אם הקובץ כבר קיים — הדגל מתעלם באדיבות והקובץ נפתח רגיל.
O_TRUNCאם הקובץ קיים — אפס את תוכנו (חתוך אותו לאורך 0). ב-cp כך נפתח קובץ היעד: O_WRONLY | O_CREAT | O_TRUNC.
O_APPENDכל כתיבה תתווסף אוטומטית לסוף הקובץ. המנגנון המדויק — בשלב 3 של אלגוריתם ה-write.
O_SYNC / O_DSYNCדגלי סנכרון מחמירים: הכתיבה תרד לדיסק מיד ולא תמתין לתהליכי הרקע (שלב 9 של write).

פירוק 0644 (אוקטלי)

6

למה דווקא 6 ו-4? המספר נכתב באוקטלי (בסיס 8) — ולכן הקידומת 0 בקוד. כל ספרה היא סכום של שלוש הרשאות: 4 = קריאה, 2 = כתיבה, 1 = הרצה. מכאן 6 = 4+2 (קריאה+כתיבה) ו-4 (קריאה בלבד). ההרשאות בפועל נכתבות לשדה i_mode של ה-Inode — אחרי סינון ה-umask.

ערכי חזרה ושגיאות

  • הצלחה: מספר שלם אי-שלילי — ה-fd. הקרנל בוחר את המקום הפנוי הראשון בטבלת תיאורי הקבצים של התהליך (למשל 3, כי 0,1,2 תפוסים).
  • כישלון: -1 — ואז בודקים fd == -1 ומדפיסים את השגיאה עם perror().

הקוד מהחוברת

מה זה עושה: פותח את הקובץ /home/Itzhak/lecture01 לקריאה+כתיבה ויוצר אותו עם הרשאות 0644 אם אינו קיים; אם הפתיחה נכשלה — מדפיס למה ויוצא; אחרת סוגר ומסיים. זו הדוגמה היחידה שמשלבת את כל שלושת הארגומנטים. 

#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>

int main() {
    int fd;

    fd = open("/home/Itzhak/lecture01", O_RDWR | O_CREAT, 0644);

    if (fd == -1) {
        perror("Error opening/creating file");
        return 1;
    }

    close(fd);
    return 0;
}

מה קורה בקרנל (Linux Kernel 6.14) מרגע ביצוע הפקודה?

  1. מעבר מ-User ל-Kernel Mode: קריאת ה-open מפעילה פקודת אסמבלי (syscall), והמעבד עובר מ-Ring 3 ל-Ring 0. בגרעין מודרני כמו 6.14 הקריאה מתועלת לפונקציית הליבה הראשית sys_openat (הפרמטר הראשון המרומז הוא AT_FDCWD, אך מתעלמים ממנו כי הנתיב אבסולוטי).
  2. העתקת הנתיב ממרחב המשתמש: הקרנל מעתיק בבטחה את מחרוזת הנתיב מזיכרון המשתמש אל זיכרון הקרנל באמצעות פונקציית העתקה ייעודית — strncpy_from_user.
  3. Path Resolution — איתור או יצירת Inode: הקרנל סורק את עץ הספריות החל מהשורש (/), עובר דרך home ואז Itzhak, ומגיע לשם הסופי lecture01. אם הקובץ קיים — הוא מאתר את ה-Inode שלו בטבלת ה-Inodes. אם הקובץ אינו קיים (וצוין O_CREAT) — הקרנל מקצה Inode חדש, רושם אותו ב-Inode Bitmap, יוצר Directory Entry חדש תחת התיקייה Itzhak, ומחיל את ההרשאות שהועברו ב-mode (בכפוף ל-umask) על שדה ה-i_mode של ה-Inode החדש.
  4. יצירת אובייקט קובץ פתוח (struct file): הקרנל מקצה מבנה נתונים דינמי בשם struct file, השומר את מצב הפתיחה הנוכחי של התהליך — כגון ה-File Offset שמתחיל כרגע ב-0, והדגלים שנבחרו כמו O_RDWR.
  5. הקצאת File Descriptor: הקרנל סורק את טבלת תיאורי הקבצים של התהליך השמורה ב-current->files (מבנה struct files_struct), מוצא את המקום הפנוי הראשון (למשל אינדקס 3), ורושם בתא מצביע אל ה-struct file שיצר.
  6. חזרה למרחב המשתמש: הקרנל מחזיר את המספר 3 אל פונקציית ה-open במרחב המשתמש. מספר זה (fd) הוא המפתח שבו ישתמש התהליך בכל פעם שירצה לקרוא או לכתוב לקובץ.

מלכודות למבחן: (1) הארגומנט mode רלוונטי רק בשילוב O_CREAT; (2) אם הקובץ כבר קיים — O_CREAT פשוט מתעלם והקובץ נפתח רגיל; (3) נתיב שמתחיל ב-'/' גורם לקרנל להתעלם לגמרי מה-CWD; (4) mode תמיד עובר סינון של ה-umask — ההרשאות בפועל אינן בהכרח מה שכתבתם; (5) ה-fd שמתקבל הוא המקום הפנוי הראשון בטבלה, לא מספר רץ גלובלי.

מקור: open.pdf (עמ' 1–3); דגלי היעד — simple_cp.pdf (עמ' 2)

2. read() — שמונה שלבים מה-fd ועד הבאפר

read() היא הפעולה הבסיסית שבאמצעותה תוכנית במרחב המשתמש שואבת נתונים מקובץ פתוח. ב-Linux Kernel 6.14 היא מתבצעת דרך שכבת ה-VFS, עושה שימוש נרחב במטמון הזיכרון (Page Cache) של הקרנל, ומנהלת את התקשורת עם התקני ה-SSD במידת הצורך.

חתימה ופרמטרים

ssize_t read(int fd, void *buf, size_t count);
פרמטרטיפוסתפקיד
fdint תיאור הקובץ שקיבלנו מ-open — האינדקס בטבלת תיאורי הקבצים של התהליך.
bufvoid * הבאפר שלכם במרחב המשתמש — המערך שאליו הקרנל יעתיק את הנתונים. הוא לא const, כי הקרנל אכן משנה אותו.
countsize_t מספר הבייטים המקסימלי לקריאה — בקשה, לא הבטחה.

ערכי חזרה ושגיאות

  • מספר חיובי — מספר הבייטים שנקראו בפועל (עלול להיות קטן מ-count).
  • 0 — הגענו לסוף הקובץ (EOF). זו לא שגיאה.
  • -1 עם errno = EBADF (בקרנל: -EBADF) — fd לא תקין / לא פתוח, או קובץ שנפתח אך ורק לכתיבה (O_WRONLY) — אין אישור קריאה ב-f_mode.
  • -1 עם errno = EFAULT — כתובת הבאפר של המשתמש פגומה או לא חוקית; copy_to_user תופסת את החריגה מבלי לגרום לקריסת מערכת ההפעלה.
🎓 מהשיעור בכיתה (מהמחברת)

המרצה כתב את הקריאה על הלוח וסימן מעל הארגומנט השלישי את השם שהוא נותן לו — granularity level (רמת הגרעיניות): כמה נתונים מבקשים בכל קריאה בודדת. 

                          granularity level
                                  |
                                  v
char my_buf[BUFFER_SIZE];
n = read(source_fd, my_buf, 1);   /* one byte per call */
  • source_fd — ה-fd שהתקבל מ-open; my_buf — הבאפר שהתוכנית מקצה לעצמה במרחב המשתמש.
  • המרצה הדגיש במפורש: read מחזירה 0 ב-EOF — ולא -1. הערך -1 שמור אך ורק לשגיאה. זו נקודה שהוא חזר עליה, וקל להתבלבל בה במבחן.
  • וכן: הערך המוחזר הוא מספר הבייטים שנקראו בפועל, לא בהכרח מה שביקשנו — Partial I/O, סעיף 5.
  • ה-granularity הזה הוא גם מה שקובע כמה יקרה הקריאה — ראו את הסעיף "Syscall יקר!" בסעיף 5.

שימוש מינימלי

מה זה עושה: מבקש מהקרנל עד 4096 בייטים מהקובץ הפתוח אל תוך המערך buffer, ובודק את שלושת המצבים האפשריים — שגיאה, סוף קובץ, או כמה בייטים באמת הגיעו. 

char    buffer[4096];
ssize_t bytes_read;

bytes_read = read(src_fd, buffer, 4096);

if (bytes_read == -1) {          /* כישלון */
    perror("Error reading from file descriptor");
    exit(EXIT_FAILURE);
}
if (bytes_read == 0) {           /* EOF — אין עוד מה לקרוא */
    /* ... */
}
/* אחרת: bytes_read בייטים תקינים ממתינים ב-buffer */

האלגוריתם בקרנל — שמונה שלבים

  1. כניסה לקרנל ואיתור אובייקט הקובץ (fdget / sys_read): פקודת ה-syscall מעבירה את המעבד מ-Ring 3 ל-Ring 0 והבקשה מגיעה ל-sys_read. הקרנל פונה לטבלת תיאורי הקבצים של התהליך (current->files) ושולף את המצביע ל-struct file * התואם. fd לא תקין → עצירה מיידית עם -EBADF.
  2. בדיקת תקינות והרשאות קריאה (File Status & f_mode): (f_mode = השדה ב-struct file ששומר את מצב הגישה שנקבע ברגע הפתיחה — קריאה, כתיבה או שניהם.) הקרנל מוודא שהקובץ נפתח במקור עם דגל קריאה חוקי (O_RDONLY או O_RDWR). קובץ שנפתח רק לכתיבה — הפעולה נחסמת מיד עם -EBADF.
  3. הפעלת ממשק ה-VFS (new_sync_read / vfs_read): פונקציית התווך הגנרית vfs_read ניגשת למערך הפעולות של מערכת הקבצים (file->f_op->read או read_iter) ומפעילה את מתודת הקריאה המתאימה — לרוב read_iter; עבור ext4 הקריאה מנותבת למתודה הייעודית ext4_file_read_iter.
  4. בדיקת מטמון הזיכרון (Page Cache Lookup — Hit vs. Miss): הקרנל מחשב איזה עמוד זיכרון (Page, בגודל 4KB) מכיל את הבייטים המבוקשים לפי המיקום הנוכחי בקובץ (f_pos) ובודק האם העמוד כבר קיים ב-RAM. Cache Hit — הנתונים כבר בזיכרון: מדלגים לחלוטין על הדיסק הפיזי, מהירות אדירה. Cache Miss — הנתונים אינם ב-RAM, וחייבים לפנות ל-SSD.
  5. קריאת הבלוקים מהדיסק (SSD Read & Block I/O — רק ב-Cache Miss): דרייבר מערכת הקבצים מתרגם את הדרישה הלוגית לבלוקים פיזיים (בעזרת עץ ה-Extents של ה-Inode); הקרנל מייצר אובייקט bio ושולח בקשת I/O דרך שכבת הבלוקים (blk-mq) ובקר ה-NVMe; הבלוקים נקראים מה-SSD אל תוך ה-Page Cache — ורק אחרי שהנתונים נטענו בהצלחה ל-RAM ממשיכים לשלב הבא.
  6. העתקה למרחב המשתמש (copy_to_user): תהליך המשתמש אינו יכול לגשת לזיכרון הליבה מסיבות אבטחה חמורות, ולכן הקרנל מפעיל את פונקציית ההעברה המוגנת copy_to_user, שמעתיקה את הבייטים מבאפר הקרנל אל הבאפר (buf) שהוקצה על ידי התהליך.
  7. עדכון מיקום הקובץ (f_pos): מצביע ה-File Offset, השמור ב-struct file, גדל בדיוק במספר הבייטים שנקראו בפועל — כך שהקריאה הבאה תמשיך לינארית מהנקודה שבה הפסיקה הקודמת.
  8. סיום והחזרה למרחב המשתמש: שחרור הנעילות מעל דפי הזיכרון, עדכון חותמת זמן קריאה (atime ב-Inode אם נדרש), מעבר חזרה מ-Ring 0 ל-Ring 3, והחזרת מספר הבייטים שנקראו בפועל (0 אם הגענו ל-EOF).

f_pos הוא פר-פתיחה, לא פר-קובץ: מכיוון ש-f_pos שמור באובייקט ה-struct file של פתיחת הקובץ הספציפית, שני תהליכים שונים שפתחו את אותו קובץ מחזיקים מצביעי f_pos נפרדים ועצמאיים לחלוטין.

מלכודות למבחן: (1) read() שמחזירה 0 היא לא שגיאה — זה סוף הקובץ (EOF); (2) count הוא תקרה, לא הבטחה — תמיד עובדים לפי הערך שהוחזר; (3) הקריאה חוסמת: הקרנל מרדים את התהליך עד שהדיסק/מערכת הקבצים מספקים את הנתונים (מההערות בקוד ה-cp).

מקור: read.pdf (עמ' 1–3)

3. write() — עשרה שלבים והסוד של ה-Buffered I/O

write() מעבירה נתונים מהתהליך אל קובץ פתוח — אבל הנקודה החשובה ביותר היא שב-Linux Kernel 6.14 הכתיבה מנוהלת לרוב במנגנון Buffered I/O (קלט/פלט ממוקד מטמון): הנתונים נכתבים תחילה אל ה-Page Cache ב-RAM ורק בהמשך מסונכרנים אל התקן ה-SSD הפיזי — אלא אם הוגדרו דגלי סנכרון מיידי.

חתימה ופרמטרים

ssize_t write(int fd, const void *buf, size_t count);
פרמטרטיפוסתפקיד
fdint תיאור הקובץ שאליו כותבים.
bufconst void * באפר המקור בתהליך. שימו לב: const — בניגוד ל-read, שבה void * (הקרנל רק קורא מהבאפר שלנו, לא משנה אותו).
countsize_t מספר הבייטים לכתיבה.

ערכי חזרה ושגיאות

  • מספר חיובי — מספר הבייטים שנכתבו בפועל (תואם ל-count).
  • -1 עם errno = EBADF (בקרנל: -EBADF) — fd לא תקין, או קובץ שנפתח אך ורק לקריאה (O_RDONLY) — הכתיבה נחסמת בבדיקת f_mode.

שימוש מינימלי

מה זה עושה: כותב לקובץ היעד בדיוק את מספר הבייטים שקראנו קודם (ולא את גודל הבאפר כולו), ובודק כישלון לפי המוסכמה של -1. 

ssize_t bytes_written;

bytes_written = write(dest_fd, buffer, bytes_read);

if (bytes_written == -1) {
    /* 1. קריאת המערכת נכשלה   2. הקרנל עדכן את errno */
    perror("Error writing to file descriptor");
    exit(EXIT_FAILURE);
}
/* 3. אם הגענו לכאן ה-write הצליח — ייתכן שרק חלקית */

האלגוריתם בקרנל — עשרה שלבים

  1. כניסה לקרנל ואיתור אובייקט הקובץ (fdget / sys_write): מעבר מ-Ring 3 ל-Ring 0; הבקשה מגיעה ל-sys_write (או ksys_write). הקרנל שולף מ-current->files את המצביע ל-struct file *; fd לא תקין → -EBADF.
  2. בדיקת תקינות והרשאות כתיבה (f_mode): נדרש דגל כתיבה חוקי מהפתיחה (O_WRONLY או O_RDWR); קובץ שנפתח O_RDONLY בלבד → -EBADF.
  3. ניהול מצבי כתיבה מיוחדים ונעילות (Locks & O_APPEND): אם הקובץ נפתח עם O_APPEND — לפני כל כתיבה הקרנל מעדכן אוטומטית את f_pos להצביע בדיוק על סופו הנוכחי של הקובץ (ערך ה-i_size של ה-Inode), כדי שהנתונים החדשים יתווספו תמיד לסוף בלי לדרוס מידע קיים — קריטי בסביבה מרובת-תהליכים. במקביל מופעלים מנעולים ברמת ה-In-Core Inode (כגון i_rwsem) כדי למנוע מצבי תחרות (Race Conditions) שבהם שני תהליכים כותבים לאותו קובץ בדיוק באותה מיקרו-שנייה.
  4. הפעלת ממשק ה-VFS ומערכת הקבצים (vfs_write / ext4_file_write_iter): הבקשה מנותבת דרך שכבת ההפשטה למתודת ה-write_iter של מערכת הקבצים — ב-ext4 זו ext4_file_write_iter, שמנהלת את אופן כתיבת הנתונים לעץ ה-Extents.
  5. הבאה/הקצאה של דפי זיכרון בטוחים (Page Cache Allocation & Read-Modify-Write): זהו הלב הפועם של כתיבה ממוקדת מטמון. הקרנל מחשב איזה עמוד 4KB תואם למיקום הכתיבה (f_pos) ובודק אם הוא כבר במטמון. אם העמוד אינו בזיכרון (Cache Miss) והכתיבה מעדכנת חלק בלבד מהבלוק (Partial Block Write — למשל 100 בייט באמצע בלוק של 4KB), הקרנל נאלץ לבצע Read-Modify-Write: לקרוא תחילה את הבלוק הפיזי מה-SSD אל ה-RAM, כדי ששאר חלקי הבלוק לא יושחתו. אם מדובר בכתיבה מלאה של עמוד שלם (4KB) — הקרנל פשוט מקצה עמוד זיכרון ריק ב-RAM בלי לקרוא מהדיסק.
  6. העתקת הנתונים ממרחב המשתמש לקרנל (copy_from_user) וסימון Dirty: הפונקציה המוגנת copy_from_user מעתיקה מבאפר התהליך אל דפי ה-Page Cache (הכיוון ההפוך מ-copy_to_user של read). מיד לאחר מכן הדף מסומן בדגל Dirty Page (SetPageDirty) — סימון שהנתונים ב-RAM שונים כעת ממה שעל הדיסק ודורשים סינכרון עתידי.
  7. עדכון המטא-דאטה, המיקום וה-Inode (i_size & f_pos): קידום f_pos בדיוק במספר הבייטים שנכתבו; אם הכתיבה הרחיבה את הקובץ מעבר לגודלו הקודם — עדכון שדה i_size ב-In-Core Inode; וסימון ה-Inode עצמו כמלוכלך (I_DIRTY_DATASYNC).
  8. הקצאת בלוקים פיזיים (Extents & Block Allocation): אם הכתיבה דרשה הקצאת מקום חדשה על הדיסק (הקובץ גדל מעבר לבלוקים שהוקצו לו בעבר), ext4 משתמשת לרוב ב-Delayed Allocation (הקצאה דחויה) — דחיית ההקצאה הפיזית על ה-SSD כדי לייעל אותה ולמנוע פיצול (Fragmentation), בעוד הנתונים שמורים בבטחה ב-Page Cache. כשההקצאה מתבצעת לבסוף, מנגנון ה-Extents של ext4 מעדכן את עץ המיפוי ב-Inode ומצביע על מתחמי הבלוקים החדשים.
  9. סינכרון ורישום ביומן (Journaling / Writeback): להבטחת אמינות מערכת הקבצים במקרה של קריסה, ext4 רושמת את שינויי המטא-דאטה ליומן הטרנזקציות המנוהל על ידי תת-המערכת jbd2. הנתונים עצמם שוהים בינתיים בבטחה ב-Page Cache, וייכתבו פיזית ל-SSD על ידי תהליכי רקע של הקרנל (חוטי ה-Writeback / flusher threads) — או באופן מיידי, אם התהליך פתח את הקובץ עם דגלי סנכרון מחמירים (O_SYNC או O_DSYNC).
  10. סיום והחזרה למרחב המשתמש: שחרור הנעילות מעל ה-Inode, מעבר חזרה מ-Ring 0 ל-Ring 3 והחזרת מספר הבייטים שנכתבו בפועל.

אז מתי הדיסק באמת מתעדכן?

זו אולי הנקודה הכי לא-אינטואיטיבית בפרק: write() שחזרה בהצלחה מבטיחה שהנתונים בזיכרון של הקרנל, לא שהם על הדיסק. המסלול המלא:

מכאן גם היתרון הגדול: כתיבה חוזרת לאותו אזור בקובץ מעדכנת דף שכבר ב-RAM, וקריאה של מה שנכתב זה עתה תיפגע ב-Cache Hit ולא תיגע בדיסק כלל. הקרנל "משלם" את מחיר הדיסק פעם אחת, ברקע, ובאצווה.

🎓 מהשיעור בכיתה (מהמחברת)

בכיתה המרצה צייר את אותו מנגנון בדיוק, אבל בשמות שלו: בקרנל יש data block buffer — ענן של בלוקים שנקראו מה-NVM אל ה-MM. בלוק ששונה בזיכרון ועוד לא ירד לדיסק מסומן בדגל dirty. זהו אותו רעיון שבשקפים נקרא Page Cache ו-Dirty Page; שווה להכיר את שני השמות, כי בשאלה בכיתה הוא עשוי להשתמש בניסוח שלו.

וההדגמה היומיומית שהוא נתן, בקופסה על הלוח: Ctrl + S → flush אל ה-NVM. כלומר: כל עוד לא "שמרתם", העריכה שלכם יושבת בבאפר של הקרנל ב-RAM בלבד — וזו הסיבה האמיתית שהמסמך נעלם בהפסקת חשמל. זו התשובה האינטואיטיבית לשאלה "מתי הנתונים באמת על הדיסק?".

שני מנגנוני הגנה בשלב 3 — אל תערבבו: O_APPEND פותר את בעיית ה"לאן כותבים" (תמיד לסוף הקובץ, לפי i_size), ואילו הנעילה i_rwsem פותרת את בעיית ה"מי כותב עכשיו" — מניעת Race Condition בין שני תהליכים שכותבים בו-זמנית. שניהם פועלים יחד בסביבה מרובת-תהליכים.

מקור: write.pdf (עמ' 1–4); תבנית בדיקת השגיאה — error.pdf (עמ' 5)

4. close() — הרבה יותר מ"סגירת חלון"

close() מודיעה לקרנל שהתהליך סיים לעבוד עם קובץ פתוח, ומבקשת לנתק את הקשר בינו לבין ה-FD ולשחרר את המשאבים. אבל הפעולה אינה מסתכמת ב"סגירת חלון" — היא מנהלת מנגנוני ניפוי הפניות (Reference Counting), שחרור זיכרון וסינכרון מורכבים.

חתימה, ערכי חזרה ושגיאות

int close(int fd);
  • 0 — הצלחה מלאה של פעולת הסגירה.
  • -1 עם errno = EBADF (בקרנל: -EBADF) — ה-fd שגוי, מחוץ לגבולות הטבלה, או אינו פתוח.

שימוש מינימלי

מה זה עושה: משחרר את שני ה-FDs של תוכנית ה-cp בסיום העבודה. שימו לב שגם במסלול השגיאה סוגרים את מה שכבר נפתח — דליפת descriptors היא באג קלאסי. 

/* close() is a system call. It informs the Kernel that we are done.
 * The Kernel can now free the resources associated with these file descriptors. */
close(src_fd);
close(dest_fd);

האלגוריתם בקרנל — שבעה שלבים

  1. כניסה לקרנל ואימות ה-FD (sys_close / __close_fd): מעבר מ-Ring 3 ל-Ring 0; הקרנל בודק שה-fd (למשל 3) נמצא בגבולות החוקיים של טבלת התהליך ושהוא אכן מצביע על אובייקט קובץ פעיל ותקין. fd שגוי או לא פתוח → -EBADF.
  2. הסרת ה-FD מטבלת התהליך (inverse fd_install): הקרנל מוחק מיד את הרישום מתוך current->files->fd_array[fd] ומאפס את הסיביות המתאימות במפת הביטים של ה-FDs. מרגע זה ה-FD חדל להתקיים עבור התהליך: read/write נוספים על אותו מספר ייכשלו מיד עם -EBADF, והמספר מתפנה להקצאה מחדש לקובץ או סוקט עתידיים.
  3. הפחתת מונה ההפניות לאובייקט הקובץ (fput): הקרנל מפעיל את fput() על ה-struct file * שאליו הצביע ה-FD, והמונה הפנימי f_count קטן ב-1 באופן אטומי (atomic_long_sub_and_test).
  4. בדיקת מצב המונה — האם זהו המחזיק האחרון? אם f_count > 0 — עדיין יש מחזיקים נוספים, הקרנל מסתפק בהפחתת המונה ויוצא מהפונקציה כאן, והקובץ נשאר פתוח עבורם. אם f_count == 0 — התהליך היה הבעלים האחרון, והקרנל ממשיך מיד לניקוי המלא בשלבים 5–6 (השמדת האובייקט).
  5. הפעלת מתודת השחרור של מערכת הקבצים (file_operations->release): מופעלת פונקציית הניקוי המותאמת של מערכת הקבצים או הדרייבר (file->f_op->release, למשל ext4_release_file): מחיקת מבני נתונים זמניים שנוצרו עבור הפתיחה, שחרור נעילות רשומות (Record Locks) שהתהליך החזיק, וניקוי הקשרים מול התקני חומרה או סוקטים רשתיים.
  6. ניקוי מתווה ה-VFS — שחרור dentry ו-inode (dput & iput): dput מפחית את מונה ההפניות של ה-dentry — שעשוי להשתחרר מהזיכרון או להישאר במטמון ה-Dcache לשימוש עתידי מהיר; iput מפחית את מונה ההפניות של ה-In-Core Inode — ואם הוא מגיע לאפס (ואין קישורים קשיחים פעילים נוספים), מתבצע סינכרון סופי של המטא-דאטה (אם הוגדר) והזיכרון משתחרר מטבלת ה-Hash של הליבה. לבסוף, זיכרון ה-struct file מוחזר למטמון ה-SLAB הקרנלי שממנו הוקצה (filp_cachep) — SLAB הוא מנגנון המחזור של הקרנל למבנים קטנים שנוצרים ונהרסים תדיר, כדי לא לבקש זיכרון חדש בכל פתיחת קובץ.
  7. סיום והחזרה למרחב המשתמש: חזרה ל-Ring 3 והחזרת הערך 0 (הצלחה).

מונה ההפניות — f_count

למה בכלל צריך מונה? כי תהליכים בלינוקס יכולים לשכפל תיאורי קבצים — באמצעות fork(), dup() או dup2() — כך ששני תהליכים שונים (או שני FDs שונים באותו תהליך) מצביעים בדיוק על אותו אובייקט struct file בזיכרון. בלי מונה, ה-close הראשון היה הורס את האובייקט מתחת לרגליהם של כל היתר.

f_count > 0 אחרי ההפחתה

ישנם עדיין מחזיקים נוספים (למשל תהליך אב ותהליך בן שירש את הפתיחה). הקרנל מסתפק בהפחתת המונה ויוצא — הקובץ נשאר פתוח עבור יתר המחזיקים.

f_count == 0

התהליך היה "הבעלים האחרון" ואיש אינו משתמש עוד באובייקט. הקרנל ממשיך מיד לניקוי המלא: release → dput/iput → החזרת ה-struct file ל-SLAB.

שימו לב להפרדה: הסרת ה-FD מהטבלה (שלב 2) קורית תמיד, גם כשהאובייקט נשאר חי. מה שתלוי במונה הוא רק גורלו של ה-struct file המשותף.

מלכודת למבחן — close אינה flush: עברו שוב על שבעת השלבים — אין בהם שלב של כתיבת ה-Dirty Pages לדיסק. כפי שראינו באלגוריתם של write, את הסנכרון הפיזי ל-SSD מבצעים תהליכי ה-Writeback ברקע (רק ב-iput, ורק כשמונה ה-Inode מגיע לאפס, מתבצע סינכרון סופי של המטא-דאטה אם הוגדר). כלומר: close() שהחזירה 0 אינה אישור שהנתונים כבר על הדיסק.

מקור: close.pdf (עמ' 1–3)

5. Partial I/O — הלולאה הנכונה

‎read() מחזירה את מספר הבייטים שנקראו בפועל — לא בהכרח את count שביקשתם. הסיבה עולה ישירות מהאלגוריתם: הקובץ עלול להיגמר באמצע (שלב 8 מחזיר את מה שהצטבר), ובקצה יש כמעט תמיד "שארית" קטנה מ-4KB. לכן קוד נכון אף פעם לא קורא "פעם אחת ודי": הוא רץ בלולאה עד שמוחזר 0 (EOF), ובכל סיבוב כותב בדיוק את מה שנקרא (bytes_read) ומוודא שהכתיבה הצליחה במלואה.

מה זה עושה: זו לולאת ההעתקה מגרסת קריאות המערכת של תוכנית ה-cp (simple_cp_syscall.c) — כל סיבוב קורא מקטע מהמקור וכותב אותו ליעד, עד סוף הקובץ; בסיום סוגרים את שני ה-FDs. 

    /*
     * read() is a system call. It requests the Kernel to copy data from the
     * file into our buffer. The Kernel puts the process to sleep until the
     * disk/filesystem delivers the data.
     */
    while ((bytes_read = read(src_fd, buffer, BUFFER_SIZE)) > 0) {
        /*
         * write() is a system call. It asks the Kernel to take data from our
         * buffer and place it into the destination file.
         */
        bytes_written = write(dest_fd, buffer, bytes_read);
        if (bytes_written != bytes_read) {
            perror("Error writing data");
            close(src_fd);
            close(dest_fd);
            exit(EXIT_FAILURE);
        }
    }

    /*
     * close() is a system call. It informs the Kernel that we are done.
     * The Kernel can now free the resources associated with these file descriptors.
     */
    close(src_fd);
    close(dest_fd);

    return EXIT_SUCCESS;

מה הופך את הלולאה הזו ל"נכונה"?

  • העתקה במקטעים: ‎BUFFER_SIZE = 4096 — קוראים וכותבים במקטעים (chunks) של 4KB, לא בייט-בייט. (וזה בדיוק גודל ה-Page של ה-Page Cache.)
  • תנאי העצירה הוא ‎> 0: הלולאה נעצרת כשמוחזר 0 — כלומר EOF — ולא לפי ניחוש של גודל הקובץ. ערך שלילי (-1) גם הוא מסיים את הלולאה, כי הוא אינו גדול מ-0.
  • כותבים bytes_read, לא BUFFER_SIZE: בסיבוב האחרון ייתכן שנקראו פחות מ-4096 בייטים — כותבים בדיוק את מה שנקרא. אחרת היינו מעתיקים "זבל" ישן מהבאפר אל קובץ היעד.
  • בודקים ‎bytes_written != bytes_read: זהו הטיפול בשגיאת כתיבה — ואם נכשלנו, סוגרים את שני ה-FDs לפני היציאה (דליפת descriptors היא באג קלאסי).
  • הטיפוס הנכון: הערך המוחזר מ-read/write הוא ssize_t (עם סימן) — לא size_t. עם size_t חסר-סימן, הערך -1 היה הופך למספר עצום חיובי והבדיקה הייתה נשברת.

🎓 מהשיעור בכיתה (מהמחברת) "Syscall יקר!" — למה גודל ה-granularity קובע את המהירות

את המשפט הזה המרצה כתב על הלוח בקצרה ובסימן קריאה: "Syscall יקר [בזמן]!". הסיבה מוכרת לנו כבר משני האלגוריתמים למעלה — כל קריאת מערכת גוררת מעבר Ring 3 → Ring 0 וחזרה, בדיקות תקינות, מציאת ה-struct file, נעילות ועוד. התקורה הזו משולמת בכל קריאה — בלי קשר לכמה בייטים ביקשנו בה.

ומכאן ההשלכה שהוא הדגים עם שלושת המספרים 1, 2, 4096: לאותו קובץ בדיוק, ה-granularity קובע כמה קריאות מערכת יתבצעו. נניח קובץ בגודל 4096 בייט:

granularity (הארגומנט השלישי)כמה קריאות read יידרשוהמשמעות
1 בייט4096 קריאות מערכתאיטי בצורה קיצונית — משלמים את מחיר המעבר לקרנל 4096 פעם כדי להעביר 4KB.
2 בייט2048 קריאות מערכתחצי מהתקורה, אבל עדיין סדר גודל רחוק מהאופטימום.
4096 בייטקריאה אחתמעבר אחד לקרנל, ובדיוק בגודל ה-Page של ה-Page Cache. זו הסיבה ש-BUFFER_SIZE בקוד ה-cp הוא 4096.

הדגש למבחן (המרצה סימן אותו לעצמו כנקודה לזכור): ה-granularity אינו משפיע על נכונות התוכנית — היא תעתיק את הקובץ נכון גם בייט-בייט. הוא משפיע על מספר קריאות המערכת, ולכן על הזמן. אם בשאלה מופיע read(fd, buf, 1) בלולאה — הפגם הוא ביצועים, לא באג.

🎓 מהשיעור בכיתה (מהמחברת) תרגיל ה-cp כפי שפורק על הלוח — טבלת ה-fd, שני in-core inodes ו-O_CREAT

המרצה פירק את אותה תוכנית שראינו למעלה למבנים שמאחוריה. שתי הפתיחות מקבלות את שני המקומות הפנויים הראשונים בטבלה — 3 ו-4, כי 0, 1 ו-2 כבר תפוסים על ידי stdin, stdout ו-stderr: 

example task_struct
   |
 [files] --> open fd table          in-core inodes
              0  stdin
              1  stdout
              2  stderr
              3  ---------------->  in-core inode  (source file)
              4  ---------------->  in-core inode  (dest file)   dirty? W/Append?
                                          |
                                          v
                                    disk inode  { owner, mode, ... , data --> data blocks }
  • שני in-core inodes נפרדים — אחד למקור ואחד ליעד. שניהם חיים ב-MM ומצביעים, כל אחד, אל ה-disk inode שלו על ה-NVM (שם יושבים owner, mode, ומצביעי ה-data אל ה-Data Blocks). המבנה המלא נלמד במודול 5.
  • פתיחת קובץ היעד: על הלוח נכתב dest_fd = open(pathname_dest, flags, mode), והמרצה סימן לעצמו את O_CREAT כנקודה לזכור — כי קובץ היעד לרוב אינו קיים, וצריך לבקש מהקרנל ליצור אותו.
  • ההחלטה Write מול Append: אחרי שהחלטנו ליצור, צריך להחליט מה קורה כשהקובץ כן קיים — לדרוס את תוכנו (O_TRUNC, כמו בקוד ה-cp) או להוסיף בסופו (O_APPEND). המרצה הצמיד לזה את lseek() (סעיף 7): O_APPEND כותב תמיד לסוף, ואם רוצים למקם את הכתיבה במקום אחר — משתמשים ב-lseek.
  • ה-write ליעד מעדכן את ה-data block שלו דרך הבאפר בקרנל, והבלוק מסומן dirty עד ה-flush — כפי שראינו בסעיף 3.
הרחבה — למה בכלל "חלקי"? מה אומרים על כך שקפי טיפול השגיאות

בשקפי ה-write המספר המוחזר מתואר כתואם ל-count, ואכן בקובץ רגיל על הדיסק זה המצב הרגיל. אבל בשקף בדיקת השגיאות (error.pdf, מודול 3) המרצה כותב במפורש בהערה בקוד: "אם הגענו לכאן ה-write הצליח — ייתכן שרק חלקית". שתי האמירות מתיישבות: הבדיקה == -1 מזהה כישלון, אבל היא לבדה אינה מבטיחה שכל הבייטים נכתבו — ולכן קוד ה-cp מוסיף את הבדיקה החזקה יותר bytes_written != bytes_read. זו בדיוק הסיבה שהנושא נקרא Partial I/O ומופיע ככותרת נפרדת בסילבוס.

מקור: simple_cp.pdf (עמ' 2–3) — נלמד לעומק בפרק "דוגמה מלאה: cp"; ההערה על כתיבה חלקית — error.pdf (עמ' 5)

ב. הקרנל — מה קורה מאחורי הקלעים

קריאהפונקציית הליבהשלביםהמנגנון המרכזימה משתנה במבני הנתונים

הסימטריה שכדאי לזכור: שלושת הצעדים הראשונים של read, write ו-close זהים כמעט מילה במילה — מעבר Ring 3 → Ring 0, תרגום ה-fd דרך current->files אל struct file, ובדיקת f_mode/תקינות — ולכן כולן מחזירות את אותה שגיאה, EBADF, על fd לא תקין. open() יוצאת דופן: היא זו שיוצרת את שני המבנים האלה, ולכן היא היחידה שעובדת עם נתיב ולא עם fd.

🎓 מהשיעור בכיתה (מהמחברת) fread/fwrite הן glibc — ו-FILE אינו file descriptor

זו ההבחנה שהמרצה סגר איתה את השיעור, והיא מבלבלת כמעט כל מי שהגיע מ-C "רגילה". ארבע הקריאות בעמוד הזה — open, read, write, close — הן קריאות מערכת. הפונקציות שמוכרות מקורס C — fopen, fread, fwrite, fprintf, fscanf, fclose — הן פונקציות ספרייה של glibc, ולא קריאות מערכת. הן רצות במרחב המשתמש, מנהלות באפר משלהן, ובסוף קוראות בעצמן ל-read/write.

למה זה חשוב: השכבה של glibc היא שמסבירה את הבאפר הכפול (באפר של הספרייה מעל ה-Page Cache של הקרנל), ואת העובדה שאפשר לבנות מעל קריאות המערכת שכבות שלמות — עד מנוע מסדי נתונים כמו MySQL, הדוגמה שהמרצה נתן בכיתה לשכבה שיושבת מעל הכול ובסוף גם היא כותבת לקובץ.

7. הרחבה — לא מהשקפים: lseek(), stat() וקריאת תיקייה

הרחבה — לא מהשקפים

הסילבוס מזכיר בשיעור 6 גם שינוי מיקום בקובץ וגישה למטא-דאטה, אך לא הועלו עבורם שקפים. כל מה שבסעיף הזה מתבסס על דפי ה-man של לינוקס ומובא כדי לסגור את התמונה — לא כחומר בחינה. הוא אינו סותר דבר ממה שהמרצה לימד; להפך, הוא נוגע בדיוק באותם שדות Inode ממודול 5.

lseek() — להזיז את מצביע המיקום

עד כה f_pos התקדם רק לבד, אחרי כל read/write. lseek() היא הקריאה שמזיזה אותו ידנית — בלי לגעת בדיסק בכלל, כי היא רק משנה שדה בתוך ה-struct file. 

off_t lseek(int fd, off_t offset, int whence);
whenceהמשמעות
SEEK_SETהמיקום החדש = offset, נמדד מתחילת הקובץ.
SEEK_CURהמיקום החדש = המיקום הנוכחי + offset (offset שלילי = אחורה).
SEEK_ENDהמיקום החדש = סוף הקובץ + offset.

ערך החזרה: המיקום החדש בבייטים מתחילת הקובץ; בכישלון — (off_t) -1 ו-errno מתעדכן.

מה זה עושה: קופץ לסוף הקובץ כדי לקבל את גודלו (כי המיקום החדש בסוף = מספר הבייטים בקובץ), ואז חוזר לתחילתו כדי שהקריאה הבאה תתחיל מ-0. 

off_t size = lseek(fd, 0, SEEK_END);   /* קפיצה לסוף → הערך המוחזר הוא גודל הקובץ */
lseek(fd, 0, SEEK_SET);                /* חזרה להתחלה */

stat() / fstat() — לקרוא את המטא-דאטה

אלה הקריאות ששואבות את שדות ה-Inode אל מבנה במרחב המשתמש. stat() מקבלת נתיב, fstat() מקבלת fd של קובץ שכבר פתוח — אחרת הן זהות. 

int stat(const char *pathname, struct stat *statbuf);
int fstat(int fd, struct stat *statbuf);
שדה ב-struct statמה הוא מחזיק
st_modeסוג הקובץ + ביטי ההרשאות — זהו בדיוק שדה ה-i_mode של ה-Inode שראינו ב-open (המקום שאליו נכתב ה-0644).
st_sizeגודל הקובץ בבייטים — מקביל ל-i_size שה-write מעדכן כשהקובץ גדל.
st_inoמספר ה-Inode — המזהה שבו רשומה ה-Directory Entry מצביעה על הקובץ.
st_nlinkמספר הקישורים הקשיחים (hard links) לאותו Inode — המונה שראינו בשלב iput של close.
st_uidה-UID של בעל הקובץ.

מה זה עושה: ממלא את המבנה sb במטא-דאטה של הקובץ הפתוח, ומדפיס את גודלו ואת מספר ה-Inode שלו. 

struct stat sb;

if (fstat(fd, &sb) == -1) {
    perror("fstat");
    exit(EXIT_FAILURE);
}
printf("size = %lld bytes, inode = %lu\n",
       (long long) sb.st_size, (unsigned long) sb.st_ino);

קריאת תיקייה — opendir / readdir / closedir

תיקייה היא קובץ שתוכנו רשומות; שלוש הפונקציות האלה (מ-<dirent.h>) עוברות עליהן אחת-אחת. כל רשומה חוזרת כ-struct dirent ששני שדותיו המעניינים הם d_name (שם הרשומה) ו-d_ino (מספר ה-Inode) — בדיוק צמד השדות שמגדיר Directory Entry במודול 5. readdir מחזירה NULL כשנגמרו הרשומות. 

DIR *d = opendir("/home/Itzhak");
struct dirent *e;

while ((e = readdir(d)) != NULL)
    printf("%s -> inode %lu\n", e->d_name, (unsigned long) e->d_ino);

closedir(d);
