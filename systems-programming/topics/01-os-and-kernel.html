0. האינטואיציה — האשליה הגדולה של המחשב

החומרה הפיזית מורכבת, מוגבלת ואינה סלחנית: המעבד מבין רק פקודות מכונה, הדיסק רק סקטורים, והזיכרון הפיזי מקוטע ומשותף. מערכת ההפעלה היא האמצעי ליצירת אשליה עבור המתכנת — מכונה ידידותית, יציבה ובלעדית, עם משאבים וירטואליים רציפים ובלתי-מוגבלים לוגית. את האשליה הזו המרצה מכנה "המכונה המורחבת" (Extended Machine) — ציר מרכזי לאורך כל הקורס.

התוכנה במערכת המחשב מתחלקת בדיוק לשניים: קוד הגרעין (ה-Kernel) וכל השאר. השיעור הזה עוסק בשאלה איפה עובר הקו — ולמה ההבחנה אינה סמנטיקה אלא כלל שהמעבד אוכף פיזית. נקודת הייחוס של הקורס: Linux Kernel 6.14.

הרחבה למתחילים — חמישה מונחי בסיס שיחזרו לאורך כל העמוד. אם המונחים האלה כבר מוכרים לכם, אפשר לדלג:

  • הוראת מכונה (instruction): הפעולה הקטנה ביותר שהמעבד יודע לבצע — למשל "חבר שני מספרים" (ADD). כל תוכנית, בכל שפה, מתורגמת בסופו של דבר לרצף של הוראות כאלה.
  • אוגר (register): תא זיכרון זעיר בתוך המעבד עצמו, המהיר בהרבה מ-RAM. חלק מהאוגרים מחזיקים נתונים שעליהם עובדים כרגע, וחלק ("אוגרי בקרה") מחזיקים את ההגדרות של המעבד עצמו.
  • ספרייה (library): אוסף פונקציות מוכנות שמישהו אחר כתב, והתוכנית שלכם משתמשת בהן במקום לכתוב הכול מאפס. glibc היא ספריית ה-C הסטנדרטית של לינוקס.
  • מצב מעבד (CPU mode): "כובע ההרשאות" שהמעבד חובש ברגע נתון. יש לפחות שניים — מצב גרעין (הרשאה גבוהה) ומצב משתמש (הרשאה נמוכה) — והמעבד עצמו בודק אותו לפני ביצוע הוראה.
  • פסיקה (interrupt): אירוע שגורם למעבד לעצור באמצע מה שהוא עושה ולקפוץ לקוד טיפול שהוגדר מראש — כמו טלפון שמצלצל באמצע שיחה.

מקור: ch01.pdf (עמ' 5), apps-kernel.pdf (עמ' 2)

1. OS מול Kernel — ההבחנה הסמנטית

OS ≠ Kernel — מושגים שונים מהותית, עם זיקה היררכית הדוקה. שלוש סיבות לבלבול:

  1. החלק מתאר את השלם: הליבה היא המרכיב העיקרי. בלעדיה אין מערכת הפעלה; בלי כלי עזר (Utilities) המערכת אינה שימושית למשתמש הקצה.
  2. מיקרו-ליבה מול מונוליט: במונוליט (Linux) כל שירותי הליבה — תהליכים, זיכרון, מערכות קבצים, דרייברים — בבינארי אחד ב-Ring 0, והגבול מטושטש פיזית; במיקרו-ליבה (L4, QNX) נשאר מינימום והשאר רץ כתהליכי משתמש — ההפרדה חדה, ושימוש מעורב במושגים נחשב שגיאה גסה.
  3. ההיבט המסחרי: "Operating Systems" של מיקרוסופט ואפל (Windows 11, macOS) כוללות דפדפנים ונגני מדיה — עבורן ה-OS היא Product; עבור מהנדס המערכת Environment.

מסקנת המרצה: השימוש המתחלף לגיטימי בהקשר פופולרי, אך בשיח הנדסי-אקדמי הוא חוסר דיוק שיש לשרש.

1.1 ההגדרות האופרטיביות

מערכת ההפעלה (Operating System): שכבת תיווך (Abstraction layer) בין החומרה ליישום, ובה:

  • הליבה (Kernel).
  • ספריות מערכת (System Libraries): libc, Win32 API — קוד מוכן במקום פנייה ישירה לגרעין.
  • כלי שירות ותוכניות מערכת (System Utilities): Shells (מפרש הפקודות), מנהלי קבצים וקומפיילרים (מתרגמים קוד מקור לקובץ הרצה) — חלק מההפצה.
  • ממשקי משתמש (User Interfaces): GUI (ממשק גרפי) או CLI (שורת פקודה).

הליבה (Kernel): המרכיב המרכזי והחיוני ביותר ב-OS; נטענת ראשונה לזיכרון (אחרי ה-Bootloader), ברמת ההרשאות הגבוהה ביותר (Kernel Mode / Ring 0), ותפקידה ניהול משאבים (Resource Management) וגישור (Mediation) — אחריות בלעדית על ה-CPU, הזיכרון הפיזי וההתקנים. בניסוח המרצה: הליבה = הישות הסטטית היחידה ב-Privileged Mode; ה-OS = ישות דינמית על שני מרחבי כתובות (Address Spaces) ו-Framework שמנגיש את הקרנל.

1.2 טבלת ההשוואה

פענוח: Binary (שורה אחרונה) = קובץ הרצה מהודר אחד, ישות אחת רציפה בזיכרון ולא אוסף קבצים; Kernel/User Space (שורה ראשונה) = חלוקת מרחב הכתובות עצמו (סעיף 5).

הדגשה טכנית שחוזרת במבחנים: "הליבה אינה מבצעת עבודה עבור עצמה, אלא מגיבה לבקשות (System Calls) או לאירועי חומרה (Interrupts)." הקרנל Reactive — אוסף שגרות שירות ש"ישן" עד שקורה אירוע, לא לולאת תוכנית. ה-OS Proactive — כוללת תהליכי מערכת (Init, smss.exe) עם לולאות ריצה משלהם.

1.3 עוד שתי נגזרות של ההבחנה

  • קריסות: רכיב OS שקורס — המערכת עשויה לשרוד. Kernel שקורס — Fatal System Error (BSOD / Kernel Panic).
  • מרחבי כתובות: הליבה ממופה למרחב הכתובות של כל תהליך (בראש הזיכרון הווירטואלי) אך חסומה בחומרה לקוד המשתמש; ה-OS = מאות מרחבי כתובות נפרדים המתקשרים ב-IPC (יחידה 5).
🎓 מהשיעור בכיתה (מהמחברת)

מפת משפחות מערכות ההפעלה. את ההבחנה הזו המרצה סגר על הלוח בשרטוט אחד: המשפחות המרכזיות זו לצד זו — BSD, Unix, Linux, Windows NT ו-macOS — וליד השרטוט, באדום, שתי מילות מפתח: מיקרו-קרנל ו-pipe (צינור להעברת נתונים בין תהליכים). כלומר: השאלה "מונוליט או מיקרו-ליבה?" אינה תרגיל תיאורטי — היא מה שמבדיל בפועל בין המשפחות שברשימה.

מקור: ch01.pdf (עמ' 1–4)

2. הדוגמה שסוגרת את הפער — מה קורה כשקוראים ל-open()

בקוד C: fd = open("file.txt", O_RDONLY);‎ — פתיחת קובץ לקריאה. מי מטפל בבקשה?

open()
הקוד שלך ב-C
→
glibc
פונקציה של ה-OS
→
SYSCALL
הוראת מעבד
→
Kernel · Ring 0
בדיקת הרשאות, גישה לדיסק
→
return
חזרה דרך glibc לתוכנית

open()‎ היא פונקציה של ה-OS — ספריית glibc, עדיין במצב משתמש. ה-glibc מבצעת את הוראת המעבד SYSCALL, וכאן הבקשה חוצה את הגבול: ה-Kernel עובר ל-Ring 0, בודק הרשאות וניגש פיזית לדיסק; התוצאה חוזרת דרך glibc לתוכנית, שממשיכה במצב משתמש.

אותו עיקרון ב-printf()‎ — אותה שורת קוד עוברת דרך שני העולמות. המכניקה המלאה (פסיקות תוכנה, wrapper routines): מודול קריאות המערכת.

נקודה שהמרצה שואל עליה במפורש: printf()‎ שייכת לחבילת ה-glibc, שמועתקת למחשב בזמן ההתקנה של Linux — לא gcc (רק בזמן הידור), לא bash, ולא ה-Linux Kernel שמספק את write()‎ שמתחתיה. שאלה בניסוח הזה מופיעה במבחן לדוגמה.

מקור: ch01.pdf (עמ' 3–4)

3. מודל השכבות — אפליקציות ⇄ קרנל ⇄ חומרה

התוויות שמימין: Many applications, One Kernel, One Hardware — הגרעין הוא נקודת המפגש היחידה, ולכן גם המגשר וגם השוטר. לשלושת החיצים (בתיבות האדומות של המרצה) משמעות שונה לגמרי:

  1. אפליקציה ← קרנל (System calls): בקשת שירות מהגרעין — שרשרת פתיחת הקובץ מסעיף 2.
  2. קרנל ← חומרה: גם מיוחסות וגם לא מיוחסות. דוגמה למיוחסת: HALT — מפסיקה את עבודת ה-CPU.
  3. אפליקציה ← חומרה (ישירות!): לא מיוחסות בלבד, למשל ADD — חישוב רגיל רץ ישירות על המעבד, והקרנל נכנס רק בבקשת שירות (החץ הראשון) או בפסיקה.

3.1 מי קבע את הכללים? מתכנני החומרה

הגבולות אינם המצאה של לינוקס — מתכנני הארכיטקטורה קובעים ברמת החומרה את:

  • ה-ISA — קבוצת ההוראות של המעבד;
  • מצבי הריצה (privileged levels);
  • מנגנון הפסיקות הממומש במעבד.

ה-ISA מחלק את ההוראות למיוחסות (privileged) ולא מיוחסות (non-privileged); מצבי הריצה — לפחות שניים: מצב גרעין (kernel mode, הרשאה גבוהה) ומצב משתמש (user mode, הרשאה נמוכה).

🎓 מהשיעור בכיתה (מהמחברת)

כמה מצבי ריצה יש באמת? ליד השקף הזה המרצה ציין שבמעבדים מודרניים מוגדרות בין 4 ל-8 רמות הרשאה (privilege levels) — ולא רק שתיים. הקורס מתמקד בשתי הרמות הקיצוניות (מצב גרעין מול מצב משתמש, ובמונחי אינטל: Ring 0 מול Ring 3), כי הן אלה שקובעות את הגבול שעליו מדובר כאן — אבל שווה לדעת שהחומרה מציעה יותר.

ובאותה נשימה, סיווג שתי משפחות ה-ISA שהוא נקב בהן: ARM היא Hybrid RISC, ו-Intel היא Hybrid CISC. (RISC — קבוצת הוראות מצומצמת ופשוטה; CISC — קבוצה גדולה ומורכבת. "היברידי" מפני ששתי המשפחות שאלו רעיונות זו מזו.)

3.2 מה קורה בשלב פענוח ההוראה (Instruction Decode)

ההחלטה אם לבצע הוראה מתקבלת בשלב פענוח קוד ההוראה (Instruction Decode / ID):

הרחבה — "שלב פענוח": המעבד מביא את ההוראה מהזיכרון, מפענח (איזו פעולה ועל אילו נתונים), ורק אז מבצע — כך שהחומרה עוצרת הוראה אסורה לפני שהתחילה לפעול.

מה זוהה בשלב ה-IDמצב המעבדהתוצאה
הוראה לא מיוחסת מצב גרעין או מצב משתמש המעבד ישלים את הביצוע
הוראה מיוחסת מצב גרעין המעבד ישלים את הביצוע
הוראה מיוחסת מצב משתמש המעבד לא ישלים את הביצוע ("יסרב לבצע אותה") וייצור פסיקה (Interrupt) — והטיפול בה יוביל להפסקה מיידית של התהליך שהקוד שלו כלל את ההוראה המיוחסת

ההגדרה בניסוח המרצה: "הגרעין של מערכת ההפעלה, למעט קטעי קוד קטנים יחסית כמו ה-bootloader, הוא כלל הקוד שכאשר הוא מתבצע המעבד מצוי במצב גרעין" — הכולל הוראות מיוחסות ולא מיוחסות כאחד. תהליך משתמש = כל הקוד שאינו של הגרעין, שבזמן ביצועו המעבד במצב משתמש.

מקור: apps-kernel.pdf (עמ' 1–6)

4. Extended Machine — הקרנל כמפעל של אשליות

הגדרת קרנל דרך "תפקידים" (Resource Manager, Abstraction Layer, Scheduler) היא לפי המרצה "רשימת מכולת". ה-Extended Machine מחליף את "מה הליבה עושה" ב"איזו אשליה הליבה בונה" — הליבה "ממציאה" את "התהליך" מעל פקודות מכונה, ואת "הקובץ" מעל סקטורים:

תת-מערכתהתפקיד הטכניהאשליה שהיא בונה
מנהל התהליכים (Scheduler) ניהול ה-Context, ‏Context Switching ותזמון (Scheduling) אשליית הבלעדיות — כל תוכנית "חושבת" שהיא רצה על מעבד משלה, רצוף ובלי הפרעות, למרות שהיא חולקת אותו עם מאות תהליכים
מנהל הזיכרון (Memory Manager) Paging, ‏Page Tables, הקצאת זיכרון ו-Virtual Address Space אשליית המרחב הרציף והבלעדי — מרחב כתובות וירטואלי רציף, שבו התוכנית כותבת בלי לחשוש שתדרוס תהליך אחר, מעל זיכרון פיזי מקוטע ומשותף
מנהל התקני הקלט/פלט (Device Management) ניהול דרייברים, Interrupt Handling, ‏MMIO/DMA אשליית השקיפות — חומרה רועשת ולא אחידה מוסתרת מאחורי ממשקים פשוטים (כמו File Descriptors); המשתמש "כותב לקובץ" בלי לדעת איך הבקר מדבר עם החומרה
מערכת הקבצים (File System) ניהול היררכיית קבצים, הרשאות, עמידות נתונים (Persistence) אשליית העמידות והארגון — "עץ היררכי" נוח לוגית מעל דיסק שהוא סדרה ארוכה של בלוקים; הנתונים "נשמרים" מסודרים גם כשהחשמל כבוי
מערך ההגנה והבידוד (Security & Protection) הגדרת Privilege Levels (Ring 0/3), ניהול הרשאות, ‏Sandboxing אשליית היציבות והאמינות — הבידוד מבטיח שתוכנית שקורסת לא "תהרוס את המחשב"; בלעדיו האשליה כולה מתנפצת

ואותן תת-מערכות זו לצד זו: אפליקציות (User space), קו קריאות המערכת, וחמש עמודות בקרנל (תהליכים, זיכרון, מערכות קבצים, מנהלי התקנים, רשת) — כל אחת יורדת לחומרה שהיא מנהלת:

4.1 הקשר הסימביוטי באקו-סיסטם

קריסה או חוסר התאמה באחד הרכיבים משביתה את ה-Ecosystem כולו:

  • הקרנל — תשתית פיזית ובידוד.
  • ה-glibc — מתרגמת בקשות משתמש לממשק המובן לקרנל (ABI: "חוזה" ברמת הבינארי — אילו אוגרים נושאים אילו ערכים בכניסה לקרנל) ועוטפת את ה-Syscalls בפונקציות C. בלעדיה המכונה האבסטרקטית "קשה מדי"; בלי הקרנל — פקודות ריקות.
  • ה-Bash (מפרש הפקודות) — "הסוכן המבצע": מקבל string ומבצע fork()‎ ו-execve()‎ שמפעילות את מנהל התהליכים.
  • הדרייברים (חלק מהקרנל) — תלויים ב-Interrupt Controller כדי לדעת מתי הגיעו נתונים, ומתרגמים חומרה לאובייקט לוגי.

כיוון ה"הזנה" מתהפך משורה לשורה: הקרנל מזין את ה-glibc ב-ABI, אך ה-Bash מזין את הקרנל בתהליכים חדשים — סימביוזה, לא היררכיה חד-כיוונית.

מקור: ch01.pdf (עמ' 5–8), Kernel-SDLC.pdf (עמ' 37)

5. Ring 0/3, ‏CPL ומרחבי הזיכרון

ב-x86_64 החומרה אוכפת את הגבולות במצבי המעבד (CPU Modes):

  • מצב המעבד (CPL — Current Privilege Level): אוגר פנימי (חלק מה-CS Segment Selector) עם רמת ההרשאה הנוכחית. Ring 0 — הפריבילגי ביותר, בו רץ הקרנל (CPL=0); Ring 3 — המוגבל, בו רצים יישומי המשתמש ולרוב שאר מרכיבי ה-OS.
  • Kernel Space מול User Space: נגזרת של מצב המעבד — חלוקת מרחב הכתובות הווירטואלי. ב-Linux 6.14: User Space אינו נגיש מ-Ring 0 ללא הגדרה מכנית מיוחדת; Kernel Space מוגן מ-Ring 3, וניסיון גישה יגרור Page Fault (ביט ה-User/Supervisor בטבלאות הדפים).

הרחבה — שלושה מונחי חומרה חדשים:

  • MMU (Memory Management Unit): מתרגם כתובת וירטואלית לכתובת אמיתית ב-RAM.
  • טבלאות הדפים (Page Tables): הקרנל בונה, ה-MMU קורא. לכל "דף" ביטי הרשאה — ביניהם ה-User/Supervisor: האם Ring 3 רשאי לגעת בו.
  • Page Fault: החריגה שנוצרת בגישה לכתובת אסורה — למשל תוכנית משתמש שקוראת מ-Kernel Space.

ההגדרה האופרציונלית של הקרנל (לשנן!): "ה-Kernel הוא אוסף כל הקוד (למעט ה-Bootloader) אשר בעת ביצועו, המעבד נמצא ב-CPL=0" — מחברת בין הקוד הסטטי שעל הדיסק למצב הדינמי בזמן ריצה. המרצה נותן אותה פעמיים (מצגת + חוברת) — סימן לחומר מבחן.

5.1 מילת מצב המעבד (PSW), ביט המצב וה-MMU

🎓 מהשיעור בכיתה (מהמחברת)

המרצה שרטט איפה "מצב המעבד" יושב פיזית: במעבד יש אוגר מצב — PSW (Process Status Word, מילת מצב המעבד) — המרכז את מצבו הנוכחי, ואחד הביטים בו הוא ביט המצב (mode bit):

  • 1 = מצב גרעין (kernel) — המעבד רשאי לבצע גם הוראות מיוחסות;
  • 0 = מצב משתמש (user) — הוראות לא מיוחסות בלבד.

כלומר CPL = ערך של ביט באוגר, שהמעבד קורא בשלב פענוח ההוראה (סעיף 3.2). בשרטוט עמד ה-MMU ליד ה-PSW: השניים אוכפים יחד את הגבול — ה-mode bit קובע אילו הוראות מותרות, וה-MMU לאילו כתובות מותר לגשת.

דוגמאות להוראות מיוחסות שנקב בהן: HALT (במצגת גם HLT — עצירת המעבד), והגדרה או שינוי של רגיסטרי ה-MMU — החלפת טבלאות הדפים הפעילות. ההיגיון: מי ששולט ברגיסטרי ה-MMU שולט במה שכל תהליך רואה בזיכרון. רק הליבה, ב-Ring 0, מסוגלת לבצען.

5.2 ציר הזמן — מתי המעבד בגרעין ומתי במשתמש

🎓 מהשיעור בכיתה (מהמחברת)

התמונה של User מול Kernel Space היא סטטית; המרצה השלים אותה בתמונה דינמית: ציר זמן שעליו כל קטע ריצה צבוע — אדום = מצב גרעין (mode bit = 1), כחול = מצב משתמש (mode bit = 0). ביום עבודה רגיל המעבד מתחלף אינספור פעמים: כל קריאת מערכת וכל פסיקה צובעות קטע אדום קצר, ואז חזרה לכחול.

על אותו ציר מיקם את שרשרת התהליכים מרגע האתחול — כולם תהליכי משתמש (כחול) מעל קרנל אחד: 

init  →  login  →  bash  →  cp

init הוא התהליך הראשון שהמערכת מריצה; הוא מפעיל את login (שם משתמש + סיסמה), זה מפעיל bash, וכשמקלידים cp נוצר תהליך נוסף. בתרשים הזיכרון שצייר, bash ו-cp בכחול למעלה (User Space) והקרנל מתחתם באדום. המשך: מסלול האתחול, יצירת התהליכים.

5.3 מנגנון מול מדיניות (Mechanism vs. Policy)

חלוקת העבודה בין הקרנל ל-OS — מנגנון מול מדיניות:

  • המנגנון (Mechanism): הליבה מספקת Context Switching, ניהול Page Tables ו-Interrupt Handlers — "איך עושים".
  • המדיניות (Policy): ה-OS (רכיבי User-space או הגדרות ליבה) קובעת מי יקבל את המשאב ומתי — "מה עושים ולמי".

מקור: ch01.pdf (עמ' 3, 4, 9)

6. דרייברים ו-ISRs — הזרועות של הקרנל ב-Ring 0

הקרנל מדבר עם החומרה דרך שני רכיבים שחיים ב-Ring 0: מנהלי ההתקנים וה-ISRs.

6.1 מנהלי התקנים (Drivers) — ה"מתרגמים"

מנהל התקן (Device Driver) הוא חלק מהקרנל, ומתרגם צרכים לוגיים לפעולות פיזיות:

  • הסמכות המכנית: ב-Ring 0 וללא הגבלה — כל כתובת בזיכרון, ופקודות I/O מיוחדות (IN/OUT ב-x86, או MMIO — גישה לאוגרי ההתקן דרך כתובות זיכרון רגילות).
  • החשיבות: בלעדיהם הקרנל הוא "מוח ללא גוף" — הם מתרגמים בקשה לוגית ("שלח מנה ברשת") לרצף חשמלי ברמת ה-NIC.

6.2 ISRs — "דפיקות הדלת" של החומרה

בפסיקה (Interrupt) החומרה דורשת תשומת לב מיידית, וה-ISR (Interrupt Service Routine) הוא הקוד שנקרא:

  • הקריטיות המכנית: המעבד עוצר וקופץ לכתובת שב-IDT (Interrupt Descriptor Table — ממפה מספר פסיקה לשגרת הטיפול). ה-ISR חייב לרוץ ב-Ring 0, כי הוא מנהל את הגישה הראשונית לחומרה.
  • אטומיות (Atomic Execution): בכניסתו נחסמות פסיקות אחרות — Masking (אוטומטית או בהוראת CLI); הליבה "עיוורת" לאירועים חיצוניים, כדי להבטיח טיפול תקין באירוע הנוכחי.
  • האיזון ההנדסי: טיפול מהיר מול הסיכון ב-Deadlock ובאובדן מידע מבחוץ. ISR שלא יחזיר שליטה בזמן — המערכת כולה תקפא.

הסימביוזה ב-Ring 0: דרייברים ו-ISRs חולקים סמכות, מרחב כתובות ו-Kernel Stack (המחסנית שהקרנל עובד מולה) — ולכן באג בדרייבר הוא באג בליבה. כל אינטראקציה עם "קובץ" או "רשת" עוברת דרכם.

קופסת ידע — ה-Bootloader (מאתחל המערכת): מגשר בין החומרה ה"עירומה" למצב שבו הקרנל יכול לפעול; בלעדיו הקרנל הוא קובץ בינארי על ה-NVM. שלבי האתחול:

  1. Firmware ו-POST: ה-Firmware (צרוב בחומרה — UEFI או Legacy BIOS) מבצע POST — Power-On Self-Test: אבחון עצמי של החומרה (מעבד, זיכרון, בקרים). רק בסיום מוצלח עוברת השליטה ל-Bootloader.
  2. טעינה (Loading): איתור ב-NVM (זיכרון לא-נדיף — דיסק/SSD) של ה-Executable בפורמט ELF (Executable and Linkable Format) המכיל את הקרנל, וטעינתו ל-RAM.
  3. אתחול המכונה: בניית ה-Page Tables הראשוניות, הגדרת ה-GDT (טבלת הסגמנטים), ומעבר מ-16-ביט (Real Mode) ל-64-ביט (Long Mode).
  4. העברת השליטה: הגדרת RSP (מצביע ה-Stack המוקדם) ואוגרי הבקרה, וקפיצה ל-Entry Point של הקרנל.

מקור: ch01.pdf (עמ' 10–11)

7. המורכבות הכמותית — LOC והטרוגניות השפות

קוד הגרעין: huge & extremely complex (המרצה). שני מדדים — LOC (Lines of Code) ושפות התכנות.

"קרנל בלבד" מול "מערכת מלאה" = ההבדל בין Kernel ל-OS מסעיף 1, במספרים. (בטבלה 6.7; הייחוס של הקורס 6.14 — סדרי הגודל זהים.) לינוקס 6.14: מעל 30 מיליון שורות קוד רשמיות, כולל מנהלי ההתקנים.

  • הליבה = ה-TCB (Trusted Computing Base) — מיליוני שורות, כולן ב-Ring 0. המורכבות איכותית: באג אחד מערער את יציבות המערכת כולה.
  • glibc ו-Coreutils (כלי שורת הפקודה — ls, cp, cat): עוד מיליוני שורות ב-User-Space, ה"תיווך" שהופך את המערכת לשמישה.
  • ההשלכה: ה-SDLC (Software Development Life Cycle — אפיון, תכנון, מימוש, בדיקות, הפצה, תחזוקה) הופך מ"רצוי" ל"הכרחי": תיעוד, Code Review, ניהול גרסאות מבוזר (מודול 02).
🎓 מהשיעור בכיתה (מהמחברת)

המספרים כפי שנאמרו בכיתה. המרצה לא הסתפק ב"מעל 30 מיליון" ונקב בטווח: 30–35 מיליון שורות קוד בקרנל. בשיעור אחר הוא פירט גם את ההרכב: כ-35 מיליון שורות בקרנל, מתוכן 95% ב-C ו-5% ב-Assembler; וכשמוסיפים לזה את שאר האקו-סיסטם — glibc, bash ותוכניות המערכת (cp, rm, ls, ps) — מגיעים לכ-100 מיליון שורות קוד. בדרך אגב הוא גם פירק את ראשי התיבות: LOC = Lines of Code.

7.1 אילו שפות — ולמה

  • C: ממפה דטרמיניסטית מבני נתונים לזיכרון — גודל, סדר שדות (Offset — המרחק בבתים מתחילת המבנה) והקשר קבועים מראש, וכך הקרנל ניגש למידע בעקביות.
  • Assembly (x86_64): השפה היחידה שהחומרה מבינה ללא תיווך, הכרחית למה שאין לו סמנטיקה ב-C — אוגרי בקרה (CR3, מצביע טבלאות הדפים), Interrupts, וה-SYSCALL עצמו.
  • User-Space (C, C++, Rust, Python): מעל המכונה המורחבת השפה נבחרת לפי פרודוקטיביות, לא לפי שליטה בחומרה — שגיאת זיכרון (Segfault — גישה לכתובת אסורה) מפילה רק את התהליך.

תלות בארכיטקטורה: מבני הנתונים בקרנל (כמו ה-task_struct, מודול 07) מעוצבים לפי ה-ISA, וה-Paging שונה בין Intel ל-ARM.

קופסת ידע — TCB (Trusted Computing Base): כל מרכיבי המערכת — תוכנה, חומרה וקושחה — שאחראים על אכיפת מדיניות האבטחה. TCB פרוץ או באגי = אין יותר הבטחה לתקינות המערכת. בלינוקס הליבה היא ה-TCB המרכזי: מפרידה בין תהליכים, מנהלת זיכרון ומגנה על ה-Extended Machine מגישה בלתי מורשית.

מקור: Kernel-SDLC.pdf (עמ' 3–6), ch01.pdf (עמ' 12–13)

8. מלכודות למבחן

ה-Bootloader רץ במצב גרעין — אבל אינו חלק מהקרנל. שתי ההגדרות ממעטות אותו: "למעט קטעי קוד קטנים יחסית כמו ה-bootloader".

קוד הקרנל כולל גם הוראות לא מיוחסות. החץ קרנל←חומרה מסומן "Both privileged and non privileged instructions": הקרנל רשאי לבצע מיוחסות — לא שהוא מבצע רק אותן.

הוראה מיוחסת במצב משתמש ← פסיקה ← הפסקת התהליך. לא "דילוג בשקט" ולא חריגה שהאפליקציה מטפלת בה: זיהוי ב-Instruction Decode, סירוב, ו-Interrupt שעוצר את התהליך מיידית.

הקרנל הוא Reactive. "הליבה אינה מבצעת עבודה עבור עצמה" — מגיבה ל-System Calls ולפסיקות בלבד. תהליכים פרואקטיביים (Init, ‏smss.exe) שייכים ל-OS, לא לקרנל.

דרייבר אינו "תוכנית נפרדת". הוא חלק מהקרנל, ב-Ring 0, באותו מרחב כתובות ואותו Kernel Stack — באג בדרייבר הוא באג בליבה.

הדגשה מהכיתה — mode bit: 1 = גרעין, 0 = משתמש. סומנו בקו תחתון על הלוח (סעיף 5.1). עוגן: הערך הגבוה (1) = ההרשאה הגבוהה — הפוך ממספור ה-Rings, שבו Ring 0 הוא הגרעין.

תמצית השינון המלאה של הקורס נמצאת בדף ההכנה למבחן (מודול 15).
