0. האינטואיציה — האשליה הגדולה של המחשב

החומרה הפיזית מורכבת, מוגבלת ואינה סלחנית: המעבד מבין רק פקודות מכונה, הדיסק רק סקטורים, והזיכרון הפיזי מקוטע ומשותף. מערכת ההפעלה היא האמצעי ליצירת אשליה עבור המתכנת — מכונה ידידותית, יציבה ובלעדית, עם משאבים וירטואליים רציפים ובלתי-מוגבלים לוגית. את האשליה הזו המרצה מכנה "המכונה המורחבת" (Extended Machine) — ציר מרכזי לאורך כל הקורס.

התוכנה במערכת המחשב מתחלקת בדיוק לשניים: קוד הגרעין (ה-Kernel) וכל השאר. השיעור הזה עוסק בשאלה איפה עובר הקו — ולמה ההבחנה אינה סמנטיקה אלא כלל שהמעבד אוכף פיזית. נקודת הייחוס של הקורס: Linux Kernel 6.14.

הרחבה למתחילים — חמישה מונחי בסיס שיחזרו לאורך כל העמוד. אם המונחים האלה כבר מוכרים לכם, אפשר לדלג:

  • הוראת מכונה (instruction): הפעולה הקטנה ביותר שהמעבד יודע לבצע — למשל "חבר שני מספרים" (ADD). כל תוכנית, בכל שפה, מתורגמת בסופו של דבר לרצף של הוראות כאלה.
  • אוגר (register): תא זיכרון זעיר בתוך המעבד עצמו, המהיר בהרבה מ-RAM. חלק מהאוגרים מחזיקים נתונים שעליהם עובדים כרגע, וחלק ("אוגרי בקרה") מחזיקים את ההגדרות של המעבד עצמו.
  • ספרייה (library): אוסף פונקציות מוכנות שמישהו אחר כתב, והתוכנית שלכם משתמשת בהן במקום לכתוב הכול מאפס. glibc היא ספריית ה-C הסטנדרטית של לינוקס.
  • מצב מעבד (CPU mode): "כובע ההרשאות" שהמעבד חובש ברגע נתון. יש לפחות שניים — מצב גרעין (הרשאה גבוהה) ומצב משתמש (הרשאה נמוכה) — והמעבד עצמו בודק אותו לפני ביצוע הוראה.
  • פסיקה (interrupt): אירוע שגורם למעבד לעצור באמצע מה שהוא עושה ולקפוץ לקוד טיפול שהוגדר מראש — כמו טלפון שמצלצל באמצע שיחה.

מקור: ch01.pdf (עמ' 5), apps-kernel.pdf (עמ' 2)

1. OS מול Kernel — ההבחנה הסמנטית

OS ≠ Kernel — מושגים שונים מהותית, עם זיקה היררכית הדוקה. שלוש סיבות לבלבול:

  1. החלק מתאר את השלם: הליבה היא המרכיב העיקרי. ללא ליבה — אין מערכת הפעלה; ללא כלי עזר (Utilities) — המערכת אינה שימושית למשתמש הקצה.
  2. מיקרו-ליבה מול מונוליט: במונוליט (Linux) כל שירותי הליבה — תהליכים, זיכרון, מערכות קבצים, דרייברים — בבינארי אחד ב-Ring 0, והגבול מטושטש פיזית; במיקרו-ליבה (L4, QNX) נשאר מינימום מוחלט והשאר רץ כתהליכי משתמש — ההפרדה חדה, ושימוש מעורב במושגים נחשב שגיאה גסה.
  3. ההיבט המסחרי: מיקרוסופט ואפל משווקות "Operating Systems" (Windows 11, macOS) עם דפדפנים ונגני מדיה — עבורן ה-OS היא Product; עבור מהנדס המערכת Environment.

מסקנת המרצה: השימוש המתחלף במונחים לגיטימי בהקשר פופולרי, אך בשיח הנדסי-אקדמי הוא חוסר דיוק שיש לשרש. הקורס מתמקד בגרעין.

1.1 ההגדרות האופרטיביות

מערכת ההפעלה (Operating System): שכבת תיווך (Abstraction layer) בין החומרה למשתמש/ליישום, המורכבת מ:

  • הליבה (Kernel).
  • ספריות מערכת (System Libraries): libc, Win32 API — קוד מוכן שהתוכניות משתמשות בו במקום לפנות לגרעין בעצמן.
  • כלי שירות ותוכניות מערכת (System Utilities): Shells (מפרש הפקודות), מנהלי קבצים וקומפיילרים (מתרגמים קוד מקור לקובץ הרצה) — חלק מההפצה.
  • ממשקי משתמש (User Interfaces): GUI (ממשק גרפי) או CLI (שורת פקודה).

הליבה (Kernel): המרכיב המרכזי והחיוני ביותר ב-OS; נטענת ראשונה לזיכרון (אחרי ה-Bootloader), רצה ברמת ההרשאות הגבוהה ביותר (Kernel Mode / Ring 0), ותפקידה ניהול משאבים (Resource Management) וגישור (Mediation) — אחריות בלעדית על ה-CPU, הזיכרון הפיזי וההתקנים. בניסוח המרצה: הליבה = הישות הסטטית היחידה ב-Privileged Mode; ה-OS = ישות דינמית על שני מרחבי כתובות (Address Spaces), Framework שמנגיש את הקרנל למפתח.

1.2 טבלת ההשוואה

פענוח: Binary (שורה אחרונה) = קובץ הרצה מהודר אחד — הקרנל הוא ישות אחת רציפה בזיכרון, לא אוסף קבצים; Kernel Space/User Space (שורה ראשונה) = חלוקה של מרחב הכתובות עצמו (סעיף 5).

הדגשה טכנית שחוזרת במבחנים: "הליבה אינה מבצעת עבודה עבור עצמה, אלא מגיבה לבקשות (System Calls) או לאירועי חומרה (Interrupts)." הקרנל Reactive — לא לולאת תוכנית אלא אוסף שגרות שירות ש"ישן" עד שקורה אירוע. ה-OS Proactive — היא כוללת תהליכי מערכת (Init, smss.exe ב-Windows) עם לולאות ריצה משלהם.

1.3 עוד שתי נגזרות של ההבחנה

  • קריסות: רכיב ב-OS שקורס — המערכת עשויה לשרוד. Kernel שקורס — Fatal System Error (BSOD / Kernel Panic).
  • מרחבי כתובות: הליבה ממופה למרחב הכתובות של כל תהליך (בראש הזיכרון הווירטואלי), אך חסומה בחומרה לקוד המשתמש. ה-OS = מאות מרחבי כתובות נפרדים (תהליכי שירות) המתקשרים ב-IPC (יחידה 5).
🎓 מהשיעור בכיתה (מהמחברת)

מפת משפחות מערכות ההפעלה. את ההבחנה הזו המרצה סגר על הלוח בשרטוט אחד: המשפחות המרכזיות זו לצד זו — BSD, Unix, Linux, Windows NT ו-macOS — וליד השרטוט, באדום, שתי מילות מפתח: מיקרו-קרנל ו-pipe (צינור להעברת נתונים בין תהליכים). כלומר: השאלה "מונוליט או מיקרו-ליבה?" אינה תרגיל תיאורטי — היא מה שמבדיל בפועל בין המשפחות שברשימה.

מקור: ch01.pdf (עמ' 1–4)

2. הדוגמה שסוגרת את הפער — מה קורה כשקוראים ל-open()

כתבתם בתוכנית C את השורה fd = open("file.txt", O_RDONLY);‎ — פתיחת קובץ לקריאה. מי מטפל בבקשה?

open()

→
glibc

→
SYSCALL
הוראת מעבד
→
Kernel · Ring 0
בדיקת הרשאות, גישה לדיסק
→
return
חזרה דרך glibc לתוכנית
  1. open()‎ היא פונקציה של ה-OS — ספריית glibc; עדיין במצב משתמש.
  2. ה-glibc מבצעת את הוראת המעבד SYSCALL — כאן הבקשה חוצה את הגבול, ה-Kernel עובר ל-Ring 0, בודק הרשאות קבצים וניגש פיזית לדיסק.
  3. התוצאה חוזרת דרך glibc לתוכנית, שממשיכה לרוץ במצב משתמש.

אותו עיקרון ב-printf()‎ — אותה שורת קוד עוברת דרך שני העולמות. המכניקה המלאה (פסיקות תוכנה, wrapper routines): מודול קריאות המערכת.

נקודה שהמרצה שואל עליה במפורש: printf()‎ שייכת לחבילת ה-glibc, שמועתקת למחשב בזמן ההתקנה של Linux. לא gcc (קומפיילר, רק בזמן הידור), לא bash (מפרש פקודות), ולא ה-Linux Kernel — שמספק את write()‎ שמתחתיה, לא את הפונקציה עצמה. שאלה בניסוח הזה מופיעה במבחן לדוגמה.

מקור: ch01.pdf (עמ' 3–4)

3. מודל השכבות — אפליקציות ⇄ קרנל ⇄ חומרה

התרשים המרכזי של השיעור — הוא חוזר שקף אחרי שקף במצגת:

התוויות שמימין: Many applications, One Kernel, One Hardware — הגרעין הוא נקודת המפגש היחידה, ולכן גם המגשר וגם השוטר. לשלושת החיצים (שהמרצה הסביר בתיבות אדומות) משמעות שונה לגמרי:

  1. אפליקציה ← קרנל (System calls): תהליך מבקש מהגרעין שירות — שרשרת פתיחת הקובץ מסעיף 2.
  2. קרנל ← חומרה: גם הוראות מיוחסות וגם לא מיוחסות. דוגמה למיוחסת: HALT — גורמת ל-CPU להפסיק לעבוד.
  3. אפליקציה ← חומרה (ישירות!): הוראות לא מיוחסות בלבד, למשל ADD — חישוב רגיל רץ ישירות על המעבד, והקרנל נכנס רק בבקשת שירות (החץ הראשון) או בפסיקה.

3.1 מי קבע את הכללים? מתכנני החומרה

הגבולות אינם המצאה של לינוקס — מתכנני הארכיטקטורה קובעים ברמת החומרה את:

  • מאפייני קבוצת ההוראות של המעבד — ה-ISA של המעבד (רשימת כל ההוראות שהמעבד יודע לבצע);
  • מצבי הריצה (privileged levels);
  • מנגנון הפסיקות הנתמך (ממומש) על ידי המעבד.

ה-ISA מחלק את ההוראות להוראות מיוחסות (privileged) ולא מיוחסות (non-privileged); מצבי הריצה — לפחות שניים: מצב גרעין (kernel mode, הרשאה גבוהה) ומצב משתמש (user mode, הרשאה נמוכה).

🎓 מהשיעור בכיתה (מהמחברת)

כמה מצבי ריצה יש באמת? ליד השקף הזה המרצה ציין שבמעבדים מודרניים מוגדרות בין 4 ל-8 רמות הרשאה (privilege levels) — ולא רק שתיים. הקורס מתמקד בשתי הרמות הקיצוניות (מצב גרעין מול מצב משתמש, ובמונחי אינטל: Ring 0 מול Ring 3), כי הן אלה שקובעות את הגבול שעליו מדובר כאן — אבל שווה לדעת שהחומרה מציעה יותר.

ובאותה נשימה, סיווג שתי משפחות ה-ISA שהוא נקב בהן: ARM היא Hybrid RISC, ו-Intel היא Hybrid CISC. (RISC — קבוצת הוראות מצומצמת ופשוטה; CISC — קבוצה גדולה ומורכבת. "היברידי" מפני ששתי המשפחות שאלו רעיונות זו מזו.)

3.2 מה קורה בשלב פענוח ההוראה (Instruction Decode)

ההחלטה אם לבצע הוראה מתקבלת בשלב פענוח קוד ההוראה (Instruction Decode, בקיצור ID):

הרחבה — "שלב פענוח": המעבד מביא את ההוראה מהזיכרון, מפענח (איזו פעולה ועל אילו נתונים), ורק אז מבצע. הבדיקה קורית כבר בפענוח — החומרה עוצרת את ההוראה האסורה לפני שהתחילה לפעול.

מה זוהה בשלב ה-IDמצב המעבדהתוצאה
הוראה לא מיוחסת מצב גרעין או מצב משתמש המעבד ישלים את הביצוע
הוראה מיוחסת מצב גרעין המעבד ישלים את הביצוע
הוראה מיוחסת מצב משתמש המעבד לא ישלים את הביצוע ("יסרב לבצע אותה") וייצור פסיקה (Interrupt) — והטיפול בה יוביל להפסקה מיידית של התהליך שהקוד שלו כלל את ההוראה המיוחסת

ההגדרה בניסוח המרצה: "הגרעין של מערכת ההפעלה, למעט קטעי קוד קטנים יחסית כמו ה-bootloader, הוא כלל הקוד שכאשר הוא מתבצע המעבד מצוי במצב גרעין" — וקוד זה כולל הוראות מיוחסות ולא מיוחסות כאחד. תהליך משתמש = כל תהליך שכשהקוד שלו מתבצע המעבד במצב משתמש, כלומר כל הקוד שאינו של הגרעין.

מקור: apps-kernel.pdf (עמ' 1–6)

4. Extended Machine — הקרנל כמפעל של אשליות

הגדרת קרנל דרך "תפקידים" (Resource Manager, Abstraction Layer, Scheduler) היא לפי המרצה "רשימת מכולת". ה-Extended Machine מחליף את "מה הליבה עושה" ב"איזו אשליה הליבה בונה": המעבד מבין רק פקודות מכונה — הליבה "ממציאה" את "התהליך"; הדיסק מבין רק סקטורים — היא "ממציאה" את "הקובץ":

תת-מערכתהתפקיד הטכניהאשליה שהיא בונה
מנהל התהליכים (Scheduler) ניהול ה-Context, ‏Context Switching ותזמון (Scheduling) אשליית הבלעדיות — כל תוכנית "חושבת" שהיא רצה על מעבד משלה, רצוף ובלי הפרעות, למרות שהיא חולקת אותו עם מאות תהליכים
מנהל הזיכרון (Memory Manager) Paging, ‏Page Tables, הקצאת זיכרון ו-Virtual Address Space אשליית המרחב הרציף והבלעדי — מרחב כתובות וירטואלי רציף, שבו התוכנית כותבת בלי לחשוש שתדרוס תהליך אחר, מעל זיכרון פיזי מקוטע ומשותף
מנהל התקני הקלט/פלט (Device Management) ניהול דרייברים, Interrupt Handling, ‏MMIO/DMA אשליית השקיפות — חומרה רועשת ולא אחידה מוסתרת מאחורי ממשקים פשוטים (כמו File Descriptors); המשתמש "כותב לקובץ" בלי לדעת איך הבקר מדבר עם החומרה
מערכת הקבצים (File System) ניהול היררכיית קבצים, הרשאות, עמידות נתונים (Persistence) אשליית העמידות והארגון — "עץ היררכי" נוח לוגית מעל דיסק שהוא סדרה ארוכה של בלוקים; הנתונים "נשמרים" מסודרים גם כשהחשמל כבוי
מערך ההגנה והבידוד (Security & Protection) הגדרת Privilege Levels (Ring 0/3), ניהול הרשאות, ‏Sandboxing אשליית היציבות והאמינות — הבידוד מבטיח שתוכנית שקורסת לא "תהרוס את המחשב"; בלעדיו האשליה כולה מתנפצת

ואותן תת-מערכות זו לצד זו: אפליקציות (User space), קו קריאות המערכת, וחמש עמודות בקרנל (תהליכים, זיכרון, מערכות קבצים, מנהלי התקנים, רשת) — כל אחת יורדת עד לחומרה שהיא מנהלת:

כל תיבה היא נושא שלם: לתרשים נחזור במודול הבא, ואת העמודות נפרק במערכת הקבצים ובניהול התהליכים.

המבט הארכיטקטוני: הקרנל הוא "מפעל של אשליות", לא "מנהל משאבים" סתמי — כל שורת קוד בו משמרת את המכונה האבסטרקטית שהובטחה למשתמש. יתרון ההגדרה החומרתית (קוד ב-Ring 0): היא בינארית. הקרנל הוא "השומר שעל החומה"; מעבר לחומה — ה-Extended Machine, מתחתיה — ה-Hardware.

4.1 הקשר הסימביוטי באקו-סיסטם

קריסה או חוסר התאמה באחד הרכיבים משביתה את ה-Ecosystem כולו:

  • הקרנל מספק תשתית פיזית ובידוד.
  • ה-glibc מתרגמת בקשות משתמש לממשק המובן לקרנל (ABI — "חוזה" ברמת הבינארי: אילו אוגרים נושאים אילו ערכים בכניסה לקרנל) ועוטפת את ה-Syscalls בפונקציות C. בלעדיה המכונה האבסטרקטית "קשה מדי"; בלי הקרנל — פקודות ריקות.
  • ה-Bash (מפרש הפקודות) הוא "הסוכן המבצע": מקבל string ומבצע fork()‎ ו-execve()‎ — קריאות מערכת שמפעילות את מנהל התהליכים.
  • הדרייברים (חלק מהקרנל) תלויים ב-Interrupt Controller כדי לדעת מתי הגיעו נתונים, ומתרגמים חומרה פיזית לאובייקט לוגי.

כיוון ה"הזנה" מתהפך משורה לשורה: הקרנל מזין את ה-glibc בחוזה ה-ABI, אך ה-Bash מזין את הקרנל בתהליכים חדשים — סימביוזה, לא היררכיה חד-כיוונית.

מקור: ch01.pdf (עמ' 5–8), Kernel-SDLC.pdf (עמ' 37)

5. Ring 0/3, ‏CPL ומרחבי הזיכרון

החומרה אוכפת את הגבולות. ב-x86_64 זה נעשה במצבי המעבד (CPU Modes):

  • מצב המעבד (CPL — Current Privilege Level): אוגר פנימי (חלק מה-CS Segment Selector) עם רמת ההרשאה הנוכחית. Ring 0 — הפריבילגי ביותר, בו רץ הקרנל (CPL=0); Ring 3 — המוגבל, בו רצים יישומי המשתמש ולרוב גם שאר מרכיבי ה-OS (ספריות, כלי שירות, ממשקי משתמש).
  • Kernel Space מול User Space: הנגזרת של מצב המעבד — חלוקת מרחב הכתובות הווירטואלי. ב-Linux 6.14: User Space אינו נגיש מ-Ring 0 ללא הגדרה מכנית מיוחדת; Kernel Space מוגן מגישה ב-Ring 3, וניסיון כזה יגרור מיד Page Fault (דרך ביט ה-User/Supervisor בטבלאות הדפים).
  • הוראות מיוחסות לדוגמה: HLT (במצגת: HALT), או שינוי רגיסטרי בקרה של ה-MMU — רק הליבה ב-Ring 0 מסוגלת לבצען.

הרחבה — שלושה מונחי חומרה חדשים:

  • MMU (Memory Management Unit): יחידת חומרה שמתרגמת כתובת וירטואלית לכתובת אמיתית ב-RAM.
  • טבלאות הדפים (Page Tables): הקרנל בונה, ה-MMU קורא. לכל "דף" ביטי הרשאה — ביניהם ה-User/Supervisor, שקובע אם קוד ב-Ring 3 רשאי לגעת בו.
  • Page Fault: החריגה שהמעבד מייצר כשתהליך נוגע בכתובת אסורה — למשל תוכנית משתמש שקוראת מ-Kernel Space.

ההגדרה האופרציונלית של הקרנל (לשנן!): "ה-Kernel הוא אוסף כל הקוד (למעט ה-Bootloader) אשר בעת ביצועו, המעבד נמצא ב-CPL=0" — מחברת בין הקוד הסטטי שעל הדיסק למצב הדינמי בזמן ריצה. המרצה נותן אותה פעמיים (מצגת + חוברת) — סימן לחומר מבחן.

5.1 מילת מצב המעבד (PSW), ביט המצב וה-MMU

🎓 מהשיעור בכיתה (מהמחברת)

המרצה שרטט איפה "מצב המעבד" יושב פיזית: בתוך המעבד יש אוגר מצב — PSW (Process Status Word, מילת מצב המעבד) — שמרכז את מצבו הנוכחי, ואחד הביטים בו הוא ביט המצב (mode bit):

  • 1 = מצב גרעין (kernel) — המעבד רשאי לבצע גם הוראות מיוחסות;
  • 0 = מצב משתמש (user) — הוראות לא מיוחסות בלבד.

כלומר CPL אינו רעיון מופשט אלא ערך של ביט באוגר, שהמעבד קורא בשלב פענוח ההוראה (סעיף 3.2). בשרטוט, ליד ה-PSW עמד ה-MMU: השניים אוכפים יחד את הגבול — ה-mode bit קובע אילו הוראות מותרות, וה-MMU לאילו כתובות מותר לגשת.

דוגמאות להוראות מיוחסות שנקב בהן: HALT (עצירת המעבד), והגדרה או שינוי של רגיסטרי ה-MMU — החלפת טבלאות הדפים הפעילות. ההיגיון: מי ששולט ברגיסטרי ה-MMU שולט במה שכל תהליך רואה בזיכרון.

5.2 ציר הזמן — מתי המעבד בגרעין ומתי במשתמש

🎓 מהשיעור בכיתה (מהמחברת)

התמונה של User Space מול Kernel Space היא סטטית; המרצה השלים אותה בתמונה דינמית: ציר זמן שעליו כל קטע ריצה צבוע — אדום = מצב גרעין (mode bit = 1), כחול = מצב משתמש (mode bit = 0). המעבד מתחלף בין הצבעים אינספור פעמים ביום עבודה רגיל: כל קריאת מערכת וכל פסיקה צובעות קטע אדום קצר, ואז חוזרים לכחול.

על אותו ציר מיקם את שרשרת התהליכים שנוצרת מרגע האתחול — כולם תהליכי משתמש (כחול) מעל אותו קרנל אחד: 

init  →  login  →  bash  →  cp

init הוא התהליך הראשון שהמערכת מריצה; הוא מפעיל את login (שם משתמש + סיסמה), login מפעיל bash, וכשמקלידים cp נוצר תהליך נוסף. בתרשים הזיכרון שצייר, bash ו-cp בכחול למעלה (User Space) והקרנל מתחתם באדום. המשך: מסלול האתחול במודול הבא, יצירת התהליכים במודול התהליכים.

5.3 מנגנון מול מדיניות (Mechanism vs. Policy)

חלוקת העבודה בין הקרנל לשאר המערכת — מנגנון מול מדיניות:

  • המנגנון (Mechanism): הליבה מספקת את ה-Context Switching, את ניהול ה-Page Tables ואת ה-Interrupt Handlers — "איך עושים".
  • המדיניות (Policy): ה-OS (דרך רכיבי User-space או הגדרות ליבה) קובעת מי יקבל את המשאב ומתי — "מה עושים ולמי".

מקור: ch01.pdf (עמ' 3, 4, 9)

6. דרייברים ו-ISRs — הזרועות של הקרנל ב-Ring 0

כדי לקיים את האשליה הקרנל חייב לדבר עם החומרה הפיזית. שני הרכיבים שדרכם — מנהלי ההתקנים וה-ISRs — חיים ב-Ring 0.

6.1 מנהלי התקנים (Drivers) — ה"מתרגמים"

מנהל התקן (Device Driver) הוא קוד שהוא חלק מהקרנל, ומתרגם צרכים לוגיים לפעולות פיזיות:

  • הסמכות המכנית: רץ ב-Ring 0 ואינו מוגבל — ניגש לכל כתובת בזיכרון ומבצע פקודות I/O מיוחדות (IN/OUT ב-x86, או MMIO — גישה לאוגרי ההתקן דרך כתובות זיכרון רגילות).
  • החשיבות: בלי דרייברים הקרנל הוא "מוח ללא גוף" — הם מתרגמים בקשה לוגית ("שלח מנה ברשת") לרצף חשמלי ברמת ה-NIC.

6.2 ISRs — "דפיקות הדלת" של החומרה

בפסיקה (Interrupt) החומרה דורשת תשומת לב מיידית. ה-ISR (Interrupt Service Routine) הוא הקוד שנקרא בתגובה:

  • הקריטיות המכנית: המעבד עוצר את עבודתו וקופץ לכתובת המוגדרת ב-IDT (Interrupt Descriptor Table — מתרגמת מספר פסיקה לכתובת שגרת הטיפול). ה-ISR חייב לרוץ ב-Ring 0, כי הוא מנהל את הגישה הראשונית לחומרה.
  • אטומיות (Atomic Execution): בכניסתו נחסמות פסיקות אחרות — Masking (אוטומטית, או בהוראת CLI); הליבה "עיוורת" לאירועים חיצוניים כדי להבטיח את תקינות הטיפול הנוכחי.
  • האיזון ההנדסי: טיפול מהיר ומונע-שיבושים מול הסיכון ב-Deadlock או באובדן מידע מבחוץ. ISR שלא יחזיר שליטה בזמן — המערכת כולה תקפא.

הסימביוזה ב-Ring 0: דרייברים ו-ISRs חולקים סמכות (Ring 0), מרחב כתובות ו-Kernel Stack (המחסנית שהקרנל עובד מולה). מכאן (1) אמון מוחלט — באג בדרייבר הוא באג בליבה; (2) הגנה על האשליה — כל אינטראקציה עם "קובץ" או "רשת" עוברת דרכם.

קופסת ידע — ה-Bootloader (מאתחל המערכת): מגשר על הפער בין החומרה ה"עירומה" למצב שבו הקרנל יכול להתחיל לפעול. בלעדיו הקרנל הוא רק קובץ בינארי על ה-NVM. שלבי האתחול:

  1. Firmware ו-POST: ה-Firmware (תוכנה צרובה בחומרה — UEFI או Legacy BIOS) מבצע POST — Power-On Self-Test: בדיקות אבחון עצמי של רכיבי החומרה (מעבד, זיכרון, בקרים). רק בסיום מוצלח עוברת השליטה ל-Bootloader.
  2. טעינה (Loading): איתור ב-NVM (זיכרון לא-נדיף — דיסק או SSD) של ה-Executable בפורמט ELF (Executable and Linkable Format) המכיל את הקרנל, וטעינתו ל-RAM.
  3. אתחול המכונה: בניית ה-Page Tables הראשוניות, הגדרת ה-GDT (טבלת הסגמנטים), והעברת המעבד ממצב 16-ביט (Real Mode) למצב 64-ביט (Long Mode).
  4. העברת השליטה: אחרי הגדרת RSP (מצביע ה-Stack המוקדם) ואוגרי הבקרה — קפיצה ל-Entry Point של הקרנל.

מקור: ch01.pdf (עמ' 10–11)

7. המורכבות הכמותית — LOC והטרוגניות השפות

קוד הגרעין הוא huge & extremely complex (במילות המרצה). שני מדדים: LOC — Lines of Code, ושפות התכנות.

הפער בין "קרנל בלבד" ל"מערכת מלאה" = ההבדל בין Kernel ל-OS מסעיף 1, במספרים. (בטבלה 6.7; הייחוס של הקורס 6.14 — סדרי הגודל זהים.) לינוקס 6.14: מעל 30 מיליון שורות קוד במקורות הרשמיים, כולל מנהלי ההתקנים.

  • הליבה: ה-TCB (Trusted Computing Base) — מיליוני שורות, כולן ב-Ring 0. המורכבות איכותית: באג אחד מערער את יציבות המערכת כולה.
  • glibc ו-Coreutils (כלי הבסיס של שורת הפקודה — ls, cp, cat): עוד מיליוני שורות ב-User-Space — ה"תיווך" שהופך את המערכת לשמישה.
  • ההשלכה: ה-SDLC (Software Development Life Cycle — אפיון, תכנון, מימוש, בדיקות, הפצה, תחזוקה) הופך מ"רצוי" ל"הכרחי": תיעוד קפדני, Code Review וניהול גרסאות מבוזר — הנושא של המודול הבא.
🎓 מהשיעור בכיתה (מהמחברת)

המספרים כפי שנאמרו בכיתה. המרצה לא הסתפק ב"מעל 30 מיליון" ונקב בטווח: 30–35 מיליון שורות קוד בקרנל. בשיעור אחר הוא פירט גם את ההרכב: כ-35 מיליון שורות בקרנל, מתוכן 95% ב-C ו-5% ב-Assembler; וכשמוסיפים לזה את שאר האקו-סיסטם — glibc, bash ותוכניות המערכת (cp, rm, ls, ps) — מגיעים לכ-100 מיליון שורות קוד. בדרך אגב הוא גם פירק את ראשי התיבות: LOC = Lines of Code.

7.1 אילו שפות — ולמה

  • C: ממפה דטרמיניסטית מבני נתונים לזיכרון — גודל המבנה, סדר השדות (Offset — המרחק בבתים של שדה מתחילת המבנה) והקשרו קבועים מראש, וכך הקרנל ניגש למידע בצורה עקבית.
  • Assembly (x86_64): השפה היחידה שהחומרה מבינה ללא תיווך, הכרחית למה שאין לו סמנטיקה ב-C — אוגרי בקרה (CR3, המצביע על טבלאות הדפים הפעילות), ניהול Interrupts, וביצוע ה-SYSCALL.
  • User-Space (C, C++, Rust, Python): אחרי שהמכונה המורחבת קיימת, השפה נבחרת לפי פרודוקטיביות ולא לפי שליטה בחומרה — שגיאת זיכרון (Segfault — גישה לכתובת אסורה) מפילה את התהליך בלבד.

קוד הקרנל תלוי-ארכיטקטורה: כל מבנה נתונים בקרנל (כמו ה-task_struct, מודול 07) מעוצב לפי ה-ISA, וה-Paging משתנה בין Intel ל-ARM.

קופסת ידע — TCB (Trusted Computing Base): כל מרכיבי המערכת — תוכנה, חומרה וקושחה — שאחראים על אכיפת מדיניות האבטחה. TCB פרוץ או באגי = אין יותר הבטחה לתקינות המערכת. בלינוקס הליבה היא ה-TCB המרכזי: מפרידה בין תהליכים, מנהלת זיכרון ומגנה על ה-Extended Machine מגישה בלתי מורשית.

מקור: Kernel-SDLC.pdf (עמ' 3–6), ch01.pdf (עמ' 12–13)

8. מלכודות למבחן

ה-Bootloader רץ במצב גרעין — אבל אינו חלק מהקרנל. שתי ההגדרות ממעטות אותו במפורש: "למעט קטעי קוד קטנים יחסית כמו ה-bootloader".

קוד הקרנל כולל גם הוראות לא מיוחסות. החץ קרנל←חומרה מסומן "Both privileged and non privileged instructions": הקרנל רשאי לבצע מיוחסות, לא שהוא מבצע רק אותן.

הוראה מיוחסת במצב משתמש ← פסיקה ← הפסקת התהליך. לא "דילוג בשקט" ולא חריגה שהאפליקציה מטפלת בה: זיהוי בשלב ה-Instruction Decode, סירוב, ו-Interrupt שעוצר את התהליך מיידית.

הקרנל הוא Reactive. "הליבה אינה מבצעת עבודה עבור עצמה" — מגיבה ל-System Calls ולפסיקות בלבד. תהליכים פרואקטיביים (Init, ‏smss.exe) שייכים ל-OS, לא לקרנל.

דרייבר אינו "תוכנית נפרדת". הוא חלק מהקרנל, ב-Ring 0, באותו מרחב כתובות ואותו Kernel Stack — באג בדרייבר הוא באג בליבה.

הדגשה מהכיתה — mode bit: 1 = גרעין, 0 = משתמש. שני הערכים סומנו בקו תחתון על הלוח (סעיף 5.1). עוגן: הערך הגבוה (1) = ההרשאה הגבוהה — הפוך ממספור ה-Rings, שבו Ring 0 הוא הגרעין.

תמצית השינון המלאה של הקורס נמצאת בדף ההכנה למבחן (מודול 15).
