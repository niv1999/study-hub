1.2 איך בונים תשובה פתוחה — שלושה משפטים

תשובות המרצה עצמו בבחינה לדוגמה הן שתיים-שלוש שורות. הן קצרות, אבל מלאות: בכל אחת יש הגדרה, מנגנון ונימוק. זה בדיוק המבנה שכדאי לאמץ:

  1. הגדרה — מה זה, במשפט אחד, במונחי הקורס. אם השאלה משווה שני דברים, פותחים בשניהם: "X הוא…, לעומתו Y…".
  2. מנגנון — איך זה עובד בפועל: איזה מבנה נתונים בקרנל, איזו קריאת מערכת, איזה שדה. כאן נכנסים המונחים המדויקים — task_struct, struct file, Inode, f_count.
  3. למה — מה נשבר בלי זה, או מה זה מאפשר. משפט אחד. זה מה שמפריד בין "משנן" ל"מבין".

דוגמה חיה, מהבחינה לדוגמה עצמה — שאלה 2 ("מהו ההבדל הבסיסי ביותר בין Process ל-Thread מבחינת מרחב הכתובות?"). תשובת המרצה: "תהליך (Process) מחזיק במרחב כתובות וירטואלי פרטי ומבודד. לעומתו Thread חולק את מרחב הכתובות של התהליך עם Threads אחרים באותו תהליך." — הגדרה, ניגוד, סוף. אין פסקה שלישית.

שימו לב לניסוח השאלה. המרצה כותב "ההבדל הבסיסי ביותר… מבחינת מרחב הכתובות". זו לא הזמנה לספר הכול על תהליכים מול חוטים — זו שאלה ממוקדת בציר אחד. תשובה שפותחת ב"fork יקר ו-pthread_create זול" עונה על שאלה אחרת, ותקבל פחות נקודות גם אם היא נכונה כשלעצמה.

1.3 שאלת "האם קטע הקוד תקין פונקציונלית?" — איך תוקפים אותה

זו התבנית הקבועה של שתי השאלות האחרונות בחלק א׳. הנוסח כמעט מילה במילה: "במסגרת מטלת תכנות בקורס 'תכנות מערכות', התבקשו הסטודנטים לפתח … לפניך קטע קוד שכתבו סטודנטים כחלק מהפתרון. עליך לקבוע האם הוא תקין פונקציונלית, ואם לא — עליך להסביר במדויק מהי השגיאה ומדוע היא מתרחשת."

שתי המטלות שמהן נלקחים הקטעים הן בדיוק אלו של הקורס: תוכנית ההעתקה my_copy.c ושרת ה-Echo המקבילי. הנה סדר הבדיקות שכדאי לרוץ עליו — מסודר לפי שכיחות השגיאות:

  1. סדר הקריאות — האם כל משתנה קיבל ערך לפני שהשתמשו בו? זו בדיוק שאלה 4 בבחינה לדוגמה: bind(server_fd, …) נקראה לפני socket(), ולכן server_fd הוא 'זבל' — משתנה מקומי לא מאותחל. הסדר הקדוש בשרת: socket → setsockopt → bind → listen → accept. בקבצים: open לפני read/write, וכל אחד מהם לפני close.
  2. בדיקת ערכי החזרה — האם כל קריאת מערכת נבדקה, ומול הערך הנכון? open / read / write / close / socket / bind / listen / accept / connect ⇐ -1; fopen ⇐ NULL; inet_pton ⇐ <= 0; פונקציות pthread ⇐ קוד שגיאה חיובי, לא -1.
  3. כמות הבתים — האם משתמשים ב-bytes_read (מה שנקרא בפועל) או ב-BUFFER_SIZE (מה שביקשנו)? write(dest_fd, buffer, BUFFER_SIZE) אחרי read חלקי = העתקת זבל לסוף הקובץ. אותו דבר ב-send.
  4. סגירות — האם כל fd נסגר, ובאיזה תהליך? בשרת המקבילי: האב סוגר client_fd, הבן סוגר server_fd. ב-cp: אם פתיחת היעד נכשלה — סוגרים קודם את המקור ורק אז יוצאים.
  5. טיפוסי ארגומנטים ומספרם — ssize_t ולא size_t לערך ההחזרה של read/write; ל-open יש ארגומנט שלישי (mode) רק עם O_CREAT; &address מומר ל-(struct sockaddr *); htons(PORT) ולא PORT ישירות.
  6. לוגיקת התהליך/החוט — האם יש exit(0) בבן אחרי הטיפול בלקוח? האם יש waitpid? האם ה-unlock נעשה בידי החוט שנעל? האם ה-Read נכנס לקטע הקריטי, ולא רק ה-Write?

"תקין" היא תשובה לגיטימית — ולפעמים היא הנכונה. שאלה 3 בבחינה לדוגמה היא מלכודת הפוכה: הקוד תקין לחלוטין, והמענה הנדרש הוא להסביר מה הבדיקה עושה. שם המרצה ציפה לשמוע ש-if (src_fd == -1) מכסה שתי סיבות כישלון: הקובץ אינו קיים, או שההרשאות אינן מאפשרות לקרוא ממנו. אל תמציאו שגיאה כשאין — אבל גם אל תכתבו רק "תקין": חייבים לנמק.

1.4 חלק ב׳ — לקרוא אמריקאיות בסגנון של המרצה

לשאלות הסגורות של המרצה יש חתימה מזוהה. חמישה דפוסים שחזרו בבחינה לדוגמה — לזהות אותם חוסך זמן ונקודות:

  • "אף אחת מהתשובות הנ"ל אינה נכונה" — הופיעה פעמיים כאפשרות ד׳, ובאחת מהן היא התשובה הנכונה (שאלה 6, על מה שמור בבלוק 0 של ה-NVM). אסור לפסול אותה אוטומטית.
  • הבהרות בסוגריים מרובעים — [= .h file], [= Process ID], [= 'אמריקאיות'], [= כזו שצריך להקצות עבורה ליבה (core)]. ההבהרה מפרשת ראשי תיבות או מגדירה מונח — ולעיתים היא רמז ישיר לתשובה. קראו אותה, אל תדלגו עליה.
  • מסיחים שהם שיבוש כתיב — בשאלה 9 המסיח היה styruct process_struct (שיבוש של struct). מסיח שנראה נכון במבט חטוף — קראו את שם המבנה עד הסוף.
  • הדגשת המילה השוללת — בשאלה 10: "מייצג עבור המתכנת, לא עבור ה-kernel (!!)". שני סימני קריאה = אזהרה שהשאלה הפוכה ממה שנדמה.
  • קיצורים בלי פירוש — NVM = הזיכרון הלא-נדיף (הדיסק), MM = Main Memory (הזיכרון הראשי). המרצה משתמש בהם כמובנים מאליהם — גם בכיתה וגם בבחינה.

וטכניקה פשוטה: לפסול קודם. ברוב שאלות המרצה שתיים מארבע האפשרויות שגויות באופן בוטה (למשל "את מהירות הקריאה" בשאלה על שדה ה-mode), ואז ההכרעה היא בין שתיים בלבד. אם אחת מהן מנוסחת במונחי הקורס המדויקים — היא כמעט תמיד הנכונה.

2. סיכום-על — דף העזר של הקורס

מכאן ועד סוף הסעיף: כל הקורס, מסודר לפי יחידות, בלי סיפורים. כל מספר וכל רשימה הם בדיוק כפי שהמרצה נתן אותם. זה לא תחליף לפרקים — כל כרטיס מסתיים בקישורים לעמודים שבהם ההסבר המלא. השתמשו בו כמסלול חזרה אחרון: קוראים כרטיס, מכסים אותו ביד, ומנסים לשחזר.

2.1 יסודות — מערכת ההפעלה והקרנל יחידה 1

  • OS ≠ Kernel — מערכת ההפעלה = הקרנל + ספריות מערכת + כלי שירות (utilities) + ממשקי משתמש. הקרנל הוא המרכיב החיוני ביותר, והוא רץ ב-Kernel Space בלבד.
  • ההגדרה הבינארית של הקרנל — כל הקוד שבזמן ביצועו המעבד נמצא במצב גרעין (CPL = 0) — למעט קטעי קוד קטנים כמו ה-bootloader, שרץ במצב גרעין אך אינו חלק מהקרנל.
  • Extended Machine — הקרנל מסתיר את החומרה ומציג "מכונה מורחבת": Scheduler ⇒ אשליית בלעדיות על המעבד; Memory Manager ⇒ מרחב זיכרון רציף; Device Management ⇒ שקיפות התקנים; File System ⇒ עמידות וארגון; Security ⇒ יציבות ואמינות.
  • שתי האבסטרקציות של הקרנל (הניסוח של המרצה על הלוח) — Task (= task_struct) ו-File (= Inode + Data Blocks). כל הקורס נבנה על שתיהן.
  • הקרנל הוא Reactive — "הליבה אינה מבצעת עבודה עבור עצמה": היא מגיבה רק לקריאות מערכת ולפסיקות.
  • Mechanism vs. Policy — הקרנל מספק את האיך; מערכת ההפעלה קובעת מי ומתי.

2.2 מסלול החיים של המערכת — בקצרה יחידה 1

  • SDLC של הקרנל — דרישות (SRS) → HLD → LLD → קידוד + unit testing → Extensive Validation → dist-manager → distribution package (מכיל: installer, קרנל, glibc, bash, תוכניות מערכת, ספריות וקובצי .h).
  • סדר האתחול — power up → POST → firmware (bootstrap) → bootloader → memory image של הקרנל ל-MM → login → bash.
  • מפת ה-NVM — GPT (Global Partition Table, בתחילת הדיסק) → bootloader → root (Inode Table + Data Blocks) → Home → Swap (זיכרון מדומה). תוכן תיקיית השורש נוצר בהתקנה על ידי ה-installer — לא באתחול.
  • 5 מקטעי ה-memory image — code (text) · data · bss · stack · heap.
  • multiprogramming ≠ task — task = משימה אחת; multiprogramming = להריץ N משימות, לחלק ביניהן את ה-MM, ולהחליף כשאחת ממתינה ל-I/O. ל-DOS לא היו לא multiprogramming ולא Security.
  • חשבונות — root = uid 0 (הודגש פעמיים); הקרנל מכיר מספר בלבד, והתרגום שם ⇐ מספר נעשה ב-user space. קובץ החשבונות: /etc/passwd.
  • הרשאות — שלוש שלישיות rwx — owner / group / other; 111 111 111 = 777. לפרק ספרה-ספרה: chmod my-file 740 ⇒ 7 לבעלים, 4 לקבוצה, 0 לאחרים. סוגי קבצים לפי התו הראשון ב-ls -l: - · d · b (SSD) · c (מקלדת) · socket.

Partial I/O — הלולאה הנכונה, זו שמופיעה בכל קוד בקורס:

ssize_t bytes_read;
while ((bytes_read = read(src_fd, buffer, BUFFER_SIZE)) > 0) {
    bytes_written = write(dest_fd, buffer, bytes_read);   /* bytes_read — NOT BUFFER_SIZE */
    if (bytes_written != bytes_read) { perror("Error writing data"); ... }
}
/* bytes_read == 0  ⇒ EOF ;  bytes_read < 0 ⇒ error */

  • בטבלת ה-FD — 0 = stdin, 1 = stdout, 2 = stderr, ולכן ה-open הראשון מחזיר 3.

    /* --- CHILD --- : fork returned 0 here */
    execve("/full/path/example", argv, envp);   /* replaces the memory image */
    exit(0);                                    /* very important! */
}
else {
    /* --- PARENT --- : pid holds the child's PID */
    wait(NULL);          /* or waitpid(pid, &status, 0) */
}
  • execve() — אינו יוצר תהליך שלישי. הוא פותח את קובץ ההרצה, מאמת את ה-ELF Header, מוחק ומאפס לחלוטין את מרחב הזיכרון הישן שהועתק ב-fork, מקצה memory image חדש, בונה את ה-Stack עם argv ומשתני הסביבה, ומאפס את מצביע הפקודות לנקודת הכניסה. ה-task_struct וה-PID נשארים אותם.
  • הקבצים הפתוחים שורדים את ה-exec — כולל stdin/stdout/stderr. הזיכרון נמחק, טבלת ה-FD לא. זה כל הטריק מאחורי הפניית קלט/פלט.
  • תהליך חדש נוצר תמיד על ידי תהליך קיים — המשפחה: fork(), clone(), clone3(), vfork().

חמשת שלבי ה-bash מהקלדה ועד הרצה — לדעת בעל-פה:

1. Terminal Line Discipline   — TTY driver, echo to screen, input buffer until ENTER
2. Tokenization & Parsing     — first token = the command name;  "./" ⇒ relative path, no PATH search
3. Built-in check             — cd / alias / history / echo / export / pwd ⇒ NO new process
4. fork()                     — clone of task_struct; child gets 0, parent gets the child's PID
5. execve()                   — child loads the new program;  parent goes to Sleep/Wait

2.7 סנכרון — Race Condition ו-Mutex יחידה 5

  • הגדרה — Race Condition הוא מצב שבו התוצאה של התוכנית תלויה בסדר שבו התזמן הקרנל את החוטים, ולא רק בקוד. שני חוטים ניגשים לאותו נתון משותף, לפחות אחד מהם כותב — ואין סנכרון.
  • שלוש הסכנות של תכנות מקבילי, בשמות שהמרצה דורש בעברית: race condition · deadlock = קיפאון · starvation = הרעבה. (וגם: Interleaving = שזירה, Critical Section = קטע קריטי.)
  • counter++ אינה פעולה אטומית — המרצה כתב זאת עם סימן קריאה: [= 3 הוראות מכונה !]. שורה אחת ב-C = Read (זיכרון→אוגר) → Modify (+1 באוגר) → Write (אוגר→זיכרון). הנימוק: ארכיטקטורת load/store של RISC. Context Switch שנופל בין השלבים הוא בדיוק מקור הבאג.

ה-Interleaving הקנוני, ב-counter = 100 (הפירוט המלא בפרק הסנכרון):

T1: Read  ⇒ reg = 100
             ← Context Switch →
T2: Read  ⇒ reg = 100 ;  Modify ⇒ 101 ;  Write ⇒ memory = 101
T1: Modify ⇒ 101 ;        Write  ⇒ memory = 101      /* one increment LOST */

בגלל זה מונה של שני חוטים × 1,000,000 ייתן תוצאה נמוכה מ-2,000,000 ושונה בכל הרצה — Non-determinism. ובדוגמת הבנק של המרצה (4 חוטים: שניים מפקידים ושניים מושכים, 100,000 איטרציות כל אחד, יתרה התחלתית $1000): שלוש הרצות נתנו $850, $1120, ולעיתים במקרה $1000. קבלת התוצאה הנכונה במקרה היא בדיוק מה שהופך את הבאג למסוכן.

התיקון — הקטע הקריטי חייב לעטוף את כל רצף ה-Read-Modify-Write:

pthread_mutex_lock(&my_account.lock);      /* [CRITICAL SECTION START] */

double temp = my_account.balance;          /* Read   — must be INSIDE */
temp += 10.0;                              /* Modify */
my_account.balance = temp;                 /* Write  */

pthread_mutex_unlock(&my_account.lock);    /* [CRITICAL SECTION END]   */

אם ה-Read נשאר מחוץ למנעול — ה-race נשאר במלואו. עם mutex נכון התוצאה היא תמיד בדיוק $1000.00.

2.9 IPC ו-Signals — שורה אחת לכל נושא עדיפות נמוכה

שני הנושאים האלה מופיעים בסילבוס אך טרם הועלו להם שקפים, והם אינם מופיעים בבחינה לדוגמה. תנו להם עדיפות נמוכה — אבל דעו את השורה האחת:

  • pipe(int pipefd[2]) — צינור חד-כיווני בין תהליכים; pipefd[0] = קריאה (כמו stdin), pipefd[1] = כתיבה (כמו stdout). חייב להיקרא לפני fork — הירושה של ה-FD היא כל המנגנון.
  • FIFO (mkfifo) — צינור עם שם במערכת הקבצים, ולכן גם בין תהליכים שאינם קרובי משפחה.
  • dup2(oldfd, newfd) — מפנה FD קיים לאובייקט קובץ אחר — הבסיס להפניית קלט/פלט (> file, |). הוא רק מוסיף מצביע בטבלה ומגדיל f_count — לא מעתיק בתים.
  • סיגנל — הודעה אסינכרונית לתהליך. SIGINT (Ctrl+C) ו-SIGTERM — ברירת המחדל היא סיום; SIGKILL ו-SIGSTOP — אינם ניתנים ללכידה או לחסימה.
  • SIGCHLD — נשלח לאב כשבן מסתיים. ברירת המחדל שלו היא התעלמות — ובדיוק לכן זומבים נערמים אם האב לא קורא ל-wait/waitpid. הסיגנל מודיע, הוא אינו קוצר.
  • sigaction() ולא signal() — signal אינה פורטבילית. וב-handler מותרות רק פעולות async-signal-safe — printf/malloc בתוכו הם באג.

3. בנק שאלות פתוחות — בסגנון חלק א׳

שתים-עשרה שאלות בתבנית של המרצה: שש שאלות הגדרה/הבדל ושש שאלות "האם קטע הקוד תקין פונקציונלית?". כל קטע קוד לקוח מקוד הקורס — my_copy.c, שרת ה-Echo האיטרטיבי והמקבילי, ודוגמאות ה-pthread וה-mutex. תחת כל שאלה: תשובת מודל בלחיצה, ושורת "מה בודקים".

איך להתאמן נכון: כתבו את התשובה על נייר לפני שאתם פותחים את הפתרון, והגבילו את עצמכם ל-3–4 שורות. אם התשובה שלכם ארוכה משמעותית מתשובת המודל — כנראה סיפרתם על החומר במקום לענות על השאלה.

שאלה 1 הגדרה

מהו File Descriptor, ומה בדיוק שמור בתא שאליו הוא מצביע?

FD הוא מספר שלם קטן שהקרנל מחזיר בעת פתיחת קובץ, והוא אינדקס בטבלת הקבצים הפתוחים של אותו תהליך (current->files). בתא שמור מצביע ל-struct file בזיכרון הקרנל, המחזיק את ה-File Offset (f_pos), הדגלים ומונה ההפניות f_count; ממנו ממשיכה השרשרת אל ה-In-core Inode ואל ה-Data Blocks. 0, 1 ו-2 תפוסים מראש, ולכן ה-open הראשון מחזיר 3.

מה בודקים: "אינדקס בטבלה של התהליך" ולא "מזהה של הקובץ", ושבתא יש מצביע ל-struct file — לא ה-Inode עצמו.

שאלה 2 הבדל

מהו ההבדל בין fork() ל-execve() — מבחינת מספר התהליכים במערכת ומבחינת מרחב הזיכרון?

fork() יוצר תהליך: אחריו יש שני תהליכים — task_struct חדש עם PID חדש, שמקבל עותק של מרחב הזיכרון ושל טבלת ה-FD. הבן ממשיך מנקודת ה-fork ומקבל 0; האב מקבל את ה-PID של הבן.

execve() מחליף תוכנית: מספר התהליכים אינו משתנה. הוא מוחק את מרחב הזיכרון הקיים, טוען את קובץ ה-ELF החדש ומאפס את מצביע הפקודות. ה-PID נשאר, והקבצים הפתוחים שורדים.

מה בודקים: "אחד יוצר, השני מחליף" — PID חדש מול PID זהה, ושטבלת ה-FD שורדת את ה-exec.

שאלה 3 קטע קוד

במסגרת מטלת תכנות בקורס "תכנות מערכות", התבקשו הסטודנטים לפתח תוכנית בשם my_copy.c להעתקת קבצים, תוך שימוש ב-System Calls בלבד. לפניך קטע קוד שכתבו סטודנטים. עליך לקבוע האם הוא תקין פונקציונלית, ואם לא — עליך להסביר במדויק מהי השגיאה ומדוע היא מתרחשת. 

while ((bytes_read = read(src_fd, buffer, BUFFER_SIZE)) > 0) {
    bytes_written = write(dest_fd, buffer, BUFFER_SIZE);
    if (bytes_written != BUFFER_SIZE) {
        perror("Error writing data");
        exit(EXIT_FAILURE);
    }
}

הקטע אינו תקין מבחינה פונקציונלית.

ה-write מעביר תמיד BUFFER_SIZE בתים, בעוד ש-read החזיר bytes_read — ומספר הבתים שנקראו בפועל אינו חייב להיות שווה למבוקש (Partial I/O). בקריאה האחרונה מהקובץ יוחזר רק מה שנשאר, והכתיבה תעתיק גם את הזבל שנותר בבאפר מהסיבוב הקודם: קובץ היעד יהיה גדול מהמקור ותוכנו פגום.

התיקון: write(dest_fd, buffer, bytes_read); ובדיקה מול bytes_read.

מה בודקים: bytes_read מול BUFFER_SIZE, ונימוק דרך Partial I/O.

שאלה 4 הגדרה

מהי מוסכמת ערך ההחזרה של קריאות מערכת בלינוקס, ובמה שונה ממנה מוסכמת ההחזרה של פונקציות pthread?

קריאות מערכת: בהצלחה — ערך אי-שלילי בעל משמעות (fd, מספר בתים, PID, או 0); בכישלון — -1, והסיבה במשתנה errno (ENOENT=2, EACCES=13…), שיש לקרוא מייד.

פונקציות pthread: 0 בהצלחה, קוד שגיאה חיובי בכישלון. הן אינן מחזירות -1 ואינן מעדכנות errno — ולכן בדיקה מול -1 לעולם לא תתפוס את השגיאה.

מה בודקים: ששתי המוסכמות מנוסחות כניגוד, ושציינתם ש-errno אינו מעודכן ב-pthread.

שאלה 5 קטע קוד

במסגרת מטלת תכנות בקורס "תכנות מערכות", התבקשו הסטודנטים לפתח תוכנית להעתקת קבצים באמצעות System Calls בלבד. לפניך קטע קוד שכתבו סטודנטים. עליך לקבוע האם הוא תקין פונקציונלית, ואם לא — עליך להסביר במדויק מהי השגיאה ומדוע היא מתרחשת. 

int src_fd = open(argv[1], O_RDONLY);
if (src_fd == NULL) {
    perror("Failed to open source file");
    exit(EXIT_FAILURE);
}

הקטע אינו תקין מבחינה פונקציונלית.

open() מחזירה int: fd אי-שלילי בהצלחה ו--1 בכישלון. הבדיקה מול NULL (שערכו 0) בודקת למעשה src_fd == 0: כישלון אמיתי לא ייתפס והתוכנית תמשיך לקרוא מ-fd לא חוקי ותקבל EBADF; ואם דווקא הוקצה fd == 0, ידווח כישלון שלא קרה.

הבלבול מגיע מ-fopen(), שמחזירה FILE * ולכן נבדקת מול NULL. התיקון: if (src_fd == -1).

מה בודקים: -1 ולא NULL, והסבר למה זה מסוכן — הכישלון פשוט לא ייתפס.

שאלה 6 הבדל

מהו ההבדל בין Deadlock (קיפאון) לבין Starvation (הרעבה)?

קיפאון: חוט ממתין ל-mutex שאף אחד לא ישחרר לעולם — המנעול אינו מתפנה, והתהליכים נתקעים לצמיתות.

הרעבה: המנעול כן מתפנה שוב ושוב, אבל חוט מסוים לעולם אינו מקבל אותו — תמיד מישהו אחר מקדים אותו.

במילה אחת: בקיפאון אף אחד לא מתקדם; בהרעבה אחד לא מתקדם.

מה בודקים: השמות העבריים שהמרצה דורש, וההבחנה סביב השאלה האם המנעול מתפנה.

שאלה 7 קטע קוד

במסגרת מטלת תכנות בקורס "תכנות מערכות", התבקשו הסטודנטים לפתח Echo server. לפניך קטע קוד שכתבו סטודנטים. עליך לקבוע האם הוא תקין פונקציונלית, ואם לא — עליך להסביר במדויק מהי השגיאה ומדוע היא מתרחשת. 

ssize_t bytes_read;
while ((bytes_read = read(client_fd, buffer, BUFFER_SIZE)) > 0) {
    send(client_fd, buffer, BUFFER_SIZE, 0);
}
close(client_fd);

הקטע אינו תקין מבחינה פונקציונלית.

ה-send שולח תמיד 4096 בתים, בעוד שהלקוח שלח bytes_read בתים. שרת echo אמור להחזיר בדיוק את מה שהתקבל, ולכן הלקוח יקבל את הודעתו ואחריה זבל — ואף גרוע מכך, שאריות מהודעה של לקוח קודם שטופל באותו באפר (דליפת מידע). התיקון: send(client_fd, buffer, bytes_read, 0);.

שאר הקטע תקין: התנאי > 0 נכון (0 = הלקוח סגר, שלילי = שגיאה), וה-close בסוף השיחה במקומו.

מה בודקים: אותה שגיאה כמו בשאלה 3 בהקשר של סוקט — ותוספת הניקוד היא על "הזבל שנשלח ללקוח".

שאלה 8 קטע קוד

במסגרת מטלת תכנות בקורס "תכנות מערכות", התבקשו הסטודנטים לפתח concurrent Echo server. לפניך קטע קוד שכתבו סטודנטים. עליך לקבוע האם הוא תקין פונקציונלית, ואם לא — עליך להסביר במדויק מהי השגיאה ומדוע היא מתרחשת. 

while (1) {
    client_fd = accept(server_fd, (struct sockaddr *)&address, (socklen_t*)&addrlen);
    pid_t pid = fork();

    if (pid == 0) {
        close(server_fd);
        while ((bytes_read = read(client_fd, buffer, BUFFER_SIZE)) > 0) {
            process_echo(buffer, bytes_read);
            send(client_fd, buffer, bytes_read, 0);
        }
        close(client_fd);
    }
    else {
        close(client_fd);
        while (waitpid(-1, NULL, WNOHANG) > 0);
    }
}

הקטע אינו תקין — חסרה השורה exit(0); בסוף בלוק הבן.

אחרי close(client_fd) הבן אינו מסתיים: הוא עותק מלא של האב, ולכן נופל בחזרה ללולאת ה-while(1) ומנסה לבצע בעצמו accept(server_fd, …) — אך הוא כבר סגר את server_fd, והקריאה תיכשל עם EBADF בלולאה אינסופית. המרצה סימן את השורה במפורש: "very important!".

ליקוי משני: ערך ההחזרה של accept אינו נבדק (if (client_fd < 0) { perror("accept"); continue; }).

מה בודקים: את exit(0), ואת ההסבר "הבן חוזר ללולאה ומנסה accept בעצמו".

שאלה 9 הגדרה

קריאת המערכת close() נראית כמו "סגירת חלון". הסבירו מה היא באמת עושה, ומדוע ייתכן שאחריה הקובץ עדיין פתוח.

close(fd) עושה שני דברים: מסירה את ה-FD מטבלת התהליך (מכאן כל read/write עליו ייכשל ב-EBADF, והמספר פנוי להקצאה מחדש), ואז מפחיתה ב-1 את מונה ההפניות f_count של ה-struct file (fput).

המונה נחוץ כי fork(), dup() ו-dup2() יוצרים כמה מחזיקים לאותו אובייקט. אם אחרי ההפחתה f_count > 0 — הקובץ נשאר פתוח עבור השאר. רק ב-f_count == 0 מתבצע הניקוי המלא (release, dput, iput ושחרור האובייקט).

מה בודקים: את המילים reference count / f_count ואת התנאי == 0.

שאלה 10 קטע קוד

במסגרת מטלת תכנות בקורס "תכנות מערכות", התבקשו הסטודנטים להגן על יתרת חשבון בנק המשותפת לארבעה threads. לפניך קטע קוד שכתבו סטודנטים. עליך לקבוע האם הוא תקין פונקציונלית, ואם לא — עליך להסביר במדויק מהי השגיאה ומדוע היא מתרחשת. 

void* deposit_service(void* arg)
{
    for (int i = 0; i < 100000; i++) {
        double temp = my_account.balance;          /* Read   */
        temp += 10.0;                              /* Modify */

        pthread_mutex_lock(&my_account.lock);
        my_account.balance = temp;                 /* Write  */
        pthread_mutex_unlock(&my_account.lock);
    }
    return NULL;
}

הקטע אינו תקין — ה-race condition נשאר במלואו.

עדכון יתרה הוא רצף Read → Modify → Write. כאן רק ה-Write בתוך הקטע הקריטי, ולכן Context Switch שנופל בין קריאת ה-balance לבין הכתיבה עדיין אפשרי: חוט אחר מספיק לעדכן את היתרה, והחוט שמתעורר דורס את השינוי עם הערך הישן ששמור ב-temp.

הכלל: כל רצף Read-Modify-Write על נתון משותף נכנס כולו לתוך אותו lock/unlock.

מה בודקים: שאמרתם במפורש שה-Read חייב להיות בפנים, ושהסברתם את הדריסה דרך Context Switch.

שאלה 11 קטע קוד

במסגרת מטלת תכנות בקורס "תכנות מערכות", התבקשו הסטודנטים ליצור שני threads ולוודא שהיצירה הצליחה. לפניך קטע קוד שכתבו סטודנטים. עליך לקבוע האם הוא תקין פונקציונלית, ואם לא — עליך להסביר במדויק מהי השגיאה ומדוע היא מתרחשת. 

pthread_t t1, t2;

if (pthread_create(&t1, NULL, increment_task, NULL) == -1) {
    perror("pthread_create failed");
    exit(EXIT_FAILURE);
}
if (pthread_create(&t2, NULL, increment_task, NULL) == -1) {
    perror("pthread_create failed");
    exit(EXIT_FAILURE);
}

printf("Final Counter Value: %d\n", counter);
return 0;

הקטע אינו תקין — ושתי שגיאות נפרדות בו.

1. מוסכמת ההחזרה שגויה. פונקציות pthread מחזירות 0 בהצלחה וקוד שגיאה חיובי בכישלון — לא -1, והן אינן מעדכנות errno. התנאי == -1 לעולם לא יתקיים. הנוסח הנכון: rc = pthread_create(...); if (rc != 0) { ... }.

2. חסר pthread_join. ה-main מדפיס וחוזר מיד — ובלינוקס סיום ה-main thread גורר את סגירת כל התהליך, כך שהחוטים ייהרגו לפני שיספיקו לרוץ והערך שיודפס יהיה שרירותי. (בשקפים המרצה המחיש את אותה נקודה עם sleep(2).)

מה בודקים: קודם כול את מוסכמת ה-pthread; אזכור ה-join הוא תוספת שמראה הבנה מלאה.

שאלה 12 הגדרה

בשרת Echo מקבילי, מדוע חייב תהליך האב לקרוא ל-close(client_fd) מיד אחרי ה-fork(), אם ממילא הבן הוא זה שמטפל בלקוח?

fork() משכפל את טבלת ה-FD, אך לא את האובייקטים: אובייקט ה-struct file של הסוקט נשאר אחד ומשותף, ורק f_count עולה מ-1 ל-2.

לכן כשהבן יסגור, המונה יירד ל-1 בלבד — הסוקט לעולם לא ייסגר באמת, כי ה-reference count לעולם לא יגיע לאפס: הלקוח לא יקבל סימן סיום, ובכל לקוח נוסף נצברת עוד הפניה עד מיצוי טבלת ה-FD. באותו היגיון הפוך, הבן חייב לסגור את server_fd.

מה בודקים: "reference count לעולם לא יגיע לאפס". "כדי לא לבזבז זיכרון" אינו מספיק — זה הניסוח שהמרצה שולל.

4. עשרים מלכודות שחוזרות

מרוכזות מכל פרקי הקורס — מסעיפי "מלכודות למבחן" של כל מודול ומהנקודות שהמרצה סימן בכיתה כ"לזכור". שורה אחת לכל אחת. קראו אותן בבוקר הבחינה.

  1. mode bit: 1 = גרעין, 0 = משתמש — ושימו לב שזה הפוך ממספור ה-Rings, שבו דווקא Ring 0 הוא הגרעין.
  2. printf, fopen, fread, fwrite שייכות ל-glibc ורצות ב-user space; רק open/read/write/close הן קריאות מערכת.
  3. שגיאות: השמות הסמליים מוגדרים ב-<errno.h>, אבל הערכים המספריים מוגדרים בקובץ header (.h) של הקרנל.
  4. פונקציות pthread מחזירות 0 בהצלחה וקוד שגיאה חיובי בכישלון — לא -1, והן אינן מעדכנות errno.
  5. לכל API ערך כישלון אחר: open ⇐ -1; fopen ⇐ NULL; inet_pton ⇐ <= 0. אל תערבבו.
  6. read שמחזירה 0 פירושה סוף קובץ (EOF) — או שהלקוח סגר את החיבור. 0 אינו שגיאה; שגיאה היא ערך שלילי.
  7. כותבים ושולחים bytes_read, לא BUFFER_SIZE — אחרת מעתיקים לקובץ (או שולחים ללקוח) את הזבל שנשאר בבאפר.
  8. שם הקובץ אינו שמור ב-Inode אלא ב-directory entry; שדה ה-mode קובע את סוג הקובץ והרשאות הגישה.
  9. המספרים של מערכת הקבצים: Inode 0 ו-1 אינם בשימוש ו-Inode 2 היא תיקיית השורש; סקטור = 512, בלוק = 4096, רשומת Inode = 256.
  10. f_count חי ב-struct file, i_count חי ב-In-core Inode — שני מונים שונים על שתי חוליות שונות בשרשרת.
  11. שתי קריאות open נפרדות לאותו קובץ ⇒ שני אובייקטים ושני Offsets נפרדים; אחרי fork ⇒ אובייקט אחד ו-Offset משותף.
  12. בטבלת ה-FD המקומות 0, 1, 2 תפוסים מראש (stdin/stdout/stderr) — ולכן ה-open הראשון מחזיר 3.
  13. אחרי fork הבן ממשיך מנקודת ה-fork עם PID חדש — לא מתחילת main, ולא עם ה-PID של האב.
  14. execve אינו יוצר תהליך שלישי — הוא מוחק את מרחב הזיכרון ומחליף את התוכנית; הקבצים הפתוחים שורדים אותו.
  15. אם ה-main thread חוזר מ-main — כל החוטים מתים איתו. מסיימים ב-pthread_join, לא בתקווה.
  16. זומבי אינו תהליך שרץ — הוא רשומה בטבלת התהליכים. בלי waitpid הטבלה מתמלאת עד שלא ניתן ליצור תהליכים חדשים במערכת.
  17. counter++ הוא שלוש הוראות מכונה (Read-Modify-Write) — ובתוכנית עם שתי קריאות ל-pthread_create יש שלושה חוטים, כולל main.
  18. רק החוט שביצע את הנעילה רשאי לשחרר — ובקטע הקריטי חייב להיכלל גם ה-Read, לא רק ה-Write.
  19. socket תמיד לפני bind — אחרת server_fd הוא 'זבל'. ו-accept מחזירה FD חדש, לא את server_fd.
  20. בשרת המקבילי: האב סוגר client_fd, הבן סוגר server_fd — אחרת ה-reference count לעולם לא יגיע לאפס; והבן חייב exit(0).

ושתי מלכודות שהן על הבחינה ולא על החומר: (א) בשאלת "האם קטע הקוד תקין" — "תקין" היא תשובה לגיטימית, ואז מסבירים מה הקוד עושה ולמה זה נכון; (ב) בחלק ב׳ — אל תפסלו אוטומטית את "אף אחת מהתשובות הנ"ל"; בבחינה לדוגמה היא הייתה התשובה הנכונה בשאלה 6.
