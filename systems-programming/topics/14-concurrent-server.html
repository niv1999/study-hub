שרת מקבילי — fork() אחרי accept(), ניהול FDs וזומבים

⏱ זמן משוער: 50 דק'

מקור: Concurrent.pdf מקור: Iterative.pdf

1. הבעיה — לקוח אחד איטי, וכל השאר מחכים

בשיעור הקודם (Sockets ושרת Echo איטרטיבי) בנינו שרת שעובד מצוין — כל עוד יש לקוח אחד. הקוד שלו הוא לולאה אחת פשוטה: 

while (1) {
    client_fd = accept(server_fd, ...);   /* מחכים ללקוח */
    while ((bytes_read = read(client_fd, buffer, BUFFER_SIZE)) > 0)
        send(client_fd, buffer, bytes_read, 0);
    close(client_fd);                     /* רק עכשיו חוזרים ל-accept */
}

שימו לב לסדר: התהליך נכנס ללולאת ה-Echo של הלקוח הנוכחי, ורק אחרי שהלקוח הזה התנתק הוא חוזר ל-accept(). זה מה שהופך אותו לשרת איטרטיבי (Iterative) — הוא מטפל בלקוחות אחד-אחרי-השני, אף פעם לא בו-זמנית.

ולמה זה קטלני? כי גם accept() וגם read() הן קריאות חוסמות (blocking) — כלומר הקרנל מקפיא את התהליך בתוך הקריאה עד שיש מה להחזיר. אם הלקוח שלנו מקליד לאט, או שולח קובץ ענק ברשת איטית, התהליך תקוע בתוך read() — ובזמן הזה הוא לא נמצא ב-accept().

המשפט של המרצה, מילה במילה: “In the first example, the server was Iterative — if one client sent a large message slowly, all other clients were blocked.”
כלומר: לקוח אחד ששולח הודעה גדולה לאט — חוסם את כל שאר הלקוחות.

🎓 מהשיעור בכיתה (מהמחברת)

בשיעור האחרון (3.9) המרצה הקרין הערה מודפסת משלו, שמסבירה איך בכלל להתייחס לשרת האיטרטיבי. מילה במילה:

"כמובן שבשרת 'אמיתי' ה-server task לא יקרא ל-listen עם הערך 3.
אבל ברור גם ששרת 'אמיתי' לא ימומש במודל הזה. במודל ה-iterative.
הבאנו אותו רק כדוגמא פשוטה להסביר את קריאות המערכת.
ולא כדוגמת [ק]וד מעש[י]."

כלומר: השרת האיטרטיבי הוא דוגמה דידקטית שנועדה ללמד את רצף קריאות המערכת — ו-backlog = 3 אינו ערך "אמיתי". המודל שבו באמת משתמשים הוא זה שבעמוד הזה.

הרעיון: לשכפל את השרת לכל לקוח

הפתרון של המרצה אינו לשכתב את לולאת ה-Echo ואינו להאיץ אותה. הוא פשוט בהרבה: ברגע ש-accept() מחזירה קישור חדש — משכפלים את התהליך בעזרת fork(), ומחלקים את העבודה:

מנגנון הקונקורנטיות (סעיף 1 בחוברת של המרצה):

  • ברגע שמתבצע accept, השרת הופך ל"מפעל לשכפול תהליכים" (process duplication factory).
  • האב חוזר מיד ל-accept כדי לקבל את הלקוח הבא.
  • הבן מטפל בלקוח הנוכחי באופן עצמאי לחלוטין.
  • יעילות: ניצול מלא של מעבדים מרובי ליבות (Multi-core) — כל תהליך יכול לרוץ על ליבה אחרת.

זהו שרת מקבילי (Concurrent Server): לא תהליך אחד שמטפל בכולם בתורות, אלא תהליך נפרד לכל לקוח.

שימו לב לנקודה שקל לפספס: הבן לא מריץ תוכנית אחרת. אין כאן execve() — הבן הוא עותק מדויק של השרת, שממשיך לרוץ מהשורה שאחרי ה-fork(), פשוט בענף אחר של הקוד (מודול 07 מפרט את הזוג fork/execve).

ויש בונוס חינוכי בדוגמה הזו: המרצה מוסיף לשרת גם לוגיקת Uppercase — המרת הטקסט לאותיות גדולות לפני שהוא נשלח בחזרה. בלשונו: התוספת הזו "מדגימה שהשרת אינו רק צינור (pipe) אלא יחידת עיבוד (processing unit)". נחזור לזה בסעיף 2.

🎓 מהשיעור בכיתה (מהמחברת)

בסוף השיעור על ה-cp (13.8) המרצה צייר על הלוח שלושה תרחישים כמפת דרכים להמשך הקורס: Ⅰ — task אחד שמעתיק src → dest (טורי); Ⅱ — multiple tasks (threads) על אותם קבצים, עם החלוקה ל-readers ו-writers (מודול 11); Ⅲ — client מול Cloud server עם multiple tasks. השיעור הזה הוא תרחיש Ⅲ.

בשיעור מוקדם יותר (26.7) המרצה העמיד זה מול זה שני קטעי קוד: simple_bash.c שמשתמש ב-fork(), מול concurrent_server.c שמבצע accept() ואז pthread_create(…) — והדגיש שתהליך "יקר" ו-pthread_create "זול". כלומר: מה שנלמד כאן עם fork() אפשר לממש גם עם Threads, בעלות נמוכה יותר (מודול 09). בשקפים של השיעור הזה — הגרסה עם fork(), וזו הגרסה שנדרשת במבחן.

ובשיעור האחרון (3.9) הוא פתח בדיוק בהעמדה הזו — "2 אופציות": fork(), שיוצר task חדש, מול pthread_create. הוא ציין שthreads הרבה יותר "קלים" ושה-context שלהם קטן יותר (ולכן גם ה-Context Switch ביניהם זול יותר) — אבל מיד הוסיף את המחיר: "הבעיה: race condition", ולכן נדרש סנכרון באמצעות mutex (מודול 11). את thread pooling הוא הזכיר בשמו בלבד ואמר במפורש שלא נכנסים לזה.

2. concurrent_server.c — מה-includes ועד listen()

זהו הקוד של המרצה במלואו, בדיוק כפי שהוא מופיע בחוברת. הוא ממשיך ישירות את השרת האיטרטיבי — אותן קריאות מערכת, באותו סדר — ומוסיף עליהן שלושה דברים בלבד: עיבוד (המרה לאותיות גדולות), fork() אחרי ה-accept, וניקוי זומבים. נעבור עליו קטע-קטע.

2.1 ה-includes וההגדרות

מה זה עושה: מצרף את קובצי ה-header (קובץ .h שמכיל את הצהרות הפונקציות שאנחנו קוראים להן, כדי שהמהדר ידע איך הן נראות), ומגדיר שני קבועים — הפורט וגודל המאגר. 

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <arpa/inet.h>
#include <sys/socket.h>
#include <ctype.h>    // Required for the toupper function
#include <sys/wait.h> // Required for zombie process handling (waitpid)

#define PORT 8080
#define BUFFER_SIZE 4096

שני ה-includes האחרונים הם החדשים ביחס לשרת האיטרטיבי, והמרצה אפילו הסביר אותם בהערה בקוד עצמו — סימן שהוא רואה בהם נקודה נלמדת:

<ctype.h>
נדרש עבור הפונקציה toupper — פונקציית ספרייה שממירה תו בודד לאות גדולה. בלעדיו המהדר לא מכיר אותה.
<sys/wait.h>
נדרש לטיפול בתהליכי זומבי — כלומר עבור waitpid והדגל WNOHANG (סעיף 5).

BUFFER_SIZE 4096 נשאר כמו בשרת האיטרטיבי — שם המרצה כתב לצדו "Standard Linux memory page size for maximum efficiency": עבודה בכפולות של גודל העמוד ממקסמת את יעילות ה-I/O מול הקרנל.

זה ההסבר המלא ל-BUFFER_SIZE 4096: הקרנל מזיז מידע בין הזיכרון הראשי לאחסון ביחידות של דפים, ולכן מאגר בגודל דף מתיישר בדיוק עם מה שהקרנל עושה ממילא.

2.2 process_echo — העיבוד עצמו

מה זה עושה: עובר על length הבייטים הראשונים במאגר וממיר כל אות קטנה לאות גדולה — בתוך המאגר עצמו, בלי להעתיק לשום מקום אחר. 

/**
 * Function to process the string - converts lowercase letters to uppercase.
 * Efficiency: Processing is done In-place on the Buffer to save memory allocations.
 */
void process_echo(char *str, ssize_t length) {
    for (ssize_t i = 0; i < length; i++) {
        str[i] = toupper((unsigned char)str[i]);
    }
}

שלוש נקודות שכדאי לשים לב אליהן:

  • עיבוד In-place. הפונקציה כותבת חזרה לאותו מאגר שהיא קיבלה (str[i] = …). אין malloc ואין memcpy — אין הקצאת זיכרון חדשה ואין העתקות מיותרות. בלשון המרצה: "זו רמת היעילות המצופה ב-System Programming".
  • עובדים לפי length, לא לפי גודל המאגר. המאגר הוא 4096 בייטים, אבל הלקוח אולי שלח 12 — ולכן מעבדים בדיוק את מה שנקרא בפועל. (זו אותה הקפדה שראינו ב-Partial I/O.)
  • ההמרה ל-(unsigned char) לפני toupper — כך בדיוק בקוד המרצה. (טכנית: char ב-C יכול להיות מסומן, וערך שלילי שמועבר ל-toupper הוא התנהגות לא מוגדרת.)

למה בכלל להוסיף Uppercase לשרת Echo? המרצה מסביר: התוספת "מדגימה שהשרת אינו רק צינור (pipe) אלא יחידת עיבוד (processing unit)". בשרת האיטרטיבי הבייטים נכנסו ויצאו כמו שהם ("we do not process the string"); כאן יש שלב מניפולציה על הנתונים — וזה ההבדל בין העברת נתונים לבין שירות.

2.3 פתיחת השרת: socket → setsockopt → bind → listen

מה זה עושה: מכריז על המשתנים המקומיים, יוצר את הסוקט המאזין ומדליק עליו את SO_REUSEADDR — כדי שאפשר יהיה להפעיל מחדש את השרת מיד, בלי להמתין לפקיעת TIME_WAIT. 

int main() {
    int server_fd, client_fd;
    struct sockaddr_in address;
    int opt = 1;
    int addrlen = sizeof(address);
    char buffer[BUFFER_SIZE];


    // 1. Create socket and set SO_REUSEADDR (as in the previous example)
    if ((server_fd = socket(AF_INET, SOCK_STREAM, 0)) < 0) {
        perror("socket failed");
        exit(EXIT_FAILURE);
    }


    if (setsockopt(server_fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt))) {
        perror("setsockopt");
        exit(EXIT_FAILURE);
    }

הבדל קטן וקונקרטי מהשרת האיטרטיבי: שם המרצה כתב SO_REUSEADDR | SO_REUSEPORT, וכאן רק SO_REUSEADDR. זו עובדה מהקוד — כדאי לזכור אותה אם שאלה בבחינה מצטטת שורה מאחת משתי הדוגמאות.

מה זה עושה: ממלא את מבנה הכתובת (כל הממשקים, פורט 8080 בסדר הבייטים של הרשת), קושר אליו את הסוקט ב-bind, ומעביר אותו למצב האזנה עם תור של עד 10 חיבורים ממתינים. 

    address.sin_family = AF_INET;
    address.sin_addr.s_addr = INADDR_ANY;
    address.sin_port = htons(PORT);

    if (bind(server_fd, (struct sockaddr *)&address, sizeof(address)) < 0) {
        perror("bind failed");
        exit(EXIT_FAILURE);
    }


    // Increased backlog to 10 as the server is now concurrent
    if (listen(server_fd, 10) < 0) {
        perror("listen");
        exit(EXIT_FAILURE);
    }

    printf("Concurrent Server listening on port %d...\n", PORT);

למה ה-backlog גדל מ-3 ל-10? ההערה בקוד אומרת זאת במפורש: "Increased backlog to 10 as the server is now concurrent". ה-backlog הוא אורך תור החיבורים הממתינים שהקרנל שומר עבור הסוקט המאזין. בשרת מקבילי האב חוזר ל-accept מהר מאוד וקצב קליטת הלקוחות גבוה בהרבה — ולכן צפוי שיצטברו יותר חיבורים בתור בו-זמנית. listen() מוסבר לעומק במודול 13.

מקור: Concurrent.pdf (עמ' 1–2, 5 — סעיף 3) · Iterative.pdf (עמ' 1–2, 5) · מחברת הכיתה 3.9.2026 (עמ' 9)

3. לב הקוד — accept() ואז fork(): שלושת הענפים

מה זה עושה: מחכה ללקוח; אם ההמתנה נכשלה — מדפיס שגיאה וממשיך לסיבוב הבא (ולא יוצא מהתוכנית!); ואם הצליחה — משכפל את התהליך. 

    while(1) {
        // 2. Accept - Waiting for a new client
        client_fd = accept(server_fd, (struct sockaddr *)&address, (socklen_t*)&addrlen);
        if (client_fd < 0) {
            perror("accept");
            continue;
        }

        printf("New client connected. Forking a new process...\n");

        /* * 3. The Magic of Concurrency: using fork()
         * fork() creates an exact duplicate of the server process.
         * Every process (Parent and Child) will have its own copy of the File Descriptors.
         */
        pid_t pid = fork();
🎓 מהשיעור בכיתה (מהמחברת)

המרצה פירק בכיתה את accept() לשתי אפשרויות, וזו נוסחה ששווה לזכור:

  1. קיים כבר Pending Connect בתור ⇒ הקריאה אינה חוסמת והיא חוזרת מיד עם קישור.
  2. אין pending connect ⇒ הקרנל מעביר את ה-Server task למצב המתנה ⇒ accept() היא קריאה חוסמת.

ומאיפה מגיע התור? הוא צייר את לחיצת היד של TCP: connect() אצל הלקוח גורם ל-TCP לשלוח Syn; בצד השרת נוצרת רשומה בתור ה-Pending (זה שאורכו נקבע ב-listen); וכשחוזר Syn-Ack-Segment הקרנל מעביר את המשימה מהמתנה ל-Ready — Context Switch. כלומר ה-backlog אינו מספר שרירותי: הוא אורך תור החיבורים שכבר החלו להיווצר.

ההערה שהמרצה כתב מעל ה-fork היא בעצם ההגדרה שצריך לדעת בעל-פה: fork() יוצרת שכפול מדויק (exact duplicate) של תהליך השרת, ולכל תהליך — אב ובן — יהיה עותק משלו של ה-File Descriptors.

תזכורת ממודול 07 — שלושת ערכי ההחזרה של fork(). אותה שורת קוד "מחזירה" שני ערכים שונים, כי מרגע הקריאה יש שני תהליכים שממשיכים מאותה נקודה: pid < 0 ⇒ ה-fork נכשל (עדיין תהליך אחד); pid == 0 ⇒ "אני הבן"; אחרת ⇒ "אני האב", והערך שקיבלתי הוא ה-PID של הבן.

🎓 מהשיעור בכיתה (מהמחברת)

המרצה נתן בכיתה שם לכל אחד משני הסוקטים, ובהערה מודפסת משלו:

"הסוקט הזה שה-server task מקבל בעקבות הקריאה ל-socket() ישמש את ה-server task 'המקורי' כסוקט האזנה.
היינו, סוקט שידרכו הוא יקבל בקשות connect().
או 'עליו' הוא יבצע accept()"

ובכתב ידו, ליד השורה /* --- Child Process Code --- */, הוא כתב את השם השני: "סוקט השירות" — הסוקט ש-accept החזירה, אחד לכל לקוח, וזה שהבן עובד איתו. שני המונחים האלה הם בדיוק server_fd (האזנה) ו-client_fd (שירות).

ענף 1 — pid < 0: ה-fork נכשל

מה זה עושה: לא נוצר בן, אז אין מי שיטפל בלקוח — מדפיסים שגיאה וסוגרים את ה-FD של הקישור. 

        if (pid < 0) {
            perror("fork failed");
            close(client_fd);
        }
מי מריץאילו FDs נשארים פתוחיםלמה
האב בלבד — לא נוצר תהליך שני. server_fd (המאזין) בלבד; client_fd נסגר כאן. הלקוח הזה לא יקבל שירות, ולכן אין סיבה להחזיק את ה-FD שלו. בלי ה-close הזה כל כישלון fork היה מדליף FD — והשרת רץ לנצח. שימו לב שאין כאן exit: השרת ממשיך ללקוח הבא.

ענף 2 — pid == 0: קוד הבן

מה זה עושה: הבן משחרר את הסוקט המאזין שאינו זקוק לו, ואז מריץ את לולאת ה-Echo של הלקוח שלו: קורא → ממיר לאותיות גדולות → שולח בחזרה. כשהלקוח מתנתק — read מחזירה 0, הלולאה מסתיימת, והבן מדפיס, סוגר ומת. 

        else if (pid == 0) {
            /* --- Child Process Code --- */

            // The child does not need the listening socket; close it for efficiency
            close(server_fd);

            ssize_t bytes_read;
            while ((bytes_read = read(client_fd, buffer, BUFFER_SIZE)) > 0) {
                // Data processing: Conversion to Uppercase
                process_echo(buffer, bytes_read);

                // Send the processed data back to the client
                send(client_fd, buffer, bytes_read, 0);
            }

            printf("Child process (PID: %d) finished handling client.\n", getpid());
            close(client_fd);
            exit(0); // Terminate child process - very important!
        }
מי מריץאילו FDs נשארים פתוחיםלמה
תהליך הבן — עותק מדויק של השרת, עם PID חדש משלו. client_fd בלבד — הבן סגר את server_fd בשורה הראשונה. הבן מטפל בלקוח אחד. הוא אינו זקוק לסוקט המאזין, וסגירתו מבטיחה שהוא לא יוכל לבצע accept נוסף בטעות (סעיף 4). בסוף: close(client_fd) ואז exit(0).

שלוש נקודות בתוך הענף הזה:

  • תנאי הסיום של הלולאה. read מחזירה 0 כשהלקוח סגר את הצד שלו (EOF) ו-שלילי בשגיאה — ולכן > 0 הוא בדיוק "עוד יש נתונים".
  • send שולח bytes_read ולא BUFFER_SIZE — שולחים בדיוק את מה שהתקבל.
  • exit(0) — "very important!" בלשון המרצה. זו לא שורה טכנית: בלעדיה הבן היה ממשיך ללולאת ה-while(1) ומתחיל בעצמו לבצע accept — כי הוא עותק של השרת ולא תוכנית נפרדת. נחזור לזה בסעיף 8.

ענף 3 — אחרת: קוד האב

מה זה עושה: האב מעביר את האחריות לבן: סוגר את ה-FD של הקישור, קוצר בדרך אגב בנים שכבר סיימו — ומיד חוזר לראש הלולאה, אל accept(). 

        else {
            /* --- Parent Process Code --- */

            // The parent has finished its part with the current client; responsibility is passed to the child.
            // It is vital to close the FD here so no unnecessary Open Handles remain in the parent.
            close(client_fd);

            /* Zombie Process Cleanup:
             * Using waitpid with WNOHANG allows the parent to clean up finished children
             * without blocking (Non-blocking).
             */
            while (waitpid(-1, NULL, WNOHANG) > 0);
        }
    }

    close(server_fd);
    return 0;
}
מי מריץאילו FDs נשארים פתוחיםלמה
תהליך האב — השרת המקורי, זה שקיבל את ה-PID של הבן כערך החזרה. server_fd בלבד — האב סגר את client_fd. האב סיים את חלקו מול הלקוח הזה. אם לא יסגור, יישארו אצלו Open Handles מיותרים והסוקט לעולם לא ייסגר באמת (סעיף 4). אחר כך הוא מנקה זומבים ללא חסימה וחוזר ל-accept.

שימו לב לשתי השורות האחרונות בקובץ: close(server_fd); return 0; נמצאות אחרי while(1) — כלומר בפועל לא מגיעים אליהן אף פעם. הן שם כדי שהקוד יהיה שלם ותקין תחבירית.

הסיפור בשורה אחת: accept יוצר קישור → fork משכפל את השרת → הבן נשאר עם הקישור ומטפל בו עד הסוף ואז מת, האב מוותר על הקישור וחוזר להאזין. שני התהליכים סוגרים כל אחד את מה שאינו שלו — וזה בדיוק הנושא של הסעיף הבא.

4. ניהול File Descriptors ב-fork — הנקודה הקריטית

המרצה פותח את הסעיף הזה במילים "This is a critical point", וזה גם הסעיף שממנו נגזרות שתי שאלות בבחינה לדוגמה. הוא נשען על שני דברים שכבר למדנו — מה fork משכפל, ואיך הקרנל סופר הפניות לקובץ פתוח — ומחבר ביניהם.

4.1 מה בדיוק משוכפל

כשתהליך מתפצל, הקרנל מייצר עותק מלא של ה-task_struct, ובכלל זה טבלת ה-File Descriptors (fd_array) ומצבי הזיכרון. אבל — וזו הנקודה — הטבלה היא רק מערך של מצביעים. הקרנל אינו משכפל את אובייקטי הקובץ עצמם: שתי הטבלאות מצביעות על אותם struct file בזיכרון הליבה.

המשפט של המרצה: "כשתהליך מתפצל, הקרנל מגדיל את ה-Reference Count של ה-File Descriptors."
ממודול 06 אנחנו יודעים איך המונה הזה נקרא ומה הוא עושה: f_count בתוך ה-struct file. close() קוראת ל-fput שמפחיתה אותו ב-1, ורק כאשר הוא מגיע לאפס הקרנל ממשיך לניקוי המלא — file_operations->release, ובסוקט: סגירת החיבור בפועל.

🎓 מהשיעור בכיתה (מהמחברת)

בשיעור 3.9 המרצה הקרין הערה מודפסת שמחדדת מה כן ומה לא משותף אחרי fork — מילה במילה:

"במודל הזה, בגלל שהכפיל נוצר על ידי קריאה ל-fork(), לשרת המקורי מוקצה memory image.
ולשרת המשוכפל גם כן מוקצה memory image. שונה מזה שמוקצה לשרת המקורי.
ולכן: אין שיתוף משאבים (שיתוף דאטה) בין המקורי לכפיל. לפחות בכל מה שנוגע למרחב הכתובות שלהם.
כמובן שייתכן שיתוף משאבים 'אחרים' כדוגמת קבצים."

שימו לב כמה זה מדויק, ואיך זה משלים בדיוק את הסעיף הזה: הזיכרון נפרד — כל שינוי במשתנה אצל הבן אינו נראה אצל האב — אבל הקבצים והסוקטים משותפים, כי הם אינם במרחב הכתובות אלא אובייקטים של הקרנל שטבלת ה-FD רק מצביעה עליהם. זו הסיבה שאין צורך לסנכרן משתנים בין האב לבן, ובכל זאת חייבים לסגור FDs.

ובניגוד גמור לכך, אמר בכיתה, threads כן חולקים data section, BSS ו-heap — ומכאן שהם חשופים לrace condition וזקוקים למנעול mutex (מודול 11). זה ההבדל המהותי בין שתי הדרכים לבנות שרת מקבילי.

4.2 שתי חובות הסגירה

מכאן נובעות שתי השורות שנראות "מיותרות" בקוד — ואינן:

מימה חייב לסגורמה קורה אם לא
האב close(client_fd) — ה-FD של הקישור. המרצה: "אם לא יעשה זאת, ה-socket לעולם לא ייסגר באמת, כי ה-reference count לעולם לא יגיע לאפס". גם כשהבן יסיים ויסגור, המונה ירד מ-2 ל-1 בלבד — החיבור יישאר פתוח, והלקוח לא יקבל את סימן הסיום. בנוסף, בכל לקוח נוסף האב צובר עוד FD שלא ישוחרר לעולם.
הבן close(server_fd) — הסוקט המאזין. המרצה: "לבטיחות וליעילות, כדי שלא יוכל לבצע accept נוסף בטעות". הבן לא אמור להאזין — יש לו לקוח אחד לטפל בו. כל עוד ה-FD פתוח אצלו, הוא מחזיק הפניה מיותרת לסוקט המאזין ובאג בקוד עלול להפוך אותו לשרת שני.

אפשר לנסח את זה כחוק אצבע: אחרי fork, כל תהליך סוגר את מה שאינו שלו. האב אחראי על ההאזנה, הבן אחראי על הקישור.

4.3 התמונה: שתי טבלאות FD, אותם אובייקטים

התרשים מראה את אותו רגע פעמיים — מיד אחרי fork(), ואחרי ששני התהליכים ביצעו את הסגירות שלהם. שימו לב רק למספר אחד: f_count.

מאיפה מגיע המספר 3 ומאיפה 4? ה-FD הוא אינדקס בטבלה של התהליך, והקרנל תמיד מקצה את המקום הפנוי הראשון. 0, 1 ו-2 תפוסים תמיד (stdin/stdout/stderr), ולכן הסוקט המאזין מקבל 3 והקישור הראשון מקבל 4. השרשרת המלאה FD → struct file → inode מפורטת במודול 05.

5. זומבים — ולמה שרת בלי waitpid חונק את המערכת

השרת שלנו יוצר תהליך חדש לכל לקוח, וכל תהליך כזה מסיים את חייו ב-exit(0). השאלה שנשארת פתוחה היא: מה קורה לתהליך שסיים? התשובה בלינוקס אינה "הוא פשוט נעלם".

ההגדרה, בלשון המרצה: "בלינוקס, כאשר תהליך בן מסתיים הוא נשאר בטבלת התהליכים כ-Zombie עד שהאב קורא ל-wait()."

זומבי הוא לא תהליך שרץ ולא תהליך שתקוע. הוא שלד: הקוד שלו כבר לא רץ, הזיכרון שלו כבר שוחרר — אבל הרשומה שלו בקרנל (ה-task_struct) עדיין קיימת, ותופסת מקום בטבלת התהליכים ומספר PID. במונחי שדה ה-__state שראינו במודול 07, זהו המצב EXIT_ZOMBIE (מחזור חיי תהליך עוקב אחרי כל המצבים).

הרחבה — לא מהשקפים

למה הקרנל בכלל שומר את השלד? כי לאב מגיעה זכות לדעת איך הבן סיים — Exit Status, האם נהרג ע"י אות, כמה זמן מעבד צרך. כל עוד אף אחד לא "אסף" את המידע הזה, הקרנל מחויב לשמור אותו. הקריאה wait()/waitpid() היא בדיוק פעולת האיסוף (reaping), ואחריה הרשומה נמחקת סופית.

5.1 מה קורה בשרת שלא מנקה

עכשיו חברו את שני הדברים: שרת מקבילי יוצר תהליך לכל לקוח, והוא אמור לרוץ חודשים. אם האב לא קורא ל-wait, כל לקוח שסיים משאיר אחריו זומבי — ואף אחד לא מפנה אותם.

המסקנה של המרצה (וזו שאלה 11 בבחינה לדוגמה): "אם השרת רץ זמן רב בלי waitpid — טבלת התהליכים תתמלא", עד שלא ניתן יהיה ליצור תהליכים חדשים במערכת. שימו לב מה לא קורה: השרת לא קורס מיד, הבנים לא ממשיכים לרוץ לנצח, והקרנל לא סוגר את השרת אוטומטית. הנפילה היא הדרגתית — ובסוף פוגעת בכל המערכת, לא רק בשרת: גם fork של תוכניות אחרות יתחיל להיכשל.

5.2 השורה שפותרת את זה

מה זה עושה: קוצר בלולאה את כל הבנים שכבר סיימו — ומפסיק ברגע שאין עוד כזה, בלי לחכות לאף אחד. 

            while (waitpid(-1, NULL, WNOHANG) > 0);

שורה אחת, שלושה ארגומנטים — וכל אחד מהם נבחר בכוונה:

הארגומנטמה הוא אומרלמה דווקא זה כאן
-1
מי		 כל בן שהוא — לא ממתינים ל-PID מסוים. לאב יש עשרות בנים והוא לא יודע מי סיים ראשון. הוא רוצה לקצור את מי שסיים, לא מישהו ספציפי.
NULL
איפה הסטטוס		 כאן היה אמור להיות מצביע למשתנה שיקבל את Exit Status; NULL = לא מעניין אותנו. המטרה כאן היא ניקיון, לא דיווח. השרת לא עושה כלום עם קוד היציאה של הבן.
WNOHANG
איך להמתין		 לא-חוסם (Non-blocking): אם אין כרגע בן שסיים — חוזרים מיד עם 0, במקום להמתין. זה כל העניין. שרת שנחסם בהמתנה לבן חוזר להיות איטרטיבי — בדיוק הבעיה שממנה ברחנו.

ומה עושה ה-while עם הגוף הריק (הנקודה-פסיק בסוף!)? waitpid קוצרת בן אחד בכל קריאה ומחזירה את ה-PID שלו (ערך חיובי). הלולאה חוזרת עליה שוב ושוב, ולכן:

  • יש שלושה בנים שסיימו ⇒ שלוש קריאות מוצלחות, שלושה זומבים נמחקים.
  • הקריאה הרביעית מחזירה 0 (אין עוד בן שסיים) ⇒ התנאי > 0 נכשל, הלולאה נגמרת מיד.
  • אין בכלל בנים שסיימו ⇒ הלולאה מסתיימת אחרי קריאה אחת, כמעט בלי עלות.

איפה השורה יושבת — וזה חשוב. היא נמצאת בענף האב, אחרי כל accept מוצלח. כלומר הניקוי מתבצע "בדרך אגב", בכל פעם שהאב חוזר מטיפול בלקוח חדש — בלי טיימר, בלי חוט נוסף ובלי לחסום.

הרחבה — לא מהשקפים

לתבנית הזו יש מגבלה שכדאי להכיר: הניקוי קורה רק כשמגיע לקוח חדש. אם בן סיים ב-02:00 בלילה והלקוח הבא מגיע רק ב-08:00 — הזומבי שלו יישב בטבלת התהליכים שש שעות. זה בדרך כלל לא נורא (זומבי בודד תופס מעט מאוד), אבל זה מסביר למה בשרתים אמיתיים משלימים את התמונה עם SIGCHLD: הקרנל שולח לאב אות ברגע שבן מסתיים, והאב קוצר אותו מתוך ה-handler — כלומר מיד, ולא בהמתנה ללקוח הבא. על אותות ועל sigaction() ראו מודול 12.

מה לא השתנה, וכדאי לשים לב: סדר הקריאות בצד השרת נשאר בדיוק אותו סדר — socket → setsockopt → bind → listen → accept — וגם BUFFER_SIZE 4096, INADDR_ANY, htons(PORT) ותנאי הסיום של לולאת ה-Echo (read מחזירה 0 ⇒ הלקוח התנתק). המקביליות היא תוספת, לא כתיבה מחדש.

🎓 מהשיעור בכיתה (מהמחברת)

כדי להסביר למה באמת צריך שרת מקבילי, המרצה הקרין בשיעור האחרון דוגמה מודפסת משלו — אפליקציית בנק. מילה במילה:

"ש'האפליקציה' בעיני המשתמש האנושי היא צד הלקוח ב-client-server."

"נניח שלמשתמש X מותקנת בסמארטפון אפליקציה של הבנק B שבו מנוהל החשבון שלו. באמצעות האפליקציה הזו הוא יכול לבצע: הפקדות, העברות כספים וכו'. כל פעולה = טרנזאקציה. ל-X יש מזהה ייחודי. שניתן לו על ידי הבנק. למשל: מספר החשבון.
לכל פעולה (טרנז') מזהה משלה. הזוג: מזהה משתמש + מספר פעולה: מזהה ייחודית את הפעולה מבין כל הפעולות שנעשות על ידי משתמש כלשהו. הזוג הזה יישמר בקובץ הלוג. 'לצדו' פרטים נוספים: כמו סוג הפעולה [הפקדה / העברה וכו']."

ואז הוא הוסיף בכתב יד את הפואנטה: שרת איטרטיבי לא יכול לשרת כך את X ואת Y בו-זמנית — ולכן קונקורנטי. שימו לב מה קורה ברגע שהמימוש הוא ב-threads ולא ב-fork: כל הטיפולים כותבים לאותו קובץ לוג, שהוא משאב משותף — וזה בדיוק המקום שבו נכנס הסנכרון (מודול 11). את הפתרון המתקדם, thread pooling, הוא הזכיר בשמו ואמר מפורשות: "לא ניכנס לזה".

7. שאלות בסגנון הבחינה

שתי השאלות הראשונות הן מהבחינה לדוגמה של המרצה, כולל התשובות שלו מילה במילה. אחריהן שלוש שאלות שבנינו באותה תבנית בדיוק ("לפניך קטע קוד שכתבו סטודנטים… עליך לקבוע האם הוא תקין פונקציונלית") — כדי לתרגל את הצורה שבה המרצה בודק את החומר הזה. ענו לפני שאתם פותחים.

שאלה 4 בבחינה לדוגמה — חלק א׳ (שאלה פתוחה, 10 נק')

במסגרת מטלת תכנות בקורס "תכנות מערכות", התבקשו הסטודנטים לפתח concurrent Echo server. לפניך קטע קוד שכתבו סטודנטים כחלק מהפתרון. עליך לקבוע האם הוא תקין פונקציונלית, ואם לא — עליך להסביר במדויק מהי השגיאה ומדוע היא מתרחשת. 

int main() {
    int server_fd, client_fd;
    struct sockaddr_in address;
    int opt = 1;
    int addrlen = sizeof(address);
    char buffer[BUFFER_SIZE];


    address.sin_family = AF_INET;
    address.sin_addr.s_addr = INADDR_ANY;
    address.sin_port = htons(PORT);

    if (bind(server_fd, (struct sockaddr *)&address, sizeof(address)) < 0) {
        perror("bind failed");
        exit(EXIT_FAILURE);
    }



    if ((server_fd = socket(AF_INET, SOCK_STREAM, 0)) < 0) {
        perror("socket failed");
        exit(EXIT_FAILURE);
    }

תשובת המרצה:

הקטע אינו תקין מבחינה פונקציונלית.
הקריאה ל-bind() מתבצעת לפני הקריאה ל-socket().
מה שאומר שערכו של המשתנה server_fd הוא 'זבל'.

ההסבר במילים שלנו: server_fd הוא משתנה מקומי שלא אותחל. הערך שיושב בו הוא מה שנשאר במחסנית — מספר אקראי לחלוטין. bind() מצפה לקבל FD של סוקט קיים, ולכן היא תיכשל (או, גרוע יותר, תפעל על FD אחר שבמקרה פתוח). ורק אחר כך נוצר הסוקט האמיתי — ודורס את המשתנה.

הסדר המחייב, בעל-פה: socket → setsockopt → bind → listen → accept.

שאלה 11 בבחינה לדוגמה — חלק ב׳ (סגורה, 6 נק')

במסגרת מטלת תכנות בקורס "תכנות מערכות", התבקשו הסטודנטים לפתח concurrent Echo server. מה יקרה אם האב לא יבצע waitpid() בכלל?

  1. השרת יקרוס מיד.
  2. טבלת התהליכים תתמלא ב"זומבים" עד שלא ניתן יהיה ליצור תהליכים חדשים במערכת.
  3. הבנים ימשיכו לרוץ לנצח.
  4. ה-Kernel יסגור את השרת אוטומטית.

התשובה של המרצה: ב׳ (2) — "טבלת התהליכים תתמלא ב'זומבים' עד שלא ניתן יהיה ליצור תהליכים חדשים במערכת".

  • 1 שגוי — אין שום דבר שמפיל את השרת ברגע שבן הופך לזומבי. השרת ימשיך לתפקד, ורק בהדרגה המערכת תיחנק.
  • 3 שגוי — הבנים דווקא סיימו: הם ביצעו exit(0). זומבי אינו תהליך רץ אלא רשומה שנשארה בטבלה.
  • 4 שגוי — הקרנל לא "מעניש" תהליך שלא קורא wait. שמירת השלד עד לאיסוף היא ההתנהגות המוגדרת, לא תקלה.

הזיכרון בשאלה הזו: הנזק אינו לשרת עצמו אלא למשאב גלובלי — טבלת התהליכים של המערכת כולה.

תרגול נוסף לא מהשקפים

לפניך ענף האב שכתבו סטודנטים ב-concurrent Echo server. האם הוא תקין פונקציונלית? אם לא — הסבר במדויק מהי השגיאה ומדוע היא מתרחשת. 

        else {
            /* --- Parent Process Code --- */
            while (waitpid(-1, NULL, WNOHANG) > 0);
        }

הקטע אינו תקין: חסרה השורה close(client_fd); בענף האב.

מדוע: אחרי ה-fork יש שתי הפניות לאובייקט הסוקט של הקישור, ולכן f_count = 2. כשהבן מסיים וסוגר, המונה יורד ל-1 בלבד — הסוקט לעולם לא נסגר באמת, כי ה-reference count לעולם לא יגיע לאפס. הלקוח לא יראה סגירת חיבור מסודרת, ובכל לקוח נוסף האב צובר עוד FD — עד שיגיע למכסת ה-FDs של התהליך וכל accept נוסף ייכשל.

התיקון: close(client_fd); כשורה הראשונה בענף האב, לפני ניקוי הזומבים.

תרגול נוסף לא מהשקפים

לפניך ענף הבן שכתבו סטודנטים. האם הוא תקין פונקציונלית? אם לא — הסבר במדויק מהי השגיאה ומדוע היא מתרחשת. 

        else if (pid == 0) {
            /* --- Child Process Code --- */
            close(server_fd);

            ssize_t bytes_read;
            while ((bytes_read = read(client_fd, buffer, BUFFER_SIZE)) > 0) {
                process_echo(buffer, bytes_read);
                send(client_fd, buffer, bytes_read, 0);
            }
            close(client_fd);
        }

הקטע אינו תקין: חסרה השורה exit(0); בסוף ענף הבן — השורה שהמרצה סימן "very important!".

מדוע: הבן אינו תוכנית נפרדת אלא עותק של השרת. כשהוא מסיים את הבלוק, זרימת התוכנית ממשיכה כרגיל — אל סוף לולאת ה-while(1) וחזרה לראשה, כלומר אל accept(). כאן זה מתחבר לשגיאה השנייה: הבן כן סגר את server_fd, ולכן ה-accept שלו ייכשל עם EBADF, ה-perror יודפס ו-continue יחזיר אותו ללולאה — לולאה אינסופית שאוכלת מעבד, ותהליך שלא מת לעולם. אילו לא היה סוגר את server_fd, המצב היה גרוע אף יותר: שני שרתים היו מתחרים על אותם לקוחות.

התיקון: exit(0); מיד אחרי close(client_fd);.

תרגול נוסף לא מהשקפים

סטודנט טוען: "אין צורך שהבן יסגור את server_fd — הוא ממילא לא קורא ל-accept, אז זה רק סגנון." האם הוא צודק? הסבר.

לא צודק — המרצה מנמק את הסגירה בשתי מילים: בטיחות ויעילות.

  • בטיחות: כל עוד ה-FD פתוח אצל הבן, הבן יכול לבצע accept — במקרה של באג, של exit חסר (השאלה הקודמת), או של קוד שיתווסף בהמשך. אז נוצר מצב של שני תהליכים שמקבלים לקוחות מאותו סוקט מאזין, וקשה מאוד לאתר אותו.
  • יעילות / נכונות המונים: הבן מחזיק הפניה לאובייקט הסוקט המאזין, ולכן f_count שלו מנופח לפי מספר הבנים החיים. גם אם השרת (האב) ייסגר, הסוקט המאזין לא ישוחרר באמת כל עוד יש בן שמחזיק בו — והפורט לא יתפנה.

הכלל הכללי: אחרי fork, כל תהליך סוגר כל FD שאינו נחוץ לו — לא כעניין של סגנון אלא כדי שהמונים יהיו נכונים.

8. מלכודות למבחן

  • fork משכפל את הטבלה, לא את האובייקטים. התשובה "הבן מקבל עותק של הסוקט" אינה מדויקת ומכשילה. הבן מקבל עותק של טבלת ה-FD; אובייקט ה-struct file נשאר אחד ומשותף, ורק ה-reference count שלו עולה. כל השאלות על "למה צריך לסגור" נגזרות מכאן.
  • מי סוגר את מי — אל תתבלבלו בכיוון. האב סוגר client_fd; הבן סוגר server_fd. קל לזכור לפי התפקיד: מי שממשיך להאזין (האב) שומר את הסוקט המאזין; מי שמטפל בלקוח (הבן) שומר את הקישור.
  • "האב לא סגר" ≠ "דליפה קטנה". הניסוח שהמרצה רוצה לשמוע הוא חד: ה-socket לעולם לא ייסגר באמת, כי ה-reference count לעולם לא יגיע לאפס. לא "יש קצת בזבוז זיכרון".
  • זומבי אינו תהליך שרץ. הבן סיים (exit(0)) — מה שנשאר הוא רשומה בטבלת התהליכים. תשובה שאומרת "הבנים ימשיכו לרוץ לנצח" היא מסיח מובהק בבחינה לדוגמה.
  • בלי waitpid — הנזק הוא למערכת, לא רק לשרת. טבלת התהליכים מתמלאת עד שלא ניתן ליצור תהליכים חדשים במערכת. השרת אינו קורס מיד והקרנל אינו סוגר אותו אוטומטית.
  • WNOHANG = לא-חוסם, ולא "לחכות לכל הבנים". בלי הדגל הזה waitpid הייתה חוסמת את האב — והשרת המקבילי היה חוזר להתנהג כמו איטרטיבי. ואת -1 אל תפרשו כשגיאה: כאן משמעותו "כל בן שהוא".
  • exit(0) בבן הוא לוגיקה, לא נימוס. בלעדיו הבן נופל בחזרה ללולאת ה-while(1) ומנסה בעצמו לבצע accept. המרצה סימן את השורה במפורש: "very important!".
  • סדר הקריאות — socket תמיד לפני bind. זו בדיוק שאלה 4 בבחינה לדוגמה: bind לפני socket ⇒ server_fd הוא 'זבל'.
  • המספרים הקטנים שקל לפספס. backlog = 10 בשרת המקבילי (מול 3 באיטרטיבי); setsockopt כאן רק עם SO_REUSEADDR (באיטרטיבי גם SO_REUSEPORT); BUFFER_SIZE 4096 בשניהם.
  • "תקין" היא תשובה לגיטימית. בשאלות "האם קטע הקוד תקין פונקציונלית?" המרצה שם גם קטעים תקינים (שאלה 3 בבחינה לדוגמה) — ואז הציפייה היא שתסבירו מה הקוד עושה ולמה זה נכון, לא להמציא שגיאה.
  • process_echo עובד על bytes_read, לא על BUFFER_SIZE. וההדגשה של המרצה היא In-place: בלי malloc, בלי memcpy.
